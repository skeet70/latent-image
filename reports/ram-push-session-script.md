# Live RAM push of the full recipe candidate (bank, D3 and Q): owner procedure (X-M1 1.50, RC0 installed)

Imported from the private research history (fuji-af) at `179c22e`; commit ids here name that history. Every value in section 0 is bound to `ef4b6f5` there. This repository's camera binary carries the bank ELF allowlist and its source-identity entry, so its builder identity and reference runtimes differ from P4, and P1-P5 are re-established for its own commit before a go ([transport README](../transport/README.md#current-state)).

Owner procedure for loading the full recipe candidate (editable bank, D3 compiled film rows and Q exposure) into RAM on XM1-body-01 over USB in an ordinary boot, using it, rolling it back and powering off. Nothing here authorizes a run. The operation is H2 under [the camera-run procedure](../spec/07-governance-and-handoff.md#3-camera-runs): a RAM write with no firmware, configuration or boot write, cleared by power-off. Its bytes at `ef4b6f5` passed the independent review (P1); it then needs the owner's go of section 8. The commands and their mechanics are [transport/README.md](../transport/README.md) (`ram-alloc`, `ram-relink`, `ram-push`, `ram-free`, `ram-unload`) and are quoted, not redefined. The previous live session pushed the bank alone at `86079af` (94 publications; E-RAM-PUSH-INSTALL-150, E-RAM-PUSH-SESSION-150), after a first attempt stopped on the journal cap (E-RAM-ALLOC-JOURNAL-STOP-150).

Labels: **hardware-observed** (seen on this body), **byte-read** (read from a pinned artifact or the tree), **emulated** (host model), **static-inference**, **unverified on this body**. ### 2.3 Model reads under the standing grant

The [read grant](../spec/07-governance-and-handoff.md#34-standing-confirmations) covers `read-config` and `read-ram` only. On the session day, before the go, the model runs and records:

1. `devenv shell -- bazel run //transport:camera -- read-config "$PWD/private-data/read-plans/gate-byte.json"`: product `X-M1`, `0xf7` nonzero. Four config windows; live duration is not calibrated by the RAM-read measurement. Record it separately.
2. `devenv shell -- bazel run //transport:camera -- read-ram "$PWD/private-data/read-plans/ram-push-prepush-250.json"`: all 250 old words match, service mode 3, table `0x015c22a0`, slot `0x00dc7874`; record heap break without requiring a fixed value. One pass, 69 RAM requests, about **10.7 s plus session/build/journal overhead**, not an instantaneous snapshot. The same run checks the reviewer windows (**hardware-observed** at these values, E-RAM-PUSH-PREPUSH-150):
   - `0x40a0fbac`, 4 bytes: the channel `0x58` queue message-size word that `0x0072503c` loads (`0x40a0f3d0 + 0x58*4 + 0x67c`). Must equal `0x00000024`. Below `0x24` the park post would return -60 and `ram-push` would refuse with -6.
   - `0x4089ea94`, 4 bytes: the prehook pointer `0x0072503c` calls with r0 = &outer (`0x007250bc`-`0x007250cc`). Must equal `0x00726478`, the stock message-trace recorder that `0x0069d1f8` installs over the image's initial `0x00723330`; any other value means foreign code runs on CPU0 inside the post.
   - `0x40a5b5e0`, 16 bytes: message-trace state. Byte 0 = 0, byte 1 = 1, byte 2 = 1, `+0xc` = `0x41ac9800`, so the prehook records only the 4-byte outer header.
   - `0x4089e9f8`, 100 bytes, read twice about 1.2 s apart (window 57, then window 65 at `0x4089e9f4`, 104 bytes, whose last 100 bytes are the same rows): five 20-byte execcpu rows {task/channel, logical core, result, kind, waiting-task selector}. Task/core pairs must be `(0x58,1)`, `(0x59,1)`, `(0x5a,1)`, `(0x5b,0)`, `(0x5c,0)` in both samples, and the `0x58` row must show zero kind and zero waiting selector in both. A nonzero kind or selector means a stock synchronous job holds that worker and would delay the park job [INFERENCE: the stock completion `0x006b0704` clears a row when its job ends]; record it for the other rows.

Any publication, mode, table, slot, queue-size, prehook or worker-row mismatch, refusal or disconnect stops the session (P7). A changed heap break alone is not a mismatch; zero output cells and request-window bytes are not acceptance conditions. After these reads the model sends no further USB request until R6 has printed its final line; the only model request between R6 and power-off is the R6a read, and the next after it is B6 after power-off and reboot. One USB client runs at a time, and any intervening D0 request during `ram-alloc` to `ram-unload` destroys the request-owned bootstrap window and is an uncertain stop (README). The owner confirms in chat that model reads are paused before R1.
