# Fujihack reuse survey: code-execution and payload infrastructure

Scope: read-only source survey of fujihack (pinned at 754acff9aa0322df19446cf7eca699b221c3330d; the repository LICENSE and README state GPL v3, with per-file notices that differ, see Licensing and provenance) supporting fuji-af gates G4-G5 (reversible execution and observation); no builds were run and no fujihack file was modified. This revision applies the independent review findings of 2026-10-07; the cited facts were re-verified against the pinned checkout.
Evidence scoping: every finding names its fujihack source file and the camera model(s) it belongs to, or "model-independent technique"; no sibling-model address, register or value below is an X-M1 fact.

## What a new model port must supply

The sections below are sibling-source leads, not an X-M1 port recipe: they list the union of fields that in-tree sibling code and patches consume, with model/xa2_130.h as the worked example and every example value belonging to X-A2 only, never to X-M1. In upstream terms a port is one header named model/<model>_<version>.h selected via `make model=<name>` (Makefile), force-included into every unit (src/Makefile), plus a load-base edit in src/Linker.ld; that header plus base edit is not an X-M1 port, and no sibling field or address below enters the proposed X-M1 configuration. The G4-G5 adoption checklist at the end of this section links the authoritative contracts.

Build and identity fields (names from model/template.h):
- MODEL_NAME, printed on-screen by src/main.c (X-A2: "Fujifilm X-A2", model/xa2_130.h).
- MODEL_CODE, hex identification string for the external patcher ("Paste_model_code_from_patcher" in model/template.h; not referenced by fujihack code; X-A2: "00050701000507020005070400050709", model/xa2_130.h).
- CODE_ARM, marker that the firmware is 32-bit ARM not Thumb (model/template.h; referenced nowhere else in this tree).
- FIRM_URL, stock firmware download URL (X-A2: "https://dl.fujifilm-x.com/support/firmware/x-a2-130-oqijkawt/FWUP0006.DAT", model/xa2_130.h; not referenced by code in this tree).
- S3_FILE, an .S3 file path on the card (X-A2: "C:\\IMFIDX10\\LX30B.S3", model/xa2_130.h; not referenced by code in this tree).
- SCREEN_WIDTH and SCREEN_HEIGHT, consumed by src/screen.c (X-A2: 720x480, model/xa2_130.h).

Firmware-image addresses (FIRM_*, usable only by patches planted into the firmware image):
- FIRM_RST_WRITE, FIRM_RST_CONFIG1, FIRM_RST_CONFIG2, called by src/patch/debug.S, src/patch/quick.S and src/patch/file.S (X-A2: 0x005b0388, 0x00592bd4, 0x005b81e0, model/xa2_130.h).
- FIRM_INSTAX_MENU with FIRM_INSTAX_MENU_MAX, the INSTAX menu code slot and its size budget (X-A2: 0x0059f604, max 400, model/xa2_130.h).
- FIRM_IMG_PROPS with FIRM_IMG_PROPS_MAX, dead-code space usable for dummy payloads (X-A2: 0x00598aec, max 2000, model/xa2_130.h).
- FIRM_USB_SCREEN, the function that prints "USB" (X-A2: 0x005ae41c, model/xa2_130.h).
- Optional slots seen on other models: FIRM_PRINTIM with FIRM_PRINTIM_MAX and FIRM_MEMO with FIRM_MEMO_MAX (XF-1, model/xf1_101.h), FIRM_PRINTIM (HS20EXR, model/hs20exr_104.h), FIRM_TAKEPIC and FIRM_PTP (X-T10, model/xt10_131.h), FIRM_PTP_9805 with FIRM_PTP_FINISH and FIRM_PTP_MAX (X-T20, model/xt20_210.h).

RAM addresses (MEM_*, live after the firmware has loaded itself):
- MEM_UNUSED_SPACE, payload staging/load area and heap base for src/load.c, src/mem.c, src/patch/file.S (X-A2: 0x0142a640, model/xa2_130.h; same value is the link base in src/Linker.ld).
- MEM_PTP_9805 and MEM_PTP_RETURN, the handler to hijack and the PTP finish function for src/patch/quick.S (X-A2: 0x00D60870, 0x00D5EAAC, model/xa2_130.h).
- MEM_PTP_TEXT, the string printed by PTP GetDeviceInfo, a minimal observation channel (strcpy demo in minimal/main.c; X-A2: 0x00d6bfd0, model/xa2_130.h).
- MEM_RUN_DEV_MODE and MEM_INSTAX_MENU, the RAM hook sites written by src/main.c (X-A2: 0x00d35774, 0x010ff5bc, model/xa2_130.h).
- MEM_INPUT_MAP, the key state struct read by src/main.c and src/sys.c (X-A2: 0x00931c80, model/xa2_130.h).
- MEM_GET_REC_LIMIT, the record-limit function patched by src/video.c (X-A2: 0x010e5d2c, model/xa2_130.h).
- MEM_MS_TIMER, the millisecond tick read by src/sys.c (X-A2: 0x00917ce0, model/xa2_130.h).
- MEM_TEXT_LAYERS, the text layer struct used by src/io.c (X-A2: 0x16facb4, model/xa2_130.h).
- MEM_OPENGL_BUFFERS, the framebuffer pointer table used by src/screen.c (X-A2: 0x007fd324, model/xa2_130.h).
- MEM_EEP_START, the EEPROM byte array behind GET_EEP/SET_EEP in src/ff_eeprom.h and src/util.c (X-A2: 0x41acd800, model/xa2_130.h).
- SQLITE_MEM_METHODS, the camera SQLite allocator hooks backing malloc in src/mem_sqlite.c (X-A2: 0x01427bf8, model/xa2_130.h).
- Defined in model/xa2_130.h but referenced by no code in this tree: MEM_RTOS_FUNCTIONS (0x0004dae0), MEM_SEARCHTBL_CALL_HIJACK (0x012598a4), MEM_SEARCHTBL_TASK (0x01259874).

RTOS function stubs (model/stub.h NSTUB entries, compiled from stub.S with -D FPIC -D STUBS per Makefile):
- The X-A2 port supplies 27 stubs: fuji_drive, fuji_fopen, fuji_fread, fuji_fclose, fuji_fwrite, fuji_get_error, fuji_fseek, fuji_file_wait, fuji_file_reset, fuji_fstats, fuji_wait_task_start, fuji_wait_task_stop, fuji_task_sleep, fuji_task_event, fuji_io_lock, fuji_screen_write, fuji_discard_text_buffer, fuji_rst_write, fuji_rst_config1, fuji_rst_config2, sqlite_snprintf, fuji_init_sqlite, sqlite_exec, sqlite_mallocAlarm, fuji_press_key, fuji_press_key_alias, fuji_get_task_id (model/xa2_130.h).
- Extra project-local stubs go in src/stub.S ("Put fujihack NSTUB() definitions here", src/stub.S); minimal/stub.S shows a test set and minptp/stub.S is empty.
- These stubs are the boundary where per-model RAM function addresses enter otherwise model-independent payload code (src/load.c, src/file.c, src/mem_sqlite.c call them).

Build integration checklist (sibling-source steps, not an X-M1 recipe):
- Provide the header as model/<name>.h and build with `make hack.bin model=<name>` or config.mak (Makefile, README.md).
- Choose a payload load address and edit the hardcoded 0x0142a640 base in src/Linker.ld (src/Linker.ld). That base belongs to X-A2, and neither the edit nor the boot.S routines demonstrate safe loading at another base.
- For the PTP channel, additionally supply MEM_PTP_9805/MEM_PTP_RETURN (src/patch/quick.S) or confirm the signature route of src/patch/debug.S; for firmware planting, supply the FIRM_* slots and the MODEL_CODE the external patcher needs (model/template.h, README.md). Keep every sibling RAM address out of any proposed X-M1 configuration.

G4-G5 adoption checklist (X-M1-owned; contracts in spec/02 §7.1, spec/08 and spec/03):
- An evidenced R4F-compatible instruction/ABI profile and a selected, audited cross-toolchain (E-CPU-PROFILE; reports/firmware-extraction.md).
- RAM with demonstrated ownership and a recorded lifetime; zeros, apparent free space or an unused-looking buffer do not establish it.
- Exact hooks with captured original bytes and replacement bytes and an exact bounded write set, matched immediately before the write.
- Cache and concurrency handling for the chosen entry mechanism (instruction/data synchronization, reentrancy, timing).
- A bounded entry/return contract with verified register and stack behavior.
- Verified unload: every installed hook and task accounted for and cleanup demonstrated in the G4/G5 observations (repeatable load/observe/unload without a firmware flash).
- A deliberately fixed-base or fully relocated payload contract, with every address-bearing section reviewed in the linker map and disassembly and the exact BSS/GOT write set enumerated before execution.

## Open questions for X-M1

- fujihack contains no X-M1 model header and no X-M1 address, register or value; the single X-M1 mention in the pinned tree is the capability row { "X-M1", 1, 0, 0, 0 } (struct FujiCameraInfo: gps_support, has_bluetooth, capture_support, firm_update_support) in etc/models.h, a table referenced by no code in the tree.
- Unknown for X-M1: whether its PTP dispatcher routes any vendor operation to a hijackable handler the way 0x9805 does on XF-1/X-A2 (src/patch/ptp.S, README.md); the host side merely probes for an installed hijack (usb/ptp.c setup()).
- Unknown for X-M1: whether a show_photo_properties-like function and the src/patch/debug.S byte patterns exist; those patterns were derived on sibling models and must be re-derived from X-M1 firmware, not assumed.
- Unknown for X-M1: whether the firmware honors AUTO_ACT.SCR at all, and whether an INSTAX-menu trigger like the one src/patch/file.S targets exists; etc/NOTES.md records that creating the file alone changes nothing on an unnamed author camera.
- Unknown for X-M1: whether a SQLite instance with the allocator hooks src/mem_sqlite.c uses (SQLITE_MEM_METHODS on X-A2) is present and safe to borrow malloc from.
- The FF80 service interface is already X-M1 evidence, so it is the transport starting point rather than an open question: E-JIG-USB-DESCRIPTORS records this body's installed-1.00 jig enumeration 04cb:ff80 with its endpoint profile, E-S02-IDENTITY-QUERY records a successful product-identity query returning X-M1, reports/ram-probe-live-protocol.md records installed-1.50 RAM reads through the service path, and E-SERVICE-READ-MAP binds the 1.50 memory-operation dispatcher and adjustment-cache gate. The closed fuji-af service operations are the current transport base. Unproved for X-M1: usb/dbg.c's execution mechanism, its 0x03000000 staging address, its 0x0113c55c pointer write and its key-press trigger binding; a service read is not execution and is not photography-capable observation.
- Reversibility conflict for G4-G5: every execution path in fujihack except the FF80 protocol (usb/dbg.c) requires installing a patched firmware (README.md), and etc/NOTES.md documents that the updater refuses reinstalling the same firmware version without header edits, both bearing on any "return to stock" plan.
- The firmware-patching tooling is external: README.md points at the fujihack.org web patcher, which is not part of this tree, and MODEL_CODE exists to feed it (model/template.h); reusing the firmware-injection techniques therefore also means adopting or replacing that external tool.
- The only in-tree cleanup is src/main.c's exit stub over MEM_RUN_DEV_MODE (mov r0,#0; bx lr), which disables one menu hook rather than restoring stock; original-byte restoration and complete teardown are unproved upstream, RAM-only and written against X-A2 addresses. An X-M1-owned design must capture and verify every original patch span, account for every installed hook and task, and demonstrate cleanup under spec/03's G4 (pre-write original-byte matching, demonstrated cleanup) and G5 (repeatable unload without a firmware flash) requirements.
- Observation primitives worth citing later, each as technique with per-source model labels: u32 RAM reads over the hijacked handler (src/patch/ptp.S action 9, exercised by usb/ptp.c test_hacks), GetDeviceInfo string overwrite at MEM_PTP_TEXT (minimal/main.c, X-A2 value), on-screen rasterizer text via FIRM_RST_WRITE plus int.S encoding (src/patch/debug.S), C:\RAM.BIN dumps from a running payload (src/dump.c), and boot-ROM dumps over FF80 (usb/dbg.c) or FH_GET (usb/ptp.c).
