# Settings and property layer: interface inventory draft

## Evidence and decision boundary

This is the host-only research inventory for the persistent-settings project (#127 application rank 2), which the menu project depends on. It follows [the file-service](file-service-manifest-draft.md) and [render-service](render-service-manifest-draft.md) manifests. It qualifies nothing and runs no guest code. Contracts are read from the X-M1 1.50 image4, image5 and plain-image listings and the digest-pinned images; inferred names carry [INFERENCE]. Proposed boundaries are **[INFERENCE]**.

The machine-readable artifact is `private-data/scratch/SettingsManifest/manifest.json` (E-SETTINGS-SERVICE-MANIFEST-150), generated by `replacement/media_permit/SettingsManifestMain.hs` (target `//replacement/media_permit:settings-manifest`) from the reviewed contract input `replacement/media_permit/settings_service_contracts.json` and validated against `schemas/settings-manifest.schema.json`. It holds 120 entry contracts, 49 shared objects, 115 property names and, for each of the 645 property ids, the storage field the getter and setter arms read and write. Menu nodes, values arrays, labels and per-property conversion tables are ControllerStrategy's `private-data/scratch/ControllerStrategy/menu-tables.json`; this manifest consumes them and does not repeat them.

## Method

The generator uses the shared `ServiceInventory.hs` for contracts, extents and the census, and `PropertyFields.hs` for the property fields. `PropertyFields.hs` reads the 645-word jump tables of the getter `0x61e110` (dispatch `0x61e124`) and the setter `0x624694` (dispatch `0x6246c4`) and interprets every arm, including the shared fallback arms, with the property id as a constant. Conditional instructions fork unless the last comparison decides them, so compare chains on the id are followed. A `storage` record is emitted only when the getter returns exactly one distinct field, the setter stores the same base, stride, offset, width and bit range from the value argument, and both explorations complete. The method text in the output (`fieldMethod`) states every rule. Each property's `getter.paths` and `setter.paths` also list every feasible path with its guards, ordered stores (unmodelled stores by instruction address) and calls, and each setter path that reaches the shared exit `0x630200` carries that exit's continuation from its own registers; `pathMethod` states those rules. The generator had independent source review in two rounds. The contracts were written by five research passes with one extension pass, independently reviewed against the listings in three scopes, corrected and verified.

## Property get and set services

Reads go `0x61c93c -> 0x624620 -> 0x61e110(property, bank, defaults flag, slot)`. The bank is the caller's r1; `0x6439e0` supplies the slot, returning 0 when word `0x951480+0xe4` is 3 and 1 otherwise. With the defaults flag 1 a field arm returns its default, otherwise it reads `0x96cc64 + 0x1c2 * bank + offset` and extracts the field. Writes go `0x61c91c -> 0x6309c4 -> 0x624694(property, value, bank, slot)`. For bank 0, `0x6309c4` re-reads the 280-byte ordinary block from the settings image into `0x96cc74` (`0x61d9ec`), calls the setter, and writes the block back (`0x61d8dc`) only when the setter stored; it returns -63 when that write fails. Every bank-0 store first copies the field's old value into `0x89ec00`, a 0x1c2-byte image of bank 0's previous values that `0x61db3c` and `0x61db18` snapshot and restore. The value `0x1affffff` makes the setter store the property's default. `0x63199c` resets the 46 properties listed at `0x79fe20` this way.

Arm forms over the 645-word getter table: 231 words point at the fallback `0x6243e4`; 291 arms return an immediate default; 36 take their default from `0x81b074` for the bank tail at `+0x19a`; 84 slot arms read `bank + 0x28 * slot + 0x140 + offset` when the slot is not 1 and an ordinary-block offset when it is 1; 3 compute their default. A post-dispatch at `0x624400` (getter) and the setter's shared continuation `0x630200` override the stored value for a short list of properties with computed defaults read from `0x96b400`, a boot copy of adjustment-cache bytes.

Conversion and availability use the per-property table `*(0x81b09c + 4 * property)` (290 non-null of 647): `0x61d514`/`0x631a00` convert between encodings, `0x61d534`/`0x631b74` test availability against the registry at `0x79944c`, and `0x61d554`/`0x631edc` count available choices. The commit dispatcher `0xd4fc74` (image5) indexes a 637-slot table at `0xd4fcd4` by property - 10; 498 slots reach a default arm that writes the column-1 conversion to bank 0 through `0x61c91c`, and 139 slots hold 129 property-specific arms.

The controller-manifest "settings/property" seeds are mostly not property services. `0x63a0f8` tests held keys and two state words and returns 0 or 1 (309 of its 367 callers pass 83). `0x63a0e0` and `0x6394d0` always return 1 and `0x6394e8` always returns 0, so the two router routes that need `0x63a0e0` to return something other than 1 are unreachable in stock firmware [INFERENCE from the bodies]. `0x632a3c` and `0x632950` read key-class bitmaps, `0x63270c` and `0x6334dc` only write (an action-parameter block and a UI event post), `0xd35fbc`, `0xd35ffc` and `0xd36090` classify the UI command word `u32[0x944580]`, and `0x69f8fc`/`0x69fc94` get and set adjustment-cache bytes (6900 and 389 callers).

## Live-settings record and property storage

Two bank images live at `0x96cc64` and `0x96ce26`, stride `0x1c2`: a 16-byte header, the 280-byte ordinary block at `+0x10`, a 24-byte block at `+0x128`, slot record 0 at `+0x140` (the area-3 payload, mirrored at settings-image `0x409c295c`) and a 40-byte RAM-only tail at `+0x19a` that boot fills from ROM `0x81b074`. Only slot 0 has a record: slot selector 1 reads the ordinary block, and a selector-2 record at `+0x190` would overlap the tail. The bank helpers go through `{pointer, size, offset}` descriptors to the settings image (`0x6a6e68` read, `0x6a6f3c` write), which refuse offset + size above `0x19a`; only writes reaching past `+0x140` commit to area 3. `0x96ccd2` is bank 0 `+0x6e`, one byte holding property `0x18` in bit 7 and property `0x78` in bits 0..4, with bits 5..6 read by the slot-form property `0x161`.

The generator assigns a storage field to 326 of the 645 ids: 286 in the ordinary block, 35 in the RAM tail and 5 in the header, all relative to the bank stride. The rest are shared-fallback ids (231 getter and 232 setter table words), slot arms whose address combines bank and slot, multi-field and computed arms, and 7 explorations cut short. Per-property records in the output give the getter's returns, the setter's stores and the bit range.

## Area-3 records, validation and recovery

Area 3 is registered by `0x6a8abc` through `0x6ac328(3, 0x34, 0xfe, ...)` with write callback `0x6a8484` and read-validation callback `0x6a84d4`. It has two banks (media blocks `0x58` and `0x59`, `0x20000` bytes each) of 127 records of 0x34 bytes: u16 sequence at `+0x00` (15 bits; `0xffff` unwritten), two compared bytes at `+0x02`, the 0x28-byte payload at `+0x04`, row parity at `+0x2c` (bit w is the parity of protected word w, w = 0..10) and column parity at `+0x30` (XOR of the 11 protected words) over `[0x00, 0x2c)`.

- Validation: `0x6a84d4` corrects a single bit, the data bit picked out by exactly one mismatched column-parity bit and one mismatched row-parity bit, and returns 0; any other mismatch, including one in the parity words, returns 1 with the record unchanged.
- Read: each bank is binary-searched for its last written record; when the newest fails validation the reader steps back to older records in that bank (`0x6ad2f8`). Across banks the newest valid record by 15-bit sequence with wraparound wins (`0x6ac4c8`); with none valid the read returns -255.
- Write: `0x6a86c4` compares record bytes `[2, 0x2c)` with the snapshot `0x89f874` and appends only on a difference; `0x6ac7d4` appends with sequence (newest + 1) & 0x7fff, moves to the other bank when one is full and erases it when both are; `0x6ad3f4` programs the record and ignores the program result. Commits come from the CUSTOM SET copy (`0x630b14`), the defaults reset `0x6a6fd8` and boot; no power-off caller was found.
- Recovery at boot: a failed read (erased area, both banks invalid, uncorrectable record) fills the live copy `0x89f838` with `0xff`, rebuilds defaults from `0x7cb804` and the adjustment cache, commits them and resets the ordinary block through `0x6a6fd8(0)`. The area-2 rejection flag `0x89f834` forces the same rewrite. `0x6a86c4` does not test its append or re-read, so boot can copy an `0xff` record into the image.

## Property names

No firmware table pairs property ids with name strings: the image4 name tables cover UI states and keys, image5 has event and service-mode strings, and the plain image's setting names are drawn by `0x1118a00` without reference to property ids. 115 ids are named: 98 from the parent menu row's label in ControllerStrategy's menu tables and English string ids, and 17 inferred from earlier reports. Every name records its source; 26 labelled ids have no dedicated getter arm and may be menu classes rather than stored properties.

## Grounded and open

Grounded: the get/set paths, argument roles and modes, the bank-0 previous-value copy, the storage field of 326 property ids, the bank-image layout, the writer census of the bank images and the previous-value copy, the commit dispatcher's table, the query and gate services' value domains, and the area-3 record format, validation, read, write and boot recovery. Open:

- 319 ids have no agreed storage field; slot arms, computed defaults and multi-field arms need a richer interpreter or reading.
- The meaning of most `0x96b400` configuration bytes, the 129 commit-dispatcher arms, and the media-ready word `0x828574`'s setter.
- Whether any power-off path commits area 3; the program and append results are ignored, so a failed write is not recovered until the next boot.
- 530 ids have no name.
- Physical flash behaviour, wear and power-loss during append are not established.

```sh
  private-data/scratch/SettingsManifest/manifest.json
"$HOME/.cache/bazel/latent-image-SettingsManifest/external/_main~lab_dependencies~lab_jsonschema/bin/check-jsonschema" \
  --schemafile schemas/settings-manifest.schema.json private-data/scratch/SettingsManifest/manifest.json
```

The generator refuses an existing output path, a non-canonical image, a getter or setter dispatch that is not the expected `cmp; ldrls pc; b` form, tables covering different properties, and repeated property names.
