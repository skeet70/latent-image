# FWUP0002.DAT container rebuild: field contract and host tool

This is UPDATE-IMAGE-01's concrete base: every field a rebuilt `FWUP0002.DAT` must get right, what computes it, what validates it on the camera and what a wrong value does, plus the host tool that parses the pinned container, verifies those fields and reproduces the stock container byte for byte from its own parts. The image-replacement steps are built: the record-4 step was exercised on the accepted decode-prefix placement, whose container was installed on 2026-10-09 (sections 5 and 6, E-FILMSIM-INSTALL-150), and the record-5 step landed 2026-10-09 with its own stock reproduction proof (section 7).

All addresses and values are bound to the exact public X-M1 1.50 DAT, SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490`, preserved at `private-data/firmware/x-m1-1.50/FWUP0002.DAT`, 38,405,148 bytes (`0x24a041c`). Container words are little-endian. Field values are **byte-read** from that file; camera behavior is **static-inference** from the mapped updater helpers in [UPDATE-01](update-validation-and-boot.md) and the restore-list census (E-ADJ-MOVERS-150, [public findings](adjustment-and-service-interfaces.md#adjustment-read-coverage-and-update-stamps)); nothing here is hardware-observed except where a label says so, and every semantic marked unproved stays unproved.

## 1. Coordinate systems

The same byte has three addresses, and the reports use all three.

| View | Mapping | Main range of this DAT |
| --- | --- | --- |
| Raw DAT offset | file byte address; header words and restore lists are named this way | `[0x25c, 0x24a027c)` |
| Payload offset | raw − `0x214`; payload byte = file byte XOR `0xff` (the complement export) | `[0x48, 0x24a0068)` |
| Media offset | payload − `0x48`, so raw − `0x25c`; media byte = file byte XOR `0xff` | `[0, 0x24a0020)` |

The file's first `0x214` bytes are the outer header, and the native updater reads `0x25c` bytes as one staging header: outer header plus the `0x48`-byte range table. The checksummed main range therefore excludes the first `0x48` payload bytes (`0xdb99c8` seeks to main offset + `0x25c`). The main range is summed in complemented form (media bytes); the auxiliary ranges are summed as raw file bytes. The two auxiliary ranges hold `0x1a0` bytes and end at the exact file length.

## 2. Field contract

Failure column: what the mapped camera edges do with a wrong value. "Refused" means the update stops before the writer touches media (persistence step S0 in UPDATE-01's table); "halt" means a boot record's self-loop after install.

The body rule accepts an equal version and rejects a numerically lower valid one. The sentinel is an observed branch, not an installation proposal.

### 2.3 Auxiliary restore lists (raw `[0x24a027c, 0x24a041c)`)

These are load-bearing. The update's configuration completion `0xdb91e0` snapshots the first `0x42000` bytes of the adjustment cache, refreshes those bytes from the factory template (270,336 bytes from raw logical blocks 7-9 through `0x69fe20(0xff)`), then restores body-specific bytes from these lists and commits (`0x69fea8`). The lists are the only mechanism that carries body-specific data through an update.

| Field | Raw bytes | Stock value | Host: what computes it | Camera: what validates it | Wrong value does |
| --- | --- | --- | --- | --- | --- |
| Restore list 1 | `[0x24a027c,0x24a0404)` | 98 little-endian sixteen-bit `(offset, length)` pairs, from `(0x0000, 0x80)` to `(0x9ad8, 0x0001)` | carried intact and correct for the target body | restore loop `0xdb9254`-`0xdb9280` runs `memcpy(cache+off, snapshot+off, len)` per pair, accepting `off+len <= 0x10000`; count = length/4; gated by bit 0 of `0x14e3578`. A pair past its bound is silently skipped (the branch goes past the copy), and a zero length or checksum disables the whole range | dropped or wrong pairs: the named offsets silently hold template values while every other pair still applies; a disabled range restores nothing at all. Silent persistent calibration loss in the affected ranges |
| Restore list 2 | `[0x24a0404,0x24a041c)` | 3 thirty-two-bit pairs: `(0x000179d5, 8)`, `(0x000179df, 4)`, `(0x00018ac0, 1)` | same | loop `0xdb92c0`-`0xdb9314`, accepting `off+len <= 0x42000`; count = length/8; gated by bit 1; bound violations are skipped the same way | same |
| Coverage | derived | 1,487 bytes of `[0, 0x42000)` (list 1 sums 1,474, list 2 sums 13) | recomputed as a check | none | - |

The camera checks only per-pair bounds and the container checksums, and a pair violating its bound is skipped rather than fatal, so a malformed pair list fails silently on the body. A rebuilt container whose lists are wrong but self-consistent passes every camera-side check and silently replaces the listed ranges with template values; a container that drops or disables both lists replaces the body's whole adjustment area and restores nothing. The guard is therefore host-side and structural: the only emitter refuses any pair list that differs from the source body's and any list that differs from this body's stock baseline, and the diff marks both lists as carried parts that must not change. On this body the stock lists are correct: the census shows all 233 bytes the body holds against the template are restore-covered or loader stamps, and all 14,340 bytes that moved between the 1.00 and 1.50 captures are attributed (E-ADJ-MOVERS-150, hardware-observed captures).

## 3. The tool

`//host/firmware:rebuild-update` (Haskell, `host/firmware/RebuildUpdate.hs` over `host/FujiAF/UpdateContainer.hs` and `host/FujiAF/LabelRecord.hs`) implements the contract above.

| Command | Behavior |
| --- | --- |
| `rebuild-update verify INPUT` | contract checks: every field above whose value the camera or the mapped consumers constrain, including both restore lists against the stock pairs and the pinned plain-extent words |
| `rebuild-update verify-stock INPUT` | contract checks plus the pinned stock values of every named field (identity records, version words, checksum words, range words, all eight segment entries, both record headers, trailer, restore coverage) |
| `rebuild-update round-trip STOCK OUTPUT` | rebuild from parts through the gated emitter, require byte identity with the input, write OUTPUT |
| `rebuild-update diff STOCK REBUILT` | per-part changed-byte counts with the first differing offset and policy label (`carried*` must match, `carried?` policy-checked, `image` content); fails when a `carried*` part differs |
| `rebuild-update replace-record4 --decoder FFLZD STOCK RECORD4 DECODED4 OUTPUT` | the image-replacement step: substitute the image-4 record (the encoder's record file plus the decoded image), derive the record header words from them, propagate the stream size into the image-4 window tail, and emit through the gated emitter; fails closed on the record header arithmetic, the shipped-record invariants, an fflzd round trip of the record, the emission gates, the carried stream, and an fflzd round trip of the rebuilt stream |
| `rebuild-update extract-record5 STOCK OUT_RECORD5` | writes the image-5 record in record-file form (the five header words and the stream as media bytes, the complement of the DAT's file bytes) |
| `rebuild-update replace-record5 --decoder FFLZD STOCK RECORD5 DECODED5 OUTPUT` | the image-5 rebuild: substitute the record and slide it inside the record's flash window (every media offset beyond the new stream keeps the stock byte), with the record-4 gate chain plus a read-back of the written file (the five stored words against the record file's, the stream, the three checksums over the file's own ranges, carried identity outside the rebuilt record and the checksum word; a failing read-back removes the output) |
| `rebuild-update extract-image2 STOCK OUT_IMAGE2` | writes the id-2 extent in media form, the form `replace-image2` reads |
| `rebuild-update replace-image2 STOCK IMAGE2_RAW OUTPUT` | the image-2 rebuild: the replacement must be the stored size word's length, and the emitted file is verified from its own bytes (checksums, extent identity, carried identity outside the extent and the checksum word) |
| `rebuild-update extract-plain STOCK OUT_PLAIN` | writes the id-6 plain image's loaded window in media form, the form `replace-plain` reads (section 8) |
| `rebuild-update replace-plain [--flash-offset 0xHEX] STOCK PLAIN OUTPUT` | the plain-extent carrier: the input is the whole window at the stored flash length, or with `--flash-offset` a bounded span carried to that flash offset with every other window byte keeping its source byte; emitted through the gated emitter and read back from the written file (section 8) |
| `rebuild-update write-label STOCK TEXT OUTPUT` | one printable-ASCII name (at most 27 UTF-16 code units plus its terminator) into the id-0x83d record's inline buffer, emitted through the same path and read back from the file |

The image-2 rebuild, its gates, the stock reproduction proof and the emitted name container are in [reports/image2-record-operation.md](image2-record-operation.md). The image-5 rebuild, its window rule, its stock reproduction proof and its new test cases are in section 7. The plain-extent carrier is in section 8.

The chain feeding it is `//host/firmware:apply-patch-set` (manifest-driven decode patching that verifies every write's current bytes against `patch-set.json` and the decode hash first) and `//lz:lz-encode` (record production with the shipped-record invariants and the F1/F2/F3 defect scans); section 6 has the chain and the first modified-input run.

Derived versus carried in the rebuild (`derivedHeader`): the type word is constant 4; main offset is 0; main length and both auxiliary lengths come from the parts; both auxiliary offsets come from the layout; the three checksum words are recomputed with the camera's arithmetic. Identity records, version words, selector, range fill, every main-range byte (including the structured words re-serialized from parsed values) and both pair lists are carried. A byte-for-byte round trip therefore proves both that the parse is faithful and that the derived words reproduce the stock ones.

Emission is structural. `rebuildContainer source parts` is the only function that produces container bytes, and it refuses rather than writes when the carried set (identity records, selector, range fill, both restore lists) differs from the source container's, when the version words fail the body policy against current 1.50, or when any contract check fails on the assembled parts, including the size relations of section 2.2 and the decoded-size word against a replacement's attached decoded image. It also compares every named part read back from its own assembly against the part it was handed (`assemblyChecks`), so a supplied length or offset word that disagrees with its bytes is refused rather than re-partitioned under stored words that describe something else. A future image-replacement step therefore cannot ship drifted restore lists or stale size words even if it forgets to run `verify`: the bytes do not exist unless the gate passes. ## 5. What the encoder question blocks, and what remains

## 7. The image-5 record rebuild (2026-10-09)

## 8. The plain-extent carrier (2026-10-09)

The id-6 plain image's loaded window is the write path for the recipe bank's bytes ([recipe-design.md](recipe-design.md) section 19 prerequisite 1). Its geometry is the container's own words: entry 6's flash word and flash length name the source span (stock `0x5a0000`, `0x360000` bytes), and the id-6 loader copies `(flash_len + 0x1ffff) >> 17` blocks of `0x20000` bytes to the loader destination word at media `0x1401a8` (stock `0x01100000`; id4 `0x6a987c`-`0x6a98b0`), a separate word from the first linked extent's base at `0x1401b4` (both read `0x01100000` on stock). The three linked extents are six-word entries at `0x1401b0`/`0x1401c8`/`0x1401e0` with base at +4 and length at +8. Every byte of the window is loaded at boot, the runs between the extents included. In the container the window sits in the carried span between the image-5 record and the id-2 extent, stored complemented like every main-range byte.

Two commands over that window, in the `replace-image2` shape (`extract-plain`, `replace-plain`, library `extractPlain`/`replacePlain`/`replacePlainAt`):

- `extract-plain STOCK OUT_PLAIN` writes the window in media form: the linked extents and the runs between them, as the loader copies them.
- `replace-plain STOCK PLAIN OUTPUT` substitutes the whole window in place; the input must be the length the stored flash word describes. `replace-plain --flash-offset 0xHEX STOCK SPAN OUTPUT` carries a bounded span to that flash (media) offset; every window byte the span does not cover keeps its source byte. One gap write per call composes, so a write plan's ordered writes are a sequence of `--flash-offset` calls.

Gates, all failing closed before any output exists: entry 6's flash word and flash length must be `0x20000`-aligned (the loader copies whole blocks, so a start or length the block rounding would move is refused); the window must sit inside the carried span (a window running past the image-2 extent or starting before the image-5 record ends is refused) and must carry every extent run (the entries' base/length words map to window runs offset from the loader destination word); the full form is refused unless the input length equals the stored flash length, the span form unless the span is non-empty, starts at or inside the window and fits it (the bounds are checked before any addition, the upper one by subtraction, so an offset near `maxBound` is refused rather than wrapping into the window). Then the emission gates carry: the carried set, the size relations, the pinned plain-load and plain-extent words, the three checksums and the assemblyChecks byte comparison of every named part. The read-back of the written file recomputes the three range checksums over the file's own ranges, compares the supplied bytes against the span's file range, and proves byte identity with the source outside the carried span and the main checksum word, so the unaffected media, config and both restore lists are retained by equality rather than by claim.

The replacement is same-size and in place: no descriptor, segment or trailer word changes, so the loaded image's size and end geometry are preserved and any relocation or growth stays outside this operation (it would need the descriptor carried fields proven and the mirrored trailer words updated first). The carrier claims no ownership of the runs between the linked extents: the descriptor-aware census ([recipe-design.md](recipe-design.md) section 18) leaves them unowned pending classification, and the carrier only moves the bytes it is handed.

Consumer-boundary cases: `//host/firmware:update-container-tests` covers the library boundary (window geometry from the stored words, extract→replace identity, a one-byte span change landing only at its offset and the checksum word, and the refusals: wrong length, empty or out-of-window span, an offset at or near `maxBound`, a window the carried span does not contain, an extent run outside a shortened window, a malformed descriptor through either word (the linked base at `0x1401b4`, the loader destination at `0x1401a8`), and non-`0x20000`-aligned flash words) and `//host/firmware:container-build-tests` covers the CLI (extract output against the fixture's fill run, stock reproduction, the one-byte span with the contract fields intact, and the same refusals with no output file left behind).
