### 1.2 Caller-facing file API and request path

The request path is FSM's: posters build a 12-byte header, send it through `0x71fde4` to mediamsg (task id `0x65`, entry `0x721744`), which routes by code minus `0x2c01` through `0x721578`, serializes opens by session class and forwards through `0x7211d4` to the media task (id `0x1c`, entry `0x71fe7c`), whose table at `0x814740` holds 34 handlers.

- Wrappers, exact: `storage_queue_modes.c` defines the asynchronous open `0x71c648`, write `0x71c75c`, close `0x71c7bc`, the blocking open `0x71c670`, read `0x71c720`, close `0x71c7e0`, and seek and submit forms; read `0x71c6fc` is `storage_read_async_wrapper.c`; `0x71c780` is exact in `tu_0071a93c.c`. All eight wrappers of FSM's caller-facing table are exact one-line calls into the base posters.
- Base posters `0x71c2b0` (open), `0x71be74` (read), `0x71bfe0` (write), `0x71c134` (close), `0x71c504` (finish): NONMATCHING. Their payload layouts stay FSM's byte-read ones.
- Routing: `0x7211d4` and the media-service start `0x71fd40` are exact; the media task `0x71fe7c`, mediamsg `0x721744`, its router `0x721578` and `0x71fde4` are NONMATCHING; the open-callback interceptor `0x7217f0` is exact.
- Workers: 20 of the 34 request handlers are exact, including open `0x7115a4`, write `0x7116e4`, close `0x711768`, close-with-attributes `0x711840`, seek `0x71eca4`, release-and-close `0x71f134`, the directory search pair `0x712700`/`0x7127e0`, the page transfers `0x71e828`/`0x71e8c4`, capacity `0x715a58`, detach `0x7122dc` and reformat `0x712580`. Read `0x71edbc`, attach `0x7120d8`, the single-path delete `0x7119b0` and attribute set `0x711f58`, the guarded format `0x7123b4`, the catalog handlers `0x718de4`/`0x718a8c`/`0x719614`/`0x719098` and the pattern test `0x715de4` are NONMATCHING.
- Direct A32 `BL` census of the four asynchronous operations across the three listings (byte-read; Thumb, register-indirect and copied-pointer calls not counted): open 1 in image4, 12 in image5, 26 in the plain image; read 0, 10, 13; write 0, 6, 9; close 1, 13, 16. FSM counted image4 only. The media-ready test `0x71ddf0` has 40 image4 call sites.

### 1.3 File and media service state

- Handle manager: tag allocator `0x71ef18`, release `0x71eff4`, tag map `0x71ea34`/`0x71eb28`/`0x71eaac` are NONMATCHING; FSM's byte-read semantics (16 slots at `0x9101c0`, sequence `0x910200`, semaphore `0x3c`, the 16-pair map at `0x910140`) stand. The file-cache slot claim `0x71e960` is exact.
- Completion translation `0x71d450` (39-entry table, client codes 0..14): NONMATCHING; FSM's table stands.
- Volume registry at `0x814730`, two 8-byte routes. `0x70ec84` (letter to device) and `0x70ec08` (device to letter) are exact. `0x71fc0c` (exact) maps route kind 0, 4, 7, 8 to filesystem volume kind 0, 3, 6, 7 and any other kind to 8.
- Active context: the word `0x910204` points at the media-state record. The detach worker `0x71fa9c` (exact) closes the volume, refreshes the device summary, sets the device to -1, clears the context pointer and calls the request's callback. The attach worker `0x71f7dc` is NONMATCHING.
- Media readiness, exact (`storage_media_ready.c`): `0x71ddf0(mode)` returns 5 with no context or device -1; otherwise it reads the media error bits: bit 0 reports `(2, 0x50)` and returns 1; bit 1 returns 0 for mode 2 or more, else reports `(2, 0x55)` and returns 5; bit 2 reports `(2, 0x53)` and returns 5; bit 3 returns 2 with report `(2, 0x52)` in mode 0, else 0.
- Pending format: when the context's pending byte is `0x80`, `storage_run_pending_format` (exact) sets it to 1 and sets the filesystem's format-requested flag. The format worker (`storage_format_execute.c`, exact) then refuses with status `0x16`, which it passes through `storage_translate_file_status(code, 0x16)` like every other result, so it cancels a pending format; the donor name says the opposite. `fs_format_volume` clears the flag on entry (`0x70e1d8..0x70e1dc`, byte-read), so a flag set before the call does not refuse there; it acts as an abort for a format already running **[INFERENCE: the NONMATCHING zeroing loop polls it]**.

### 1.4 Filesystem

The filesystem handles FAT12, FAT16, FAT32 and exFAT: image4 holds the type strings `EXFAT   `, `FAT32   `, `FAT12   ` and `FAT16   ` and the FSINFO signatures `RRaA`/`rrAa` at `0x781ef0..0x781f30` (file offsets `0x165af0..0x165b30`, byte-read); the exFAT name and entry code is NONMATCHING. It keeps up to three volume contexts, a sector cache and cluster-mapping caches. From exact C:

- `fs_read_volume_pages` `0x700cd8` and `fs_write_volume_pages` `0x700d20` check the volume write state first; write flushes the operation device and returns `0x27` when that fails, `0x19` on a write failure, read `0x18`.
- `fs_update_fsinfo` `0x6ff4f0` runs only for volume kind 2 with the FSINFO dirty flag: it writes `0xffffffff` to the free-count and next-free fields (`+0x1e8`, `+0x1ec`), the `0x55aa` signature, and the same sector again at FSINFO page + 6. Stock invalidates the FSINFO hints instead of maintaining them.
- `fs_format_volume` `0x70e1c4`: returns 2 with no sectors, `0x12` when bit `0x10` of the write state is set, `0x16` when the format-requested flag is set during the call (it clears the flag on entry), `0x27` when the flush fails; format codes 0, 6 and 7 select three other formatters; otherwise sectors per cluster follow capacity in MiB of `sectors & 0x7fffff` (below 16: 8, below 128: 4, below 256: 8, below 512: 16, below 1024: 32, else 64), and a cluster count of `0xfff6` or more selects the other formatter (FAT32 by threshold **[INFERENCE]**). The guarded format `0x70e328` (code `0x2c11`, which halts on `FMT_NG` per FSM) is NONMATCHING.
- The filesystem bodies FSM could not read: `0x700768` and `0x6ff4f0` are exact; `0x7004b0`, `0x719de0`, `0x71a93c`, `0x704374` (directory-entry commit), `0x6ff138` (seek) and `0x6ffc68` (close and release) are NONMATCHING; `0x7008a4` and `0x700b10` have no C.
- Block-device edges (byte-read census). The filesystem span makes 33 direct calls from 22 functions into 12 entries of the block-device API `[0x6f4d00,0x6f5480)`: read `0x6f4fa8` (12 sites) and `0x6f4f04` (4), write `0x6f5120` (8), and `0x6f4d00`, `0x6f4d24`, `0x6f4e18`, `0x6f4e78`, `0x6f524c`, `0x6f52d4`, `0x6f52e4`, `0x6f5420`, `0x6f5448` (one each). Nine of the 33 are in `fs_device_interface.c` (exact); the other 24 come from the NONMATCHING unit `tu_00707644.c`, the mapping-status functions, the directory commit `0x704374`, the directory page write `0x709690` (2), the page cache `0x7097b8` (3), the device-kind set `0x709eec` (exact, 1) and `0x709df4` in `fs_device_interface_more.c` (NONMATCHING, 1). The filesystem also makes 30 calls into 11 mapping-cache entries at `0x720028..0x720ee4`, which themselves make 10 calls into the same API (`0x6f4f04`, `0x6f4fa8`, `0x6f5120`, `0x6f53b8`, `0x6f53c8`, `0x6f53d8`). The cut under the stock filesystem is therefore the 21-function block-device API, not one file.

### 1.6 Raw NAND service and the record (persistence) service

Internal flash is reached by 128 KiB block (`>> 17`) through the raw service, not through the filesystem.

- State: `0x828574` holds a mode word, which must be 1, and a remap table at `+0xc` (`0x828580`). Erase `0x6a8c10`, write bytes `0x6a8c94` and write blocks `0x6a8de0` (exact) return -255 unless the mode is 1; the NONMATCHING reads test it the same way (byte-read at `0x6a8d58..0x6a8d6c` and `0x6a8f38..0x6a8f4c`). ### 1.7 Startup readers

- The boot ROM and boot record 1 read the loaders and image 4's record from NAND (`reports/firmware-extraction.md`); no decomp tree covers them.

## 2. What the decomp changed

- Before: FSM had 101 partial contracts with the filesystem bodies unread, 53 refused extents including 23 request handlers, and no map below the workers; SSM left the `0x828574` setter open; the NAND and SD drivers had no inventory.
- Extents: every function-ranges row is hashed against our images (all 41,910 match), so 224 of FSM's 230 entries now have a verified extent; the other six (`0x70ebb4`, `0x70edc4`, `0x70f38c`, `0x71cfdc`, `0x71d36c`, `0x71f72c`) start no row. Of the 53 refused extents, 22 are exact functions, 11 of them request handlers.
- Exact bodies: 117 of the 230 FSM entries are exact, 107 NONMATCHING; 44 of the 101 partial contracts are exact and can be completed from C. The `unknown` lists of all 230 entries in the manifest name 205 distinct six-digit addresses: 96 are exact functions, 81 NONMATCHING, and 28 are not the start of a function with C.
- New structure: the layering of §1.1; the block-device API as the cut under the filesystem; the exact NAND request API; the format and FSINFO rules; the two-level record service with its nine client entries and five areas; the call chains from records to NAND requests. The decomp gave the map and the names; several facts that settle questions (the `0x828574` store, the area-4 callbacks, the call chains) were then read from bytes because the C there is NONMATCHING or absent.
- Not changed: the bodies that decide behaviour under faults (read retry `0x6f4fa8`, SD initialisation and transfer, directory commit `0x704374`, the catalog `0x719de0`, mediamsg and the media task, the handle manager, record registration, read-latest and append-request, the program step `0x6addf0`) are NONMATCHING; their facts still come from FSM's byte reads or need byte confirmation. No physical law is learnt from source.

## 3. Target design

What we would build from scratch, as `no_std` Rust crates with typed boundaries; stock addresses live only in the shims of §4. **[INFERENCE]** throughout.

1. **Media drivers.** `SdCard` over the SD host at `0xfff50000` implements a `BlockDevice` trait (`read(Lba, &mut [Sector])`, `write(Lba, &[Sector])`, `flush`, `geometry`, typed `BlockError`), with card detect on GPIO 12.7 and write protect on GPIO 12.6 as `CardPresence` and `WriteProtect`, an initialisation state machine, single and multiple block transfers with SDMA and auto CMD12, and a typed card class SDSC/SDHC/SDXC. `NandFlash` over the controller at `0xfff52000` has its own interface, because NAND is not a sector device: `read_page(Page) -> Result<EccStatus, NandError>`, `program(Page, offset, &[u8])`, `erase(PhysicalBlock)`, spare access and status. Completion is an interrupt-driven future or semaphore of the owned RTOS; DMA buffers carry their cache-maintenance obligation in the type (a `DmaBuffer` that cleans on submit and invalidates on completion).
2. **Flash management.** `FlashMap`: the bad-block scan and logical-to-physical remap, replacing `0x828574` and `0x95dae0`, and a typed `Region` table (boot records, loaders, images, overlays, adjustment, record areas) with per-region permissions: firmware regions read-only outside the updater. The on-flash map and region layout are kept byte-compatible, since stock firmware and the boot ROM read the same flash. A `BlockDevice` over NAND exists only if an internal-flash volume is confirmed (§8).
3. **Persistence service.** `RecordStore`: one generic append-only multi-bank record ring per `RecordArea` (an enum of the five areas with record size, count, banks and blocks), with read-latest-valid, read-at-position, append, bank rotation, erase-all, and a `RecordCheck` and `RecordSeal` trait pair per area (the check and prepare callbacks; the area-3 validator replacement of `E-AREA3-VALIDATOR-REPLACEMENT-150` is the first check). Program and erase failures are typed results, which stock ignores. The record format stays byte-identical, because existing bodies hold these records and a return to stock firmware must read them. State is derived from the medium at open, so the store holds no state a reboot cannot rebuild.
4. **Filesystem.** A `Volume` trait. FAT12/16/32 from `rust-fatfs` pinned at a reviewed git revision: the crates.io release 0.3.6 README needs `core_io` (nightly) for `no_std` and `alloc` for long names, and only the unreleased master (`38b3a7950bf0e765e34286d1dfe76c519ee347e2`, 2026-10-16) makes `lfn` a feature separate from `alloc` (https://github.com/rafalh/rust-fatfs, checked 2026-11-05). exFAT from a reviewed crate or our own implementation: `exfat-slim` 0.7.0 (commit `e3a0c2702ab298456644804b553c82be9dce0821`, Cargo.toml license Apache-2.0 and one author; README at that commit, https://github.com/ninjasource/exfat-slim, checked 2026-11-05) is a candidate for review, not a selection; it has no format operation, does not maintain the volume dirty bit, warns that power loss can leak pre-allocated clusters, parses no MBR or GPT, and its TODO list includes reads past the valid data length. `embedded-sdmmc` is not suitable: its 0.10.0 documentation describes a FAT16/FAT32 implementation only (https://docs.rs/embedded-sdmmc/0.10.0, checked 2026-11-05), so no FAT12 and no exFAT. Accepted differences to decide explicitly: FSINFO maintenance, cluster-size table, dirty-bit handling, exFAT format.
5. **DCF layer.** Typed `DcfFolder` (100..999), `DcfFileNumber`, `DcfName`, numbering policy and the per-directory counts and windows of codes `0x2c0e`..`0x2c10`, owned over the filesystem; the next-number state is a settings property.
6. **File service.** A single file-service task owning every mounted volume, with a typed API: `open(path: VolumePath, mode: OpenMode) -> Result<File, FileError>`, `read`, `write`, `seek`, `flush`, `close` (durable), directory iteration, delete, attributes, `format`, `capacity`. Handles are generation-checked (`FileHandle { slot, generation }`) so a stale handle fails instead of aliasing a reused tag. Requests are messages with a typed completion; cancellation and media loss produce a defined `FileError::MediaRemoved` for every outstanding request. Media state is one `MediaState` enum (Absent, Initialising, Ready { write_protected }, Full, Error(kind)) published to readers, replacing the flag bits behind `0x71ddf0`.
7. **Card lifecycle.** Detect, initialise, mount, unmount and removal during a write as one state machine in the file-service task, with format and the guarded format as explicit operations.

## 5. Device laws

Laws the emulator must model correctly for a qualification to mean anything on silicon. Hardware column from DFA §2.3 and §2.5 and the ledger.

| Law | Needed by | FujiMod model | Hardware evidence |
| --- | --- | --- | --- |

## 6. First increment: the owned record store

Selection **[INFERENCE]**: the persistence service is the storage component whose read laws have hardware support (NAND reads and the maps), whose callers are few and known (nine entries, 30 direct client sites, 29 in image4 and one in image5, five areas), whose effects are bounded to five areas, whose device boundary is exact C (the NAND request API `0x6fb7c8`, `0x6fb904`, `0x6fb57c` and the wait and release), and whose ownership is the settings service's removal condition. The exact client entries are `0x6ac2b4`, `0x6ac478`, `0x6ac984`, `0x6acda0` and `0x6ae0fc`; registration `0x6ac328`, read-latest `0x6ac4c8`, append-request `0x6ac7d4`, `0x6acab8`, the program step `0x6addf0`, `0x6a8d40` and the per-kind write layer are NONMATCHING and are read from bytes for the contract. The filesystem and SD paths depend on laws with no hardware evidence and on a body without a working slot.

Scope: own the whole record service for all five areas behind the nine entry adapters, with the area-3 check from `E-AREA3-VALIDATOR-REPLACEMENT-150`, stock seal and check callbacks for the other areas, the stock raw NAND service as backend and the handover shim for post-boot installs (§4). Program and erase results are returned to the owned store; at the stock adapters they are reported as stock reports them.

Qualification, following the property-service pattern (`E-PROPERTY-SERVICE-ORACLE-150`, `E-PROPERTY-SERVICE-NATURAL-150`):

1. Native oracle. The nine stock entries and the owned candidate run in `fujimod-xm1-native-case`, both roles over the same declared medium model reached by trampolines over the NAND request entries the record path reaches (`0x6faf00`, `0x6faf40`, `0x6fb7c8`, `0x6fb904`, `0x6fb57c`), as the recovery-emul cases trampoline the writer's entries (`emulation/README.md`, "the 1.50 writer block loop"). Cases per area geometry: erased area; one bank partly written; a full bank (rotation); all banks full (erase of the next bank); sequence wrap at `0x7fff` across banks; newest record invalid (step back); all banks invalid (-255); single-bit correctable and uncorrectable area-3 records; full-bank refusal; erase-all through `0x6ac984`; read at a position; close and re-register; uninitialised service and inactive slot (-14). Fault cases: program and erase failure injected at the model, and interruption after each persistence step of an append and of a rotation (the recovery-emul injection), each followed by a read-latest on the medium left behind. Expectations come from SSM's byte-read record format, the bytes of the NONMATCHING entries and the hardware-captured area-2 banks and area-3 record, not from the candidate. Observations: r0, r4-r11, sp, delivered record bytes, the client words, and the ordered medium journal (request, block, offset, length and bytes); the stock wrapper and slot objects are not compared, since no code outside the service reads them. Must-fail controls: no sequence wrap, no bank rotation, erase of the current bank, no step back on an invalid newest record, ignored check result, off-by-one at bank full, cross-bank comparison without wraparound, erase-all that skips a bank, a torn append accepted as newest.
2. Natural pair. Post-boot cases on the FujiMod RAM-push route, stock role against owned role after handover: the property-service routes that append area 3 (two appends per role in `E-PROPERTY-SERVICE-NATURAL-150`), CUSTOM SET save, the defaults reset `0x6a6fd8` (which commits the custom record through `0x6a877c` and `0x6a86c4`), the queue-2 lifecycle save that appends area 2 through `0x6a8074`, a jig session ended by the power switch, which runs both (`E-JIG-CYCLE-D-150`, `E-ENDING-RESET-CALLER-150`), and the diagnostic areas' writes. Boot cases (erased store with boot recovery, populated store built from the captured banks) run the owned store from a staged candidate DAT on the FujiMod flash-boot route (`E-FUJIMOD-XM1-FLASH-BOOT-150`, staged DATs as in `E-FIRST-STAGE-COMBINED-SDK-HANDOFF-150`), since the root task opens the service before any RAM push; populated areas come from the bridge's `--record-nand` (`E-RECORD-AREA-MEDIUM-150`). Compare ordered record-service calls and results, the medium journal at the NAND request API, final area-block bytes, the settings images and menus, with must-fail guest controls as in the oracle.
3. Promotion question for hardware: does an owned append read back through stock after a reboot. It writes persistent flash and needs its own camera-run plan; the read-only read-media operation can confirm the result.

Later increments **[INFERENCE]**: the file-service task, handle manager and completion behind the caller adapters over the stock filesystem, qualified on the card-backed FujiMod routes (`E-FUJIMOD-XM1-SD-HOST-150`) and the recipe-bank storage cases; the owned `NandFlash` and `FlashMap` replacing the raw service; the owned `SdCard` under the stock filesystem at the block-device API; FAT through `fatfs`; exFAT; DCF.

## 7. Interfaces

- Settings service (#127, `replacement/property_service`). Its "base-fixed accessors" shim is removed when "owned settings storage replaces the stock layout and carries its own defaults, with the area-3 writer and validator integration" (`replacement/README.md`). The storage project supplies that storage: `RecordStore` for area 3 (and areas 2 and 4 if the settings service owns them), typed append and read-latest results, and the commit points the settings service drives: CUSTOM SET `0x630b14`; the defaults reset `0x6a6fd8`, which commits the custom record through `0x6a877c` and `0x6a86c4`; boot recovery; and the queue-2 lifecycle save, which appends area 2 through `0x6a8074`. In a jig session the power switch runs the defaults reset through the `0x504` reset bridge and the lifecycle save (`E-JIG-CYCLE-D-150`, hardware-observed; `E-ENDING-RESET-CALLER-150`, which also finds the same switch in an ordinary boot wrote nothing the store kept); for ordinary boots an orderly power-off is the only area-2 rewrite (`E-RESET-ORIGIN-BOOT-150`). The settings service owns the record payload layout, its seal and check, and the commit decision; the record store owns sequence, banks, validation dispatch and flash effects.
- Startup (#155, #153). Flash is read before the file service exists: image 5 through `0x6a96c0` and the plain image through `0x6a9844`, both on the raw service, whose maps the root task builds through `0x6a9354` at `0x69d1c4`; the root task opens the record service at `0x69d1d4`. The owned `NandFlash` and `FlashMap` must therefore be usable from the root task's context with a synchronous read path, and the owned `RecordStore` must be initialised at the root task's open or earlier, which is what removes the handover shim. Until then, startup keeps the stock setup and the record store takes over after boot.
