# Boot ROM window map: 0x80000000-0x80003fff

Artifact: private-data/analysis/x-m1-1.50/bootrom/bootrom-0x80000000-4000.bin, 16384 bytes, SHA-1 bed698ed1d91b5c29ce7c5d650156e6100c32cce, verified on this file and reproduced by concatenating the 64 files private-data/sessions/20261008T020127Z-probe-bootrom/windows/80000000.bin through 80003f00.bin in ascending address order (256 bytes each, same SHA-1).
Provenance: docs/evidence.jsonl entry E-BOOTROM-PROBE-150 (hardware-observed, session 20261008T020127Z-probe-bootrom, official 1.50), pinned fffw bootrom lead as recorded in that entry.
Follow-up capture: docs/evidence.jsonl entry E-BOOTROM-DISCRIMINATOR-150 (hardware-observed, session 20261008T035458Z-probe-bootrom): 66 windows, the 64 lead windows byte-identical to the artifact (same SHA-1), plus 0x80004000-0x800040ff (windows/80004000.bin, SHA-256 ce27e3d02a39e1ed362923b40ddbba32e6b20d71a8cd509828901ba95e2192b3) and 0x00000000-0x000000ff (windows/00000000.bin, SHA-256 ceb2d5dc1c5431ead2e60c7d6abf4da496fd847e771ac21cbcd0f16878050ea7); the 0x00000000 window is live post-boot state, not immutable ROM content.
Discriminator capture: docs/evidence.jsonl entry E-BOOTROM-DISCRIMINATOR-150 (hardware-observed, session 20261008T050828Z-probe-bootrom): 130 windows, the 64 lead windows reproducing the artifact SHA-1, the full 0x80004000-0x80007fff block compared against 0x80000000-0x80003fff window by window, the 0x80008000 period probe and the 0x00000000 handoff window; results in sections 5 and 6.
Strap capture: docs/evidence.jsonl entry E-STRAP-READ-150 (hardware-observed, session 20261008T061646Z-probe-straps, maintenance boot): the 0x400a0000 port mirror (64 bytes), the 0x80010000 and 0x80100000 alias windows (256 bytes each), the 0xfff89014 and 0xfff98000 strap registers (4 bytes each) and the two gate readbacks; results in sections 1, 4, 5 and 6.
Mode-4 decode: docs/evidence.jsonl entry E-BOOTROM-MODE4-150 (static-inference over the same artifact and its cross-artifacts: decode/boot-40048.bin, decode/boot-50048.bin, lz/id4-0061c400.bin, lz/id5-00bf1a00.bin and the complemented payload private-data/analysis/x-m1-1.50/payload.bin, under the full listings private-data/analysis/x-m1-1.50/bootrom/bootrom.dis, lz/id4.dis and lz/id5.dis); the mode-2, mode 3-6 and controller decode is in sections 8 and 9 and the port-mirror attribution in section 5.
Facts about these bytes are X-M1 1.50 hardware-observed facts per E-BOOTROM-PROBE-150; anything compared with another camera is labeled "sibling lead" and is not an X-M1 fact; anything not directly in the bytes is labeled "inferred".
CPU encoding assumptions: A32 (ARM 32-bit), little-endian, ARMv7 instruction set (movw/movt, ubfx/bfc, wfi/dsb/isb hints, Thumb-2 sdiv/mls), CP15 c6 PMSA-style MPU (inferred from the region programming at 0x80000030-0x800000cc).
Tooling: the locked llvm-objdump 21.1.8 rejects `-b binary` (GNU syntax) and the locked GNU objdump has no ARM target, so the raw file was wrapped with `llvm-objcopy -I binary -O elf32-littlearm` and disassembled with `devenv shell -- llvm-objdump -D --triple=armv7-none-eabi --adjust-vma=0x80000000`; the two Thumb-2 helpers at 0x800022cc were decoded by hand from the halfwords.

## 3. The ffsys.bin and ffboot.bin consumer

Identity: the mode-1 handler at 0x8000082c-0x80000934, entered from the dispatch at 0x80000158 (case 1) with r0=0; r0 is never read, the function overwrites it at 0x80000838.
The bytes show this call chain for the names: 0x80000864 add r0,pc,#560 computes 0x80000a9c (ffsys.bin) and 0x800008c4 add r0,pc,#476 computes 0x80000aa8 (ffboot.bin); both pass the name to 0x80001dc4 (open by 8.3 name) and file data is read through 0x80001e88.
Control flow at the level the bytes support:
- 0x80000830-0x80000854: retry loop with r4=3 calling 0x80001ba0(0xfff00404), the FAT mount (sector-0 FAT volume or first MBR partition entry at sector 0 offset 0x1be, BPB at offset 13, FAT12/16/32 detect by cluster count at 0x80001d50-0x80001d70); four attempts including the initial call, on exhaustion 0x80000858 writes 0 to [0xfff88084] and returns -1.
- 0x80000864-0x80000898: open ffsys.bin via 0x80001dc4; on success read 0x400 bytes to 0xfff00004 via 0x80001e88(0xfff00004, 0x400, sp) at 0x80000874-0x80000880; r4=3 retry counter; on exhaustion the same failure path.
- 0x8000089c-0x800008a8: call 0x80000304(0xfff00004); the bytes show 0x80000304 programs MMIO registers of 0xfff88000, 0xfff99000, 0xfffb3000, 0xfff01000, 0xfff52000 from fields of the 0xfff00004 block and executes an (address,value) pair write loop at 0x800006f4-0x80000700, so ffsys.bin is consumed as a hardware register configuration image; nonzero return goes to the failure path.

### 3.3 Card-level FAT contract

The following requirements are byte-read from `bootrom.dis` `0x80001ae0`-`0x80002090`; the proposed conservative layout is static-inference, not a card exercise.

- The SD/MMC initialization and 512-byte CMD17 block path must succeed on channel 0 (`0xfff50000`). CMD8/HCS and OCR CCS distinguish byte-addressed SDSC from block-addressed SDHC. The FAT parser assumes 512-byte sectors (`lsr #9`, offsets masked to 511); it does not read BPB bytes-per-sector at `+11`. A 4096-byte-sector filesystem is not compatible with its arithmetic.
- Sector 0 must end in bytes `55 aa` at `+510`. If it has `FA` at `+54` or `+82`, it is accepted directly as a FAT volume: a FAT superfloppy is supported, and the earlier MBR-only description is withdrawn. Otherwise the ROM reads only the first 16-byte MBR entry at `+0x1be`, requires its type byte `+4` to be nonzero, takes the little-endian start LBA at `+8`, and checks that sector for the same signature and FAT tag (`0x80001bd8`-`0x80001c60`). It does not scan later partitions, follow extended partitions or parse GPT; no active flag, CHS values or particular nonzero partition type is required.
- The BPB must describe a consistent FAT12, FAT16 or FAT32 volume. The parser consumes sectors-per-cluster `+13`, reserved sectors `+14`, number of FATs `+16`, root-entry count `+17`, total sectors `+19` or `+32`, sectors-per-FAT `+22` or `+36`, and FAT32 root cluster `+44`. Its `N = (total - reserved - numberOfFATs * sectorsPerFAT - rootEntries / 16) / sectorsPerCluster`, then `N + 2 < 0xff7` means FAT12, `N + 2 < 0xfff7` means FAT16, otherwise FAT32. Use a nonzero power-of-two cluster size, sufficient FAT space and valid cluster numbers/chains; malformed metadata is not made safe by the limited ROM checks.
- The FAT used for chain reads is the first FAT at `startLBA + reserved`; FAT32 active-FAT selection flags are not parsed. Keep the first FAT current and all copies consistent. The file and FAT32-root directory chains must be readable to their declared lengths; fragmentation is supported by `0x80001678`, so contiguous allocation is not a ROM requirement.
- Put ordinary root-directory short-name entries `FFSYS   BIN` and `FFBOOT  BIN` on the volume. The ROM uppercases its literal input names and compares all 11 short-name bytes (`0x80001a6c`-`0x80001a7c`, `0x800018a0`-`0x800018c8`); volume-label/LFN entries are skipped by attribute bit 3, and directory entries are refused for these file opens by bit 4. Long-name display text alone is insufficient, and the literal calls do not select subdirectories.
- Set `ffsys.bin`'s directory size to 1024. Keep `ffboot.bin` small, nonempty and a multiple of 512 for the first diagnostic: the DMA sector dispatcher `0x80001ffc` uses a full-sector read for destinations in `[0x40000000,0x80000000)`, regardless of the requested sub-sector byte count. Reserve its sector-rounded destination span and report/stack ranges without overlap; the ROM does not enforce a maximum executable size.

**Static-inference:** the conservative project card is an ordinary SD/SDHC card with a single first primary MBR FAT32 partition, 512-byte sectors, a standard nonzero FAT32 partition type, and the two root 8.3 files above. FAT32 follows the manual (reported), not an exclusive ROM requirement. A normal formatter and file copier, or a Haskell image builder, can create it on the host today. A host image round-trip through the decoded FAT path is a check to perform, not a result claimed here. Physical card preparation and any subsequent camera use are not performed by this research; camera use awaits the owner's go.

**Hardware-observed, owner account 2026-10-09:** every attempted Function-plus-button combination, including the sub-command dial press and all body buttons except flash release, booted normally; Function plus DISP/BACK reached the ordinary firmware-upgrade screen. **Static-inference:** these application boots selected mode 4, not an SD route. The service manual names no dial, rotation, direction, duration or release, and the owner's manual documents a press only for the sub-command dial centre, while the main dial is described as rotation (reported). No document-supported press form remains untried. The documented entry is evidence-negative on this body, not merely unverified; an alternative means of selecting ROM mode 1 or 2 is the single external gate to this diagnostic lane. Host payload/report engineering, hardware staging/config survival, R3 storage-boundary work and the absent restorative writer remain separate deliverables, not a missing service-card gate.

## 9. The mode-4 boot path, the media layout and the handoff

Flow, byte-read from 0x80000938-0x80000a64 with the section 8 routines:

1. Entry: dispatch case 4 calls 0x80000938 with r0 = 1 after the mode detect reads 0xfff89014 bits 11:10 = 3 and 0xfff98000 bits 2:0 = 1 (E-STRAP-READ-150, hardware-observed).
2. Controller init 0x80000b74.
3. Marker scan (0x80000954-0x80000968 and 0x80000988-0x80000a18): for page index r5 from 0, up to 2048 and at most two pages whose select succeeds, it requires the six-unit select, then reads the page's units in pairs (r4 = 0, 2, 4 with r4+1) into 0xfff00004 and compares the first three words of the even unit with 0x00ffaa55, 0x01234567 and 0x89abcdef, bytes 55 aa ff 00 67 45 23 01 ef cd ab 89. A miss advances the unit pair and then the page; a hit falls through.
4. Config apply (0x80000a1c-0x80000a28): calls 0x80000304(0xfff00004), the register-configuration consumer the mode-1 path also uses for ffsys.bin; a nonzero return goes to the failure path (0xfff88084 bit 0 cleared at 0x80000978-0x80000980, -1 returned, dispatch halts).
5. Load parameters (0x80000a2c-0x80000a48): destination 0x40000000, count = `[block+0x18] & 0x3ffff`, retry budget = `[block+0x10]` bits 10:8, teardown argument = `[block+0x10]` bit 1, device select 1.
6. Load 0x80000dec: as in section 8; for the container's config block the count is 2, so 2 pages of 128 KiB from the third selectable page on, to 0x40000000.
7. Handoff: success returns r0 = 0 to the dispatch, which moves its own r1 = 1 into r0 and branches to the handoff stub 0x80002298; the stub writes 2 to 0xfff98008 (1 only when its r0 is 0, the mode-0 value), clears the APSR flags and branches to 0x00000000. Failure returns -1 to the dispatch halt at 0x80000020 (wfi then a self-loop), after the load's own failure path calls 0x80000b3c(r4), which writes 0xfff88084 bit 0 = (r4 != 0).

The media layout this binds (media = the complement of the DAT main range, media offset = payload offset - 0x48, from reports/update-validation-and-boot.md plus the file checks below):

| Media offset | Content | Binding |
|---|---|---|
| 0x00 | config block: marker at +0x00, +0x10 = 0x00000300, +0x14 = 0x00000011, +0x18 = 0x00000002 (payload.bin 0x48-0x68, verified) | the ROM's scan target and the source of its load parameters; the same offsets mode 1 reads from ffsys.bin |
| 0x40000 | first boot record (payload record 0x40048, 0x4300 bytes, base 0, reset entry 0x1800) | staged to 0x40000000, the low-RAM alias, which is RAM 0; the ROM's jump to 0 lands on its vector table, the live 0x00000000 window (section 2) |
| 0x50000 | second boot record (payload record 0x50048, base 0x10000, vector literal 0x11800) | staged to 0x40010000, which is RAM 0x10000, the base its own vector literal names |
| 0x140000 | segment table read by the record (reports/firmware-extraction.md) | record-side |
| 0x24a0000 | trailer block, 32-byte trailer, halfword +0x1e = 0xaaaa (reports/update-validation-and-boot.md) | record-side |

Cross-check of the staging (static-inference composing the above): the 256 KiB load covers media [0x40000, 0x80000), the two records' media offsets differ by 0x10000, and their staged addresses differ by 0x10000, so the second record's base 0x10000, inferred in reports/update-validation-and-boot.md from its vector literal, has a second independent support; the "base 0x50000, not settled" note in private-data/analysis/x-m1-1.50/bootrom/strap-read-safety.md is the raw record-file offset convention. A hazard in the same reading, and it is load-bearing: a failed select at 0x80000ea4 branches to 0x80001054, which increments the page index and continues, r10 counts staged groups rather than media positions and +0xa4 advances only across real unit transfers, so an unselectable page inside [0x40000, 0x80000) shifts every later page down 128 KiB and the load still returns 0, and a failed select among the first two skips moves the staging origin the same way. Nothing in the ROM checksums the staged copy, and the trailer and segment gates read the media directly rather than the staged RAM (reports/update-validation-and-boot.md), so neither catches a compacted stage: the outcome is executing the wrong bytes at RAM 0 or a hang in the companion-core synchronization, not the dispatch halt. A successful mode-4 load therefore certifies transfer status only, never range integrity, and for any future write the six-sub-unit accept tags and the bad-block marks are load-bearing, because the reader skips unselectable pages and a write that damages those tags or marks relocates the image in RAM instead of failing visibly.

Where this meets reports/update-validation-and-boot.md:

- That report maps the two supplied records and their downstream gates and leaves "the ROM's stage selection, any early SD entry and recovery routes" to this work; the staged offsets here name the record the reset vector enters (the first, base 0), so its S1-S3 interruption rows and the first record's halt branches are the gates that run after this handoff (static-inference).
- The record's own gates act on the same media through the same controller: the trailer compare reads media 0x24a0000 and the segment table reads media 0x140000 through the record's 0xfff52000 traffic, and the update writer's marker discipline (trailer erased first, programmed last) is why a damaged trailer reaches the record's halt branch.
- The ROM validates only the config block's marker, the six-unit accept condition and 0x80000304's own apply result; nothing in the ROM checksums the staged records, and the first checksum-like gate is the record's trailer halfword and then the segment/decompressor path (reports/update-validation-and-boot.md).
- Mode 4 needs no SD controller, FAT or file name, and the ROM's SD routes (mode 1 FAT with ffsys.bin/ffboot.bin, section 3; mode 2 raw on SD channel 1, section 1) read no internal media, so the two route families are independent at the ROM level.

## 10. What this means for recovery, and the R1 criterion

- Mode 4 as an entry: it is ROM code plus media content plus the power-up strap state, it runs before the application exists, and nothing in it calls into the application. Its prerequisites are enumerable: the strap pair that selects mode 4 on this body (0xfff89014 bits 11:10 = 3, 0xfff98000 bits 2:0 = 1, hardware-observed); a readable page 0 whose first unit carries the marker and the two load fields; six accepted units per page scanned; and media [0x40000, 0x80000) readable for the load. It only reads and stages, so by itself it offers no repair entry, and a damaged config block, page 0 or record area takes it to the halt at 0x80000020 rather than to an alternate source (byte-read from the failure paths).
- Application-independent entries the ROM does offer (byte-read): the SD routes of sections 1 and 3. Mode 1 needs a FAT card carrying `ffsys.bin` and `ffboot.bin`; mode 2 uses channel 1 with config in raw blocks 0 and 1 and the record from block 2, count from config `+0x18`. Neither reads internal media or calls the application before staging and handoff. The reported trigger is power-up while pressing the Function button and command dial (E-SD-BOOT-LEAD); the manual names no dial, rotation, direction, duration or release, and the document-supported press is evidence-negative on this body after the owner's 2026-10-09 observation (section 3.3).
- The historical diagnostic-card buildability assessment (static-inference, sections 3.1-3.3, E-SDBOOT-CARD-IMAGE-150) found that the stock two-half config and a project-authored bounded A32 record needed no service package. Entry was the single external gate at that stage. A finished observable report payload and its full write audit remained host work; mode-1/2 config survival, staging and execution were then unproved. The [standing safety rules](../spec/07-governance-and-handoff.md#33-standing-rules) require a verified body-specific calibration backup before any use of the path. That minimal-diagnostic assessment delivered no application-independent restorative writer; card buildability alone establishes neither R3 nor R4. The later demonstrated repair is separate evidence below.
- R1 was accepted by the owner on 2026-10-08 for the decoded ROM routes and their field-level prerequisites (spec/04-recovery.md 10.1, E-BOOTROM-MODE4-150). That historical acceptance is not withdrawn or promoted by the card construction verdict or the entry-negative result. ## 11. The first record's image-4 decompression device

The stock first record decodes image 4 through the LZ engine at `0xfff43000`; it does not run a CPU token loop. All addresses below are offsets in `boot-40048.bin` (payload `0x40048`, base 0) and are byte-read from `private-data/analysis/x-m1-1.50/decode/boot-40048.dis`; the record is the first record of `private-data/firmware/x-m1-1.50/FWUP0002.DAT`.

The path is `0x2250` (segment id 4) -> `0x3d3c` (session setup) -> `0x3ea0` (media feed callback) -> `0x3c54`/`0x3cbc` (job registers/trigger) -> `0x3d08` (status) -> `0x3ce4` (count acknowledge) -> `0x3dc0` (finish) -> `0x3c1c`/`0x3b9c` (close). `0x2250` reads segment word 6 (`+0x18`, `0x160000`) as 11 128 KiB units, starts the bss fill through `0x3844`, stages the record at `0x42e40000` through `0x30d8` with callback `0x3ea0`, passes `[segment+4]` (`0x61c400`) to setup, calls finish `0x3dc0`, and then polls `0x39b0` until `0xfff02024` bit 6 is set.

`0x3ea0` is asynchronous. Its guards at `0x3eb4-0x3ed4` return when `available` (`[0x42b4]`) is above the callback argument, when the argument is at most 20, or when `finished` (`[0x42a8]`) is set. It stores the argument as `available` and clamps it to `record_length` (`[0x42b0] + 4`). When `busy` (`[0x42ac]`) is set it calls `0x3d08` once at `0x3f18` and returns at `0x3f20` if the job is incomplete, submitting nothing; otherwise it acknowledges the completed job, adds its `0x4c` count to produced, and clears busy. It then computes the feed end and returns at `0x3fb4` when `consumed` (`[0x42a4]`) is at least the end. Otherwise it submits at `0x3fec`/`0x3ff0`, stores `consumed = end` at `0x3ffc`, sets busy at `0x400c`, sets finished at `0x403c` when `available == record_length`, and returns at `0x4040` without waiting.

The NAND read `0x2ab8` calls this callback at `0x2be8`, after each 256-sector chunk's command write at `0x2bc8` and with the count before that chunk, on every iteration of the completion loop (`0x2c24`), and after the read (`0x2d04`), so a job runs while the next unit is read. The only blocking waits are in finish `0x3dc0`: `0x3ddc-0x3de4` wait for a busy job and acknowledge it, and `0x3e70-0x3e78` wait for the final job.

The feed end is the staged `available` clamped to `record_length`; if `available >= record_length` it is `record_length - 20`, otherwise `floor(available / header[+0xc]) * header[+0xc] - 20` (`0x3f64-0x3fa4`). The division calls loader A's helpers at `0x4da6c` (divide with remainder) and `0x4d978` (divide), which lie outside this record, so the arithmetic assumes loader A is already staged; there is no zero check on `header[+0xc]`. The stock record has `record_length = 0x146567` and `header[+0xc] = 0x4000`: the first feed is fixed at `0x1ffec`, while the next nine `0x20000` and the final `0x6567` are the non-deferred case, where each job completes before the next unit does. A job deferred because the engine was busy covers every whole page staged by then, so its length is a page multiple and the remaining sizes differ. The source is `staging + 0x14 + consumed`; the destination advances by the accumulated `0xfff4304c` counts.

### 11.2 Agreement with the pinned model

The FujiMod `3d90035d` model at `crates/emulator-exr2-codecs/src/lz.rs` uses the same base and registers: `0x00` reset, `0x04` start, `0x40` source, `0x44` length, `0x48` destination, `0x4c` output count, `0x80` control, `0x88` status/ack, `0x8c` enable. It requires `0x80 = 0x30003000`, `0x8c = 1`, and `0x44 & !0x7ffff == 0` at start; it reads the source, decodes method 4, writes the destination, sets `0x4c` and `0x88 = 1`, sets `0x88 = 0x101` on a malformed stream, clears `0x88` on a `1` acknowledge, and accepts `0x8c = 0` plus `0x88 = 0xf01` at close. Its source buffer is 983,040 bytes, but the 19-bit length field caps one job at `0x7ffff`, so the buffer never binds; 128 KiB is stock's staging unit, not a model requirement. The owned driver writes exactly this sequence in `replacement/first_stage/engine.rs`.

The owned `images::decompress` stages the record at `0x42e40000` one 128 KiB unit at a time, submits the same feed boundaries with source `0x42e40000 + 0x14 + consumed` and destination `load + produced` (`0x4061c400` for the stock record), and closes the session; like stock it does not compare the accumulated count with the header's decoded length, so a decode that stops short or runs long hands off with the device's output. The CPU method-4 decoder remains only as a host oracle under `#[cfg(not(target_arch = "arm"))]`, used by `//replacement/first_stage:media-stream-model` and the media tests; it is not linked into the first-stage image.

### 11.3 The completion cell

Stock `0x1fdc` calls storage fini `0x2044`, then `0x1fe0` `movw r3,#0`, `0x1fe4` `movt r3,#0x400a`, `0x1fe8` `mov r2,#0`, `0x1fec` `str r2,[r3,#0xc4]` zeroes `0x400a00c4`; `0x1ff0-0x1ff8` clears the peer cell `0x40020000`, and `0x1ffc` follows with `dsb`. The owned first stage calls `xm1_first_stage_completion_zero` at `0x6154` after storage fini and before the peer cell clear: `ldr r0,=0x400a00c4`, `mov r1,#0`, `str r1,[r0]`. The artifact admission requires a literal-loaded base and a zero-offset store, so the owned instruction form differs while the address, value and order match.

The first stage is compiled by `replacement/toolchain/rust.bzl` with the default `-C opt-level=z`, not `--profile release`; the latter describes the SDK crate only.

### 11.4 What the decode leaves to other code

- `0x22a0` calls `0x3844`, which programs the DMA block at `0xfff02000`: eight zero words at `0x400042c0` (`0x38c8-0x38e4`), destination `[segment+0xc]` (the raw `0x89ec00`), `([segment+0x10] >> 2) << 2` bytes at `0xfff02008`, control at `0xfff0202c`, source at `0xfff02000`, destination at `0xfff02004` and start at `0xfff02028` (`0x3930-0x397c`). The fill runs concurrently with the decode; after engine close `0x22fc-0x230c` calls `0x39b0` until `0xfff02024` bit 6 is set. The owned stage drives the same block from `media.rs` in the same order and at the same points, refusing the requests stock reports as errors (`0x384c-0x3878`): a zero or misaligned destination, or a word count outside `1..0x07ffffff` (`0x3868-0x3870`), instead of CPU-filling them (`0x3988-0x399c`).
- `0x4044` is a poll helper with no `bl` caller.
- Stock changes no cache or MPU state around the decode. Region 1 (`0x40000000`, attributes `0x30c`) is non-cacheable and region 0 (`0x303`) is write-back cached; coherency rests on the device writing RAM directly and on no cached access to the destination beforehand. Stock then reads `[0x61c40c]` (`0x1db4`) and the loader entry word (`0x1d80`) through cached addresses.
- The engine path has no delay. The only delay loop is the peer wait at `0x2010-0x201c` (100 iterations).
- Between the last job and handoff: close `0x3e94` and clock disable `0x3e98`; the BSS DMA wait `0x22fc-0x230c`; log `0x11000200` (`0x1d64-0x1d70`); store `[0x4300]` (`0x1d74-0x1d84`) and `[0x4304]` (`0x1da4-0x1db8`); result check `0x1fcc`; fini `0x1fdc`, completion zero `0x1fe0-0x1fec`, peer clear `0x1ff0-0x1ff8`, `dsb` `0x1ffc`; peer wait `0x2000-0x2028`; `cps #0x13` at `0x183c` and the jump at `0x1850`.

### 11.5 Differences from stock left open by decision

Two differences are open design choices for the architect; the block's declared timing law and the media-error path follow, and the list after them remains uncounted. None is a byte-level defect: the register sequence, the fill sequence (the width and the `0xfff02008` length come from the word count, and the bound is `1..0x07ffffff` words) and the per-job feed arithmetic match stock. The output-count refusal and the CPU bss fill that stood here are gone: the stage no longer compares the device's accumulated count with the header's decoded length, and it zeroes the bss through the `0xfff02000` block from `media.rs` in stock's order, submitting before the session opens and polling `0xfff02024` bit 6 after finish.

1. **Wait after every job instead of stock's asynchronous feed.** Stock's feed `0x3ea0` submits at `0x3fec`/`0x3ff0`, sets the consumed counter at `0x3ffc` and the busy flag at `0x400c`, and returns at `0x4040` without waiting. When the engine is busy it polls `0xfff43088` once at `0x3f18` and returns at `0x3f20` without submitting. Only finish `0x3dc0` blocks, at `0x3ddc-0x3de4` and `0x3e70-0x3e78`, and its tail trigger `0x3e6c` is the only job it polls immediately (`0x3e70`). The NAND read `0x2ab8` calls the feed at `0x2be8`, after each chunk's command write at `0x2bc8` and with the count before that chunk, on every iteration of the completion loop (`0x2c24`) and after the read (`0x2d04`), so stock decodes while the next unit is read. The owned `Session::submit` polls `0xfff43088` immediately after every trigger (the trigger store is `0x80c4` and the poll is `0x80c8`/`0x80cc`), so the stage's decode time adds to its media time instead of overlapping it and no job is ever deferred.
2. **Whole-unit job boundaries.** Stock's feed arithmetic (`0x3f64-0x3f6c`, `0x3f74-0x3f8c`, `0x3f90-0x3fa0`) sizes each job from the bytes staged when it runs, and `available` advances one 256-sector chunk at a time (`0x2cc4-0x2cd4`), so every stock job end is `n * 0x20000 - 20` or `record_length - 20`; a deferred job covers every whole page staged by then. Only the first feed `0x1ffec` is fixed by the bytes; the next nine `0x20000` and the final `0x6567` are the non-deferred case. The owned driver submits all eleven boundaries from a record staged one 128 KiB unit at a time, where a deferring stock submits a subset: the difference splits a job stock merged and never cuts one stock could not.
3. **The block's timing.** The owned stage now waits on the block instead of filling on the CPU, and both emulator models of `0xfff02000` declare completion after `max(2, bytes/32)` ticks, a law with no hardware measurement. The terminal observer shows the consequence: core 0's fill loop of 3,485,184 instructions becomes a 108,912-tick wait, which at the run document's 24 instructions per tick is about 2.6 million instructions of spinning, so core 0's count to loader A falls from 3,684,493 to 2,957,507 and not to the 199,309 the CPU-loop cost alone would predict. The same law sets the retained engine's boot ticks: the owned packages reach the 80-million-instruction snapshot at 101,768,072 ticks against the stock controls' 86,758,447. A measured throughput, not this law, decides whether the block is faster than the loop on hardware.
4. **The media-error path.** On a non-timeout read error stock's unit loop records status 3 or 4 at `0x3740-0x375c` and reads the next unit at `0x3760-0x3778`; only a timeout returns at once (`0x3738`, `0x3794`). Finish `0x3dc0` then submits the unconsumed tail `record_length - consumed - 20` at `0x3e14-0x3e68`, including units never read, waits for it at `0x3e70-0x3e78` and acknowledges at `0x3e7c`, then closes at `0x3e94` and `0x3e98`. The owned driver stops at the failed unit and closes, so its four close writes match stock's in address, value and order and stock's path before them does not.

Other differences that remain, not counted above:

- The entry check reads stock's fixed `0x61c40c` (`0x1dac`..`0x1db4`), refuses a decoded range that does not contain `[0x61c40c,0x61c410)`, and refuses a word outside the decoded image; stock jumps to that word unchecked, so a zero or out-of-range handoff word stops in the owned fail path before the handoff stores. The check no longer depends on the record's load address.
- The table read and both loader reads match stock: every status is discarded, including the timeout that ends stock's unit loop with status 6 (`0x1f5c`, `0x1d4c`, `0x1d58`; `0x3738`..`0x3794`), and a loader whose first unit reports a nonzero status returns without reading its remaining units (`0x2360`, `0x2364`). Each site keeps its last discarded status at `0x4808`, `0x480c` or `0x4810` for a diagnostic. The image-4 record (`0x22f0`) and trailer (`0x21a0`, `0x1ce4`) reads stay fatal, as stock's are.
- The owned driver reads unit 0 twice and starts the bss fill before opening the session; stock opens at `0x22e4` before its read at `0x22f0` and starts the fill at `0x22a0`.
- Refusals stock lacks: the record header's field checks (`images.rs` `CompressedHeader::parse`), the engine's length and page checks (`engine.rs`), and the loader-header, staged-extent and table refusals on the decode ranges (`images.rs`). Every one passes for the RC0 record's header fields, read from `FWUP0002-prefix.DAT` (sha256 `acb0fbbb9507421f48a6254920cafb5ce20e1fd6bf821bc80c912c1f99c29ca8`): image 4 at `0x61c340` with length `0x2828e8`, bss `0x89ec00`/`0x352e00` and source/stored `0x160000`; compressed header decoded `0x2828c0`, record `0x146602`, page `0x4000`, method 4; loader entries 0 and 1 are the stock ones. The staged extent is `[0x61c340,0x89ec00)` with bss `[0x89ec00,0xbf1a00)`, disjoint from the `0x61c000` table and the `0x42e40000` staging area, and every job stays within the engine's `0x7ffff` length bound because the driver stages one `0x20000` unit at a time.
- On failure stock still waits for the BSS DMA, logs `0x11000200` (`0x1d64-0x1d70`) and stores `0x4300`/`0x4304` before `0x1fd4`; the owned driver waits for the fill before returning from `decompress` and then returns before the handoff words.
- Stock's cells `0x42a0-0x42b8` and `0x400042e0` are not written by the owned driver; the descriptor at `0x400042c0-0x400042dc` is, as stock writes it.
- The load address is the record's segment word 1, which stock loads at `0x22e0` and passes to setup at `0x22e4`; the handoff argument stays at stock's fixed `0x61c40c` (`0x1dac`). Image 4's loaders read the table after the decode: `0x657114` and `0x6571bc` walk the entry and sub-list ids, `0x657184` and `0x6571a0` return header words 2 and 1, `0x6a90f8` reads header word 3, and `0x73b924` and the MPU code at `0x73bcd4`/`0x73bcd8` walk the sub-list header and entries. The stage reserves `[0x61c000,0x61c1fc)` for the stock and RC0 records from the record's own terminators, sub-list header and publication cell, and accepts the RC0 record's `0x61c340`; a cell or sub-list header placed higher extends that reservation to cover it, and the RC0 image prefixes the stock body with `0xc0` bytes, so `0x61c40c` still holds the image entry `0x69cdf8`.
- The RC0 layout is accepted end to end. The owned stage takes the record's `0x61c340` load address, decodes to `0x4061c340`, and reads the handoff word at the fixed `0x61c40c`, which holds `0x69cdf8` at image offset `0xcc`. `//emulation:flash-boot-check` on the RC0 container with the owned first stage reaches SHOOTING MENU (1,5,2) at 382,538,290 instructions with the boot snapshot at 80,000,022, 114 after the stock-DAT package's 382,538,404 and 1,007,084 before the unmodified RC0 control's 383,545,374; the unmodified stock control passes at 383,544,246 with the same 80,000,821 snapshot. Both owned packages pass (E-FIRST-RECORD-FLASH-BOOT-CHECK-150).
