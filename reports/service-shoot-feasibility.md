# What a maintenance session can show and shoot (1.50)

This answers SERVICE-SHOOT-01, step 5 of [the unlock plan](filmsim-unlock-plan.md): whether a jig session can show the film-simulation menu and take a photograph in the same power session as a RAM write. It is the G5 feasibility report for that step, and it carries a follow-up correction: the first version's negative answer on the photograph was drawn over a bounded command inventory and is revised below.

Evidence labels: **byte-read** for bytes read from the pinned artifacts, **static-inference** for a conclusion drawn from those bytes, **hardware-observed** for a camera observation, **unproved** where the named fact is unavailable. Inputs are the decoded X-M1 1.50 images (image 4 at `0x0061c400`, image 5 at `0x00bf1a00`, plain image at `0x01100000`, DAT SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490`) and the pinned Ghidra decompilation of all three images (`private-data/analysis/x-m1-1.50/af/functions/`, 41,683 functions). `FUN_` names are analysis labels.

## Answer

No on the menu path. The shot path is corrected below: a service-driven imaging-job family reaches the recorder and returns job-result buffers over the connection for the values with a publication case (`0xa5`-`0xa9`), so the first version's "no photograph" answer holds only for the keys and not for the host (**byte-read**, E-SERVICE-CAPTURE-PATH-150).

The film-simulation menu cannot be shown in maintenance mode `0xb`: the maintenance UI state dispatches no menu or shutter action and draws nothing, so the display shows neither the ordinary UI nor a service surface (**byte-read**, and a blank screen with the green LED on this body's 1.00 jig sessions, **hardware-observed**, E-JIG-OBSERVED). The S1, S2 and menu keys still produce nothing in this mode; what changed is the host side, where the queue-7 action set carries recorder jobs the first inventory could not see ([the service imaging-job surface](#the-service-imaging-job-surface-150-follow-up)).

A mode change inside the session cannot carry the patched RAM into ordinary operation: every mode requester reachable in mode `0xb` writes a shutdown-class pending mode, and no service command drives the mode machine (**byte-read**, **static-inference**).

The rebuild would not have been the problem. A mode change does not reload the images from storage; the patch survives any transition and dies only at reset or power-off (**byte-read**, **static-inference**). The failure is that no transition to ordinary operation exists, not that a transition would discard the patch.

Step 5 therefore fails at "no route reaches the menu while the patch is live". The shot half no longer fails on the firmware side: the imaging-job family can produce and return a frame in the same power session as a RAM write, with the exposure inside mode `0xb` the one unproved link. G5's feasibility branch still applies to the menu question, and the alternative entries are named below. Step 6's photograph splits in two: a frame from the write session is available as developed output, and a photograph of the patched menu waits for the persistent route or the R2 patch.

## What mode `0xb` runs

The whole boot and task set comes up before and independent of the mode decision. Boot record 1 loads the two loader records and decompresses image 4 at reset (E-LOADER-ATTRIBUTION-150, **byte-read**); image 4 startup `0x0069cdf8` creates the tasks; the `flashloader` task (`0x0073b028`, body `0x0073b3a0`) serves commands `0x4c00`-`0x4c08`: image 5 decompression (`0x006a96c0`), data ids 2 and 3, the plain image (`0x006a9844`) and the language blocks (`0x006aa63c`); image 5 entry `0x00d985a4` runs and creates `reccont` (task 3, creator `0x00dca604`, entry `0x00e00a80`). The tasks named in [the AF map](autofocus-static-map.md) (`syscont` 2, `reccont` 3, `usbcont` 7, `timer` 9, `media` `0x1c`, `lcdevf` `0x22`, `graphic` `0x28`, `saclac` `0x2b`, `lensdc` `0x32`, `lenscom` `0x62`, `lswatch` `0x63`, `lensdata` 100) all exist and block on their queues in every mode (**byte-read**).

The mode decision runs once. Init action `0x0073e0b0` calls settings initialization `0x0073cbfc`, then `0x0073ccb8` → `0x00639b1c`, which folds the boot key records (`0x00634b40` via `0x0073acb4`), runs the poller `0x00635280` and commits (`0x0063975c`). Key states UP (`0x2`), S2 (`0x8`) and USB (`0x10`) select pending mode `0xb` through `0x006330d8(0xc)` (E-JIG-ENTRY-KEY-BIND-150). Init sub-machine 0's matrix at `0x00817724` (stride 2, rows = boot phase) selects this action only at row 0, state 0, cell `{02,01}`; later queue-`0x3b` messages run actions `0x0073e138`/`0x0073e15c`/`0x0073e1d4` and never `0x0073e0b0` again (**byte-read**).

The frontend then enters the maintenance surface. `0x00c2453c`'s mode-`0xb` branch sets outer UI state `0x01467588 = 10`, sets UI code `0x0094f64c = 0xb` (`0x00d357e8` → `0x0063270c`), and dispatches modal `0x4f` row 0 (`0x00c0db50` → `0x00bfb028`) → `0x00c84b80` → `0x00c02938` → modal `0x30` row 0 → `0x00c32708`, which posts internal request `0x503` with payload `0x81` to queue 2. The backend completes the service entry and activates USB transport mode 3 (queue-7 `0x1705` → `0x00ecc104` → `0x00d82478(3)`), which selects the four-command vendor table (C0/D0/D1/C4). What runs on the host side is the service surface: the identity query, the configuration read/write (`0x1a0002`), the debug opcode `0x200001` (functions 1 and 4 read the console-log ring at `0x409c1e2c`, function 2 reads RAM through `0x00647b1c`, function 3 writes RAM bytes through `0x00647b78`, function 5 is the debug-key text parser) and the whitelist cache commands including the word write `0x24` (**byte-read**, [adjacent service hazards](adjustment-and-service-interfaces.md#adjacent-service-hazards)).

### Recording task and pipeline

`reccont` runs and serves its queue. Its queue-3 producers are the image-5 recorder bridge family (`0x00db3eec`-`0x00db44f0`, sixteen posters, plus image-4 sites) driven by the shooting-state machine (`0x00d3a46c`/`0x00d396f0` select commands `0x88`/`0x87` for shooting states `0xca`-`0xcf`) and the recording S1 branch `0x00db46f8` → `0x00dca544` (message `0x13e8`). The key modal and the shooting-state machine drive some of them, and the first version of this report generalised that to all of them; that generalisation is wrong. At least nine of the sixteen posters are called from queue-7 action handlers that a host config write reaches directly: `FUN_00db3eec` (value `0xa0`), `FUN_00db3f64` (`0xa1`), `FUN_00db4024` (`0x20c` jobs), `FUN_00db409c`, `FUN_00db415c`, `FUN_00db41d8`, `FUN_00db4254`, `FUN_00db42c0` and `FUN_00db43cc` (the `0xa2`-`0xac` sequences) (**byte-read**, private raw-media findings `private-data/analysis/x-m1-1.50/end-setting/followup/raw-media-read.md` section 9.1 and the closures recorded in private safe-jig-exit coverage `private-data/analysis/x-m1-1.50/safe-jig-exit/coverage.txt`). The trigger word they carry, `0x87`, is the same shooting command the shooting-state machine selects, so this is a capture-shaped request and not a side channel (**byte-read**, **static-inference**). The inventory that missed it was a direct-call closure and its own limits say it cannot see queue-mediated handlers (private carrier search `private-data/analysis/x-m1-1.50/end-setting/followup/gate-free-carrier.md` section 6); the imaging-job family sits exactly in that blind spot ([the service imaging-job surface](#the-service-imaging-job-surface-150-follow-up)). Whether the job completes a sensor exposure inside mode `0xb` is **unproved** and is the one question a run must settle.

### Live view

No mapped mode-`0xb` path starts the preview. The frame, statistic and draw pipelines are driven from shooting-mode producers; the mode-`0xb` entry chain contains no sensor or preview start call, and the queued draw events `0xa2b`/`0xa2c`/`0xa2d` into the image-4 GPU layer have producers only on the AF-frame latch path in shooting modes ([AF map](autofocus-static-map.md)). The only display-side request the maintenance entry produces is the `lcdevf` display-mode transition (queue-0x22 request `0x3200`, enum 2 from the service entry `0x00ec27f8`; the exit uses enum 0 and the post-exit commit enum 6 through `0x006d15d4`); what each of the 14 display modes of the `0x006d35e0` machine does to the panel is **unproved**. Frame cadence is unmapped in this repo, so "live view does not initialise" is **static-inference**, corroborated by the blank display observed on 1.00 (**hardware-observed**).

### Lens

The lens tasks are created at startup regardless of mode (`lenscom` from `0x006bd9a0` in image-4 startup, `lensdc` from `0x0076fce4` via `0x00772ccc`/`0x00ef8c90`, `lensdata` from `0x006c08ac`, `lswatch` from `0x006c5924`), so they run and their queues are live in mode `0xb` (**byte-read**). The lens command API `0x0076e2d0`'s mapped producers are the AF and motor paths behind modal `0x39` and the shooting-state machine, so mode `0xb` requests no lens movement and no AF (**static-inference**). Whether the lens is electrically powered and exchanging descriptor traffic in a maintenance session is **unproved**: mount power control is not mapped, and the jig enumeration carries no lens identity (no string descriptors, E-JIG-USB-DESCRIPTORS, **hardware-observed**).

### Display

Neither the ordinary UI nor a service screen is drawn. The maintenance chain posts the service request and returns to the modal machine; no draw event is produced (**byte-read**). The observed 1.00 state is a blank screen with the green LED (E-JIG-OBSERVED, **hardware-observed**); the 1.50 panel state in maintenance mode is **unproved**.

### Shutter and menu

They do not respond. Modal `0x38` is the maintenance modal; its dispatcher `0x00c0396c` selects rows only for application events `0x10` (USB), `0xd` (`BARR_OP`), `0xb` (`K_PLAY`, from the key table at `0x00ed2df8`), `0xa4d` and `0xa05`, plus a catch-all row that is reached only when `0x00d35fbc()` returns 1. Its six reachable actions are the two exit requests `0x00c36fa0` and `0x00c37008` (both `0x00d350c4(0xe)`), the two dead timer arms `0x00c36fb8` and `0x00c36fe0` (behind `0x006394e8`, which returns literal zero, E-PLAYBACK-A4D-DEAD-150) and the two modal re-dispatchers `0x00c37028`/`0x00c3703c`. None starts a capture, opens a menu or draws (**byte-read**). The key modal `0x39` (raw key codes `0x7`-`0x34`, including S1 `0x7`, S2 `0x8`, `EXE_M` `0x1` and `K_Q` `0x32`) is dispatched only from modal-0 actions that outer state 10 never selects (E-EXIT-ENTRY-PRODUCERS-150 and the carrier pass, **byte-read**). S1, S2 and the menu keys therefore produce no action at all in mode `0xb`.

## The service imaging-job surface (1.50 follow-up)

This section records the follow-up search of the gap the first conclusion left open. The dust inspection program documents a host-driven capture over the connection (4-3-4, **reported**), [F4] and [F5] document camera-produced image data (3-10, 3-11, **reported**), and the first inventory reached no capture trigger, so the lead was left **unchased**. The pass below covered the ten D0 opcode handlers, the `0x450006` diagnostic-id dispatcher, all 144 whitelist records and their queue-7 action set, the recorder bridge posters, the reccont machine family and the frame module of the pinned 1.50 images. It found a host-reachable imaging-job family and a matching return path (**byte-read** for the sites, **static-inference** for reachability and role). No camera or USB device was touched and no camera run is proposed here.

### The gap the first inventory could not see

The carrier pass walked direct A32 calls from the D0 dispatcher and named its own blind spots: indirect table calls and queue-mediated handlers (private carrier search `private-data/analysis/x-m1-1.50/end-setting/followup/gate-free-carrier.md` section 6). The config-write path crosses both. Config function 3 runs `FUN_00dc7564`, which posts queue-7 `0x1707` through `FUN_00ed1300` and returns; `FUN_00eca4c0` maps the payload byte to a group-2 row, the width-7 matrix `0x00ece2b8` selects an action for the state in `0x015c20b0`, and the action table `0x00ecdf7c` reaches the handler through a thunk (`0x00ecc3e4`-`0x00ecd19c`) (**byte-read**, [the raw media read interface](adjustment-and-service-interfaces.md#raw-media-read-interface)). Nothing behind that dispatch is in the direct-call closure, so "no service function posts a capture request" described the closure and not the service surface (**static-inference**).

The same blind spot hid the `0x450006` callback. The mode-3 registration `FUN_00ecc104` runs `FUN_00ecfa60`, whose `FUN_00dc74b4` copies the 0x44-byte table at `0x00dc7460` into RAM `0x015c22a0` before `FUN_00d82478` installs it: the slots are `{0x00dc7564, 0x00dc7664, 0x00dc7848, 0x00dc7874}`, the config write, the config read, the streaming completion and the diagnostic-id dispatcher (**byte-read**). The `0x450006` inner effect the earlier pass left **unproved** is therefore bound: `FUN_00d806c8` → `FUN_00d8270c` → `FUN_00dc7874`, a switch over diagnostic ids returning pointer and length pairs.

### What the jobs reach and what returns

The queue-3 messages are consumed by the `reccont` loop `FUN_00e00a80` → `FUN_00df7db8`, whose own body calls a single dispatcher, `FUN_00df7cd8` (byte-read at `0xdf7db8-0xdf7dd4`: `bl 0xdf7cd8` and nothing else between the two lock calls), so the opcode classification is spread over `FUN_00df7cd8`, `FUN_00df7dd8`, `FUN_00df7fc0`, `FUN_00dfefe4`, `FUN_00dfa674` and the rest and reaches them both from that loop and from the job-record walkers `FUN_00dcf7b8`/`FUN_00dd22f8` (machines 0 to `0x5d`, each a matrix plus action table at `0x00e3c3a0`/`0x00e3a444`) (**byte-read** for the first call, **static-inference** for the remainder). The capture-side action of that family is `FUN_00e14914` (machine `0x14`, table `0x00e3bf28`): it queries the `0x209`/`0x87` result slot through `FUN_00dce40c(0x209, 0x87, 0)` and hands the frame to the frame module through `FUN_00e676ec`, whose message `0x1349` is labelled `Reccf_SaveMultiExpo` and is received by `FUN_00e8659c` (**byte-read**). The frame module carries the buffer strings `Reccf_Offset_FIX`, `Reccf_Offset_INT`, `Reccf_Offset_RAW`, `Reccf_FaceDetect_Stop`, `Reccf_FaceDetect_Comp` and `/reccurfrm_XXX.X` (**byte-read**), and its completion `FUN_00e772ec` publishes a buffer for the host: case chosen by `FUN_0073ac60`, which is cache byte `0x80`, the whitelist value itself; cases `0xa5` and `0xa7` publish `*(record+0x188)` with length `width*height*2` or `width*height`, case `0xa6` `(record+0x8c, record+0x90)`, case `0xa8` `(record+0x2928, record+0x292c)`, and `FUN_00e6f9a0` publishes case `0xa9` from the `FUN_00e883f0` slot pair (**byte-read**). Those five are the only publication cases; `0xa2` and the other job values have none, so a capture driven through them is not returned on this channel and its return is **unbound**. That pointer and length pair at `0x015967a8`/`0x015967ac` is written only by those two completion handlers and read only by `FUN_00dc3558`, so it is a service-only return channel (**byte-read**). What each of the four buffer kinds is, and which of them carries the film binding, is analysed in [the service rendering section of the film-simulation map](film-simulation.md#service-rendering-without-firmware-writes) (E-FILMSIM-SERVICE-RENDER-150), which concludes blocked on the unbound service-field-to-canonical link rather than infeasible; the developed-output reading below is **static-inference** from the pipeline, not from the buffer identity, and the per-buffer findings are cited there and not restated here.

The develop stage sits in the same pipeline. The frame module creates the develop task (`FUN_00e87e70` and `FUN_00e88158` → `FUN_00e922bc`, entry `FUN_00ea17d0`), whose jobs run `FUN_00ea0934`, then the develop setup `FUN_00e55918` and `FUN_00e561b4`, then `FUN_00d79408`, then `FUN_00d78a80`, which calls the film-simulation develop dispatch `FUN_00d78418` (**byte-read** for the call chain, **static-inference** that a service job passes through it). The develop parameter's simulation code is a field of the job record (`FUN_00e55918` copies record `+0x508`), so a published buffer from this path is read as developed output rather than a raw dump, which is **static-inference** from the pipeline; the per-buffer classification sits in [the service rendering section](film-simulation.md#service-rendering-without-firmware-writes) and is not claimed here.

What a session can observe from them is the handler's own status return, the RAM read of the parameter blocks (`0x014e4384`, `0x014e5f30`, `0x014e5b44`) and their job slots, and for `0xa2` whatever the machine-`0x14` path stages for the image-object ids. **Unproved:** whether a media or FAT write happens further down any of the six closures; the downstream action closures were not walked to the end.

### The decisive question, and what stays unproved

On the mapped 1.50 firmware a frame can be produced and retrieved in a maintenance session, for the job values with a publication case: the whitelist imaging-job family drives the recorder's own job machinery from a host config write, the frame module's completion publishes a per-command buffer (`0xa5`, `0xa6`, `0xa7`, `0xa8`, `0xa9`), and `0x450006` ids `0x12`/`0x263` hand it to the host (**byte-read** for every site, **static-inference** for the production claim). For `0xa2` and the other values without a case there is no pair publication and the return path is **unbound**. Installed 1.50 equals the decoded images over their extents (E-DUMP-RAM-150), so the map applies to this body. What a run must still settle is the exposure: whether the job completes a fresh sensor exposure inside mode `0xb`, where no preview starts and no shooting state is dispatched, is **unproved**. The pass did not walk the machine cells from trigger to the develop task one by one, and it did not bind which of the 62 modal injectors of the trigger's application event `0x91b` is live in mode `0xb` (modal 8's `0x91b` action `FUN_00c25b9c` returns `-1` and does nothing).

## The mode word and the mode change

The mode cells are current `0x009500ec`, previous `0x009500f0`, pending `0x009500f8`, request id `0x00950100` and transition flag `0x00950110`. A whole-image pass over the pinned decompilation plus a data-word reference scan (no address word of `0x00639b1c`, `0x0073ccb8`, `0x00635280`, `0x00634b40` or `0x0063975c` exists in images 4 or 5, so there are no indirect callers) gives the complete writer set (**byte-read**):

| Cell | Writers |
| --- | --- |
| pending `0x009500f8` | `0x006330d8` (poller machine, one call site), `0x00d350c4` (UI requester), `0x00638d0c` (initialiser), `0x0063975c` (clears it on commit) |
| current `0x009500ec` | `0x00638d0c`, `0x0063975c` (commit: current ← pending, history rotated), `0x00c24994` (a dispatcher variant that forces `10 → 3`; it has no direct caller and no mode-`0xb` branch) |

The commit `0x0063975c` runs from `0x00639b1c` (the one-shot init action above) and from the UI transition `0x00d3c3b4`, which the application event `0xa05` drives. What a mode change does: `0x00d350c4(selector)` writes the pending cell, posts `0xa05` through `0x006334dc`, sets `0x00950110` and refreshes a state block; the UI pump then runs `0x00c2453c` → `0x00d3c3b4`, which commits, rotates the mode history and runs teardown and rebuild: per-previous-mode teardown cases for modes 3 to 7 (`0x00d38f34(2)` on specific pairs), a common reset (`0x00d38d98(0x508)`/`(0x909)`, `0x00d0bd88`, `0x006396ec(0x7e)`), maintenance-only calls for new modes 7 and `0xb` (`0x00d0bf3c` → `0x00d0ba20`, `0x00d2fd50(0x21)`), and per-new-mode setup (`0x00d39410(5)` for `0xb`, `(1)` otherwise; `0x00c2453c` then sets the outer state and dispatches the per-mode modal chain). The orderly exit additionally runs the modal-`0x62` lifecycle (`0xa04 → 0x500e → 0xa2f`, queue-2 opcode 2, the nine-bit barrier, `0x816`, terminal `0x00ec5804`). **byte-read**.

What can change it live from mode `0xb`:

- Physical inputs reach `0x00d350c4(0xe)` through outer-modal action 8 `0x00c2340c` (outer events 0/3/4/5/6 in state 10: `POWER OFF`/`RING_OFF`, `ADAPTER`, `CRADLE`, `BARR_OP`, `BARR_CL`) and through the modal-`0x38` actions above, and reach the poller only at boot. Every one of them writes a shutdown-class pending mode (`0xc`, `0xd` or `0xe`); the selectors that can write pending `3`/`4` (`0x006330d8(1)`/`(2)` from boot conditions `0xd`/`0xe`, and `0x00d350c4(1)`/`(2)`/`(4..7)`/`(9)` from modal-0 actions) are driven by boot conditions or by modal-0 actions that state 10 never selects (**byte-read**, **static-inference**). The power switch's runtime route is only partly mapped: the poll chain is single-shot per power session, so the polled direct commit is a boot-time path and what the switch runs at runtime is **unproved** (inherited from private physical-exit findings `private-data/analysis/x-m1-1.50/end-setting/followup/physical-exit.md` section 2.4; public exit context is in [settings-preserving exit research](service-query-and-jig-reset.md#settings-preserving-exit-research)).
- Service commands change it only as a raw write. The whitelist word write `0x24` (`0x00dbc924`) and the debug function-3 byte copy (`0x00647b78`) can both write the mode cells, which lie inside the accepted window `[0, 0x1fffffff]`, but no service command drives the transition machinery: the direct-call closure from the D0 dispatcher reaches `0x00647bd4` (function 5) and the envelope constructor `0x00db4af4` and nothing of the mode chain (E-END-SETTING-GATEFREE-NEGATIVE-150 and the carrier pass, **byte-read**). A bare poke posts no `0xa05` and runs no teardown or rebuild, and the next physical input that does post `0xa05` overwrites the pending cell first (`0x00d350c4` also ignores every selector but `0x10` while pending is `0xc`/`0xd`/`0xe`). This is **unproved** as a behaviour and is not a closed operation.

Does a mode change rebuild from storage? No. Image 4 is loaded only by boot record 1 at reset (E-LOADER-ATTRIBUTION-150); image 5 and the plain image load through flashloader commands `0x4c00` and `0x4c03`, requested only from the startup state machine (`0x0073eb00`/`0x0073eba8` through `0x0073cce8`/`0x0073cd4c`), and both senders short-circuit once their completion flag at `0x00944440[n]` is set, so each image loads once per power session (**byte-read**). Runtime flashloader requests exist only for commands 2, 6 and 8 (data ids 2 and 3 and one data command) from capture flows (`0x00e54c84`, `0x00e575fc`) and the update commit `0x00ec4618`; none overwrites image 4's menu data, and the language block at `0x0039c000` reloads with the stock strings that already contain the PRO Neg labels. The mode-change machinery calls none of these loaders (**byte-read**, **static-inference**). The patched values arrays, label entries and availability-matrix cells in image 4 survive every mode change and die only when the boot reloads the images at the next power-on.

No transient entry on the mapped 1.50 firmware shows a patched film-simulation menu. The write surface exists only in mode `0xb` (the vendor transport is activated solely by the service entry), and ordinary operation is reachable only through a power cycle, which reloads the images from storage before any UI exists. The service imaging-job entry changes what a write session can observe, not what it can show: it adds a frame to the readback, and the menu stays undrawn.

## Weaker observables

With the patch applied and the menu never drawn, the body shows nothing: the display stays blank (**hardware-observed** on 1.00, **static-inference** for 1.50). The one surface that reflects the offered list is the running image itself, read back over the service channel: the debug RAM read (D0 opcode `0x200001`, function 2, `0x00647b1c`, the `probe-ram` primitive of [the RAM probe protocol](ram-probe-live-protocol.md), gate-enabled like every debug command) returns the patched values-array rows with the moved terminator, the parallel label entries and the matrix cells for col2 `0xb`/`0xc` at their image-4 addresses (**byte-read** for the primitive, **static-inference** that these words are the menu walker's inputs). That is byte-equality evidence that the offer list is live in the running image. It is weaker than a photograph and says nothing about drawing, but it is the readback step 6 requires anyway.

A property read over the service interface does not reflect the offered list. The configuration read (`0x1a0002`, function 2) reaches the adjustment cache and the flash-log settings area, which hold the current selection and the C-slot record, not the offered rows (E-SERVICE-READ-MAP, **byte-read**); the debug opcode reads RAM and the console-log ring. The offered list's only consumers are the menu walker and the availability wrapper `FUN_0061d534`/`FUN_0061d564` at draw or selection time, whose callers are not service-reachable (**static-inference**). A property read therefore shows at most a selection, and no selection of rows 5 and 6 can exist without the menu or a raw write. The strongest non-photographic evidence a write session can produce is the readback of the patched words.

## Consequences for the plan

- Step 5's menu half is no, with the mode-change sub-answer as above: the rebuild does not reload the images, the mode word is set by the one-shot boot commit and by the `0xa05`-driven UI transition, no service command drives it, and no mode-`0xb` physical input reaches ordinary operation. Its shot half is corrected: a service imaging-job family reaches the recorder and returns job-result buffers for the case values `0xa5`-`0xa9` (E-SERVICE-CAPTURE-PATH-150), so the write session is no longer readback-only, with `0xa2` and the other non-case values returning nothing on that channel.
- Step 6 can be split. The develop half of the observation is available in the write session for the case values: the develop dispatch `FUN_00d78418` runs in that path, and a published buffer is read as developed output (**static-inference** from the pipeline; the per-buffer kinds and the film binding are analysed in [the service rendering section](film-simulation.md#service-rendering-without-firmware-writes) and are not claimed here). The menu half, the patched offering being shown and selected, still needs the persistent route (steps 8-13) or the R2 early-boot patch, because the service job bypasses the menu entirely.
- What the RAM-patched film simulation would render into such a frame: the develop stage reads the simulation code as a job-record field (`FUN_00e55918`, record `+0x508`) and runs the same `FUN_00d78418` dispatch the ordinary capture uses, so on that reading the difference between simulations would be in the pixels, not in a mode tag or a metadata claim. The patch set itself, the values arrays and the availability matrix, is read by the menu walker and the draw-time check and not by the develop dispatch, so the frame evidences the develop chain and not the offering; whether the host can choose the job's simulation code through the cache-derived fields is **unbound**, which is the link [the service rendering section](film-simulation.md#service-rendering-without-firmware-writes) leaves blocked rather than impossible. A frame would be visible evidence of rendering and would still not demonstrate the unlock on its own.
- Step 4's deferral reason is weakened but not removed: a write session now buys a readback and a frame at the first write risk, so the closed word-write operation revives with a camera run that also exercises the imaging-job family, and G4's scope should name that run. The persistent route stays the critical path for the goal of a selectable, persistent unlock (spec 19.4).

## What this does not establish

- The 1.50 display and lens state in maintenance mode is hardware-unobserved; the blank display is a 1.00 observation (E-JIG-OBSERVED).
- The runtime power-switch route; the mapped poll chain is boot-only (**byte-read**), and the switch's runtime behaviour is **unproved** (inherited).
- Whether the imaging-job family completes a fresh sensor exposure inside maintenance mode on this body: the firmware path is mapped (E-SERVICE-CAPTURE-PATH-150) and the exposure is the one link a run must observe. The HyperFFW and dust-inspection programs themselves were never obtained, so no request byte is bound to [F4], [F5] or 4-3-4.
- Installed-1.00 correspondence for any claim here.
