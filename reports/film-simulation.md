# X-M1 1.50 film simulation, menus and custom setting

Static inference on the exact public 1.50 DAT (SHA-256 `43d67afa…1490`), using the plain image at 0x01100000 and decoded images 4/5 at 0x0061c400/0x00bf1a00 ([firmware report](firmware-extraction.md)). The user's body ran **1.00** when this work was done, so none of it was attributed to the installed code; the body then ran official **1.50** (E-STOCK-150-OWNER-REPORT), the release these images come from, and since 2026-10-09 it runs the RC0 container built from them, whose film-simulation list shows seven entries (E-FILMSIM-INSTALL-150). Author mapping and an independent review on 2026-10-03; rows marked *author only* weren't re-derived by the reviewer. `FUN_` names are analysis labels. Private notes and the Ghidra project are in `private-data/analysis/x-m1-1.50/filmsim/` and `review/`. This bears on [spec/10](../spec/10-film-recipes.md).

## UI strings

- Each of the 35 language slots is linked at RAM 0x0039c000; in-slot pointers resolve as slot + offset.
- id4 `FUN_006aa63c(lang ≤ 0x22)` first loads a per-language font, then reads flash 0x1100000 + lang·0x20000 (one 128 KiB block, probably NAND) to 0x39c000 (table 0x7c8dd4).
- A string ID is an index into a 0x83c-entry table of 8-byte `{attr, ptr}` entries (English at slot + 0x3754); each pointer leads to a 12-byte record whose first word points to the UTF-16 text. ID 0x83c is blank.
- English labels exist for 10 named modes (PROVIA, Velvia, ASTIA, PRO Neg Hi/Std, MONOCHROME/B&W, +Ye/+R/+G, SEPIA), including icon glyphs (U+F06A–F06E; PRO Neg U+F201/F202; filters U+F1B3–F1B5). The font's glyph coverage isn't checked.
- *Author only:* the 0x83c count is hard-coded and tied to per-ID layout data in segment-table entry 2 (RAM 0x130000). Stock-table extension only: new labels need room in all 35 slots (the tightest has 0x6d98 bytes free); reusing the unused PRO Neg/filter IDs keeps the count unchanged. The RC1 design instead serves recipe ids from `0x83f` from patch-owned records, which needs no room in the slots ([recipe design section 4](recipe-design.md#4-labels)).

## Film-sim enumeration and menus

Menus are static nodes in id4 (`{id, type, property, kind, 0, 0, flag, parent, values, labels, …}`), whose value lists are `{row, child}` pairs ending in 0x7ffffffe. Rows index a per-property conversion table found through the pointer at 0x81b09c + 4·property; converter id4 `FUN_00631a00`.

Film simulation is property 0xfe, table 0x77ac30, shared byte-for-byte by the bracket properties 0x100–0x102. Each row is `{col0, 0x7ffffffe, col2}`, and a 0xffff row ends the table. Col0 is probably the stored code and col2 the value used downstream; both readings are inferred from use.

| 5 | 9 / 0xb | — |

- Every property-0xfe node with labels lists rows {0, 3, 1, 7, 0xc}: shooting menu 0x7823a4, Q menu 0x78b000, 0x785d74 and 0x77d184. The bracket FILM 1–3 nodes (0x78b714's children, properties 0x100–0x102) list the same rows.
- Node 0x78d2d0 lists 9 rows {0, 3, 1, 7, 0xb, 9, 8, 0xa, 0xc}. It sits under root 0x7910a4, with flag 0 and only blank labels. Whether it is ever displayed or reachable isn't established.
- RAW conversion (property 0x22b, node 0x78bd5c) offers 5 of its own 10-row list. *Author only:* that table maps all 10 named modes to record codes, which plain `FUN_01118a00` decodes using the ASCII name table at 0x11205d8.

### Availability by mode

Matrix 0x795c98 (descriptor 0x79944c `{0xfe, 0, 0x795c98}`) has 13 rows, keyed 0, 3, 1, 0xb, 0xc, 4, 7, 9, 8, 0xa, 5, 2, 6. Each row has cells for 22 mode numbers, listed at 0x792fac. A value is allowed when its cell is 1 or 2. Wrapper `FUN_0061d564` returns the value if allowed and otherwise the mode default (`FUN_00631d58`).

- Key 0 (PROVIA) is the default in all 22 listed modes.
- Keys 1 and 3 are allowed in modes {0, 0x1f, 0x21–0x24, 0x2c}; keys 4 and 5 are allowed in those plus mode 1.
- Keys 2 and 6–0xc are allowed in **no** listed mode.

What each mode number means is unknown; 0x21–0x24 (probably P/S/A/M) and 0x2c (probably C) are author readings. Keying by col2 is an inference, but it is the only reading consistent with the 5-item menu.

### Naming the unoffered values

id5 `FUN_00eaac74` is a 13-way switch, probably a metadata encoder. Values 4 and 7 give 0x300, 5 gives 0x310, and 8/9/10 give 0x301/0x302/0x303. Values 2 and 6 give 0, and 0, 1, 3, 0xb and 0xc are mode-dependent.

So 8–10 are probably three filtered-monochrome modes, and 7 a second plain monochrome. PRO Neg Std/Hi are probably two of 2, 6, 0xb and 0xc. Neither assignment is bound.

## Processing by value

Author trace and independent review, 2026-10-03. Static inference on the 1.50 images only, except where the 2026-10-08 body read is named (E-ADJ-READ-150); private notes in `filmsim-proc/` and `review/`.

**Data flow.**
- The film value travels through the capture request into id5 develop builders.
- id5 `FUN_00d78418` (sole caller 0xd78a80, writing `+0x104`; reached from 0xd79544, 0xedcde8, 0xedd23c, 0xeef2cc and 0xeef520) maps col2 to an 8-value develop code: 0←{0, 2, other}, 1←6, 2←{4, 7, 8, 9, 0xa}, 3←5, 4←3, 5←1, 6←0xb, 7←0xc.
- The monochrome filter index (`+0x110`) is set to 0 in builders 0xd79408, 0xedccd8, 0xedd120 and 0xeef1e4. The setter, `FUN_00d7851c`, ignores the film value passed to it. Builder 0xeef4b0 relies on the zeroing init. One unexplained store to `+0x110`, at 0xd756f0, is still open.
- Byte-read, 2026-10-09: `FUN_00e55918` copies capture field `+0x508` to develop-request word `[9]` (`+0x24`). The canonical-picture-parameter source and the unbound service input are separated in [the service rendering findings](#service-rendering-without-firmware-writes).

**Parameter selection.**
- Each develop stage reads selector bytes from the adjustment area at 0x41acd800.
- `FUN_0069f204` loads that area from body-specific flash (class-2 blocks from 0x3a9, table 0x7c8cd8). Only if its `+0x202` word isn't 0xaa55 does it fall back to flash 0xe0000 (payload 0xe0048), a fallback adjustment image in the DAT that carries the 0xaa55 signature and "X-M1".
- The colour-matrix stage (`FUN_00d671b4`) uses the filter table 0xd680f8 only when code = 2 and `+0x110` ≠ 0. Otherwise it uses table 0xd6891c, or the alternate table 0xd67e64 when `+0xe4` = 23.

Row attribution is bound (2026-10-08, E-ADJ-READ-150 limits): the row term `rec+0x108` is written only 0, so the colour, chroma and hue selectors index row 0 only and their row-0 slices below are their complete reachable entries; the filter table is never indexed because its `+0x110` term is written only 0; the H/S-tone and `0xd6a5c4` selectors can also reach rows 1-2, their row byte coming from `0x0073f940`.

Row-0 selectors per develop code 0–7, from the fallback image; the body's own bytes hold the same values across the develop-stage tables' extents (E-ADJ-READ-150):

## Service rendering without firmware writes

**Result (static-inference, E-FILMSIM-SERVICE-RENDER-150).** A no-firmware-write demonstration is **blocked on an unbound service-field-to-canonical-picture-parameter link**, not established as infeasible. The lower film/develop chain accepts col2 `0xb` and `0xc` without consulting the menu availability matrix. Of the service capture selectors traced below, `0xa9` is the film-enabled output candidate; the other published pointers do not establish a hidden-film rendering route. No camera run, USB operation, pixel output or new state-changing camera byte is proposed by these findings.

### Missing boundary and demonstration decision

Unproved: the host-selectable service byte or word that fills the **particular canonical picture-parameter `+0x9c` consumed by the next capture**. This is the single missing film-value link. The address resolver above does not close it: `FUN_00df054c` can select newly allocated picture-parameter objects, conditionally copy a master object and exchange snapshots with the processor through `FUN_0074e284`, `FUN_00752928` and `FUN_0075ae78`. A write to a guessed master object could be ignored or overwritten before `FUN_00eb17a4` reads another object.

Static-inference, next host-only work: trace the service `0x200`/`0x20c` flat-parameter handoff through `FUN_00ddf3f8`, `FUN_00df0030` and `FUN_00df054c` to the processor's canonical import/export (`FUN_0074e284`/`FUN_00752928`, including `FUN_00f2a468`), recording the provenance of all writes to the relevant `+0x9c` words until `FUN_00eb17a4` latches `+0x508`. If static reading cannot resolve the indirect object and copy flow, the needed host-side experiment is an instrumented execution of that parameter-copy path with tagged input values and memory-write provenance. It must model the real ARM instructions and copies, not substitute a mock film assignment or claim to emulate ISP pixels. A body RAM readback can then check a resolved canonical word and its latched record value under the separately reviewed read procedure; it is not permission to try candidate writes.

**Emulation and its boundary (E-FILMSIM-PARAM-PROVENANCE-150, first run 2026-10-09, widened rerun 2026-10-09).** The instrumented execution this section asked for was built and run: `//emulation:param-provenance` drives the real stock instructions with distinguishable tags (canonical source `0x015b5cec` film word `0xb`, processor slot `0x0096ed3c` film word `0xc`, other words indexed by address) and the runner records every valid read and write with its PC, instruction word, address and value, rejecting truncated logs. The first run stopped at three instruction forms the runner refused; the [2026-10-09 ISA admission](../emulation/README.md#isa-admission-expansion-2026-10-09-parameter-provenance) admitted them, with a fixture per form, and the rerun ends on data and profile boundaries instead. Five experiments ran without stubs or substituted copy code.

- **Reached and proved (emulation).** The canonical `+0x9c` transport now executes natively in both directions with tagged values. The export `FUN_00752928` returns after the real 168-byte copy: the four film-byte loads from the processor slot `0x0096edd8..0x0096eddb` at PC `0x00043590` carry `0c 00 00 00` and their four stores to the sink `0x3000009c..0x3000009f` at PC `0x00043594` carry the same bytes; the default-slot branch does the same. The control `FUN_0075ae78` through stock `FUN_0004357c` records the same four sites carrying `0b 00 00 00` from the canonical source `0x015b5d88` into the processor slot, which is the import's own copy tail at the destination formula `param_3*0xa8 + index*0x2158 + 0x96ed3c`. The instrumented path therefore transports a tagged film value end to end when it is fed one, and the copy is byte-for-byte.
- **Not reached, data-dependent (emulation).** The import `FUN_0074e284` returns early: the ownership-token predicate for family 5 returns 0 for the configured object pointer `0x00fe0000` (the checks read the captured token tables at `0x00915d38`), so `popeq` at `0x0074e2a4` ends the call before the copy. The import's `+0x9c` site is the same call pair the control exercises (`0x0074e338` into `FUN_0075ae78` with the computed destination), so the site itself is proved by the control with those addresses; what is not shown is a *service* write reaching the object the import would copy.
- **Reached and attributed (emulation).** The service handoff from `FUN_00df0030(0x42,1)` now executes 3734 stock instructions: the dispatcher's flat-array reads and writes, `FUN_00dfb3e0`, the queue-7 machine walk `FUN_00df74ec` (register-offset halfword table reads and the `mla`/`uxth` index arithmetic), the indirect handler dispatch `blx r3` to `0x00e2322c`, the handler's getters, the action `FUN_00df0114` and the entry of the object selector `FUN_00df054c`. It stops at `0x00dcd5b8`, an `ldrh` through the flat-state pointer word at `0x01529fb8`, which the case leaves zero because a service session supplies it. Across the run's 1266 provenance records no read or write touches the canonical object `0x015b5cec` or the processor slot `0x0096ed3c`: the tagged `0xa400001b` value the dispatcher reads from `0x014e447c` stops at `0x0152d698`, the action word-fills the flat block from `0x0152d6a8` with zeros, and the handler pair writes `0x0152ff90`. The executed service closure therefore shows no service-tagged value arriving at the canonical object, and the executed selector entry is where the service action's object handling begins.
- **Not executed (harness and profile limit, byte-read).** The object selector `FUN_00df054c` resolves picture parameters through `FUN_00eb2c7c` and reaches the processor bridge `FUN_00f2a468` in static closure, but that closure is 162 functions and includes the cache-maintenance coprocessor and RTOS queue layer the profile excludes, so it is outside both the case's 32-function bound and the admitted profile. The ranking this leaves is the same as the first run's: the service-render route is neither closed nor demonstrated, and the missing link is still the writer that fills the canonical `+0x9c` with a service-reachable field.

**Snapshot timing, as far as bytes and this emulation take it (emulation, byte-read).** The executed export gives one concrete ordering instance: the copy reads the processor slot at `0x00043590` and writes the sink at `0x00043594`, and no later executed write touches the sink's `+0x9c`, so a value present in a consumed object at copy time is transported byte for byte and is not rewritten afterwards in that call tree. **Byte-read static-inference:** `FUN_00df054c` selects handle-resolved objects, conditionally copies a master object or per-slot 168-byte object into the selected ones and passes their pointer array to `FUN_00ef8fa0`; the processor bridge `FUN_00f2a468` can import selected objects and export its snapshots back through `FUN_00752928`/`FUN_0075ae78`; the capture builder `FUN_00eb17a4` latches the film word into record `+0x508` (except when the film-bracket branch reads `+0x608`). The order matters and this is the actionable part: a write that lands **after** the copy into the object the frame consumes, or that targets a different object than the resolver returns, cannot change that frame. The reach order itself is set by task scheduling and completion edges the harness does not model, so no safe window is established here: the emulation settles only the order inside one call tree, and a write landing after the copy in that tree demonstrably survives to the end of the run because nothing rewrites it.

Static-inference, invasiveness order: (1) the existing offline selector/curve proof plus RAM readback is the available no-firmware-write fallback, but does not show visible pixels; (2) a transient canonical-parameter control followed by the film-enabled `0xa9` job is the preferred candidate **only after the missing source and snapshot timing are closed**; (3) changing the loaded menu/matrix bytes is a RAM firmware modification, outside the no-firmware-write demonstration; (4) the reviewed prefix-container firmware install is the existing menu-exposure route and changes firmware storage. Persistent settings/adjustment writes add body-state risk without closing this parameter binding and are not a demonstration substitute.

Unproved: whether any eventual scene shows a visible difference. The existing body read settles that hidden codes have complete, distinct selector/curve data in the ordinary branches, not that every branch and every scene differs from PROVIA. A valid future comparison would preserve one raw source or a controlled scene, exposure, white balance, DR and processing mode, bind each completed job's `+0x508` to 0, `0xb` or `0xc`, and compare **film-developed pixels**, not raw bytes or film metadata. ## Tone curves and the curve-record table

New section, 2026-10-08, not yet re-derived by a second analyst. It was prompted by the sibling lead [S19](../spec/09-sources.md#s19): a writer reports that on another model each film simulation takes its tone curve from a curve table, and that a simulation whose entry was missing silently fell back to PROVIA's curve. The lead raised the question only; every statement below is static inference on the pinned 1.50 inputs (the 2026-10-08 body read is named where it applies, E-ADJ-READ-150), namely image 4 (`id4-0061c400.bin`, base 0x0061c400), image 5 (`id5-00bf1a00.bin`, base 0x00bf1a00) and the fallback adjustment image the DAT carries at payload 0xe0048, whose base is bound by the string "X-M1" at +0x15c and the halfword 0xaa55 at +0x202. Resolver and raw output: `private-data/analysis/x-m1-1.50/filmsim-proc/tools/tcurve.c` and `private-data/analysis/x-m1-1.50/filmsim-proc/tcurve-out.txt`.

**The record table.** Image 4 holds a table of 37 tone-curve records at 0x824bc8. The count is a word at 0x824bc4 (0x25), loaded at run time by the reader. Each record is 0x48 bytes: a u32 key at +0, nine bytes at +4, 28 little-endian u16 at +14, and two unused bytes. Keys are 0 to 36 in order, so the table is keyed by curve id and is not addressed by the film value.

**Reader and fallback.** `FUN_00690924` (id4 0x690924) searches the table linearly for the requested key and, on a match, copies the nine bytes and the 28 halfwords out; when the loop reaches the count without a match it copies **record 0** instead. That silent substitution is the behaviour the sibling lead describes, and it exists here too, but nothing in the 1.50 data reaches it (see the inventory). A second substitution sits one level earlier: `FUN_00d66eac` calls `FUN_0073f7b8(value, 60)` (id4 0x73f7b8, returns 1 only for `1 <= value <= 60`) and writes a curve id of 0 when the family byte is 0 or above the limit, which then reads record 0 by the ordinary path. The 28 halfwords are a monotone 14-bit curve ending at 0x3fff. The nine-byte head is the same in every record except key 32, so a per-value difference is in the curve alone. Keys 31 and 32 are the records the stage's two overrides name: with the adjustment byte at +0xb5 or +0xcb74 set to 1, the id passed to the reader is the adjustment byte at +0xcb75 or +0xcb76, which in the fallback image are 0x1f and 0x20, whose curves are a regular ramp and a hard clip. Reading those two as service or test patterns is an inference from the curve shape, not from a named caller.

**Indexing.** The tone stage `FUN_00d675d8` (id5) resolves two ids per call and blends the two curves; the film side of that selection runs through a family byte and a level:

| Step | Table | Index | Failure |
| --- | --- | --- | --- |
| family A, B | id5 0xd684a0, 0xd683b0, u16 offsets into the adjustment image | `5*code + 40*mode + level1` | family byte 0 or > 60 → curve id 0 |
| family A, B, scene path | id5 0xd68296, 0xd67e82 | `43*mode + filter` | as above |
| curve id A, B | adjustment image through id5 0xd685f4, whose u16 entries are the consecutive offsets 0xcb77 and up | adjustment byte at `0xcb77 + 6*(family-1) + level2` | id absent from the 37 records → record 0 |

- `code` is record +0x104, the 8-value develop code `FUN_00d78418` writes.

- The blend weight is the adjustment byte at the offset `0xd685e0[record +0x13c]`, and the stage writes `(w*A[i] + (128-w)*B[i] + 64) >> 7` clipped to 0x3fff. In the fallback image the two A-path tables resolve to the same id for every code, so the blend is a no-op there; the scene tables agree with each other except at their mode 0, filter 0 entry (families 8 and 7, both landing on key 1), which is unreachable because a filter of 0 takes the A-path branch. A second output, from table 0xd68108 at `5*code + record +0x154` scaled by record +0x118, is written when the `mode` byte is 0 and is 0 otherwise.

## Rendered output of the unlocked modes

Measured 2026-10-09 from the owner's three fixed-scene shots taken on the RC0 container, with identical exposure (1/100, f/4.5, ISO 6400, DR Standard, WB Daylight) and identical adjustment settings, and with the camera's own film tag distinct on each: DSCF3095.JPG `F0/Standard (Provia)`, DSCF3096.JPG `Pro Neg. Std`, DSCF3097.JPG `Pro Neg. Hi` (E-FILMSIM-RENDER-150, hardware-observed images, host-side measurement). The camera moved on its support between the frames, by about 50 to 100 pixels with a 10 to 15 pixel gradient across the frame, so no single rigid alignment exists and the comparison is regional and content-matched rather than per-pixel.

**Method and limits.** Host-only Haskell tool `private-data/analysis/x-m1-1.50/filmsim-render/RenderCompare.hs` (`pair`, `pairsum`, `matrices`, `rows`); the JPEGs are converted to PPM with ImageMagick and stay under `private-data/`. A 24 by 14 grid of 204 by 197 pixel blocks; for each block a local integer offset is found by normalised cross-correlation within 24 pixels of a global seed, so a rigid shift and its gradient across the frame are absorbed block by block. Block statistics are the medians of L*, of C* and of the hue of the median (a*, b*), over pixels sampled every second pixel. Only blocks with a local NCC of at least 0.95 enter a comparison; that filter rejects the small display in the scene, whose content changes between frames, and every block whose content does not match. The tone pattern is then read on the flat subset (mean absolute gradient of luma at most 0.013), where a block has no edges to misalign and a shift of its median is a level difference rather than parallax. Limits: the numbers are block medians, not per-pixel transfer curves; parallax beyond the per-block rigid offset survives as residual mismatch in textured blocks; hue is read only where C* is at least 8; a global lighting change cannot be separated from a uniform render brightness change, so the level-resolved pattern, the sign of the differences across frame halves and the mutual consistency of the three pairs are what carry the result; and the `mode` field is bound to 0 for these frames while `level2` is bounded to its 1 to 5 rule ([the fields section](#the-develop-records-mode-and-level2-fields-bound)), so the firmware comparison names the rows per level2 rather than leaving the family open.

**Null behaviour.** If the three modes rendered identically, matched flat blocks would differ only by sampling noise (about 7,000 samples per block, standard error of the median below 0.3 L*) and by a global lighting change, which would move every block the same way. The measured flat-block differences are +1.73 +- 0.32 (n=22), -1.32 +- 0.57 (n=10) and -3.23 +- 0.32 (n=26) L*, their sign is the same in every frame half, and the three pairs satisfy the triangle within their errors, so the identical-render hypothesis is rejected.

**Measurements** (B minus A over matched blocks, +- standard error; L* and C* in Lab units, hue in degrees).

| Pair | dL* | dC* at C* >= 5 | dh* at C* >= 8 |
| --- | --- | --- | --- |
| 3095 to 3096, PROVIA to PRO Neg Std | +2.18 +- 0.59 (n=70) | -1.65 +- 0.37 (n=43) | +4.4 +- 2.3 (n=30) |
| 3095 to 3097, PROVIA to PRO Neg Hi | -0.87 +- 0.46 (n=41) | -0.99 +- 0.45 (n=28) | +0.6 +- 0.9 (n=22) |

The per-channel block medians move with the luma difference (3095 to 3096: dR +5.2, dG +5.3, dB +6.2 in 8-bit levels; 3096 to 3097: dR -4.6, dG -5.6, dB -6.9). The PRO Neg Hi against PROVIA difference is the smallest of the three and sits at about two standard errors in each of luma and chroma, so it is the weakest of the claims; the other two comparisons are well above the noise.

**Against the firmware's tables.** The selectors were re-read for this measurement (id5 tables 0xd6891c, 0xd621a0 and 0xd62040 resolved through the adjustment image): develop codes 0 to 3, PROVIA among them, take colour matrix, chroma and hue-range ids 1, 1, 1; code 6 (PRO Neg Std) takes 4, 4, 3; code 7 (PRO Neg Hi) takes 5, 5, 3. On 24 hue-rotated test colours around mid grey the matrix chroma gain is 1.287 for matrix 1, 1.152 for matrix 4 and 1.105 for matrix 5. ### Repeatability analysis

The host pixel analysis is complete (E-FILMSIM-RENDER-REPEAT-ANALYSIS-150). Its original provenance is the private `analysis/x-m1-1.50/render-repeat-9/report.md`, not a public input fixture. This is a result for one scene, one body and the installed 1.50 RC0 prefix state, not colorimetric equivalence to another camera.

The frozen comparison uses 8-bit PPM conversions, a 24 by 14 grid of 204 by 197 pixel blocks, global alignment followed by local integer-offset normalized cross-correlation within 24 pixels, and block medians sampled every second pixel. Keep blocks with local NCC at least 0.95. Measure C* differences only where reference-block C* is at least 5 and hue differences where it is at least 8. A low-gradient subset uses mean absolute luminance gradient at most 0.013 and is reported only with at least ten blocks. These thresholds and reference-side selections are part of the method, not post-result exclusions.
