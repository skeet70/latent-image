# Film-simulation offering routes and acceptance constraints (X-M1 1.50)

This report retains the route comparison, byte-bound write hazards and acceptance chain for exposing existing film simulations and extending recipes. The RC0 unlock is installed and settings are reported retained after recovery; the [film-simulation report](film-simulation.md) owns rendering/readback findings, [D3 patch](recipe-patch-d3.md) and [recipe design](recipe-design.md) own current feature designs, and [GitHub Issues](https://github.com/skeet70/latent-image/issues) owns open work. Numbered steps below describe the research chain, not a current camera run authorization.

Evidence labels: **byte-read** for bytes read from a pinned artifact or captured session, **static-inference** for a conclusion drawn from those bytes, **hardware-observed** for a camera observation, **unproved** where the named fact is unavailable. Repo-record states (gates, reviews, open work) are cited to their record.

## What gates the offering

An offered code needs a downstream-completeness statement, a bounded independently reviewed change and owner authorization for the camera operation. [The offer mechanism](filmsim-offer-mechanism.md) and [film-simulation findings](film-simulation.md) own the per-code analysis. The persistent RC0 install establishes the menu observation but does not demonstrate reversible load/unload: returning the list to stock requires another flash. G4/G5 and measured-AF acceptance remain separate requirements.

### R2 against the persistent route

The R2 route buys the earliest observation of the patch on the body, without a flash and without the persistent-install risk: an SD-staged diagnostic patches image 4 after decompression and returns, ordinary operation then shows seven entries and takes shots, and the patch is gone at the next reset. It is also not a rival to the persistent route but a rung inside it: the recovery levels are demonstrated one at a time (R2 bounded early execution, R3 storage read reachability, R4 a defined failure repaired, [spec 04](../spec/04-recovery.md#103-required-failure-classification)), and the R4 practice decision (RECOVERY-R4-PRACTICE-01, 2026-10-09) means the persistent route installs without the repair claim, its residual risk accepted; a repair demonstrated on a real failure is what earns R4.

What R2 does not have is a demonstrated foothold. The document-supported entry press is now evidence-negative on this body: the owner exercised Function plus the sub-command dial press and every other body button except flash release on 2026-10-09, all reaching the application on mode 4; Function plus DISP/BACK reached the ordinary firmware-upgrade screen (E-SD-BOOT-ENTRY-HOLD-150, hardware-observed outcomes and static-inference mode selection). The manual names no dial, rotation, direction, duration or release, and the owner's manual supports a press only for the sub-command dial centre (reported), so no document-supported press form remains untried. A working alternative mode-1/2 entry is the single external gate. The diagnostic SD-BOOT card is buildable without ZJ02217 from the held two-half stock config and project-owned bounded A32 code; `ffuser.bin` is not a ROM requirement (E-CONFIG-APPLY-150, E-SDBOOT-CARD-BUILDABLE-150, byte-read and static-inference). An observable report payload with a bounded SD write helper and C3 audit is unfinished host engineering, while mode-1/2 config survival and execution are unproved. Mode 1 applies no checksum or executable-size bound; the page-compaction hazard belongs to the mode-4 internal-media stage, not FAT/raw SD staging (window map sections 3.2-3.3 and 9, byte-read). A body-specific calibration backup comes before any SD-BOOT use ([standing rules](../spec/07-governance-and-handoff.md#33-standing-rules)), and any camera exercise awaits the owner's go.

The persistent route is bounded where R2 is not: the container rebuild, the restore-list check and the image diff are host work with named deliverables (steps 8 and 9), and its remaining unknowns are named (the encoder question, R2 to R4, the backup). Its failure is worse: a bad flash is the invalid-application class with no demonstrated repair. The routes converge on the same foothold anyway, so R2 work never blocks the persistent route; it builds the recovery ladder's first rung (R2, then R3) and, if it lands first, a pre-flash rehearsal of the same patch content.

The recommendation for the owner's decision is to move the R2 foothold's host-side work up to run alongside the container rebuild. Both are offline, both consume the same patch set, and the foothold is the longest-lead unknown on every route that touches the body. Do not schedule camera-side R2 work ahead of the container rebuild and do not let the R2 search delay it: the rebuild is what the goal of a selectable, persistent unlock actually requires. If seeing the patched menu on the body soonest matters more than persistence, fund the R2 search first and treat the flash as the later step; if the unlock as specified matters, the rebuild is the critical path and R2 is the recovery ladder's first rung, no longer a gate on the flash (RECOVERY-R4-PRACTICE-01). Step 3's emulation proof comes before either: it is the one piece both routes consume and it costs no risk.

## Steps

The evidence chain first: steps 1 and 2 build the patch set, step 3 proves it offline in the native harness, and the later steps carry it by whichever route can be observed. Steps 4 to 7 hold the deferred write work, the answered observation question, the run shape and the claim position; steps 8 to 13 are the persistent route. Each step states what it is, what it depends on, whether it is host work or a camera run, what review or owner decision it needs, and its failure modes. The path's completed steps are the delivered inputs named in the distance section above: the static map, the adjustment capture that satisfied RC0's body dependency, the primitive chain, the dump correspondence and the update-path map.

### Step 1. Settle the offer list with one evidence statement per code

What: name the film simulations the unlock offers (PRO Neg Std and PRO Neg Hi; filtered B&W is excluded because exposing it yields plain B&W tagged as filtered, [film-simulation](film-simulation.md), static-inference), and for each code record the stored value and row it takes, the develop code, the colour, chroma and tone selectors its processing reads, and the curve records on this body.
Depends on: FilmSimGate's per-code findings for downstream completeness (the deciding mechanism arrived 2026-10-08; their full findings file goes to reports/); E-ADJ-READ-150 (done); the static map (done).
Class: host work. Decision: the list is offered to the owner only after G4 and G5 clear; no review is needed for the analysis itself. The owner chooses which shooting-mode columns the new availability cells cover (FilmSimGate, byte-read): the ASTIA/Velvia pattern of 7 columns (modes 0, `0x1f`, `0x21`-`0x24`, `0x2c`) is the nearest analogue for a mode with its own develop code, and the B&W/SEPIA pattern adds mode 1.
Fails if: a code's downstream-completeness statement is missing or its processing the chain rejects, and the code then comes off the list. The numbering question is settled (FilmSimGate's read of the conversion table at `0x0077ac30`, byte-read): values-array entries are conversion-table row indices and the availability matrix is keyed by col2, so the offered rows `{0, 3, 1, 7, 0xc}` carry col2 `{0, 3, 1, 4, 5}` and B&W and SEPIA never touch matrix keys 7 and `0xc`. PRO Neg Std and PRO Neg Hi are rows 5 and 6 with col2 `0xb` and `0xc`.

### Step 2. Compile the RC0 patch write set

What: produce every word the change touches, each with its address, its current bytes verified against the E-DUMP-RAM-150 capture, its new bytes, and the ordered one-word write sequence. The change is a menu-list change plus an availability-matrix change (spec 19.3 RC0), and FilmSimGate's read names two gates to remove: rows 5 and 6 are absent from every labelled surface's values array, and their col2 keys `0xb` and `0xc` are allowed in no matrix row, so a listed row would still be suppressed at draw time by `FUN_00d52684` case `0xfe` via `FUN_0061d534` (byte-read). The two arrays cannot be extended in place (byte-read: values `0x0078319c` ends at `0x007831c4` with the next property's array at `0x007831cc`; labels `0x0078d4f8` ends at `0x0078d548` with node `0x0078d558` following), so the write set is a relocated values array and label array built in free space, two pointer swaps per extended surface (node `+0x20` values, `+0x24` labels), and the matrix cells at key-`0xb` base `0x00795dac` and key-`0xc` base `0x00795e08`, each `+4·column` into the 22-entry list at `0x792fac`. Label entries cost nothing new: both modes have their stock-shape quadruples among existing string ids below the `0x83c` class boundary (PRO Neg Std `{0x49b, 0x49a, 0x499, 0x49c}`, PRO Neg Hi `{0x497, 0x496, 0x495, 0x498}`), so the 35 language slots and the id count stay untouched (FilmSimGate, byte-read). The Q cell stays on its stock rows: its labels live in the closed vector-glyph space of P5 and no record for the two mode icons is bound there. The surfaces to extend follow the coverage list in recipe-design section 14.2.
Depends on: step 1; the dump correspondence (done); P18's row-`0xd` sentinel note (done, [recipe-design](recipe-design.md) section 11).
Class: host work. Decision: none.
Fails if: no free space qualifies for the relocated arrays (G4 preflight wording: zeros and unused-looking buffers do not establish ownership); a pointer swap, array word or matrix cell falls among the 781 runtime-written bytes whose writer is unestablished (E-DUMP-RAM-150, byte-read), so its current content cannot be matched stably; a target address is unaligned or outside the primitive's two accepted windows; the set cannot be carried by one reviewed closed operation, in which case it splits and each part needs its own review.

The stock-case discipline of [the harness README](../emulation/README.md) applies unchanged, so each manifest pins exact input provenance with SHA-256, names the dump windows covering the executed bytes with their correspondence to installed bytes established by E-DUMP-RAM-150, and screens the 781 runtime-written data bytes out of both the executed ranges and the input slices; the patched case's data bytes come from the step-2 write set with their own provenance. The runner's R4F-only rule and instruction preflight bound the closure as they did for the area-3 stock case.
Depends on: step 2 (the patched arrays, pointers and matrix cells); the dump correspondence (done, E-DUMP-RAM-150); the harness (done, G3 accepted).

### Step 4. The closed word-write operation and its G4 preflight, deferred

What: the closed `//transport:camera` word-write operation (disarm cache `0x80` with `0x33`, load direction `0x81`, address `0x83`-`0x86` and data `0x87`-`0x8a`, trigger with `0x24`, poll the status byte `0x82`, verify each written word by readback, internally built bytes, journaling before sending, no retries, stop on any unexpected reply) and the A/B/F preflight record over its write set. Both are deferred 2026-10-08: with step 5's answer a write session can observe only the readback, so the work buys a byte-equality check and the first write risk on the body at no observation (orchestrator decision, E-SERVICE-SHOOT-150). The work revives with a persistent install, where a RAM session rehearses the exact image-form change with readback before the flash, or with an R2 foothold, where the same write set lands before the UI starts and the menu observes it.
Depends on: step 2; the primitive chain (done, byte-read); the open review findings on the sibling `read-media` operation (RAW-MEDIA-READ-01, changes-required 2026-10-08), whose plumbing this shares.
Class: deferred host work plus one independent review before any live run (H2 new bytes, docs/principles.md and spec 07 section 3.1).
Fails if, when revived: any code path can place a value other than the disarm `0x33` or the trigger `0x24` in cache `0x80`; the whitelist rescan rule is not contained (only a write whose start index is `0x80` re-scans, and the scan fires on a zero-length request and on a repeat of the same value, byte-read); the overloads of cache `0x81` are not contained (it is the write's direction byte and also the erase dispatcher's case selector, so `0x81 = 1` plus a mis-triggered `0x28` runs erase case 1, byte-read). The preflight keeps its own failure conditions (original bytes not matched, the RAM-ownership argument rejected, the owner rejecting the residual recovery limitation, R1 accepted and R2 unavailable).

## Risks, stated plainly

The recovery-level and diagnostic-only statements in this retained risk assessment describe the 2026-10-09 installation decision. Current historical-class acceptance and the unavailable SD route are recorded in [recovery status](recovery-status.md#historical-recorder-failure-r4-decision-2026-10-27).

- The first write of any kind to the body was the 2026-10-09 install and the body accepted it (E-FILMSIM-INSTALL-150); the deferred RAM word write (step 4) is still unexercised, so how the body reacts to that service write stays static-inference until a run says otherwise (the one earlier state-changing attempt was rejected at the gate, E-END-SETTING-150-REJECTED, hardware-observed).
- The write primitive shares its request field with six destructive values. Cache `0x80` is the whitelist trigger; `0x24` posts the RAM word write, and `0x06`, `0x20`, `0x21`, `0x22`, `0x28` and `0xc3` post storage-write or state-destroying handlers (`0x22` commits the whole 4 MiB adjustment area, `0x28` is the erase dispatcher) (raw-media-read.md section 9, byte-read). The mode word neutralises them only at the single value that also defeats the read, so the only protection is that the closed operation can never place another value there.
- The same field overloading reaches the direction byte: cache `0x81` is the write's direction and the erase dispatcher's case selector, so the write direction `0x81 = 1` is also erase case 1 (byte-read).
- The primitive's accepted range covers the running images and the adjustment cache mirror at `0x41acd800`, which sits in the second accepted window (byte-read, static-inference). An address error can reach firmware data or the calibration mirror that action `0x22` would then commit to storage.
- Recovery is at R1. R2 is unavailable, so the initial H2 execution scope must carry the remaining recovery limitation, and the undo for a RAM failure is a cold start (spec 03 G4, spec 04 section 10.3).
- The persistent route's failure is worse and slower to undo: an interrupted or bad flash leaves the invalid-application class with no demonstrated repair, which the owner accepted explicitly on 2026-10-09 (RECOVERY-R4-PRACTICE-01) with the standing capability diagnostic until a write half exists, and body-specific data has no persistent-level backup yet (recovery-status.md preservation table, byte-read). The 2026-10-09 install completed without interruption, which earns no recovery credit.
- The observation gap is closed on the menu half and open on the frame half: a write session shows no menu (E-SERVICE-SHOOT-150), and the menu half arrived through the persistent install on 2026-10-09 (E-FILMSIM-INSTALL-150); a write session can produce and return a job-result frame for the case values `0xa5`-`0xa9` through the imaging-job family (E-SERVICE-CAPTURE-PATH-150), which stays a write-session question, and the offline proof stands (step 3).
- Known session costs: jig cycles that end with the power switch reset date, time, language and the C slot (E-JIG-OBSERVED, hardware-observed). The power-cut ending preserves settings but is the ending that discards the patch.
