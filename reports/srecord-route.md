# The S-record service route as a firmware install path (1.50)

Status: host-only static analysis, mapped and rejected. It decides whether the service S-record loader (`C:\IMFIDX10\LX30A.S3`, `FUN_00db8ab0`) can install the patched image, and compares it with the stock update route ([UPDATE-01](update-validation-and-boot.md), [install procedure](install-procedure.md), [container contract](update-container-rebuild.md)). No camera run stands behind it and nothing here authorizes one.

Evidence labels: **byte-read** for bytes read from a pinned artifact or captured session, **static-inference** for a conclusion drawn from those bytes, **hardware-observed** for a camera observation, **reported** for vendor documentation or owner reports, **unproved** where the named fact is unavailable. All addresses bind to the public X-M1 1.50 DAT, SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490`, and its decoded images 4 and 5 (SHA-256 `f2e2acab892dafeed85171f6870a411f0a2d5eae10921b86a24630d401dcff16` and `3cd501c07533938ae4d9347616986fd1649005a588c36b5abf05e36ef4fd892a`).

## 1. What the route is

One service trigger starts it: a config function 3 write of value `0x20` to adjustment cache index `0x80` matches whitelist record 24 at `0x00dc7a84`, posts queue-7 message `0x1707`, and the group-2 matrix at `0x00ece2b8` sends row 24 to action 27 in states 0, 1, 2, 3, 5 and 6 (state 4 takes the inert action 3). The action wrapper `0xecc63c` passes the descriptor `0xdbcc10` = `{0x81, 0, 0}` to `FUN_00dbc858`, which runs `FUN_00db8ab0` and stores its status byte at cache `0x81` through `FUN_0069fc94` (**byte-read**).

`FUN_00db8ab0` is a firmware-span writer (**byte-read**; the binding was first recorded in [UPDATE-01](update-validation-and-boot.md) and is re-derived here from the decompilation `private-data/analysis/x-m1-1.50/af/functions/00db8ab0.c`). It probes staging RAM at `0x42e40000`, opens the literal path `C:\IMFIDX10\LX30A.S3` (string at `0x00dba31c`), parses Motorola S-records from the file into staging at media offset = record address, and on the terminating record erases the boot-trailer block `0x125` and bulk-programs the whole selection-0 span, logical blocks `[0, 0x126)` = `0x24c0000` bytes from staging, through `FUN_006a95cc` → `FUN_006a9268`. The status byte it returns is `0` on success and `1`, `3`, `4`, `5`, `7` or `9` on the failures named in section 4.

## 2. The volume question

The file layer resolves `C:` to a volume, and the answer is the SD card, so the file can be placed where the loader looks.

The open helper `FUN_0071c2b0` treats a path whose byte 1 is `:` as drive-qualified: it maps the letter through `FUN_0070ec84` against the volume registry at `0x814730` and accepts the path only when the mapped volume index equals the active index at `[0x910204 + 0x114]` (error 5 otherwise, error 8 for an unregistered letter) (**byte-read**). The registry is statically initialized in image-4 data: record 0 is `{letter 0x43 'C', valid 1, index 0, kind 8}` and record 1 is `{letter 0x42 'B', valid 1, index 1, kind 7}` (**byte-read**, `xxd` at `0x814730`). `C:` therefore names volume index 0, and the loader's literal path opens only while volume 0 is active.

Every other path in this firmware replaces its byte 0 with the active volume's letter at runtime, and its literal letter is decorative: the update container name is built that way at `0xdb971c`, the demo movie path at `0x73c2d8`/`0x73d828`, the AUTO_ACT path at `0xed1de0`, and the frame-name builder `0x1275b90` writes byte 0 from `DAT_015253dc`, which `0x1277f74` sets from `FUN_0071f708` (**byte-read**). The S-record loader passes the constant unchanged, so it binds to volume 0 whatever the active letter is.

Volume 0 is the SD card on this body. The retained-header frame-name field at `0x409c2904` holds `C:\DCIM\963_FUJI\DSCF3087.JPG` and `C:\DCIM\963_FUJI\DSCF3091.JPG` in the 2026-10-08 captures (**byte-read** of the dump diff records), the named files are the body's photographs on the SD card (**reported**), and the builder forms that field with byte 0 = the active letter, so the active volume during ordinary shooting carries letter `C` and holds DCIM content. The SD card is the body's only host-writable FAT volume (**reported**; the X-M1 has no internal photo memory). The vendor-side leads converge: fujihack records the per-model S3 file in `IMFIDX10` as card content and its reader as `usbcont` work (**reported**, sibling scope [S22](../spec/09-sources.md#s22), [S27](../spec/09-sources.md#s27)).

The owner can create `\IMFIDX10\LX30A.S3` on the card with ordinary host access; both path components are 8.3-conformant. A run with the card absent or a different volume active fails at the open with status 1 and touches no media (**byte-read**), so the volume question cannot produce a partial write.

Unproved: the device behind registry record 1 (letter `B`, kind 7), the semantics of the kind byte `8`/`7`, and the active volume at loader time inside a maintenance session. None of them blocks the route, because the loader binds to `C` = volume 0 and the failure mode is a no-op.

## 3. The stale-staging hazard

The loader pre-fills nothing. The only pre-parse write is the RAM probe `FUN_00db8944(0x42e40000)`, which stores `0x55aaaa55`, `0`, `-1` over the first 12 bytes of staging and verifies them (**byte-read**); those 12 bytes stay as the probe pattern unless records cover them. Data bytes land at `staging + record address` and nowhere else, then `FUN_006a95cc(0x42e40000, 0x24c0000)` programs the whole span from staging whatever the file covered (**byte-read**). The write length is the selection-0 capacity from `FUN_006a93e8(2)` = `0x24c0000`, so an uncovered byte is programmed from stale RAM at its staging offset.

Staging `0x42e40000` is the firmware's image staging buffer: the boot stages the compressed image-4 stream there, the update path's in-memory staging is `0x42e4025c` in the same region, and image 4/5/6 code uses the region as a buffer elsewhere (**byte-read** and **static-inference**, [firmware-extraction](firmware-extraction.md)). What it holds at loader time is whatever its last user left, which no static pass can name (**unproved**).

A complete S-record file covering all `0x24c0000` bytes removes the hazard, because every programmed byte then comes from the file. Any file with gaps programs stale RAM in them, including gaps inside the trailer block, the image streams and the segment table. The parse does not check coverage: the high-water address it tracks is bounds-checked but never compared against the span, and a file with correct records over half the span and an `S7` terminator parses clean (**byte-read**).

A complete file is large. The line buffer holds 63 characters, so a record line carries at most count `0x1D` = 29 bytes = 4 address + 24 data + 1 checksum for an S3 record (S2 gives 25 data bytes), and an S2 address tops out at `0xFFFFFF`, which covers 16,777,215 of the 38,481,920 bytes, so the top 56% of the span needs S3 records (**byte-read** parse, **static-inference** arithmetic). Full coverage at 24 data bytes per record is 1,603,414 records; at 62 characters plus LF per line that is about 101.0 MB (about 96.3 MiB), or about 102.6 MB with CRLF, against the stock container's 38,405,148 bytes. S0 and S1 records carry no data here: the parser classes them as headers and stores nothing (**byte-read**).

The 512-byte chunked read and the parse loop carry that file in code structure: the read loop refills its 512-byte buffer through the file server with no record-count or file-size cap, a zero-byte read before the terminator record aborts with status 3 before any media write, and the parse is one pass over the bytes (**byte-read**). The cost is about 197,300 chunk reads (about 200,430 with CRLF) and about 101 million byte-loop iterations; nothing bounds the duration and nothing on this body measures it (**unproved**).

| File | `<volume>:\FWUP0002.DAT` on the card root, name built at runtime | `C:\IMFIDX10\LX30A.S3` literal on the card |
| Prewrite validation | Header type 4, identity records against the body identity, version format and policy, the main complement-sum against header word `0x20c`, two auxiliary raw sums, read-count checks, staging RAM probes ([container contract](update-container-rebuild.md) section 2) | Per-record line/count consistency, per-record checksum summing `0xff`, per-record address bound `[0, 0x2740000]`, the terminator record requirement, one staging RAM probe. Every failure status (`1`, `3`, `4`, `5`) returns before the first media write |
| Whole-image binding | The three sums bind the whole main range and both auxiliary ranges to the container header | The per-record sums bind each line to itself; a consistent wrong image, a stale build or a cross-model file is written as presented (**byte-read**, **static-inference**) |
| Identity and version | The eligibility gate checks the body identity and refuses a numerically lower version ([UPDATE-01](update-validation-and-boot.md)) | No identity or version check anywhere in the path |
| What is written | Blocks `[0, 0x126)` via `0x6ab4cc`: per-block window-check, compare, erase, 64 × `0x800` program and verify at per-logical remapped targets, bad-block shift with budget `0x14`; then the configuration completion `0xdb91e0` (template refresh plus 1,487 restore-list bytes and the commit) and the session commit | Block `0x125` erase (result checked, status 7), then one bulk request `FUN_006a9268(0, 0x126, 0x42e40000)` with the run's start block resolved through the remap table `0x828580` and a cache maintenance over `0x24c0000` bytes; the same optional pre-erase (`min(10, property 0x276)`, sleep `property 0x275`) as the stock route. No configuration completion and no session commit (**byte-read**) |

| Marker discipline | The trailer-block erase result is unchecked, so a silently failed erase can leave the old `0xaaaa` marker over a mixed image with no checksum to notice | The erase result is checked and a program failure re-erases block `0x125` before returning status 7, so a completed failed run does not leave a live marker over a mixed image (**byte-read**) |

## 5. Could it install the patched image

The route programs a raw media span, not a container, so the file must carry the whole program span in S-record form. Closed (**byte-read** of the segment table and the loader chain): the span holds the two supplied boot records (media `0x40000` and `0x50000`), the pointer words and segment table at `0x140000`, the image 4 record and stream at `0x160000`, the image 5 record and stream at `0x2c0000`, the plain image and table regions, the trailer at `0x24a0000` with its `0xaaaa` marker, and the tail `[0x24a0020, 0x24c0000)`. A file that supplies all of it installs a bootable image.

The project can produce that content. The stock container's main range is the same bytes complemented (media byte = file byte XOR `0xff`, [container contract](update-container-rebuild.md) section 1), so the unpatched span comes from the pinned DAT; the patched image-4 stream and its derived words come from the FILMSIM-PATCH-01 write set through the encoder that reproduces both stock streams (E-LZ-ENCODER-150) and the rebuild tool's size relations; and the tail needs a policy byte value, `0xff` being the natural one since no traced reader consumes it (the same residue class the stock route leaves in block `0x125`).

The configuration areas are where the route loses to the stock one. The configuration completion `0xdb91e0` (template refresh, restore lists, commit through `0x6a8de0(0x29, 33)`) does not run on this path at all, so whatever the program span does to the configuration store is final. Where the store sits relative to the span is unproved: [UPDATE-01](update-validation-and-boot.md) remaining work 2 names the open item, and the reports' current phrase "media `[0x520000, 0x940000)`" overlaps the segment table's image 5 and plain-image flash windows `[0x2c0000, 0x900000)`, so the commit's device-index space and the image's media offsets cannot be one space until that is settled. The consequence branches: if the store lies inside the programmed span, the file must carry this body's media-form bytes there or the calibration is overwritten from the file or from stale RAM, with no restore lists to repair it, and the project holds no media-form capture of that store (the E-AREA2-BANKS-150 capture covers different blocks and the adjustment captures are RAM-cache form of the first `0x42000` bytes); if the store lies outside the span, the write leaves it untouched and the route also skips the template refresh and the restore re-apply the stock route performs. The project cannot state which branch holds today, so it cannot state the file's full required content, and that alone keeps the route off the install path.

## 6. Recommendation

Reject the S-record route as the install path and record it as mapped and rejected. The stock route has the mapped owner procedure ([install procedure](install-procedure.md)), camera-side validation that binds the whole container to the header and the body identity, the per-block program/verify loop with bad-block handling, and the restore lists that preserve this body's calibration, which the census has shown complete for this body (E-ADJ-MOVERS-150). The S-record route offers no validation the stock route lacks, removes none of the stock route's exposure, and adds the gaps of section 4: no whole-image binding, no identity or version gate, a bulk program whose interior blocks ignore the remap table, no configuration completion, no restore lists, and a live one-byte trigger that stays armed in every future service session.

The route's better properties are small and do not change the decision. Its trailer erase is checked and a failed program re-erases the marker, so a failed run cannot leave a live marker over a mixed image. Its parse phase is entirely before the first media write and it has no cached-success byte to skip validation on a retry. Neither offsets the missing validation and preservation, and the second property only matters once a wrong file has already been parsed.

For the owner's purpose the file is 2.6 times the container's size, takes an unmeasured session of card reads and hex parsing, and lands the same image the stock route would land. Keep the stock route as the single install path; keep this route's map in this report so it is not re-litigated from the `0x20` row of the hazard table.

## 7. What this changes for the raw-media records

The `0x20` row of the hazard table in [the adjacent service hazards](adjustment-and-service-interfaces.md#adjacent-service-hazards) now names a firmware writer instead of an unspecified reach of the device-write primitive `FUN_006f0f6c`: `FUN_00dbc858` runs the S-record loader, which erases the boot-trailer block and bulk-programs the firmware span when the S3 file exists on the card. The row's conditionality is part of the hazard: the same cache byte is inert with the file absent and a firmware install with it present, and nothing on the camera distinguishes the two before the erase.

The `read-media` safety argument keeps its rule unchanged and gains a named worst case. The command's type restriction still admits only `0x35` and `0x33` at index `0x80`, and the disarm-first order still makes a repeated or zero-length request inert (`transport/FujiAF/ReadMedia.hs`, [the raw media read interface](adjustment-and-service-interfaces.md#raw-media-read-interface)). The value the rule keeps out is now bound: `0x20` is the firmware-install trigger whose first media write is the boot-trailer erase, the same unrecoverable window as the stock update, so a mistyped trigger byte is not a generic write risk but an install attempt. The rule matters more once an S3 file exists on a card in the lab, because the trigger is then live; every future operation that can write cache `0x80` gets reviewed against this binding.

## 8. What stays unproved

The configuration store's placement relative to the program span (UPDATE-01 remaining work 2) and with it the file's required bytes at those offsets and the route's calibration outcome; what backs volume index 1 and the active volume at loader time in a maintenance session; the driver-side behaviour of the bulk request `FUN_006faf5c` (per-block erase/program/verify, ordering, bad-mark writes) and the interior-block behaviour under a non-identity remap; the timing of a full-coverage file; what staging holds when the loader runs; and the vendor's intent for the file, which the fujihack leads describe as an EEPROM-patch carrier (**reported**, sibling scope) while this decode shows a firmware-span writer. No S-record file was built and no camera run stands behind any claim here.
