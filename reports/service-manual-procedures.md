# What the service documentation says maintenance mode is for (X-M1)

## Scope and evidence

This reads the procedure chapters of the owner-purchased X-M1 service manual ([S15](../spec/09-sources.md#s15), procedure reading recorded as [S31](../spec/09-sources.md#s31), PDF sha256 `7ebe30b1feb41f7fc20488ad674080de69cc5e38fc4e29b4647a04b08dd6ac9b`, kept in the owner workspace and not committed) and classifies every documented procedure against the firmware work this project has bound.

Every manual claim is **reported** and makes no durable claim about this body; the two serial-like strings printed in the manual are sample data (E-SERVICE-MANUAL limitations).
Firmware statements are **byte-read** or **static-inference** over the pinned official 1.50 artifacts, the existing reports cited inline, and a bounded disassembly pass over the identity handler `0x00d7fdec` of decoded image 5 (file offsets `0x18e3ec`..`0x18e784` of `private-data/analysis/x-m1-1.50/lz/id5-00bf1a00.bin`).
Camera observations are **hardware-observed** on installed 1.00 unless a line names 1.50.
No procedure was executed, no camera or USB device was touched, and no sibling-model fact is used as X-M1 evidence.

Sections read: 1-3 to 1-5 (jig and inspection tool lists), 3-1 to 3-15 (adjustments), 4-1 to 4-3-4 (inspection), 6-1 (technical update list).

## The answer the documents give

Maintenance (jig) mode exists to run three Windows programs against the camera over USB: the PC adjustment software ZJ02216 ("X-M1 W PC Soft", app name HyperFFW), the SD-BOOT package ZJ02217 used by MAIN PWB Initialize, and the dust inspection software ZJ02218 (3-4-2, 3-4-4, 4-3-2, **reported**).
In that mode the technician writes calibration and identity data, downloads firmware, initializes a bare main board and ends the repair session with End Setting (3-8 to 3-15, **reported**).
The mode is a repair workflow rather than a shooting mode, and the one photographic check it drives is the dust inspection capture (4-3-4); the electrical and resolution inspections run in ordinary modes (4-1, 4-2, **reported**).

## Capabilities the documents name that the firmware search has not looked for

These are the leads that matter, because the service command set the project has mapped is small (eleven reviewed read operations, `transport/README.md`) and the documents describe writes and driven hardware.

- A capture and image-transfer path inside maintenance mode. The dust inspection software enters jig mode the same way and returns a captured image to the PC with OK/NG and dust locations (4-3-4, **reported**), and [F4] and [F5] must likewise read sensor images (3-10, 3-11, **reported**). **Found in the firmware**: the queue-7 imaging-job family (whitelist `0xa0`-`0xac`) drives the recorder from a host config write and the case values `0xa5`-`0xa9` return job-result buffers over `0x450006` (E-SERVICE-CAPTURE-PATH-150, [service-shoot-feasibility](service-shoot-feasibility.md)), so this is no longer the strongest open lead; what remains open is the exposure completing in maintenance mode, the return path for the non-case values, and the request bytes of the three programs.
- A calibration-write path per adjustment item. [F9] writes per-body mount data from a PC file and [F1], [F4], [F5], [F7] write measurement results (3-9 to 3-13, **reported**). The adjustment-cache commit sites are mapped (E-ADJ-COMMIT-MAP) but no service function is bound to any of these items. **Unchased**.
- A firmware-download command family over the USB service link, distinct from the SD update route, followed by an "Adjustment Value Protection Reset" that resets the EEPROM while preserving adjustment values (3-14, **reported**). The project binds only the SD-card container route (E-UPDATE-REBUILD-150). **Unchased**.
- A destructive PC-issued initialization: flash ROM reset plus internal memory format ([I], 3-8, **reported**). The destructive `0x00dbcaa4` selector dispatcher is the nearest mapped code (raw-media-read.md section 2) and is not bound to it. **Unchased**.
- Repair identity writes: destination, USB_ID, repair data, administrator ID, repair station ID, automatic repair serial, WLAN MAC (3-15, **reported**). No mapped writer covers any of them. **Unchased**.
- Flash firing under software control in maintenance mode ([F7] pop-up prompt, 3-12, **reported**). **Unchased**.
- A progress and result channel for those operations. The NORMAL/WRITING/SUCCESS/FAILnn tag family is **byte-read** in the identity handler and is the firmware shape the manual's OK/NG and download-progress screens imply; its operating procedures are **unchased**.
- Host-side scripting and variable watching over the connection (3-6, **reported**; the menu marks Script and Watch variables "Do not use"). No camera claim; a lead for what the connection can drive.

## Entry and exit

Entry is documented twice and the firmware supports the PC one.

- PC jig entry: power on while pressing the shutter button and UP arrow with USB attached and power supplied, then check the green LED (3-7-1 Step 6, 3-7-2 Step 6, **reported**). **Confirmed** by the boot key-state binding (E-JIG-ENTRY-KEY-BIND-150, **static-inference** over byte-read sites) and by owner observation on 1.00 (E-JIG-OBSERVED, **hardware-observed**). The manual requires the LED check and nothing else; the firmware maps two further entry words the manual never mentions (**byte-read**).
- SD-BOOT entry: "Switch camera power ON while pressing the Function button and command dial" (3-8 Step 1(3), **reported**), with the SD-BOOT card in and no USB, then watch the LED sequence. The manual's verb is "pressing" for both controls; it names no rotation, direction, duration or release and no main/sub dial, and the owner's manual gives a press action only to the center of the sub-command dial (**reported**, owner's manual), so spinning is not a documented reading. The ROM's consumer for two of the three file names is **byte-read** (bootrom-window.md section 3); the press itself is now exercised: on 2026-10-09 the owner powered on with the Function button together with every button except the flash release and with the sub-command dial press, with no card and no USB, and every documentation-supported reading booted the application normally (E-SD-BOOT-ENTRY-HOLD-150, **hardware-observed**), so the documented entry is **evidence-negative** on this body and no documented press form remains untried.

Exit is documented as one real exit and one non-exit.

- The documented exit is [F12] End Setting: it is "the final step before returning the camera to customers", it switches repair mode to product mode, and the manual repeats at 3-1-2 and 3-15 that the adjustment software's work is not finished without it (3-7-2 Step 8, 3-15, **reported**). After it, the closing steps are power off, battery out, USB disconnected, lens removed (3-15 Step 5, **reported**).
- The documented non-exit is [X] Restart and any power-off before End Setting: both leave the camera in repair mode and unrecognized as PTP or mass storage (3-7-1 Step 7, 3-7-2 Step 8, **reported**).
- Whether the firmware supports the documented exit: one mapped route matches its shape, the function-5 `POWER OFF` finalizer (mode `0xb` to `0xd`, persistence attempts, completion barrier, terminal action; E-END-SETTING-CANDIDATE, **static-inference**), but nothing binds function 5 to the name [F12] and the single live attempt was rejected at the closed gate byte `0xf7` before any parser ran (E-END-SETTING-150-REJECTED, **hardware-observed**). The route is a **confirmed** candidate shape, its binding to [F12] is **unproved**, and a settings-preserving host exit is **unproved** either way (E-JIG-EXIT-MODEL).
- The three endings the owner has used, the power switch, the supply cut and the disconnect, are all power-side endings. The manual documents the power switch ending at the close of every procedure and documents none of the three as an exit from repair mode; only End Setting is documented to restore product mode (**reported**). The supply cut's settings preservation on this body (E-JIG-POWERCUT-PRESERVES-150, **reported**, 1.50) has no documented counterpart and the manual does not discuss it.
- Re-entry after any OK/NG window requires a power-off and a fresh jig boot (3-7-2 precautions, **reported**), which matches the firmware's single-shot boot poll: the key-state test runs once per power session (service-shoot-feasibility.md, **byte-read**).

## What this does not establish

- No procedure here was executed; every camera behavior in the tables is a manual claim except where an evidence id names an observation.
- No HyperFFW, dust-inspection or SD-BOOT binary was obtained, so no request byte is bound to [F8], [F9], [F4], [F5], [F7], [F1] or [I] and the function-5 to [F12] binding stays **unproved** (end-setting-live-protocol.md).
- The identity and status tags are read from the pinned 1.50 images; what this body's installed firmware returns for them is **unobserved**, and the S02 live run covered only the product tag (E-S02-IDENTITY-QUERY).
- The sibling service manuals (S24, S25) show the same workflow family but are **reported** leads for other bodies and are not X-M1 evidence (evidence rules, [the public survey](service-mode-public-survey.md)).
- The sample serial and USB_ID strings printed in the manual are sample data, not this body's (E-SERVICE-MANUAL limitations).
