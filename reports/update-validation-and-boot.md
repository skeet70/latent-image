# X-M1 1.50 update validation and boot failure branches

UPDATE-01 has a bounded **static inference** contract for the inspected X-M1 1.50 paths: descriptor/event selection, modal inputs, initial selectors, raw and managed commit direction, spare-window setup, bad-marker software ordering and timeout-abandon control flow are mapped below. These source findings do not establish interrupted-operation durability, cancellation semantics or bad-marker retention after reboot. The first supplied boot record has concrete halt branches; the second initializes peripherals and hands off into the same shared images, with configuration-failure continuations and unbounded waits. Neither examined route demonstrates damaged-image fallback or recovery. The separately accepted R1 boot-ROM mapping does not authorize an updater or repair write.

All addresses below belong to the exact public X-M1 **1.50** DAT, SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490`, preserved at `private-data/firmware/x-m1-1.50/FWUP0002.DAT`. Installed correspondence is limited to the measured byte-equal ranges accepted by [G2](firmware-extraction.md#g2-acceptance-decision). All 781 differing bytes and their containing instructions remain excluded; that acceptance does not establish their writers, harmlessness or non-executable status, or whole-extent repeatability. Source acquisition, export hashes and inferred decompression are recorded in [firmware extraction](firmware-extraction.md).

## Container, file path and validation

The body/lens/other selector is explicit. Body means selector 0 at these functions; other selectors must not be used to infer body policy. The UI gate reads selector `0x9503c4` (`0x944580 + 0xbe44`), while write dispatch reads `[[0x15c20a8] + 0x224]`. The gate stores a normalized `0`/`1`/`2` copy of `0x9503c4` in the latter field: `0xd0c5c4` stores 0, `0xd0c6a4` stores 1 when the UI selector is 1, and `0xd0c794` stores 2 otherwise. The base object is `0x95d460`. The first boot record initializes its selector word `0x95d684` to zero: `0x2250` reads id-4 record BSS base/length `0x89ec00/0x352e00`, and `0x22a0` calls fill `0x3844` with that range and value 0 before decompression. This is a source contract of the mapped boot path, not a new hardware retention observation.

The computed-offset UI initializer is closed (**byte-read**, E-UPDATE-SELECTION-COMMIT-150): `0x6390b4` sets offset `0xbe3c`, two successive `add #4` instructions reach `0xbe44`, and `0x6390c8` stores zero through `[0x944580 + offset]`. This store is missed by a literal-only reference scan. The six image-5 selector stores are `0xc83ed4`, `0xc83f6c`, `0xc840fc`, `0xc84130`, `0xc841f4`, `0xc8429c`, each followed by request `0xd38d98(0x60c)`. Broad initializer `0x638d0c` also zeroes `[0x944580,0x954d78)`, including `0x9503c4`. On event `0x600`, `0xec1b8c` loads payload word 0 from `0x15c2084`, and `0xec1b90` calls `0xec8f24`, which stores it at `0x15c20a8`; the body poster supplies `0x95d460`. Selector equality holds at gate time only, not after a later UI-selector change or a write event without another gate call. Arbitrary RAM corruption and untraced dynamically generated code are outside this store inventory.

### Model and version policy

`0xec8554` emits the parsed type, 512-byte identity field and major/minor values into body UI state. `0xec90e4` copies the identity field with the bounded string-copy helper `0x721b40` (stop at NUL and zero-pad), to state `[+0x10,+0x210)`. The matcher at `0xd0a2b4` compares 16-byte records there with the 16-byte current identity at `0x96b402`–`0x96b411`, ending at a zero-leading record or after 32 records. A first record consisting entirely of `0xff` returns success; an empty first record returns failure. The current identity is supplied through `0x639b1c` → `0x73acfc` → `0x72b8c4` → `0x69f600`; it is encoded configuration identity, not a proven literal `X-M1` comparison or a cryptographic model binding.

New major/minor are stored at `0x95d670` / `0x95d674`, from raw DAT `0x204` / `0x208`. Current major/minor at `0x95d678` / `0x95d67c` come from `0x69f520` through `0xec9048` / `0xec907c`. That version getter can return configuration bytes or its built-in 1.50 value depending on configuration byte `+0x206`; it is not independently verified storage identity.

`0xd0a590` accepts either both new version words `0xffffffff`, or each word at most `0x99` with a decimal low nibble (consistent with packed BCD). `0xd0a728` then implements the following unsigned comparison for **body selector 0**:

```
accept = both new words are 0xffffffff
      or new_major > current_major
      or (new_major == current_major and new_minor >= current_minor)
```

The body branch therefore permits equal-version eligibility and rejects a numerically lower valid version. The equal-minor decision is visible at `0xd0a7a4`–`0xd0a7ac` (`cmp`, `movlo 0`, `movhs 1`). Lens/other selectors instead require a strictly greater minor for equal majors. The sentinel's existence is an observed branch, not an installation proposal. UI eligibility is called by `0xca6108`; it does not establish that every alternate service/in-memory caller enforces this gate.

### Commit step and service writers

The descriptor walker is `0xec09e8`, not a literal reference to either chain (**byte-read**, E-UPDATE-SELECTION-COMMIT-150). For slot `s`, it loads the chain through `[0xec4aec + 4*s]`, width through the u16 at `[0xec4eb0 + 2*s]`, event row through `[0x15b8094 + 2*s]`, and current state through `[0x15b8078 + 2*s]`. The record index is `(row*width + state) & 0xffff`, multiplied by 12. Record `+4` is the optional callback, invoked with slot `s`; kinds 4/5 additionally call record `+8`, while other kinds write record `+8` into the current-state halfword unless it is `0xffffffff`. These are indexed state/event matrices, not linked lists or an automatically advancing commit sequence. No bounds check is present in this walker.

This binds the actual instruction addresses and arguments, without treating a wrapper name as a write target.

The `0xdbd028` target is a raw read, not a hidden writer: `0x6fba08` validates device presence and `start+count` against capacity, then calls `0x6fed00`. The latter reads main pages through `0x6f1a74`; request word 3 enables the additional 16-byte spare-window read through `0x6f1aa8`, with a `0x40`-byte buffer stride reserved after each page. On the selected geometry the request covers eight raw blocks starting at `8*property(0x82)`, into `0x4b2ece00`, with asynchronous completion enabled and timeout 2000. Property `0x81` chooses whether spare windows are included, not write direction. No erase, main/spare program or bad-marker persistence follows from this call. The `0xecd178` site only posts its service opcode; it does not independently select a media address.

## Native writer boundary and preservation limits

`0x6ab4cc` uses a static 27-row `{block_count, logical_start, class}` table at `0x7c8c6c`, referenced through the class-field pointer `0x7c8c74`. Selection 0 includes class < 2; selection 1 includes class == 1. The included rows are `{7,0,0}`, `{0x11c,7,1}`, `{2,0x123,1}`, `{1,0x125,1}`: selection 0 covers logical blocks `[0,0x126)`, while selection 1 covers `[7,0x126)`. At the native `0x20000` stride, capacity is `0x24c0000` for selection 0. The body chooses the selector from header word `0x210` bit 0 via `0xec88c8`; on this DAT the word is 1, yielding selection 0. Consequently the checksummed main bytes and rounded storage block span differ.

The routine's media order is closed (**byte-read**). It first erases raw block `0x125`, the trailer block, through `0x6a9aa4` (its argument is ignored; it runs `0x6a9010(0x125, [0x7c8c90])` with `[0x7c8c90]` = 1), and does not test that result; it then optionally pre-erases `min(10, property 0x276)` times through `0x6a9010(0, 0x126)` with returns ignored, which erases the contiguous physical run from `remap[0]` rather than the per-logical targets the program loop uses, targets that shift under bad blocks, and sleeps `property 0x275` seconds; then it programs blocks in ascending logical order, sourcing block `i` from `(image_base & ~1) + (start+i) * 0x20000`. Media offset therefore equals image offset: the checksummed main bytes land at media `[0, 0x24a0020)` while the rounded span covers `[0, 0x24c0000)`, whose tail past the trailer holds the auxiliary pair lists on the in-memory route (contiguous after the main bytes) and unrelated RAM on the file route. Each block goes through an eight-word request `{remap[start+i], 1, 0x14 - [0x828578], staging|0x40000000, 1, out-status, 1, 500}` to `0x6faf5c` → `0x6fc638`: read the 16-byte page-0 window (`0x6f1aa8`, decode `0x6fbd2c`), compare-read the block (`0x6fbedc`, 0x800 main bytes per page by `0x72232c`; a match skips erase and program), erase (`0x6f0e18`, NAND word `0x60d07000`), program 64 pages of 0x800 (`0x6fc0a4` → `0x6f0f6c`, command words `0x801070xx` or `0x80000001`), then verify by compare-read again. A nonzero return aborts the writer; a zero return with out-status set marks the block bad (`0x6fc408` programs all 64 pages with `0xff`), retries the same data at the next contiguous physical block within the `0x14 - [0x828578]` budget (exhaustion returns 5, mapped to `-40`), rebuilds the map through `0x6a90ac` and continues without advancing the source. **byte-read**; the runtime geometry (64 pages of 0x800 from record 3 at `0x82988c`, selected by index `[0x918844]`) is **static-inference**.

Marker ordering (**byte-read** and **static-inference**): the old trailer block is destroyed first and the trailer block is programmed last (ascending loop; its page 0, carrying the 32-byte trailer at media `[0x24a0000, 0x24a0020)`, is programmed first within the block). The DAT trailer bytes at `0x24a025c` (`ff ff b5 fd ff ff b5 fd df ff ff ff ff ff ff ff ff ff ff ff ff 3b 9e ff d7 d7 d7 ff 00 00 55 55`) complement to media words `0x024a0000`, `0x024a0000`, `0x20`, 0, 0, `0x0061c400`, `0x00282828` and halfwords `0xffff`, `0xaaaa`, so the boot record's compare (`0x1cec`–`0x1cfc`, halfword `+0x1e` against `0xaaaa`) reads the trailer's last halfword, restored by the checksum pass's in-place complement. Because the marker-erase result is not checked, a silently failed erase can leave the old marker beside rewritten body blocks; on the mapped success paths the marker is absent from the first erase until the last block's page 0 completes.

Remap and bad blocks are closed at the software level (**byte-read**): the u16 remap table `0x828580` (314 entries, zeroed at `0x6a9158`) maps logical block to physical block by the cumulative-skip rule physical = logical + (bad blocks at or below), rebuilt at `0x6a9168`–`0x6a9200` from the bad-block list pointer at `0x9552f0` (the list is at `*(0x9552f0)`, count at `+0`, entries at `+4`). The list is first filled from the boot record's scanned buffer (`[[0x61c00c]]+4`, scan of `[0, 0x13a)` at `0x2058`, published at `0x1f60`–`0x1f78`) and later rebuilt by `0x6a90ac` → `0x6fb1f4` → `0x6fbd88` from window decodes; the boot record applies the same rule at `0x209c`. A window decoding 2, erase status bit 0, program status bit 0 or a verify mismatch marks a block bad. The lower entries enforce `block + count <= device size` (return `-30`), and the wrappers additionally require the start block below `0x400`. The multi-block configuration entries `0x6a8de0` / `0x6a8e84` do not consult the remap table (absence scope: their full listings in the id 4 listing); their engines retry around bad blocks with the same primitives.

The 16-byte window is separate from the four 512-byte main-data sectors in the controller's format-1 address construction (**byte-read**): `0x6f1aa8` passes selector 4 to `0x6f0df4` → `0x6dde74`, which sets column 512; ordinary sector selectors 0–3 set columns `528*selector`. It reads 16 bytes from `0xfff52400..0xfff5240c`. This is the first sector's spare position in that software format, not the first 16 main bytes. `0x6fbd2c` returns 0 for an all-`0xff` window, 1 when nonempty with bytes 4/5 both `0xff`, and 2 otherwise. Before normal raw programming, `0x6fc638` loads four `0xffffffff` words into spare registers `0xfff52040..0xfff5204c` through `0x6de0d4`. The bad-block writer `0x6fc408` instead calls `0x6ef084(0,1)`: this loads a spare record with byte 5 = `0xe0`, alongside main data filled with `0xff`, and programs pages ascending. Thus its bad mark is not the main-data `0xff` fill. The source reader recognizes that spare byte as bad on a later scan; actual retention across power removal remains observationally unverified.

Spare-register stores precede main transfer setup and controller submission; there is no separately acknowledged spare-program command before or after the main program in these paths. The software therefore does not establish a within-operation durability order between spare metadata and main cells. No software ECC computation is present in the inspected writer/primitives; controller-generated ECC, partially programmed spare/main combinations and the atomicity of their visibility after interruption are hardware questions, not inferred from the MMIO store order. The MMIO contract is submit `0xfff52008`, poll `0xfff52004` bit 2, status `0xfff52028`, command words `0xfff52018` / `0xfff5201c`, data port `0xfff52400`. Event wait or 625 × timeout polling bounds completion; timeout 500 gives 312500 polls. Timeout-abandon writes 0 to `0xfff52008` and never re-polls. It remains unknown whether this cancels an operation, merely disables its interface, leaves NAND busy or permits later completion, which main/spare cells persist, and what reset does to that in-flight operation. No timeout, abandon, power-loss or reboot-retention experiment was run.

Retry budget zero is explicitly unbounded in `0x6fc638`: the entry value is latched as a boolean and every decrement/exhaustion check is conditional on that boolean. A positive budget permits that many bad-block skips, then returns 5 on the next bad block; zero skips the budget check throughout the walk. It is not an immediate failure or a zero-write request. The caller's existing device-range validation is not a new per-retry terminal bound.

After the main writer, `0xec88c8` calls `0xdb91e0`. Cache `[0x96ca50] = 0x41acd800` holds `0x420000` bytes. The routine snapshots the first `0x42000`, refreshes that prefix from raw logical blocks `[7,10)` through `0x69fe20(0xff)` → `0x6a9ac4`, restores the auxiliary-listed ranges, then calls `0x69fea8` to commit the whole cache. The enable producer is the header parser `0xdb9cd4`: it clears the selected mask (`0x14e3578` for body selector 0, adjacent words for selectors 1/2) at entry, then ORs bit 0 when header `(offset,length,checksum)` at `+0x244/+0x248/+0x24c` has offset != `0xffffffff`, nonzero length/checksum and length <= `0x10000`; bit 1 uses the same conditions on `+0x250/+0x254/+0x258`. Length above the bound returns status 3 rather than enabling that input. These bits admit restore-list inputs, not writes by themselves. Each auxiliary-1 u16 pair must satisfy `off+len <= 0x10000`, and auxiliary-2 u32 pairs `off+len <= 0x42000`.

The commit address space is now distinguished from the raw template address space (**byte-read**, E-UPDATE-SELECTION-COMMIT-150). `0x6a9354` supplies `{physical_base=0x380,physical_count=0x80,logical_count=0x6c,map=0x95dae0,async=0,timeout=1000,index=0}` to `0x6fb2a0`, which publishes the map at `[0x919a20]` and rebuilds it through `0x6fea48`. Its header contains base/count/logical-count, a free-candidate u16 at `+12`, bad count at `+14`, a logical→relative-physical u16 table at `+16`, and a free bitmap after that table. Rebuild scans the physical pool `[0x380,0x400)`, excludes bad windows, admits erased windows as free, and associates occupied blocks only when first/last-page window logical numbers agree and are in range. Invalid/duplicate associations are erased, or marked bad on erase failure. `0x6fca60` resolves a logical entry as `map.base + map.u16[logical]`, not the logical index itself.

`0x6a9fdc` subtracts `0x380` from descriptor starts `0x3a9` / `0x3d1` before calling `0x6a8de0`; the 33-unit whole-cache request starts at logical index `0x29`. These are indices within the managed pool, not physical blocks `0x29..0x49`. The previous media range `[0x520000,0x940000)` was therefore incorrect. Physical targets are dynamically allocated in `[0x380,0x400)`, byte range `[0x7000000,0x8000000)` at the selected `0x20000` geometry. The template at raw `[7,10)` is a different source, not an alias of that pool. The raw image/remap scan `[0,0x13a)` ends below this pool, so the loaded-image span and configuration targets do not overlap on these bounded mappings.

The managed engine `0x6fdf00` proceeds in ascending logical order, from `floor(start_page/pages_per_block)`, increasing logical index by 1 and source pointer by `written_pages*main_bytes_per_page`. Its physical order is allocator order, not necessarily ascending: `0x6fd06c` selects a free relative-physical bit; the engine reserves it in RAM, programs a complete new block with the logical-number spare metadata (`0x6ef084`), preserving prefix/suffix pages for partial-block requests, and verifies when requested. Only afterward does it erase the old physical block, mark the old block bad on erase failure, and publish the new logical→physical entry in RAM through `0x6fd00c`. Failed program/verification marks the new candidate bad and retries without consuming the logical input. Reboot rebuild requires matching first/last-page metadata; if interruption leaves both old and new copies, rebuild keeps the first accepted copy in physical scan order and erases the duplicate, not necessarily the most recently programmed copy. This is not an atomic, generation-numbered cache transaction.

Cache interior handling on these paths is byte-range based, not a single checksummed `0x420000` record: `0x69f204` loads `[0,0x76800)` and `[0x400000,0x40fd00)` and tests only the u16 `0xaa55` at `+0x202`; absent validity, it zeroes all `0x420000` bytes and reloads the raw template prefix. Command-6 helper `0x69f920` additionally refreshes six variable-length regions at offsets `0x76800`, `0x3b4940`, `0x11c840`, `0x3b8ba8`, `0x2bb8e0`, `0x3c31b0`, with lengths derived from property triples `0x28e0..0x2903`: `align64(34*A)/8 + ceil(34*B/8)`. If cache byte `+0x244` is 1, it also reloads template `[0x3000,0x42000)`. This separates the fixed validity/prefix records, variable packed records, and untouched RAM ranges; no whole-cache integrity or all-or-nothing persistence follows from the prefix's validity marker.

The two auxiliary inputs of that restore are the container's auxiliary restore lists, bound to the checksum table above: auxiliary 1 at raw DAT `0x24a027c` holds 98 little-endian sixteen-bit `(offset, length)` pairs and auxiliary 2 at raw DAT `0x24a0404` three thirty-two-bit pairs, each pair restoring `memcpy(cache + off, snapshot + off, len)` and the 101 pairs covering 1,487 bytes of `[0, 0x42000)` in total (E-ADJ-MOVERS-150, **byte-read**; [public census findings](adjustment-and-service-interfaces.md#adjustment-read-coverage-and-update-stamps), with every pair recorded in private provenance `private-data/analysis/x-m1-1.50/adj-read-01/findings.md`). The lists are the only mechanism that carries body-specific data through an update, so a rebuilt container that does not carry both lists intact and correct for the target body replaces its adjustment data with the template and restores nothing, and a diff that checks only the payload passes such a container (UPDATE-IMAGE-01).

The census closes in both directions (**byte-read**, E-ADJ-MOVERS-150): of the 233 bytes this body holds against the template (E-ADJ-READ-150), 224 are restore-covered (among them `+0x204`/`+0x205`, restore pair 9) and 9 are stamps (`+0x1e8`/`+0x1e9` from the executing build's refresh, `+0x4069` to `+0x406e` and `+0xd8` from the boot load), with zero others, and no byte among them is reset-written or use-written; all 14,340 bytes that moved between the 1.00 and 1.50 captures are attributed the same way, 14,336 now holding the template value and the four exceptions being stamps (`+0x205`, `+0x406a`, `+0x406c`, `+0x406e`). The boot load `0x69f204` stamps `+0x204`/`+0x205`, `+0x4069` to `+0x406e` and `+0xd8` on every successful load and never writes `+0x1e8`/`+0x1e9`.

A durable marker of the update sits at adjustment `+0x1e8`/`+0x1e9`, which reads `01 54` in both the S03 1.00 capture and the 2026-10-08 1.50 capture (E-S03-FULL-CAPTURE, E-ADJ-READ-150). The refresh stamps those two bytes with the executing build's compile-time constants (`01 78` in the 1.50 code), so the stored pair is the stamp of the build that ran the update rather than of the installed one; no restore pair covers the bytes (auxiliary-1 pair 8 starts at `0x1ea`) and nothing has rewritten them since (**static-inference** over **byte-read** stamps, E-ADJ-MOVERS-150). They are therefore a durable marker of which build performed the most recent update, readable from the adjustment area as a diagnostic.

### Second supplied boot record: companion initialization and shared-image handoff

The exact complemented payload slice `[0x50048,0x54cc8)` is `0x4c80` bytes, SHA-256 `2f1bf3f0e483b892d2890599679c1b515cfc1be8b8c27cbb06d4d913e428abb4`. A fresh extraction matches the existing record. Base `0x10000` is supported by its vector literal `0x11800`, reset code at record offset `0x1800`, and absolute globals/literal-pool words `0x14c80`–`0x14ca0`. The exception-vector targets `0x3fff00xx` have unresolved mapping; they are not identified ROM handlers.

Initial entry and unobserved banked-register state remain distinct from this post-initialization frame. That observation does not cover unmapped exception targets, the actual reset selector/loading order, all unused helpers, boot ROM or other early entry routes.

### Source resolution and observational limits

Descriptor traversal, commit record selection/indexing, modal normalization, root/module dispatch, selector initialization and auxiliary enable production are mapped above. The native writer mapping distinguishes raw template reads from managed configuration commits, establishes ascending logical traversal and allocator-selected physical targets, and records software ordering of main/spare submission, bad marking, new-copy verification and old-copy erase. The configuration pool is `[0x7000000,0x8000000)`, disjoint from the loaded-image/raw-template region on this layout.

The remaining hardware facts are interrupted-page durability and visibility of main cells, spare metadata and ECC; bad-marker retention after reboot or power removal; whether timeout-abandon cancels, leaves NAND busy or permits late completion; and reset treatment of an in-flight operation. They require separately authorized controller/NAND observation. MMIO store order does not supply those observations.

Conclusions cover the inspected firmware and named boot/reset paths. ROM/reset selection and SD prerequisites retain the separate [boot-ROM mapping's](bootrom-window.md) scope; neither supplied boot-record handoff demonstrates an application-independent recovery path. [G2](firmware-extraction.md#g2-acceptance-decision) accepts only its measured byte correspondence, not another firmware/model, modified-image installation or a repair write.
