# X-M1 1.50 update validation and boot failure branches

UPDATE-01 now has a bounded **static inference** map: on the ordinary UI route, the body updater parses the container and an eligibility gate checks model/version; the write action then validates up to three byte sums (unless a cached-success byte is set) before entering a native storage writer whose persistence order, marker discipline and interruption behavior are mapped below. The update-flow event producers, the UI/write selector agreement, the cached byte, source/staging ownership and the indirect service writers are closed as well. The first supplied boot record has concrete halt branches; the second initializes peripherals and hands off into the same shared images, with configuration-failure continuations and unbounded waits. Neither examined route demonstrates damaged-image fallback or recovery. R1 remains unaccepted.

All addresses below belong to the exact public X-M1 **1.50** DAT, SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490`, preserved at `private-data/firmware/x-m1-1.50/FWUP0002.DAT`. The owner's body ran **1.00** when this work started and reports **1.50** after the stock update (E-STOCK-150-OWNER-REPORT); installed-1.50 bytes equal the decoded images over their artifact extents apart from 781 bytes, none of them in an AL-condition word (317 in 41-90% AL-density data blocks; E-RAM-PROBE-150, E-DUMP-RAM-150), which are runtime-written data words whose writer is unestablished, so the addresses and policy below hold for the installed code as well as the public DAT, except at those bytes. Source acquisition, export hashes and inferred decompression are recorded in [firmware extraction](firmware-extraction.md). Decoded id 4/id 5 retain that report's static-only limitations.

## Container, file path and validation

The body/lens/other selector is explicit. Body means selector 0 at these functions; other selectors must not be used to infer body policy. The UI gate reads selector `0x9503c4` (`0x944580 + 0xbe44`), while write dispatch reads `[[0x15c20a8] + 0x224]`. ### Model and version policy

`0xec8554` emits the parsed type, 512-byte identity field and major/minor values into body UI state. `0xec90e4` copies the identity field with the bounded string-copy helper `0x721b40` (stop at NUL and zero-pad), to state `[+0x10,+0x210)`. The matcher at `0xd0a2b4` compares 16-byte records there with the 16-byte current identity at `0x96b402`–`0x96b411`, ending at a zero-leading record or after 32 records. A first record consisting entirely of `0xff` returns success; an empty first record returns failure. The current identity is supplied through `0x639b1c` → `0x73acfc` → `0x72b8c4` → `0x69f600`; it is encoded configuration identity, not a proven literal `X-M1` comparison or a cryptographic model binding.

New major/minor are stored at `0x95d670` / `0x95d674`, from raw DAT `0x204` / `0x208`. Current major/minor at `0x95d678` / `0x95d67c` come from `0x69f520` through `0xec9048` / `0xec907c`. That version getter can return configuration bytes or its built-in 1.50 value depending on configuration byte `+0x206`; it is not independently verified storage identity.

`0xd0a590` accepts either both new version words `0xffffffff`, or each word at most `0x99` with a decimal low nibble (consistent with packed BCD). `0xd0a728` then implements the following unsigned comparison for **body selector 0**:

```
accept = both new words are 0xffffffff
      or new_major > current_major
      or (new_major == current_major and new_minor >= current_minor)
```

The body branch therefore permits equal-version eligibility and rejects a numerically lower valid version. The equal-minor decision is visible at `0xd0a7a4`–`0xd0a7ac` (`cmp`, `movlo 0`, `movhs 1`). Lens/other selectors instead require a strictly greater minor for equal majors. The sentinel's existence is an observed branch, not an installation proposal. UI eligibility is called by `0xca6108`; it does not establish that every alternate service/in-memory caller enforces this gate.

## Native writer boundary and preservation limits

`0x6ab4cc` uses a static 27-row `{block_count, logical_start, class}` table at `0x7c8c6c`, referenced through the class-field pointer `0x7c8c74`. Selection 0 includes class < 2; selection 1 includes class == 1. The included rows are `{7,0,0}`, `{0x11c,7,1}`, `{2,0x123,1}`, `{1,0x125,1}`: selection 0 covers logical blocks `[0,0x126)`, while selection 1 covers `[7,0x126)`. At the native `0x20000` stride, capacity is `0x24c0000` for selection 0. The body chooses the selector from header word `0x210` bit 0 via `0xec88c8`; on this DAT the word is 1, yielding selection 0. Consequently the checksummed main bytes and rounded storage block span differ.

The routine's media order is closed (**byte-read**). It first erases raw block `0x125`, the trailer block, through `0x6a9aa4` (its argument is ignored; it runs `0x6a9010(0x125, [0x7c8c90])` with `[0x7c8c90]` = 1), and does not test that result; it then optionally pre-erases `min(10, property 0x276)` times through `0x6a9010(0, 0x126)` with returns ignored, which erases the contiguous physical run from `remap[0]` rather than the per-logical targets the program loop uses, targets that shift under bad blocks, and sleeps `property 0x275` seconds; then it programs blocks in ascending logical order, sourcing block `i` from `(image_base & ~1) + (start+i) * 0x20000`. Media offset therefore equals image offset: the checksummed main bytes land at media `[0, 0x24a0020)` while the rounded span covers `[0, 0x24c0000)`, whose tail past the trailer holds the auxiliary pair lists on the in-memory route (contiguous after the main bytes) and unrelated RAM on the file route. Each block goes through an eight-word request `{remap[start+i], 1, 0x14 - [0x828578], staging|0x40000000, 1, out-status, 1, 500}` to `0x6faf5c` → `0x6fc638`: read the 16-byte page-0 window (`0x6f1aa8`, decode `0x6fbd2c`), compare-read the block (`0x6fbedc`, 0x800 main bytes per page by `0x72232c`; a match skips erase and program), erase (`0x6f0e18`, NAND word `0x60d07000`), program 64 pages of 0x800 (`0x6fc0a4` → `0x6f0f6c`, command words `0x801070xx` or `0x80000001`), then verify by compare-read again. A nonzero return aborts the writer; a zero return with out-status set marks the block bad (`0x6fc408` programs all 64 pages with `0xff`), retries the same data at the next contiguous physical block within the `0x14 - [0x828578]` budget (exhaustion returns 5, mapped to `-40`), rebuilds the map through `0x6a90ac` and continues without advancing the source. **byte-read**; the runtime geometry (64 pages of 0x800 from record 3 at `0x82988c`, selected by index `[0x918844]`) is **static-inference**.

Marker ordering (**byte-read** and **static-inference**): the old trailer block is destroyed first and the trailer block is programmed last (ascending loop; its page 0, carrying the 32-byte trailer at media `[0x24a0000, 0x24a0020)`, is programmed first within the block). The DAT trailer bytes at `0x24a025c` (`ff ff b5 fd ff ff b5 fd df ff ff ff ff ff ff ff ff ff ff ff ff 3b 9e ff d7 d7 d7 ff 00 00 55 55`) complement to media words `0x024a0000`, `0x024a0000`, `0x20`, 0, 0, `0x0061c400`, `0x00282828` and halfwords `0xffff`, `0xaaaa`, so the boot record's compare (`0x1cec`–`0x1cfc`, halfword `+0x1e` against `0xaaaa`) reads the trailer's last halfword, restored by the checksum pass's in-place complement. Because the marker-erase result is not checked, a silently failed erase can leave the old marker beside rewritten body blocks; on the mapped success paths the marker is absent from the first erase until the last block's page 0 completes.

Remap and bad blocks are closed at the software level (**byte-read**): the u16 remap table `0x828580` (314 entries, zeroed at `0x6a9158`) maps logical block to physical block by the cumulative-skip rule physical = logical + (bad blocks at or below), rebuilt at `0x6a9168`–`0x6a9200` from the bad-block list pointer at `0x9552f0` (the list is at `*(0x9552f0)`, count at `+0`, entries at `+4`). The list is first filled from the boot record's scanned buffer (`[[0x61c00c]]+4`, scan of `[0, 0x13a)` at `0x2058`, published at `0x1f60`–`0x1f78`) and later rebuilt by `0x6a90ac` → `0x6fb1f4` → `0x6fbd88` from window decodes; the boot record applies the same rule at `0x209c`. A window decoding 2, erase status bit 0, program status bit 0 or a verify mismatch marks a block bad. The lower entries enforce `block + count <= device size` (return `-30`), and the wrappers additionally require the start block below `0x400`. The multi-block configuration entries `0x6a8de0` / `0x6a8e84` do not consult the remap table (absence scope: their full listings in the id 4 listing); their engines retry around bad blocks with the same primitives.

No software ECC is computed, stored or checked anywhere in this path (absence scope: the full listings of `0x6ab4cc`, `0x6a8f1c`, `0x6a9010`, `0x6a9268`, `0x6a90ac`, `0x6a9aa4`, `0x6faf00`, `0x6faf40`, `0x6faf5c`, `0x6fb058`, `0x6fb13c`, `0x6fb1f4`, `0x6fbd2c`, `0x6fbd88`, `0x6fc0a4`, `0x6fc408`, `0x6fc638`, `0x6f0df4`, `0x6f0e18`, `0x6f0f6c`, `0x6f1a74`, `0x6f1aa8`, `0x6fbedc`, `0xdb90ac`, `0xdb89a4`, `0xdb91e0` in the full decoded id 4/id 5 listings and `decode/boot-40048.dis`). The only integrity arithmetic in the path is the whole-range byte sums and the per-page compare. Whether the 16-byte page-0 window is spare or main data, and whether an `0xff`-filled block survives reboot as a bad mark, is **unproved**. The MMIO contract (**byte-read** accessors) is submit `0xFFF52008`, poll `0xFFF52004` bit 2, status `0xFFF52028`, command words through `0xFFF52018` / `0xFFF5201C`, data port `0xFFF52400`; each operation waits by joining event 256 or polling up to 625 × timeout iterations (the writer's timeout 500 gives 312500), and the timeout-abandon paths write 0 to `0xFFF52008` and never re-poll, leaving the media operation unconfirmed and possibly still executing (inherited `area2-invalidation.md` section 6.10, sites verified here; the hardware abort semantics of an abandoned operation stay **unproved**). This cannot be used as a validated flash layout or writable target specification.

After the main writer, `0xec88c8` calls `0xdb91e0`, whose chain is now closed (**byte-read**). The configuration cache at `[0x96ca50]` = `0x41acd800` holds `0x420000` bytes. `0xdb91e0` snapshots its first `0x42000` bytes into the scratch buffer, refreshes those `0x42000` bytes from raw logical blocks `[7, 10)` through `0x69fe20(0xff)` → `0x6a9ac4` (bounded `0x60000`, read through `0x6a8ff0`), restores from the snapshot the ranges the container's two auxiliary inputs list (auxiliary 1: little-endian 16-bit offset/length pairs, count `len/4`, accepted when `off+len <= 0x10000`, 98 pairs on this DAT; auxiliary 2: 32-bit pairs, count `len/8`, `off+len <= 0x42000`, 3 pairs on this DAT; gated by bits 0/1 of `0x14e3578`), and commits. Completion `0x69fea8` passes the whole `0x420000`-byte cache to `0x6a9fdc`, which programs 33 units through `0x6a8de0(0x29, 33, cache)` over descriptor rows `0x3a9` / `0x3d1` minus `0x380`, i.e. device indices `0x29..0x49`, media `[0x520000, 0x940000)`; those entries do not consult the remap table and the engine `0x6fdf00` rewrites each block with the same window check, erase, page program and mark-bad primitives. **byte-read**. This resolves the `0x42000` / `0x420000` discrepancy: cache offsets `[0x42000, 0x420000)` are never snapshotted, refreshed or restored and are written back as the RAM cache holds them, while `[0, 0x42000)` becomes the refreshed template plus the DAT-listed user ranges. The boot load itself covers only `[0, 0x76800)` and `[0x400000, 0x40fcc0)` (`0x69f228` → `0x6a9e98`, `0x69f23c` → `0x6a9c70`), so what `[0x76800, 0x400000)` and `[0x40fcc0, 0x420000)` hold at commit time is the open cache-record question. **byte-read** and **static-inference**. The cache's validity halfword `0xaa55` at `+0x202` decides the boot-time load (`0x69f244`–`0x69f27c`): without it, `0x69f25c` zeroes the cache and reloads the factory template from raw blocks `[7, 10)`, which carries its own `0xaa55` at media `0xe0202`, while the image-written bytes at media `0x520202` do not (`0xaa55` arrives only with the commit content). **byte-read**. The DAT is not a complete body-specific backup, apparent exclusion from the main block table does not prove a persistent region is untouched by the complete update, and reconciling `0x6a9ac4`'s raw-block space (blocks 7–9) with the commit's device-index space (`0x29..`) remains **unproved**.

The two auxiliary inputs of that restore are the container's auxiliary restore lists, bound to the checksum table above: auxiliary 1 at raw DAT `0x24a027c` holds 98 little-endian sixteen-bit `(offset, length)` pairs and auxiliary 2 at raw DAT `0x24a0404` three thirty-two-bit pairs, each pair restoring `memcpy(cache + off, snapshot + off, len)` and the 101 pairs covering 1,487 bytes of `[0, 0x42000)` in total (E-ADJ-MOVERS-150, **byte-read**; [public census findings](adjustment-and-service-interfaces.md#adjustment-read-coverage-and-update-stamps), with every pair recorded in private provenance `private-data/analysis/x-m1-1.50/adj-read-01/findings.md`). The lists are the only mechanism that carries body-specific data through an update, so a rebuilt container that does not carry both lists intact and correct for the target body replaces its adjustment data with the template and restores nothing, and a diff that checks only the payload passes such a container (UPDATE-IMAGE-01).

The census closes in both directions (**byte-read**, E-ADJ-MOVERS-150): of the 233 bytes this body holds against the template (E-ADJ-READ-150), 224 are restore-covered (among them `+0x204`/`+0x205`, restore pair 9) and 9 are stamps (`+0x1e8`/`+0x1e9` from the executing build's refresh, `+0x4069` to `+0x406e` and `+0xd8` from the boot load), with zero others, and no byte among them is reset-written or use-written; all 14,340 bytes that moved between the 1.00 and 1.50 captures are attributed the same way, 14,336 now holding the template value and the four exceptions being stamps (`+0x205`, `+0x406a`, `+0x406c`, `+0x406e`). The boot load `0x69f204` stamps `+0x204`/`+0x205`, `+0x4069` to `+0x406e` and `+0xd8` on every successful load and never writes `+0x1e8`/`+0x1e9`.

A durable marker of the update sits at adjustment `+0x1e8`/`+0x1e9`, which reads `01 54` in both the S03 1.00 capture and the 2026-10-08 1.50 capture (E-S03-FULL-CAPTURE, E-ADJ-READ-150). The refresh stamps those two bytes with the executing build's compile-time constants (`01 78` in the 1.50 code), so the stored pair is the stamp of the build that ran the update rather than of the installed one; no restore pair covers the bytes (auxiliary-1 pair 8 starts at `0x1ea`) and nothing has rewritten them since (**static-inference** over **byte-read** stamps, E-ADJ-MOVERS-150). They are therefore a durable marker of which build performed the most recent update, readable from the adjustment area as a diagnostic.
