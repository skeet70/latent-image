# RC1 named film recipes: data structures and behaviour

Offline design for [spec/10 section 19.3 tier RC1](../spec/10-film-recipes.md#193-tiers): named menu entries that apply a stock base mode plus stored parameter values. Host-only, no patch bytes, no camera access. The target is the official X-M1 1.50 image (SHA-256 `43d67afa…1490`) and nothing else; every address below is a 1.50 decode address, and the body now runs 1.50 (E-STOCK-150-OWNER-REPORT).

Evidence classes: owner-reported (menu records), byte-read (private node map), static-inference (decompiled 1.50 code and tables), unbound (named as a prerequisite in section 11). Where a claim is one reviewer's reading rather than an independently re-derived one it says so.

## 2. Recipe model

A recipe is a complete preset: one stock base mode plus explicit values for the look parameters the X-M1 1.50 stores. Every field is mandatory in the JSON (section 8), so "recorded settings match its definition" is checkable field by field rather than by absence.

| Recipe field | Property | Payload field (record) | Conversion table | Owner-recorded range |
| --- | --- | --- | --- | --- |
| base film simulation | 0xfe | +0x24 bits 0-3 | `0x0077ac30` | PROVIA/STANDARD, Velvia/VIVID, ASTIA/SOFT, B&W, SEPIA |
| dynamic range | 0x104 | +0x05 bits 6-7 | `0x00775428` | AUTO, 100%, 200%, 400% |
| highlight tone | 0x110 | +0x17 bits 5-7 | `0x00775e24` | −2 … +2, 0 in the middle |
| shadow tone | 0x111 | +0x09 bits 5-7 | `0x0077643c` | −2 … +2 |
| colour | 0x10e | +0x07 bits 5-7 | `0x0077a810` | −2 … +2 |
| sharpness | 0x10f | +0x08 bits 5-7 | `0x00778620` | −2 … +2 |
| noise reduction | 0xef | +0x10 bits 5-7 | `0x00779f10` | −2 … +2, LOW to HIGH |
| white balance mode | 0xed | +0x21 bits 0-3 | `0x0077a60c` | AUTO, CUSTOM, FINE, SHADE, FLUORESCENT 1-3, INCANDESCENT |
| ISO | 0x141 | +0x20 bits 0-4 | `0x0077af48` | AUTO, L100, 200 … 6400, H12800, H25600 |

The conversion tables are bound for all nine properties (prerequisite pass P7, byte-read): the pointer is `*(0x0081b09c + 4·property)`, so property 0xfe's pointer sits at `0x0081b494` and the bracket properties 0x100-0x102 follow it; rows are `{col0 stored, 0x7ffffffe, col2 downstream}`, and the stored code is what the payload carries. Two properties store a code that is not the menu value: colour's rows `{+2, +1, 0, −1, −2}` store `{3, 4, 0, 6, 5}`, and WB mode's CUSTOM row stores 9 while its display order puts it second. The compiler resolves every name through these tables, so an instance never carries a code.

Noise reduction is in the model, and the earlier exclusion is withdrawn: it is property 0xef at payload `+0x10` bits 5-7, with table `0x00779f10` and node `0x0078d108` offering rows `{4,3,2,1,0}` as HIGH, MEDIUM HIGH, STANDARD, MEDIUM LOW, LOW. The custom-settings payload map omitted the field, which is why the first design draft read it as unrepresentable (prerequisite pass, adjacent finding to P8).

The live-column values come from the getter `FUN_0061e110(prop, bank, use_defaults, slot)`; only the film-sim row is quoted with a read in this report: image byte `0x8a` bits 4-7, the ordinary branch of the case at `0x00620d28`. The other live offsets are unbound and the compiler needs the read direction only, because every write goes through the property setter.

Excluded from the model, with reasons:

- Two-axis white balance shift. The payload's 0xee field at `+0x17` bits 0-4 is a single scalar of 31 one-to-one rows (table `0x00775ca4`, stored `0x00`-`0x1e`), so it cannot carry the two independent axes the menus show; the grid axes are properties 0x113 and 0x114, which have no payload field at all, and the one 19-code axis a C record can hold is property 0x122 at `+0x10` bits 0-4, whose relation to the grid is unbound (P13). A recipe that claimed an owner-recorded R and B grid position could not be shown to reproduce it, so RC1 recipes carry no shift (P13 revised).
- Long-exposure NR. Offered as OFF/ON, but no payload field is mapped for it and the run through its node is not traced; a recipe cannot claim a value it cannot store.
- Image size and image quality. All three fields are stored and bound (P9): size is property 0xf6 at `+0x1a` bits 5-6 (three size groups), the aspect group is property 0xf9 at `+0x1e` bits 5-6 (table `0x0077538c`, identity on `0`-`3` = 4:3, 3:2, 16:9, 1:1), and quality is 0xfa at `+0x0d` bits 5-7. The image-size menu row is the product `row = 4·size + aspect` (row table `0x007a00cc`) and its commit writes size and aspect as two properties, so a C record and a recipe table entry can both carry a full capture format. The recipe model keeps them out as a scope rule: a recipe is a look, not a capture format, and the C slot remains the vehicle for full presets. The rule is now a choice, not a representability limit.
- Grain, clarity, Color Chrome and any processing the 1.50 build does not implement. [spec/10](../spec/10-film-recipes.md#191-goal-and-relation-to-autofocus) requires rejection rather than silent approximation, and the schema has no field for them.
- Filtered monochrome (+Ye/+R/+G). The 1.50 still-develop builders leave the filter index at zero, so exposing a filtered entry yields plain B&W with a filtered label ([film-simulation report](film-simulation.md#processing-by-value)). RC2 work, not RC1.

A recipe's base mode is one of the five offered stock modes. PRO Neg Std/Hi stay out of the recipe model until RC0 ships and the body's adjustment data for their slots is read; a recipe whose base mode is not offered is a different tier and the validator refuses it (section 9, C3).

## 3. Presentation in the film-simulation list

Property 0xfe has four labelled list surfaces and two unlabelled ones in the 1.50 images:

| Surface | Node | Values | Labels |
| --- | --- | --- | --- |
| shooting menu 1 | `0x007823a4` (type 2, kind 4) | `0x0078319c` | `0x0078d4f8` |
| Fn-assigned submenu | `0x00785d74` (type 2, kind 5, parent `0x0077f684`) | `0x0078319c` | `0x0078d4f8` |
| unnamed node, same arrays | `0x0077d184` (type 9) | `0x0078319c` | `0x0078d4f8` |
| Q menu cell | `0x0078b000` (type b, parent `0x0078e4a0`) | `0x00782348` | `0x00789e2c` |
| FILM 1-3 bracket children | `0x0078b714` → `0x00786774`/`0x00786da8`/`0x007898d4` (properties 0x100-0x102) | own | own |
| unlabelled 9-row list | `0x0078d2d0` (parent `0x007910a4`) | `0x00780008` | blank ids |

Three nodes share the same values and labels arrays, so one extension serves the shooting menu, the Fn path and `0x0077d184`. The owner observes the same five entries from the shooting menu, from the Fn assignment and from the Q cell, whose options scroll with the sub-command dial (E-RECIPE-150-OWNER).

Design decisions:

1. Recipe rows are appended after the five stock rows in table order; the stock five keep their order, their stored codes, their labels and their help text byte for byte. Appending rather than prepending keeps the stock list's first-entry default and every stock row's index unchanged.
2. Each recipe gets its own conversion-table row, and that row number is the selection token the commit path carries. The film-sim table `0x0077ac30` ends after row `0xc`; the patch copies the stock rows, appends one row per recipe with `col0` equal to its base mode's stored code and `col2` equal to the base mode's downstream code, and terminates the copy, then repoints only the property-0xfe pointer at `0x0081b494` (`0x0081b09c + 4·0xfe`). The bracket properties' pointers at `0x0081b49c`, `0x0081b4a0` and `0x0081b4a4` keep the stock table. The token is therefore distinct for every recipe while the stored code and every downstream value stay the base mode's, and a missing hook would degrade to the base mode rather than to a wrong mode (finding 3).
3. The Q cell and the bracket lists keep the stock five rows for the first release. A Q label is not text: the Q id space `0xff000000 | n` with `n <= 0x8c5` indexes 12-byte records in image 2 that name a vector glyph block, and the drawer returns 0 above `0x8c5`, so the space is closed and a recipe name cannot be added to it without new graphics (P5 bound). The shooting menu, the Fn list and `0x0077d184` carry text labels and take the recipe rows; the Q cell would need drawn glyphs, so it stays stock. A recipe selected from the shooting menu therefore does not highlight its own row when the Q cell is opened, and the Q cell shows the base mode. The display hook of section 5 removes the divergence on the surfaces that have text once the Q question is revisited: the resolver is `FUN_00d588b8`'s default arm, reached with the open node's property from `FUN_00bfa800` (`0x331505`) and `FUN_00bf8d20` (`0xbf8dd8`).
4. The RAW-conversion list (`0x0078bd5c`, property 0x22b, its own five rows and its own code domain) is not extended. RAW conversion is a playback operation whose film value is separate from the shooting value, and a recipe is a shooting-time preset.

## 4. Labels

What is known from the static map:

- Each language slot is linked at `0x0039c000`; the string table has `0x83c` entries of 8 bytes `{w, attr, pad, lineptr}` (byte-read: the width halfword first, `FUN_0117de64` reads `ldrh` at table + 8·id), the line pointer leading to a 12-byte line record whose first word points at the UTF-16 text. The English table base is slot + 0x3754. Ids at or above `0x83c` are special, and `0x83c` is blank.
- A menu label entry is 16 bytes `{a, b, c, d}` of string ids, terminated by −1, and parallel to the node's values array. The four roles are bound for the film-sim list: preview icon, list icon, help line, name. The row-1 entry `{0x48a, 0x489, 0x48c, 0x48b}` carries `<f06a>` as both icons, `Ideal for a wide` as the help line and `<f06f>/STANDARD` as the name, and the other rows repeat the shape with one help line each (finding 2).
- Film-sim glyphs exist as font codes: U+F06A-U+F06E for the five stock modes, U+F201/F202 for PRO Neg, U+F1B3-F1B5 for the filter entries.
- The loader (`id4 FUN_006aa63c`) reads one 128 KiB block per language from flash `0x1100000 + lang·0x20000`; the per-id layout data lives in segment-table entry 2 (RAM `0x130000`), 10 bytes per id, and the `0x83c` count is hard-coded. The tightest language slot has `0x6d98` bytes free (author-only reading).

Design decisions:

1. Recipe names render as text through the string table. The patch draws no new glyph, so the two icon fields of a recipe row carry the blank id and the row shows its help line and name; reusing a mode's glyph would misattribute the entry and editing the font block is out of scope for RC1. The three questions this rested on are bound (P6): the draw path resolves text through the resident `FONT_LATIN.FDL`, whose cmap covers every printable ASCII code, the metrics are UI-surface pixels (decision 4) and the row boxes are measured there, so the text strategy is no longer conditional. The first compiled set still takes a rendering test on the body or in the native harness as an acceptance confirmation rather than a strategy condition, and a name that fails it is shortened rather than accepted.
2. Recipe text is carried by the patch, not by the language slots. The label path for recipe ids is served end to end by patch accessors: the entry accessors (`0x0117de18` for the attribute byte, `0x0117de64` for the width halfword, `0x0117deb0` for the entry pointer), the locator (`0x0117dfd8`) and the layout accessors of decision 3, each returning the recipe's data for a recipe id and the stock result for every stock id. The stock per-language slots and the `0x83c` entry count stay as they are. All languages then show the same recipe names; the film-sim names are already Latin-script in every language slot, so this matches the stock precedent for this list. P17 lists the sites and their current bounds.
3. Layout and entry access follow the stock id classes, and the boundary matters. Ids below `0x83c` use the 10-byte per-id records at image-2 RAM `0x130000`, and the patch keeps that path untouched for the stock ids. Ids `0x83c`-`0x83e` are a separate class: the accessor family (`0x0117dc08`, `0x0117dc74`, `0x0117dce0`, `0x0117dd48`, `0x0117ddb0`) serves them from 66-byte (`0x42`) records at image-2 RAM `0x37b784` whose layout halfwords sit at `+0x38`-`+0x41` and whose first 56 bytes are an inline UTF-16 buffer (byte-read: each accessor tests `id - 1 <= 0x83d` and splits at `id <= 0x83b`, for example `0x0117dc14` and `0x0117dc24`; the special branch loads `0x37b784`, for example at `0x0117dc30`). The string-entry accessors return fixed fallbacks above `0x83b` instead of reading an entry (`0x0117de18`, `0x0117de64`, `0x0117deb0`), and only three special records exist before a GVFF block at image-2 offset `0x24b84c`. A recipe id above `0x83b` therefore has no stock layout record and no stock entry: the patch owns those ids end to end, extends the special branch's table and bound in each accessor (or hooks the accessors), and reproduces the stock treatment for the three stock special ids. P17 lists the bound sites. The position pair is the stock film-sim records' x/y (rows stepping 0x30 px apart) and the shared metric triple is the glyph em (30 px wide, 36 px high) with the 48 px line pitch, copied from the same records; the units are pixels (P6 bound). This is the ownership the earlier draft left implicit when it said the segment-entry-2 table was "left alone".
4. Character set and length are proven rendering bounds with measured budgets (P6). The metrics are UI-surface pixels: the layout triple is the glyph em (30 px wide, 36 px high) and the line pitch (48 px), and the string entry's width halfword is the row's alignment box width in the same pixels. The film-sim rows measure 440 px for a name (box x-extent 40-480, right-aligned) and 400 px for a help line (60-460, left-aligned); the draw path aligns to the box and clips only at the draw window, and its code caps are 50 UTF-16 units per draw and 33 per wrap half. `FONT_LATIN.FDL` covers all 95 printable ASCII codes (U+0020-U+007E) plus Latin-1 and more, so the schema's charset is a design subset and not a coverage limit: names use ASCII letters, digits, space and `./+-`, at most 12 characters, and one help line of the same set plus `,` and `'`, at most 18 characters. The width rule is the box budget, measured in per-mille of em with `'W'` the widest schema character at 911: twelve worst-case 'W's measure 328 px and fit the 440 px name box with 112 px to spare, while eighteen measure 492 px and can exceed the 400 px help box, so the validator checks the advance budget (at most 13 333 per-mille for a help line, 14 667 for a name) alongside the character cap. What remains for observation is visual, not textual: what the UI shows outside a row's box edges, and whether any runtime draw call narrows the clip window on this surface.
5. Recipe ids are allocated from `0x83f` upward in the patch's own table, one per recipe name and one per help line, above the three stock special ids (`0x83c` blank, `0x83d` and `0x83e` stock records) so no stock label changes meaning; the two unoffered PRO Neg ids and the three filter ids stay free for RC0.

## 5. Selection and apply behaviour

Apply reuses the property layer; there is no bulk slot-to-live copy anywhere in the images ([custom-settings report](custom-settings.md#5-apply-path)). Reads go `FUN_0061c93c` → `FUN_00624620` → `FUN_0061e110(prop, bank, use_defaults, FUN_006439e0())`. Writes go `FUN_0061c91c` → `FUN_006309c4`, which loads the ordinary block with `FUN_0061d9ec`, calls the setter `FUN_00624694`, and stores the block back with `FUN_0061d8dc` when the value changed. The target record is chosen by `FUN_006439e0`: bank 0's slot record while the mode-class cell `0x00951564` is 3, the ordinary block otherwise.

The menu commit is `FUN_00d4fc74(property, row)`, called only from `FUN_00c2d8ec` (`0x362654`) and `FUN_00c321a8` (`0x367670`) with the open item's property and row cells. It saves the row in `r5` at `0x00d4fc80` and runs three common conversions through `FUN_0061d514` at `0x00d4fc8c` (`r8`), `0x00d4fca4` (`r4`) and `0x00d4fcbc` (`r7`) before the property dispatch at `0x00d4fccc`; the film-sim case begins at `0x00d50a48`, writes the two converted values (`r4` to `FUN_0063458c`, `r8` to `FUN_0061c91c(0xfe, col0, 0)`) and leaves `r5` alone. Both hook locations are therefore available and the design picks the case-level one: a recipe row's col0 and col2 equal its base mode's, so the values the case already holds are the base values, and the token is `r5`, callee-saved across the case's calls. The hook wraps the case in the order of the numbered sequence below: it reads `r5`, applies the parameter field block, executes the stock arm (which writes the base code the conversions already produced), and ends with the forced index store. No interception before the conversions is needed or attempted. A hook that failed to fire would commit the base code, so the failure mode is the base mode rather than an unknown value. The case serves every film-sim surface, so no Q-menu-specific or Fn-specific commit exists and the Q cell's five stock rows clear the index like any other stock row. The instruction stream, the register use and the call sites above are byte-read from the images; the wrapper's own order and effects are a design rule built on them.

Selecting a recipe row runs one sequence against the record the slot selection names:

1. The parameter values in the recipe's field block, through the property setters for 0x104, 0x110, 0x111, 0x10e, 0x10f, 0xef, 0xed and 0x141.
2. The base mode's stored code into the film-sim field, through the same conversion and write the stock row uses.
3. The recipe index, nonzero, written last into the freshly loaded block and stored explicitly.

The ordering rule that survives the reload: `FUN_006309c4` calls `FUN_0061d9ec` at `0x006309ec` before every ordinary property write and `FUN_0061d8dc` at `0x00630a10` only when the setter reported a change, so a byte poked into the buffer earlier in the sequence is discarded by the next setter's reload. The index is therefore written after the last setter and the store is forced rather than inherited from a setter's change flag: the hook writes the byte into the buffer and calls `FUN_0061d8dc(0x0096cc74)`, which stores image `0x10`-`0x127`. For the record target the `0x28`-byte record lives in the bank's slot area and the stock property-write route does not store it at all: `FUN_006309c4` reloads and stores only the ordinary block, and a setter's record write stays in bank RAM (P16). The per-write reload covers image `0x10`-`0x127` only and never the record at `0x140`, so record writes accumulate in RAM across setters and no reload on that path discards them. The image mirror at offset `0x140` is written only by an explicit `FUN_0072b3d0` store of the record, the same call the CUSTOM SET copy `FUN_00630b14` makes with `{0x0096cda4, 0x28, 0x140}`, so the patch's record-target index write must make it too. That store commits area 3 on the spot: `FUN_0072b3d0` → `FUN_006a6f3c` → `FUN_006a86c4` compares record bytes `[2, 0x2c)` and appends one area-3 record immediately on any difference. Clearing the index on a stock selection uses the same forced store, for the same reason: after the film-sim setter the buffer may already be stored, and a later reload would drop an unforced clear.

Identity means the stored values match the compiled entry, not that a recipe was once selected:

- The display hook shows a recipe row only when the index is nonzero and the current values of the eight parameter fields and the film-sim code equal that entry, compared through the same property reads the menu uses.
- Any commit of one of those nine properties that did not come from a recipe selection clears the index, because every such commit passes through `case 0xfe` or the other property arms of `FUN_00d4fc74`; the clear is one write and one forced store.
- The index is never rebuilt from matching values, so a manually built preset is never renamed to a recipe.
- An interrupted selection degrades the same way: the index is written last, so a sequence cut short leaves the previous index, which no longer matches the values and fails the display comparison. In the ordinary block a battery pull before the orderly power-off commits nothing, and the previous record stands intact. At the record target the outcome is the same by a different route: the setters commit nothing, because the only image write is the forced slot store at the end of the sequence, and an interruption before it leaves the previous committed record intact (P16 bound). The uncommitted tail survives in the record's bank RAM across dial moves (E-CPOS-EDIT-VOLATILITY-150), so the index-last rule is also what keeps the menu honest until the next power cycle or state reload drops it.

Selecting a stock row writes only the stock code and clears the index, under the same rules.

No property write commits area 2: `0x006a8074` has two call sites, `0x00ec2cdc` and `0x00ec4160`, both queue-2 opcode-2 callbacks of the orderly power-off, and the commit is a whole-record compare-and-append with no dirty flag. A selection in the ordinary block (slot 1) therefore persists at the next orderly power-off, and an abrupt power loss loses it as it loses any other ordinary setting (P10 bound, slot 1). The record target differs (P16 bound): its forced slot store reaches area 3 through `FUN_006a86c4` in the same call, so a completed C-target selection persists immediately and an interrupted one commits nothing.

The C position is bound (P15). `FUN_006439e0` returns slot 0 while the mode-class cell `0x00951564` is 3, and the physical C position latches that cell to 3: the board's input map (`0x00828120`, 36 records of 28 bytes, key code in each record's first word) carries exactly one custom-mode line, key code `0x317`, and the key table at `0x007a01b0` names that line `KEY_C1_MODE` (record `0x007a0468`); the line's bit is folded into the input bitmap by `FUN_00634b40`/`FUN_006329c4`, the class map `FUN_0063b728` sends state `0x317` to class 3 (entry `0x0063b7ac`), and the state application (`FUN_00637478` through `FUN_00636230`) writes that class to the cell. The two candidate states of the earlier reading are resolved: `0x314` is `KEY_MOVIE_MODE`, fixed mode code `0x2c`, class 0, with no line in the input map, and `0x318` (`KEY_C2_MODE`, class 4) has none either, so the custom-settings report's "mode code `0x2c` is the C code" is superseded and its captured BSS dump (class 0 with mode cell `0x24`, the M state) remains dial-provenance-free. The residual is electrical: which physical dial contact drives the `KEY_C1_MODE` line is board wiring and is not in the image; the firmware-side argument closes it (the map carries one custom line, the body has one custom dial position, CUSTOM SET writes only slot 0 and only class 3 reads slot 0), and a C-position-correlated RAM window or an emulation case injecting line `0x317` is the remaining confirmation.

With that, the record-target outcomes are design facts rather than consequences: entering C restores the record's values and its index byte, a C-target selection persists at its forced slot store (area 3, on the spot, P16) and an interrupted one leaves the previous committed record intact. The same claims hold for slot 1, the ordinary block, by the P10 route: the area-2 commit runs only at the orderly power-off, the index store is explicit, and identity follows the stored values. The target rule is unchanged: writes and the index go to whichever record `FUN_006439e0` names.

How the record behaves across a dial move is hardware-observed (E-CPOS-EDIT-VOLATILITY-150, 2026-10-09): a setting changed with the dial at C survives moving the dial away and back, and is lost at a power off/on unless CUSTOM SET was run. The transition reloads nothing over the record, and the code agrees: a class change rebinds the current-record selection without copying (`FUN_00636230` writes the class cell and `FUN_006439e0` resolves the record per access), the per-write reload of `FUN_006309c4` covers the ordinary block only, and the one routine that reloads the slot record from the mirror (`FUN_00630a34` through `FUN_0061d994`) runs at boot init (`FUN_00639b1c` → `FUN_00638d0c` → `FUN_0061c8cc`) and as the teardown of UI mode `0xc` in `FUN_00d3c3b4` case `0xc` (E-CUSTOM-RESET-150), never on the dial path. That reset is a mode-machine transition, not a menu item: mode `0xc` is a shutdown-class mode the mode requester writes for power, ring, barrier, adapter and cradle inputs ([the mode word](service-shoot-feasibility.md#the-mode-word-and-the-mode-change), E-SERVICE-SHOOT-150), and neither a shooting action, a menu commit nor the SET-UP menu's CUSTOM RESET action calls it. The edit lives in the bank's slot record (bank 0 at `0x0096cda4`, with bank 2 at `0x0089ed40` written in parallel by the setter's record branch), so power loss is what drops it. CUSTOM SET is the only stock action that carries a user edit into the mirror and area 3; the SET-UP menu's CUSTOM RESET action writes the default record there instead (`FUN_00c32320` through the same copy routine with the defaults flag, [custom-settings section 4.1](custom-settings.md#41-the-custom-reset-action)), so selecting it clears the stored record, its mode field and the index byte.

## 6. Persistence

Ordinary values live in the settings image at `0x0096cc64` (bank 0). Slot 1 is the ordinary block: `FUN_0061d8dc` stores settings-image offset `0x10`, length `0x118`, from the buffer reached through `0x0061d940`, and `FUN_0061d9ec` reloads the block (byte-read, [custom-settings report](custom-settings.md)). `0x118` is also the area-2 payload length, written only by `0x006a8074` from callers `0x00ec2cb8`/`0x00ec4154` (E-RESET-ORIGIN-BOOT-150, E-AREA2-WRITERS-150), so the ordinary block is image bytes `0x10`-`0x127` and every byte in it persists with the ordinary settings. A stock film-sim selection survives power-off, and its nibble at image `0x8a` bits 4-7 lies inside that range. Prerequisite P2 is bound.

Design decisions:

1. The recipe index has two homes, both zero when no recipe is selected: image byte `0x127`, and a copy in the C-slot payload at +0x27 bits 3-7. The payload copy is the only free payload site: `+0x26` is fully allocated to properties 0x183, 0x107, 0x106, 0x148 and 0x142, and the earlier fallback at `+0x0a` bits 5-7 is claimed by properties 0xe9 and 0x285, so that sentence is withdrawn. `+0x27` bits 3-7 are unclaimed, and the default block `0x007cb804` holds `0x00` there, so a fresh record means "no recipe" without a defaults change.
2. The live home is image `0x127` (bank address `0x0096cd8b`, settings-image address `0x409c2943`). The tail of the ordinary block is not free as first read: blob property `0xa8` writes `0xa0`-`0xbf`, `0xaa` writes `0xc0`-`0xdf`, `0xac` writes `0xe0`-`0xe7`, `0x267` writes `0xe8`-`0x117`, `0xc0` writes `0x118`-`0x11f` and `0xc9` writes `0x120`-`0x123`, all through `FUN_0061dbb4` from live menu and status callers, and property `0x283` owns `0x126`. That leaves `0x124`, `0x125` and `0x127`, all `0x00` in the image-resident ordinary defaults block at `0x0089e8e0`; `0x127` is chosen because it touches no property field at all. The film-sim byte is not available: image `0x8a` bits 4-7 are the film-sim value (property 0xfe, case `0x00620d28`) and bits 0-3 are the FILM 1 bracket value (property 0x100, case `0x00620d9c`).
3. The index write follows section 5's ordering: it is written into the block after the last parameter setter and stored by an explicit `FUN_0061d8dc(0x0096cc74)` call, not by inheritance from a setter's change flag. Writing before the setters, or leaving the store to whichever setter happened to change something, loses the byte to the next `FUN_0061d9ec` reload (review item 3). Writing the byte with the block means the ordinary commit path persists the index with the other ordinary settings, and no extra commit or flag is needed.
4. C slot. The C copy is written by the CUSTOM SET action: the copy set `FUN_00630b14` copies properties, and the index is not a property, so the patch writes it into the slot mirror before the commit chain `FUN_0072b3d0` → `0x006a6f3c` → `FUN_006a86c4` → `0x006ac7d4` appends the area-3 record. The two copied setters alone would preserve bits 3-7 rather than set them, which is why the write is explicit. The record-target route for an index write made while the mode class is 3 is the same store, forced by the hook after the last setter (P16): no property write reaches the image mirror at `0x140`, and its stock writers are the CUSTOM SET copy, the boot record read `0x006a8abc` and the CUSTOM RESET action, which writes the per-slot defaults there ([custom-settings section 4.1](custom-settings.md#41-the-custom-reset-action)). A user selecting CUSTOM RESET therefore clears a stored recipe the way the jig-cycle defaulting clears one: the record, its mode field and the index byte return to the defaults, and that state is in area 3 on the spot (P20). Entering C restores the index through the module that reads the selected record, so a recipe selected before CUSTOM SET is the C setting afterwards (P15 bound: the C position latches class 3 and the property layer reads slot 0).
5. Jig-cycle reset. An area-2 failure runs `0x006a6fd8(0)`, which copies the `0x118`-byte ordinary defaults block from `0x0089e8e0`, overlays the ten cache-bound fields, writes adjustment-cache values `0x9742`-`0x9761` into image `0xa0`-`0xbf` and zero-fills `0xc0`-`0xe7`; `0x006a8abc` then defaults the custom record and commits area 3 (E-RESET-ORIGIN-BOOT-150, E-RESET-ORIGIN-AREA2-150). Image `0x127` is `0x00` in that block, so the index reads "no recipe" after the reset and needs no defaults change; the body's jig cycles reset date, time, language and the C slot (E-JIG-EXIT-ORDER-OWNER, G1), and a recipe selection is lost where a stock selection is lost. P4 is bound.
6. No new persistent structure is introduced. Section 7's table is read-only compiled data, and nothing is written to the adjustment area or to any service-visible block.

## 7. Compiled recipe table layout

The table is patch-owned read-only data, laid out so that one entry's parameter area is byte-compatible with the C-slot payload:

```
header          { u8  magic[4] = 'R','C','1','T'
                  u16 format_version        /* layout revision; 1 here, increments on any layout change */
                  u16 entry_size            /* bytes per entry */
                  u16 count                 /* 1..31, the C-copy width */
                  u8  firmware_major        /* 1 */
                  u8  firmware_minor        /* 50 */
                  u16 firmware_digest_prefix /* first two bytes of the target DAT SHA-256, big-endian */
                  u32 reserved }
entry[i]        { u16 name_id, u16 help_id, u8 index, u8 row, u8 base_code, u8 reserved[3],
                  u8 payload[0x28] }
sentinel        { 0xffff, 0xffff, 0xff, 0xff, 0xff, 0x00, 0x00, 0x00, 0x28 × 0xff }
```

`format_version` is the layout revision and says nothing about the camera; `firmware_major`/`firmware_minor` and `firmware_digest_prefix` identify the target image, and a table whose identity fields do not match the running image is refused by the loader rather than parsed. The full DAT SHA-256 stays in the host patch manifest, which is the build gate's authority; the header is the runtime check, and the two are separate values with separate owners (review item 9).

- `index` is 1..count, assigned in table order; `index` 0 means no recipe.
- `row` is the conversion-table row this recipe's values-array entry names, allocated above the stock rows (row `0xd` upward in the repointed 0xfe table of section 3). It is the selection token the commit hook maps to the base row, and `base_code` is the col0 both rows carry. Row `0xd` is the index the stock render path probes as "not found" (`FUN_00d52684` case 0xfe at its `param_2 == 0xd` arm, reached as `FUN_00d52684(0xfe,0xd)` from the outer case 0x13 of the same function); the first appended row makes that walk return a live row, so the probe's behaviour is an acceptance item (check 7) rather than an assumption.
- `payload` uses the C-slot payload field map byte for byte, so the compiler and the apply path share one field map and a recipe can be diffed against a real C record.
- `name_id` and `help_id` are recipe ids from `0x83f` upward, resolved by the patch accessors of section 4 decisions 2 and 3: each is a patch table entry plus a layout record in the extended special branch, not a 10-byte record at `0x130000` and not a language-slot id.
- `base_code` is the stock stored code both the recipe row and its base row write.
- Entries are ordered by `index`, and the menu values array references each entry's `row` token, so the commit hook maps token to entry without depending on list position (finding 3).
- The table's placement, alignment and extent belong to the patch plan; the extent must lie inside a range the uploader checksums or be covered by an explicit re-checksum (P11).

## 8. Host JSON format

The instance schema is `schemas/recipe-set.schema.json`, beside the other research schemas, and the first instance belongs at `manifests/recipe-set.json` with the other pinned manifests when recipe data is first authored. Draft 2020-12, `additionalProperties: false` throughout, `$ref` to `common.schema.json` only where its definitions fit.

Shape:

```json
{
  "schema_version": 1,
  "tier": "RC1",
  "origin": "host-authored",
  "target": {"model": "X-M1", "firmware_version": "1.50",
             "firmware_sha256": "43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490"},
  "recipes": [
    {"id": "kodachrome-64",
     "name": "KODACHROME",
     "help": ["Warm, saturated"],
     "film_simulation": "PROVIA/STANDARD",
     "parameters": {
       "dynamic_range": "200", "highlight_tone": 1, "shadow_tone": -1,
       "color": 2, "sharpness": 0, "noise_reduction": -1,
       "white_balance": {"mode": "AUTO"},
       "iso": "400"}}
  ]
}
```

The schema encodes the owner-recorded ranges directly, because they are ordinary-control choices rather than firmware addresses: dynamic range `AUTO/100/200/400`, the five tone-scale fields (highlight tone, shadow tone, colour, sharpness, noise reduction) as integers −2..2, white-balance modes as the eight stock modes, ISO as the 1.50 offered set (`AUTO`, `L100`, `200` to `6400`, `H12800`, `H25600`), the base mode as the five offered names, and the name and help patterns of section 4. Two-axis white-balance shift has no field, per section 2. The duplicate AUTO row of the ISO menu (row `0x1b`) is not modelled; `AUTO` resolves to stored code `0x00` and the second row is left unused.

The schema pins `target` with `const` values including the firmware SHA-256, so an instance for another version or another DAT is refused by the schema itself, as [spec/10 section 19.3](../spec/10-film-recipes.md#193-tiers) requires. `maxItems` on `recipes` is the design ceiling of 31, set by the five-bit C-slot copy of the index; the live byte at `0x127` would allow more, and the compiled check enforces the layout module's bound.

Host-side behaviour: the JSON is the source of truth; stored codes, table row positions and label ids are compiler outputs and never appear in an instance. That keeps the file reviewable by someone who knows the camera menus but not the firmware.

## 12. Acceptance against spec 19.4

- Offline. The patched menu and the commit hook are shown statically; the diff explains every changed byte; the bound checksum is recomputed with the independently checked algorithm. The layout fingerprint check (C7) fails on an unintended layout change, and the compiled content digest is recorded, so a table edit cannot pass unnoticed.
- On camera, first through a temporary loop. If G4/G5 can exercise the change without flashing, the recipe rows are tested that way first.
- Persistent installation stays an H3 operation with the owner's go naming the image, one independent review of the diff, the preserved body data and the required recovery level.

Acceptance work, planned and unexercised until a patched image exists (review item 6):

1. Fixed-scene stock-output comparison, all five offered stock modes. One fixed scene and fixed exposure settings, each stock mode captured on the stock image and on the patched image with the recipe rows present but unselected, compared as recorded output; if an output differs, the difference and its extent are stated. The five modes traverse different processing paths, so each is its own case.
2. Recorded-settings check per recipe. Select a recipe, power off orderly, read the stored record and compare the nine fields with the compiled entry for that index, then select a stock row and confirm the index clears.
3. Manual-edit and interruption cases. Edit one constituent property after a recipe selection and confirm the index clears and the menu stops showing the recipe; pull power mid-apply in the ordinary mode and confirm the previously committed values and identity stand. The same case runs at the C dial position, where the bound expectation is that an interrupted selection leaves the previous committed record intact because record setters commit nothing (P15, P16); the uncommitted tail survives dial moves (E-CPOS-EDIT-VOLATILITY-150), so confirm the menu shows no recipe right after the interruption, not only after a power cycle.
4. Other-menu and other-setting regression. Walk the 1.50 menu record and confirm every entry and range unchanged, and diff the settings image over a fixed operation set against the stock image.
5. C-position cases. Run select, edit and CUSTOM SET from the C dial position and record each behaviour separately, so no check passes on a value that merely shows: the mode-class cell reads 3 with the dial at C (the last residual of P15); a setting changed at C survives moving the dial away and back and is lost at a power off/on unless CUSTOM SET was run, which is the record-target signature and not the ordinary block's (E-CPOS-EDIT-VOLATILITY-150); CUSTOM SET carries the edit into the area-3 record; with the patch a completed selection appends one area-3 record at its forced store rather than at the power-off (P16); and selecting the stock `CUSTOM RESET` item clears the stored record, its mode field and the index byte back to the per-slot defaults, with the default payload as the new area-3 tail (P20, stock behaviour, so it runs before the patch as well).
6. Numbering-consistency check per recipe. For one selected recipe, read back the four identities from the running image and compare each with the compiled entry: the menu row position, the conversion row the values array names, the stored code col0 and the downstream col2 in the record, and the name and help text shown on the three text surfaces. A disagreement is a failure, not a cosmetic difference (S-B failure mode 1; C10 and C12 are the host half).
7. Value-domain and row-0xd probe. Confirm on the patched image that every recipe row's col0 and col2 equal its base mode's (C11), then record what the render probe `FUN_00d52684(0xfe,0xd)` returns with a recipe row at row `0xd` on the surface whose outer case 0x13 reaches it, beside the stock image's answer, and state any difference (S-B failure mode 4, P18).
8. Uncovered-surface walk. On the patched image, walk the Q cell, the FILM 1-3 bracket children, the unlabelled 9-row node and the RAW-conversion list and record that each shows its stock entries and behaviour, and that the shooting-menu tile, the Fn function list, the display-customisation list and the absent My Menu are unchanged (section 14.2, S-B failure mode 5).
9. Adjustment-data and white-balance copy cases. After a CUSTOM SET with a recipe selected, read the C record back and confirm the index byte, the payload copy at `+0x27` bits 3-7, the WB mode field, and that neither grid axis 0x113/0x114 appears in the record (P13, P19); after each defaults path (jig-cycle reset or a fresh record), confirm both index sites read zero (S-B failure modes 3 and 6).

Acceptance mapping: each recipe is selectable (section 3); a selection in the ordinary block survives an orderly power cycle as its parameters, its base mode and its identity, and an abrupt power loss drops it as it drops any other ordinary setting (section 6, P10), while a selection at the C position persists at its forced slot store to area 3 and an interrupted one leaves the previous committed record (section 5, P15, P16); recorded settings match the definition field by field, because the JSON is total (C8), the compiler is the only writer of codes, and any manual edit clears the identity (section 5); stock modes are unchanged on the static evidence that stock rows keep their arrays, codes and write path, with check 1 as the runtime requirement; the four identities of a row agree (check 6), no recipe reaches a dispatcher default (C11, check 7), the uncovered surfaces keep stock behaviour (check 8), and the index survives every stock persistence path while the C record keeps its stock white-balance limits (P13, P19, check 9). RC0's missing reference output for newly offered modes does not apply to RC1, which offers no new processing; a recipe's reference is its base mode's stock output with the recipe's parameters.

## 13. Alternatives considered

- Recipe as a first-class stored code. The stored film-sim field is 4 bits and the table's 13 rows already use codes 0x0 through 0xc, so exactly three codes (0xd, 0xe, 0xf) are free in both columns. Three recipes, plus changes to develop dispatch, the metadata encoder and the availability matrix. Rejected as the primary design. P12 shows it is not a substitute for the display hook either: the reverse scan returns the first row for a code, and distinct codes per recipe are the only way to get stock-path identity without patching the resolver.
- Recipe as a macro with no stored identity. Select the row, write the base code and the parameters, store nothing else. No new field and no display hook, but after a power cycle the menu shows the base mode and a host cannot tell which recipe produced the settings. The binding pass found a free live byte and a zero default, so this is no longer a fallback; it stays recorded as the behaviour to fall back to if a later RAM or emulation check finds a consumer of image `0x127`.
- Recipes only in the C slot. Compile a recipe into the C record and let the C dial position select it. This works with stock code only, needs no patch at all, and is the semantic model the design reuses; it fails the goal of named entries in the film-simulation menu, and the C slot holds one setting.
- User-editable recipe storage in the camera. Later work by [spec/10](../spec/10-film-recipes.md#193-tiers); the area-3 log has room for more records, but nothing here writes it.

The submenu layer's data shape is fixed by the stock analogue node `0x78c7d4` (kind 6) whose values array `0x78eebc` holds three `{token, child}` rows that each open a child node, so the seven per-slot submenus are kind-6 nodes whose four rows are the verbs themselves - `{0x40+4s, 0}`, `{0x41+4s, editor node}`, `{0x42+4s, edit screen}`, `{0x43+4s, 0}` - followed by a hidden `{0x82, dialog node}` row, and the verb items are acted on by code rather than by a keyed dispatcher, which the byte-read of `FUN_00d4e4d4` settles: that function branches on `r0 == 0x91` for the `CUSTOM RESET` item and otherwise reads the list cursor (`0x61d244`), a state cell at `0x944580 + 0xbb6c` and properties `0x1ec`/`0x1ed`, so each item's action is its own function registered in an action-table slot, the way `CUSTOM SET` sits at `0x00c74e5c` (its pointer in the run holding `0xd04214`) and `CUSTOM RESET` at `0x00c32320` (`0xd04764`). The bank's four verbs therefore need four action functions and four slots in the modal-75 action table (base `0xd04080`, pointer slot `0xcfe3d4`), whose precedents are index 101 = `CUSTOM SET` at `0xd04214`, index 83 = `FUN_00c72844` at `0xd041cc` (the buffer-A open shape the rename verb mirrors) and index 115 = `FUN_00c75ed4` at `0xd0424c` (the editor row select that runs `FUN_00d4ad38`); each item's first values word carries its identity. A byte-read of the table's first 200 words finds no terminator and exactly two zero words, indices 0 and 1 at `0xd04080` and `0xd04084`; a 4096-byte window of the modal-75 matrix `0xcd1ae4` contains no word equal to 1 and twelve zero words deep in the window, and the next table `0xce4dd8` opens with eight zeros before its first pointer. Four verbs need four slots and the run offers two, so the registration the design takes is a relocation rather than a bespoke slot hunt: the patch copies the action-table run into the bank's region, appends the four bank verb entries, and repoints the table's pointer slot `0xcfe3d4` at the copy, the same relocation shape RC0 used for the film arrays. Whether index 0 is a no-action sentinel is then moot, because the copy keeps every stock entry at its own index and the bank's four take fresh indices above the run's end. The matrix anchors are modal-75 base `0xcd1ae4` (slot `0xcf59e4`, stride word `0xcd5f0e` = 46, cell = event*46 + variant, variant at `0x0146761e` written `0x1e` by the open and event at `0x0146777a` written by the key router `0x00c0bae8`), and the measured points are action 115 at cell `0xcd211c` (event 8, variant `0x1e`) and action 83 at cell `0xcd1fa8` (event 6, variant `0x1d`); the earlier `0xce5ec8` figure in this lane's notes was modal 73's matrix. The three verbs that commit (`SAVE CURRENT SETTINGS`, `RESET`, and the editor's confirm) are the arm entries of section 17.3; the remaining binding is the action dispatch that reaches them from a submenu item.

Semantics that the acceptance turns on:

- Recall applies the slot's stored fields over the live state field by field through the getter/setter walk, so the recalled state is the state that was saved; the nine-field model of section 2 is the recipe subset that the compiled D3 rows and the bank's staged field edits use.
- Save Current snapshots the whole current record, so a slot carries a complete custom preset and Recall reproduces the state that was saved, not a nine-field subset of it.
- No auto-update is structural, not a flag: a slot is a record that only the save and reset arms write, and a manual edit after a recall writes the live block only. Nothing compares live values against a slot.
- The stock C record is untouched by every bank operation. The bank never writes image offset 0x140 and never issues the area-3 mirror store; its operations walk the bound fields into the slot or the live block, and a recall at the C position is refused before any write.
- D3 and the bank are disjoint: D3's rows are film-table codes 0xd/0xe on the RC0b arrays, the bank's rows are rows of its own property's table, and neither reads the other's arrays or tables.

### 17.3 Hosting property and the commit arm

Superseded by section 17.7: the property route is withdrawn and the class route with the modal interposer is the live binding. The two lists commit two spare properties. The commit dispatcher `FUN_00d4fc74` (image 5) dispatches `sub r3, r6, #10; cmp r3, #636; ldrls pc, [pc, r3, lsl #2]` over a 637-word table at `0x00d4fcd0` (byte-read this pass), so any property in 10..646 has a table word. 498 of the 637 words point at the shared no-op arm `0x00d52664`, which writes the property through the generic setter and then notifies. The design repoints the two spare properties' table words at the bank's own arms, a 4-byte data write per property in the image-5 decode; no stock arm's code changes and the shared arm keeps its 498 stock properties.

At an arm entry the registers hold the row token in r5 (the values-entry word), the property in r6, the row's col0 in r8 and its col2 in r4, and the dispatcher's prologue has pushed `{r3,r4,r5,r6,r7,r8,r11,lr}`, so an arm returns with `pop {r3,r4,r5,r6,r7,r8,r11,pc}` (byte-read this pass at `0xd52664`-`0xd52680`; register roles inherited from the D3 pass). An arm may call stock functions under AAPCS as long as it keeps the stack balanced and preserves r4-r8 and r11 around its own use.

### 17.4 The two arms

The recall arm, for the recall list's property: resolve the slot from the row token and hand it to the storage lane's kernel `rb_recall(slot)`, which validates the whole bank and then applies the stored record field by field through the stock write entry, or through the stock commit dispatcher for a code its conversion table carries, and reads every field back through the stock reader; at the C position it refuses with status 8 before touching anything, so the C record is never a bank target.

The save arm: read the slot's name back, keep it, and hand it to `rb_save_current(slot, name)`, which reads the live record's bound fields through the getter and writes them into the slot's payload; the nine-field model stays the recipe subset that the compiled D3 rows and the staged field edits use.

The reset arm writes the slot's payload from the per-slot defaults row through `rb_reset(slot)` and leaves the name in place; `rb_readback(slot, name, payload)` is what the menu uses to stage a slot's field edits, one `FUN_00624694(prop, code, 0, scratch)` at a time, against the recipe model's nine fields.

The three arms exist as source in `menu/recipe_bank_arm.S` and `menu/recipe_bank_hook.c` (section 19); they call the storage lane's kernel and touch only the label record themselves. Each entry balances its own pushes and ends in the stock epilogue, so it can be entered by the dispatcher's table jump; the trampolines carry the three absolute stock addresses, which keeps the blob relocatable to the plan's base.

### 17.5 Identity and the highlight

The bank stores no identity token. A recall leaves the live values equal to the slot's payload and nothing marks which slot was used, so no list row highlights on recall and no field's identity can go stale. This is a deliberate reduction from RC1: RC1 needed an index because its recipes were compiled constants that a menu row had to highlight; the bank's slots are user data, and the owner's no-auto-update requirement forbids the value comparison an identity would need.

### 17.6 Names

The seven bank names ride a new label id class served from seven 66-byte records in patch-owned RAM, with the inline UTF-16 buffer at `+0` and the layout halfwords at `+0x38` (the stock record shape, special-label report section 3). The ids are `0x83f`..`0x845`, above the stock special ids `0x83c`-`0x83e`, so the stock blank id, D3's compiled name record and the 0x83e record keep their present meaning, D3 included.

A census of every `movw` immediate in the plain image finds 37 sites holding `#0x83d` or `#0x83b`, and reading each site's instruction classifies them into 30 class gates and 7 non-gates.

The 30 gates, each a `movw rX,#0x83d` that bounds which ids the site admits, split into three families: the label family proper at `0x01178564`, `0x01178694`, `0x01178cf4`, `0x01178fb8`, `0x01179a58`, `0x01179abc`, `0x01179b14`, `0x01179efc`, `0x0117a734`, `0x0117dc14`, `0x0117dc80`, `0x0117dcec`, `0x0117dd54`, `0x0117ddbc`, `0x0117de24`, `0x0117de70`, `0x0117deb8`, `0x0117def4`, `0x0117df7c`, `0x0117dfe8` (20 sites: the record locator, the five layout accessors, the two entry accessors, the entry pointer, the metric reader, the text accessor, the attribute and width wrappers, the line query and the line layout); the text-layout family at `0x011122c0`, `0x01112448`, `0x01112664`, `0x011127e8`, `0x01112a74`, `0x0111373c`, `0x01113994` (7 sites, each reached after a draw call); and the three draw sites at `0x011640f0`, `0x0116bbbc`, `0x0116bcb4` (each tests the id returned by the label getter `0x00bf93e0`). The edit at each is the same one-immediate change, `#0x83d` to `#0x845`.

The seven non-gates must not be touched: five sites build a Q-glyph id rather than a class bound (`movw rX,#0x83d` followed by `movt rX,#0xff00`, giving `0xff00083d`, at `0x011459b8`, `0x011459dc`, `0x01145c18`, `0x01145e20`, `0x0114c740`) and two pass the constant as an argument (`0x0111d2d0` calls `0x011397a4(0x83d, 0)`). The ten `#0x83b` sites are the language-table/special-record split inside the gates above and need no change, because the bank's ids take the special branch.

The stock record base does not stay `0x37b784`. The bank's record table lives in the placement region instead (gap 2, provisional), and it carries the three stock records verbatim first: the builder reads ids `0x83c`, `0x83d` and `0x83e` out of the image-2 decode at `0x37b784` (`stockNameRecords`) and writes them at the new base ahead of the seven bank records (ids `0x83f`..`0x845`), so the blank id, the one compiled D3 name (`0x83d`, `WARM STANDARD` as the image-2 patch writes it; there is no second compiled name and `0x83e` stays the stock empty record unless a recipe input declares otherwise) and the `0x83e` record all resolve to what they resolved to before. Each gate's new immediate is derived from the site's own test form rather than applied uniformly: gates that compare the id itself take `0x845` (the last bank record, id `0x845`), while the eight gates that compare `id - 1` (the `sub r2, r0, #1` form: the five layout accessors `0x0117dc14`, `0x0117dc80`, `0x0117dcec`, `0x0117dd54`, `0x0117ddbc`, the two entry accessors `0x0117de24`, `0x0117de70` and the locator `0x0117dfe8`) take `0x844`, because their normalized input is one less. The glue (`rb_name_edit_open`, `rb_name_edit_commit`) is the name-editor lane's, in `menu/recipe_bank_hook.c`. The editor node needs no dispatcher table write, and none should be made: the property `0x131` and `0xb6` words of `FUN_00d4fc74`'s table already point at the shared no-op arm, the generic setter has no case for either property, and the rows are dispatched by `FUN_00d4ad38`, entered directly by the modal handler family. The routing is not node-keyed: a byte-read of the modal-76 matrix `0xcea6e8` (stride 49) finds packed flag words, not pointers or node ids, and its state words `0x146777c`/`0x1467620` sit in image 5's bss outside the decode, so the editor is live when the open path puts the modal machine in the editor mode and the row dispatch then routes by property and row. The bank's editor is the buffer-A flavor whose open is `FUN_00c72844` (`0x0146761e = 0x1e`, cursor 0, buffer `0x954385`), not the wireless buffer-B flavor (`0x01467620 = 0x24`, cursor 9, buffer `0x954394`), and the open path reproduces the stock open's `FUN_00d3d858(0xe,0x1d)` and `FUN_00c12aac()` pair through `rb_call_stage_open` and `rb_call_transition` before the editor is live, with the confirm case owning the gate on a result of -1 or 2. That makes the native case the settlement: drive the OK press chain into cell `0xcd211c` with `rb_name_edit_commit` as the confirm case's callee, assert the mode word, cursor and buffer, and observe the persist and the record refresh. The editor case carries a refusal leg too: a `nav_result` outside {-1, 2} must leave the mode word, cursor, buffer and both name halves untouched, because that is the one path where the editor glue could write before the editor is open. The route that makes an editor row live is now bound: modal-75 base `0xcd1ae4`, cell = event*46 + variant with the event at `0x0146777a` and the variant at `0x0146761e`, and the OK press on the editor variant reaches `FUN_00c75ed4` through cell `0xcd211c`, which runs `FUN_00d4ad38` and the current row, so the case must drive that chain rather than call the glue directly.

The decode prefix is exhausted. The window is `[0x0061c1fc, 0x0061c400)`, 516 bytes; RC0 occupies `[0x0061c340, 0x0061c400)`, 192 bytes, and RC0b occupies `[0x0061c240, 0x0061c340)`, 256 bytes, leaving 68 bytes at `[0x0061c1fc, 0x0061c240)` (patch-01 section 5, patch-02 section 3). It may carry assembly, linking and native-runner cases while the ownership question is open; no emitted candidate and no live write may rest on it, and the report claims no owned memory. Gap 1 (80,480 B) and gap 3 (88,608 B) stay empty. Any gap-resident initialization must depend on its own bytes having been copied and on removal of the relevant transient protection, because extent callbacks run before the whole copy completes.

Capacity, per storage option, with the stock bank addressing as the floor: the property layer addresses `bank*0x1c2 + 0x140 + 0x28*slot` with 1 reserved for the live values, so a bank image holds slot codes 0 and 2 (code 0 is the C record and stays stock) and slots beyond 0x1b8 overrun the 0x1c2-byte image. Prerequisites, each with what it needs and why the design cannot supply it:

1. The plain-extent container operation. Built in this pass as `rebuild-update extract-plain` and `rebuild-update replace-plain [--flash-offset 0xHEX]` ([update-container-rebuild.md](update-container-rebuild.md) section 8): the id-6 window addressable by flash offset, with the same assembly gate, checksum recomputation and read-back verification `replace-image2` carries. It is the carrier for every bank byte, and it claims no ownership of the inter-extent runs it writes.
2. The storage backend. Landed on 2026-10-09 as `menu/recipe_bank_storage.c` with the kernel operations of section 16 and an SD-backed two-generation file (`RECIPEA.BIN`/`RECIPEB.BIN`); its symbols are what the blob link above resolves.
3. The commit path's emulation case. Commit dispatch is `menu/recipe_bank_actions.c`: the interposer `rb_bank_interpose` decodes a bank token through `rb_bank_action` and calls the kernel, so the native case enters `rb_bank_action` with a mapped bank rather than an arm entry.

5. The bootstrap publication gate. 6. The on-camera rename. 7. The page-discovery rescan. Fixed in the hook: slot 0 opens a visit and owns the one `rb_load`, a failed load latches its status for the rest of the visit, and every row re-reads the seven names from the resident image, so a discovery costs one scan instead of seven and a card swap cannot publish a mix of two cards' names. `rb_load`'s two scans stay contractually required for a cold discovery, and the kernel's other accessors still rescan per call - an epoch memo for those is an option, not a need of this path.

## 20. Acceptance additions for the bank

- Recall applies the slot's stored fields over the live state field by field. On a fixed scene, recall one slot, then read the settings image back: every bound field the slot carries matches, and the setters' own mode restrictions are the only exceptions the run may record. Where a staged nine-field edit is used instead, only those nine fields' bytes differ.
- Save Current then edit, power off, power on: the slot payload read back is byte-identical to the saved payload, and the live values are the edited ones. No auto-update holds across the cycle.
- A slot whose payload carries a code the pinned table does not hold is refused whole: the live values are unchanged and no field is applied. The same refusal is the offline `codeToRow` case in `RecipeBankTests`.
- The C record is untouched by every bank operation: its payload, its mode field and the image-2 index sites are byte-identical before and after a bank save, recall and reset.
- D3's two rows still select their base modes and their Q exposure with the bank present, and the seven stock film rows are unchanged.
- The two new menu items appear once, on the shooting-menu page, and no other surface changes; the fallback when placement or storage fails is the D3-only image, which this design does not modify.
