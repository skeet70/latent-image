## 1. The install in one paragraph

The updater is application code: the firmware currently installed runs the update, reads the container from the card, checks it in RAM, and then rewrites internal storage in place while the old firmware is still running. The body resolves the file name `A:\FWUP0002.DAT` (the template at `0xdba2c8` is altered with configuration bytes queried at keys `0x1c0`-`0x1c3`, which hold ASCII `0002` on this body in both the 1.00 and 1.50 adjustment captures, E-CONFIG-OFFSET-NAMES, **byte-read**). Nothing about the procedure is first-time territory: the owner ran the stock 1.00 to 1.50 update through this route (E-STOCK-150-OWNER-REPORT, **reported**). What is new is the container, and the fact that the writer takes no backup and leaves no rollback: it destroys the boot marker first and writes it back last.

## 2. What the camera does when, inside the update

Ordered from the mapped write path (**byte-read** mutation and ordering cells, **static-inference** residues; [UPDATE-01](update-validation-and-boot.md) carries the full table and the addresses).

| Phase | What happens | Touches media |
| --- | --- | --- |
| File read and parse | Opens `A:\FWUP0002.DAT`, reads a `0x25c`-byte staging header, requires header word 0 to be 4 (else status 10), parses the main and two auxiliary ranges | no |
| Eligibility | UI gate `0xd0c530`: identity records against the body's current identity at `0x96b402`, version format and version policy (section 10), alongside earlier camera-state checks that are **unproved** | no |
| Staging and three sums (S0) | Reads the declared ranges into RAM, complements each main byte in place, requires the complemented byte sum to equal header word `0x20c` and the two raw auxiliary sums to match `0x24c`/`0x258` (a mismatch is status 5 and stops here) | no |
| Trailer-block erase (S1) | Erases raw block `0x125`, the trailer block holding the boot marker; its result is not checked | **yes, first write** |
| Optional pre-erase (S2) | Erases the contiguous span up to `min(10, property 0x276)` times and sleeps `property 0x275` seconds; returns are ignored | yes |
| Block program (S3) | Blocks `0` to `0x125` ascending at the `0x20000` stride, each block window-checked, compared, erased, programmed in `64` pages of `0x800` and verified; media offset equals image offset, so the new firmware image lands at media `[0, 0x24a0020)` | yes |
| Bad-block handling (S3b) | A failing block is programmed with main `0xff` and spare byte 5 `0xe0`; the following physical targets shift after the map rebuild, budget `0x14 - [0x828578]`, exhaustion aborts with `-40`. Bad-marker retention after reboot or power removal remains unobserved | yes |
| Configuration completion (S4) | `0xdb91e0` snapshots the first `0x42000` bytes of the adjustment cache, refreshes them from the factory template (raw logical blocks `[7, 10)`), restores the 1,487 bytes named by the container's two auxiliary restore lists from that snapshot, and commits logical indices `[0x29,0x4a)` to allocator-selected blocks in physical pool `[0x380,0x400)`, media `[0x7000000,0x8000000)` ([bounded mapping](update-validation-and-boot.md#native-writer-boundary-and-preservation-limits)), not a fixed physical write span | yes |
| Session commit (S5) | Chain-A row 13/state 0 selects `0xec4618`, which issues flashloader commands 2/6 (reads) and registers the separate directory-journal step. Its total order against S1-S4 and screen binding remain unproved ([selection contract](update-validation-and-boot.md#commit-step-and-service-writers)) | yes |

The boot marker is the 32-byte trailer at media `[0x24a0000, 0x24a0020)` with the halfword `0xaaaa` at `+0x1e`, programmed inside block `0x125`'s first page, which is the last block of the loop. The old trailer is destroyed at S1 and the new one arrives at the end of S3; that ordering is why an interruption in between leaves a body that cannot boot.

## 4. Card preparation

1. Format the SD card in the camera (SET-UP menu, FORMAT). **reported** (vendor procedure); formatting erases the card.
2. Copy the container to the card root as `FWUP0002.DAT`, without altering a byte and without letting a browser rename it (`FWUP0002 (1).DAT` is not recognized, **reported**). The name is load-bearing: the body derives the lookup name from configuration bytes that read `0002` (**byte-read**).
3. Re-read the card copy on the host and compare its SHA-256 against the intended container hash before the card goes back into the camera. The camera's three sums are the second check; this one catches card or copy errors before any camera involvement.
4. Keep only the update file on the card.

## 5. Power arrangements

The install needs a supply that cannot be interrupted for the whole S1 to S5 window. The vendor reports about 5 minutes (maximum) for an X-series update (**reported**). **Hardware-observed, 2026-10-09:** the owner's process video measures the span from the accepted confirm to the completion screen at 57.3 s (17.0 s to 74.3 s of video time, one-frame precision; [the session's timing table](filmsim-install-session-script.md#phase-durations-and-pauses), E-INSTALL-TIMING-150), with the longest unchanged stretch inside it at 13.7 s. No mapped edge supplies a timeout, so an uninterrupted supply is still required and the S0-to-S5 split stays unmeasured; a future image is not covered by this measurement.

The project's power-cut observations bound only idle sessions. Four cut endings preserved settings: the two no-command jig trials of E-JIG-POWERCUT-PRESERVES-150 (**reported**), the read-config session cut recorded by E-ADJ-READ-150 (**hardware-observed** capture, **reported** settings outcome), and the control arm of E-JIG-CYCLE-D-150, which ran a read-only dump pair and its gate enable/restore before the cut (**hardware-observed**). E-JIG-HEADER-DIFF-150 cycle B is a further cut ending observed at the level of retained-header bytes, both headers valid and the adjustment cache byte-identical across endings. None of these had a storage write in progress, so none of them says anything about a cut during a flash: the interruption table of section 6 is the only authority there. Cuts are also not uniformly benign even when idle: the battery pull of E-RESET-ORIGIN-AREA2-150 returned the setup menu through the area-2 branch, so the four preserved instances bind their own context only.

Arrangements for the run:

- The owner has used the dummy-battery supply (E-DUMMY-POWER-SUPPLY) in prior sessions. It removes the battery-runtime window, but voltage/current margin, transient response, grounding and erase/program load are **unproved**. A supply sag inside S1 to S3 is an interruption like any other; the project has no evidence that this arrangement is safer under flash load than a genuine fully charged battery.
- Mains-backed supply, its connector secured and not on a shared switch; camera on a stable surface; card door closed; lens mounted; no USB attached (the update route is the card, not the service session); nobody touches the POWER switch or the battery door during the run.
- The alternative is a genuine freshly charged battery, matching the vendor's "fully charged battery" wording (**reported**), at the cost of a runtime window the mapped path does not bound. If the supply's transient behaviour under flash load is doubted, that doubt is an owner judgement: the project has no measurement of either arrangement under load.

## 6. The procedure, step by step

1. Record the pre-install state (section 3) and set the power arrangements (section 5).
2. Power the camera off, insert the card, power on while holding the DISP/BACK button. **reported** (vendor procedure for X-series interchangeable-lens cameras). The version screen appears, showing the installed and the container version (the parsed words live at `0x95d670`-`0x95d67c`, **byte-read**; the on-screen wording is **unproved** on this body). The entry decision does not read the Function button: the boot poller's DISP/BACK branch requires key state `DISP_B` (`0x9`) behind configuration byte `0x0096b429` bit 1 and raises the boot mode to 8, and no test of `FUNCTION` (`0x28`) or `FUNCTION2` (`0x219`) appears in the boot key fold or the poller (**byte-read**; E-UPDATE-ENTRY-KEY-BIND-150, whose branch-to-screen binding is **static-inference**). The owner's power-on with Function plus DISP/BACK reached this screen on 2026-10-09 (E-SD-BOOT-ENTRY-HOLD-150, **hardware-observed**), which is this entry with Function ignored. This screen is ordinary firmware reached after a normal boot; it is not the ROM SD-BOOT path of [the recovery design](recovery-status.md) and takes no part in it.
3. **Abort point A.** If the screen does not offer the update, or anything looks wrong, power off and stop; media is untouched. This screen is also the free observation of the same-version branch (section 10): with a container carrying 1.50 on a 1.50 body, either the update is offered and the equal-version acceptance becomes hardware-observed, or it is refused before any write, which answers the question at no cost. On 2026-10-09 the screen offered the update (section 10, E-FILMSIM-INSTALL-150).
4. Follow the BODY item and upgrade-confirm screens one press at a time, as [session acts I3–I5](filmsim-install-session-script.md#5-camera-acts-enter-inspect-confirm-wait) specify. **Byte-read, vendor illustrations:** there can be several OK presses, including a final battery-cover/power warning with BACK CANCEL. The OK that starts processing is the visible point of no return; if this body omits intermediate screens, treat its first accepted upgrade confirmation as the commitment. **Unproved:** the equal-version X-M1 screen order.
5. The camera now runs the phases of section 2 on its own. Touch nothing: no button, no card door, no power. Per-step indications are **unproved**; the vendor shows a progress flow throughout (**reported**).
6. When the update screens report completion and ask for the power off (**reported**), switch the camera off and continue with section 9.

## 7. Abort points and the point of no return

- **Last abort with a working camera: before the [OK] of step 4.** Everything up to that point has touched only the card and RAM.
- The mapped media boundary is S1, the trailer-block erase: staging and the three sums are RAM only (**byte-read**), so a stop before S1 leaves the old firmware intact and booting. But no screen shows where that boundary sits and no cancel is mapped after the confirmation, so operationally the [OK] press is the commitment.
- **After S1 the body is committed.** The marker is gone; the application that contains the updater cannot boot again until S3 has rewritten the whole image and its trailer. There is no mapped interruption point and no second chance. An interruption in this window is the invalid-application class of spec/04 section 10.3: no repair is demonstrated, the standing recovery capability is diagnostic rather than restorative until a write half exists, and the owner accepted this residual risk explicitly (RECOVERY-R4-PRACTICE-01, 2026-10-09).
- **Byte-read:** the checksum-success byte `0x15c1e58` is set once staging and the sums succeed, and nothing clears it but power-cycle RAM loss. A later attempt in the same power session skips staging and the sums. After any aborted prewrite attempt, switch off, then make a real supply cut or remove the battery after shutdown before any newly scoped attempt. A menu exit, card swap or second confirmation does not clear it. After processing begins, do not cut power or retry.

## 8. Interruption residues, and which are recoverable by repeating the update

Residues and next-boot behaviour are [UPDATE-01](update-validation-and-boot.md)'s interruption table (**byte-read** ordering, **static-inference** residue granularity; the marker-based next-boot cells presume the unproved `0x1cc0` transfer unit, private item O8). Recoverability by repeating the update is judged here from one fact: the updater is application code, so it can only run again if the body boots.

**Byte-read:** E-RECOVERY-EMUL-150 records 36 of 36 passing cases in the native harness at the declared media-model boundary. **Static-inference:** this strengthens the software erase/program ordering and modeled interruption residues, not recoverability on the body. **Unproved:** device physics, bad blocks and power loss inside one persistence step remain hardware questions. The table's repeat-update column describes a conditional application-code route, not an instruction to reflash after an unexpected result; a new operation still needs host analysis and the owner's named go.

| Interrupted at | Leaves on media | Next boot | Recoverable by repeating the update? | What the owner sees |
| --- | --- | --- | --- | --- |
| S0, staging and sums | nothing | old firmware boots normally | nothing to recover; walk away | normal operation |
| S1, trailer erase | block `0x125` erased, marker gone (if the erase lands) | marker compare fails, boot record self-loops: no application starts | **No.** The updater never runs again on this route. The R1 SD-BOOT candidate has no known actuation on this body; no repair is demonstrated | a camera that does not boot; the mapped failure branches are self-loops, so no error message |
| S2, pre-erase | marker already gone; the contiguous run from `remap[0]` erased at whole-block granularity | same halt | **No** | same |
| S3 before block `0x125` page 0 | blocks `[0, i)` new, block `i` partial, marker gone | same halt | **No** | same |
| S3 inside block `0x125` after page 0 | marker present, blocks `[0, 0x125)` complete (the whole image), tail of block `0x125` holds staging residue no traced reader consumes | boots the complete new image; the configuration area still holds the old body data | **Yes.** The application runs, so a repeat completes S4/S5 and rewrites the residue | possibly a normal boot with settings intact |
| S3b, bad-block event | failing block programmed `0xff`, following physical blocks shift after the map rebuild | depends on the bad mark surviving the reboot (**unproved**); a content block of `0xff` is missing image data and a load halt or hang | **unproved**; repeatable only if the body still boots | normal boot, or no boot |
| S4, configuration commit | torn configuration area; before its first block lands the validity `0xaa55` is absent, after that block torn bytes are accepted with no further gate | firmware boots either way (its marker came with S3); before the first block: cache zeroed and the factory template loaded, settings at defaults; after: torn adjustment bytes accepted | **Partly.** A repeat rewrites the area, but the restore lists restore from the then-current cache, so body-specific bytes lost or torn here are not repaired by repeating. Repair needs the backup and a writer (unlock plan step 11, not built) | the setup menu or quietly wrong settings; calibration damage is not visible without a capture diff |
| S5, session commit | torn directory-journal block pair | consumed by task `lensdata`; no demonstrated boot failure, only the inherited area-2 exclusion analysis | **unproved** | **unproved** |

One hazard outside the rows: if the S1 erase silently fails (its result is unchecked), the old marker survives and can accompany a mixed body, and no mapped checksum would notice (**byte-read**). The boot performs no checksum matching the updater's body sum.

## 9. Post-install checks and their interpretation

First establish normal boot, retained watched settings and working capture/playback. The [session's V0–V5 acts](filmsim-install-session-script.md#6-verify-normal-operation-then-seven-entries) then record the menu/shot observations; [R0–R6](filmsim-install-session-script.md#8-readback-and-evidence-handoff) bind them to the running bytes and stored body state. A visible unlock remains an observation, not an accepted byte-level install, until those checks pass: the 2026-10-09 run satisfies steps 1 and 3, step 2 for the owner's four reported names (manual settings, date, time, language) and, on the process recording, four watched names more (ISO 6400, IMAGE SIZE `L 16:9`, IMAGE QUALITY `F+RAW`, DYNAMIC RANGE `DR100`) with `M`, 1/100 s and f/4.5 on the shooting screen and the seven-entry list in its byte-read order ([the session's timing and screen record](filmsim-install-session-script.md#phase-durations-and-pauses), E-INSTALL-TIMING-150), and the menu half of step 4, while steps 5 to 7 remain open, the fixed-scene shots of step 4 are unrecorded and the rest of the watched list is unobserved.

1. **First boot.** Does the camera boot at all: no halt, no hang, menus respond. **Static-inference:** a nonbooting body can reflect the S1 to S3 interruption class or a load/decompression failure; the symptom alone does not distinguish them. Stop; do not cycle power repeatedly or copy generic battery-removal advice (spec/04 section 10.4), and preserve the last display, supply/card state and session artifacts for host analysis.
2. **Settings.** The setup menu did not appear and the watched settings of the pre-install record are intact. The setup menu appearing is S4's template defaulting: settings at defaults, and the restore-covered bytes need the capture diff below before the body is trusted. **Hardware-observed, 2026-10-09:** no setup menu appeared and the owner reports manual settings, date, time and language intact, which covers four names of the watched list rather than all of it; the rest and the restore-covered bytes still need the capture diff below.
3. **Version.** BODY VERSION reads as expected. Weak evidence: the version getter can return configuration bytes or its built-in 1.50 value depending on configuration byte `+0x206`, so the displayed number is not independently verified storage identity (**byte-read**).
4. **Ordinary operation and tentative unlock observation.** One shot on the fixed scene, played back (the camera-run procedure's own step), followed by the seven-entry menu photographs, PRO Neg Std/Hi selection and test shots, stock-mode comparison and ordinary power-cycle check. **Byte-read:** the intended list is stock five followed by Std/Hi. **Hardware-observed, 2026-10-09:** the seven entries are in the ordinary menu, the owner names PRO Neg Std and PRO Neg Hi among them and selects both for fixed-scene shots; **unproved:** their output, the list order beyond the stock five and the power-cycle check. Unexpected functionality or settings differences stop the sequence; no successful install is inferred from the list alone.
5. **Byte-level confirmation that the install landed.** A read-only jig capture of the running image 4 (the dump-ram technique of E-DUMP-RAM-150, **hardware-observed** method) covering the changed bytes, compared against the intended decoded image at those addresses, with the 781 runtime-written bytes screened out (E-DUMP-RAM-150). The same session's adjustment capture compares against the pre-install capture: the 224 restore-covered bytes must hold their pre-install values (they are the calibration the restore lists carry, E-ADJ-MOVERS-150; `+0x204`/`+0x205` sit in that set and are also stamped by the boot load on every successful load), the nine stamp bytes move per their writers, and `+0x1e8`/`+0x1e9` should now read `01 78`, the compile-time constants of the stock 1.50 build that executed the update, a durable marker that S4's refresh ran (**static-inference** over **byte-read** stamps; the 2026-10-09 pre-install capture still read `01 54`, stamped by the 1.00 build that ran the previous update, so this readback is the first one that can test the prediction).
6. **End the verification session by cutting the dummy-battery supply, not the POWER switch.** A switch-ended jig cycle resets date, time, language and the C slot (E-JIG-OBSERVED, **hardware-observed**), erasing what step 2 just verified; the cut ending preserved settings in all four observations of section 5.
7. **Final ordinary check and recorded result** (unlock plan step 13): after the settings-preserving maintenance ending, new modes remain selectable, survive a power cycle and produce captures whose recorded settings match their selections; stock modes work on the fixed scene; no other menu or watched setting regresses. Combine these **hardware-observed** results with the **byte-read** readback/configuration/bank comparison, or leave the install/unlock outcome unresolved.

**What a partial write that reported success looks like.** The updater's success is its own sequencing: the S1 erase result is unchecked, there is no software ECC anywhere in the path, the boot performs no checksum matching the updater's sum, and nothing re-reads media after programming (**byte-read** absence scope named in UPDATE-01). So the outside signals are, in order of strength: a readback mismatch at any byte outside the 781-byte screen and the intended change set (the only content-level check), a first-boot failure or hang, the setup menu or lost settings, and the `+0x1e8`/`+0x1e9` stamp still reading `01 54`, which means S4's refresh never ran. A wrong-but-consistent write (right sums, wrong bytes) boots and behaves; without the readback of step 5 it is undetectable.

## 10. The same-version container

The body rule accepts it. The format gate `0xd0a590` requires each version word at most `0x99` with a decimal low nibble (packed BCD), so `0x1`/`0x50` passes; the comparison `0xd0a728` for body selector 0 accepts `new_minor >= current_minor` at `0xd0a7a4`-`0xd0a7ac` and rejects a numerically lower valid version (**byte-read**). Lens and other selectors require a strictly greater minor and are not the body route. The write action repeats no model or version check, no mapped edge special-cases an equal version, and the writer programs all `0x126` blocks whether or not the bytes differ from what is installed (**byte-read**). The `0xffffffff` sentinel is an observed branch, not an installation proposal.

**Hardware-observed, 2026-10-09 (E-FILMSIM-INSTALL-150):** no UI-layer or camera-state check refused the equal-version container. The upgrade screen read 1.50 to 1.50, the owner confirmed, and the update completed, so the UI-refusal question is answered as not refused; the eligibility gate's modal call (`0xca6108`) and the write chain's independence from it stand as read. Abort point A's free observation did not arise: the update was offered, so the refusal branch could only have been tested by a deliberate refusal attempt, and the answer arrived at the commitment instead. It does not block anything below: keep the version words at 1.50, since raising them would make the version screen and BODY VERSION report a version the firmware does not carry and the run shows equality is sufficient.
