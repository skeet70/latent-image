# The reported SD-boot unbrick practice against this body's 1.50 bytes

Scope: host-only analysis over the pinned 1.50 artifacts and a host-only read of the privately shared X70 emulator checkout (`../x70view`, cited by path and function name, no code copied or run). No camera or USB device was touched and no camera operation is authorized. Labels: **byte-read** names ROM, record, image or tool instructions, **hardware-observed** names existing reviewed captures, **reported** names the Discord statement, the service manual and the X70 checkout's own documents, **static-inference** names deductions the bytes support without proving, **unproved** names what nothing here establishes.

The reported input (fujihack Discord, 2026-10-09): `tiredboffin` describes booting working firmware from the SD card instead of broken firmware in EEPROM, then updating through the normal update process, and calls SD boot his low-risk way to experiment with firmware modifications without a hardware emulator. The same day `jitl` reports a full-system X70 emulator that boots unmodified firmware with two CPUs, cache models, NAND and the boot sequence modeled. Neither statement is evidence about the X-M1; both are checked here against this body's bytes, and the X70 material the second statement is about is read on its own terms in section 3.

## 1. What selects SD boot (byte-read)

The ROM's mode detect `0x80000260` reads two registers once per reset: `0xfff89014` bits 11:10 at `0x80000274` and `0xfff98000` bits 2:0 at `0x80000278`, combines them into one 5-bit value (`0x8000027c`-`0x80000284`) and returns it as the mode (`0x80000288`-`0x80000300`).

| `0xfff89014` bits 11:10 | `0xfff98000` bits 2:0 | Mode | Handler |
| --- | --- | --- | --- |
| any | 7 | -1, halt | none |
| 0 | 0-6 | 1, SD/FAT channel 0 | `0x8000082c` |
| nonzero | 0 | 3, internal format 4 | `0x80000938` r0=0 |
| nonzero | 1 | 4, internal format 1 | `0x80000938` r0=1 |
| nonzero | 2 | 5, internal format 2 | `0x80000938` r0=2 |
| nonzero | 3 | 6, internal format 3 | `0x80000938` r0=3 |
| nonzero | 4 | 2, raw SD channel 1 | `0x8000071c` |
| nonzero | 5 | 7, receive engine | `0x80000ac0` |
| nonzero | 6 | 0, RAM handoff | `0x80000b2c` |

The `-1` halt is the chain's first test and looks only at the combined word's low three bits (`0x80000288`-`0x80000290`: `mov r0, #7`, `bics r0, r0, r1`, `mvneq r0, #0`), so a low selector of 7 halts whatever the high pair reads; the high pair's bits 4:3 do not enter that test. A nonzero high pair reaches mode 0 only through low selector 6. The X70 harness test that calls the real `0x80000260` asserts the same table, including high pair zero with any low selector other than 7 returning mode 1 (section 3).

SD boot is two modes: mode 1 (`ffsys.bin` and `ffboot.bin` on a FAT volume, SD host channel 0, dispatch case at `0x8000014c`) needs the high pair zero; mode 2 (raw blocks on channel 1, dispatch case at `0x80000164`) needs the low selector 4 with a nonzero high pair.

The two registers are the whole input. From reset at `0x80000028` to the detect call at `0x80000130` the ROM programs SVC mode and the stack, five MPU regions, the MMU and cache enable, the flag `0xfff88084` = 1, a 32-byte SRAM copy and an SRAM zero-fill; it reads or writes no card, no media, no key state and no application byte. The detect's only write is the combined mode word back to `0xfff98000` (`0x800002f0`), which preserves bits 2:0.

The dispatch calls one handler per boot and halts at `0x80000020` on any nonzero return (`0x800001f8`-`0x800001fc`); on success it jumps to the handoff stub `0x80002298`. A call-site pass over `bootrom.dis` finds `bl 0x80000260` and `bl 0x8000082c`/`0x8000071c`/`0x80000938` at the dispatch sites only, so no handler re-runs the detect or invokes another mode.

On this body the sampled values are bits 11:10 = 3 and low 1 (`0xfff89014` = `0x00000d4e`, `0xfff98000` = `0x00000019`, E-STRAP-READ-150; the reset-stage mirror word 0 is `0x00000d62`, bits 11:10 = 3), giving mode 4. No observed boot presents the strap values either SD mode needs.

## 2. What could move the selector (byte-read, static-inference and unproved per item)

- **A card property:** excluded for the main CPU. The selection precedes every media access and reads only the two registers, so no card content or presence can set it. Card content could matter only through external logic that drives the strap pins, which firmware cannot show.
- **A button:** the ROM reads no key state; the boot key scan is application code that runs after the ROM's handoff (E-UPDATE-ENTRY-KEY-BIND-150). A button can therefore affect the mode only electrically, by changing the pads the GPIO block samples. This body's own input table puts exactly two controls on those pads: image 4's condition rows at `0x82828c` and `0x828388` bind `KEY_FUNCTION` (Fn, input code `0x28`) to GPIO0 bit 11 and `KEY_CMDL_PUSH` (sub-command push, code `0x2b`) to GPIO0 bit 10, each asserted while its bit reads 0, through the kind-2 arm of `FUN_006a0888` (operand bank in bits 31:16, bit in bits 3:0, read at `0xfff89014 + bank*0x40`); the act-logged session binds a physical Fn press and a physical sub-command push to those two codes (E-PRESS-MAP-150, hardware-observed). The owner's cardless sweep held Function together with each body button and with the sub-command dial push (E-SD-BOOT-ENTRY-HOLD-150), so the pair this table names was held at power-on, and every combination still booted mode 4.
- **State left by a previous boot:** no decoded writer sets either register. The census in strap-read-safety.md section 3 (scanner plus manual re-read of every reported site) finds no store to `0xfff89014` in any artifact and no access to `0xfff98000` anywhere except the ROM, whose store preserves bits 2:0; a `movw`/`movt` pass over the ROM, both records, both loaders, images 4 and 5 and the plain image materializes `0xfff98000` nowhere and `0xfff89014` only as the base of the 16-word port-mirror loops (record 1 `0x2688`, record 2 `0x22b8`, image 5 `0xec7dac`). The ROM rewrites `0xfff89008` = `0x0c000c00` before every sample (`0x80000270`), so a previous boot's control state at that register is overwritten. The census's literal-load form in `strap-scan.c` (the `LDR` pattern matched without constraining `Rn` to PC) can resolve a non-PC load as a constant, so its reported copy sites need re-derivation and its register-indirect and table-driven blind spots are unchanged. Whether the sampled pads can be driven from elsewhere or hold a warm-reset value is electrical and unproved.
- **An invalid application:** the selection consults nothing about the application, and section 4 shows there is no validity check it could fall back from.

**Unproved:** both checks have declared blind spots: register-indirect writers, table-driven accesses and literal-pool constants outside the scanner's forms are not covered, and image 4's ten-word MMIO base table at `0x829144` (containing `0xfff89000` and `0xfff98000`) has no established consumer. No decoded route to a later-boot selector change is established, and absence for the indirect forms is not proved. The reset-time source of the two sampled pads is a separate open item, taken up in section 5.

## 3. What the X70 model supplies, and what this body's own table binds (reported and byte-read)

The X70 checkout is a sibling project over the same ROM, read here host-only; each statement about it is **reported** until this body's bytes or a capture confirm it, and it is the only held material that reaches the ROM's SD path.

**Strap values and how its board supplies them (reported).** `emulator/boot_devices.py` `BootControls.__init__` takes both inputs as construction arguments, `boot_source=1` and `boot_gpio=0xc00`; `boot_source` is stored to `0xfff98000` and is the low selector, `boot_gpio` is installed as port 0's input word and sets bits 11:10 high, and the pair gives the combined value `0x19`, mode 4. Its comment calls the source "an inferred NAND type-1 normal-boot profile" and its snapshot limits call the straps and initial register values "simulation fixtures". A write to a port's input word raises `UnsupportedDevice('GPIO input status is read-only in boot model')`, while `0xfff98000` sits in the model's writable system set and nothing writes it before the ROM's sample. `native/tests/test_driver_harness_api2.py` `RomImageTests.test_rom_selector_runs_through_the_harness` executes the real `0x80000260` and asserts the table of section 1, including high pair zero with any low selector other than 7 returning mode 1.

**The SD entry as the model reaches it (reported).** `emulator/sd_boot_board.py` declares three differences from its normal board: `SD_BOOT_PINS = ((0, 10), (0, 11))` held low at reset through `set_gpio_input_pin(..., 0, source='SD-boot buttons held at power-on')` and released when the ROM writes `0xfff98008`; a card present (GPIO12 bit 7 low) carrying a FAT image; and a strict ROM-grammar SD host in `emulator/rom_sd_boot.py` serving the ROM's polled reads until the handoff. The case results in `research/sd-boot.md` are: pins 10/11 low with a card gives the mode-1 chain (154 sectors read, 70,144 bytes DMA'd to `0x40000000`, handoff `0xfff98008 = 2`); the normal fixture `0xc00` gives the internal-media path with the card never read; pins low with a missing `ffsys.bin` or no card halts in the ROM's `0x20`/`0x24` loop with no NAND fallback.

**Which controls its pins belong to (reported).** `research/button-monitor/README.md` names GPIO0 bit 10 `KEY_CMDL_PUSH` and bit 11 `KEY_FUNCTION3`, and its emulator rows run `P0 0C2C` idle to `082C` on the dial push to `002C` with both, marking `SD:YES`; the names come from the X70's key tables, one owner visual confirmation (the monitor showed FN3 while the red record button was pressed, a photo retained) and a later owner report naming both controls, with no saved pin-word read. `research/sd-boot.md` states the derivation: the two-button strap is "static, 2026-10-05" and "inferred from the key tables and has not been observed on hardware", which refers to the ROM's SD selection itself never having been exercised on that camera; upstream never published how the X-E2 was made to select SD boot. `research/sd-boot-card/README.md` gives the modelled physical procedure: card in, power switch off, hold the rear command dial pressed in and the red record button, switch on while holding both, release once the camera starts, and "the ROM samples the two buttons only at power-on"; a missing or invalid card leaves the screen dark, with a switch-off or battery pull as the recovery, a state it marks as untested on the camera.

**What transfers.** Both bodies use the same ROM, so the selector arithmetic, the mode table, the file names and the unvalidated handoff transfer as code facts, and the model's normal-boot strap values are this body's live values, high pair 3 and low selector 1 (`0x19`, mode 4), which agrees with the capture and with the model's own internal-media case. Control identities do not transfer, and one of them differs: this body's table binds GPIO0 bit 10 to `KEY_CMDL_PUSH` as the X70 does, but binds bit 11 to `KEY_FUNCTION` (Fn) where the X70 binds its record button, so the two service procedures name different controls for the second pin.

**This body's binding (byte-read).** Image 4's input table is 36 rows of 28 bytes at `0x828120`; row 13 at `0x82828c` is code `0x28` with kind 2, operand `0xb` and compared level 0, and row 22 at `0x828388` is code `0x2b` with kind 2, operand `0xa` and compared level 0. `FUN_006a0888` reads the kind byte at row `+9`; for kind 2 it takes the operand at `+0xc`, loads the word at `(0x3ffe240 + (operand >> 16 & 0xf)) * 0x40 + 0x14`, extracts bit `operand & 0xf`, and stores `(halfword at +0x12) == bit` to the row's state byte at `+0x16`. The base expression is `0xfff89014 + bank*0x40`, so row 13 reads GPIO0 bit 11 and row 22 GPIO0 bit 10, each asserted while the bit reads 0. The idle jig capture reads bits 11:10 = 1, their unasserted level, and the act-logged session records Fn and the sub-command push producing their press and release codes, so the two rows track the two buttons on this body.

## 4. No invalid-application fallback in the bytes (byte-read)

The ROM validates no application. Mode 1 stages the directory-declared `ffboot.bin` in chunks up to `0x8000` to `0x40000000` and hands off to RAM 0 with no header, checksum, version or size-bound check (window map section 3.3); the mode 3-6 handler scans for the 12-byte config marker, applies the config and stages page groups, and validates nothing else. There is no validation step to fail and no alternate-media attempt on failure.

The failure paths halt. Mode 1 (`0x8000082c`), mode 2 (`0x8000071c`) and the mode 3-6 handler (`0x80000938`) return -1 after clearing `0xfff88084` bit 0 (mode 1 at `0x80000858`-`0x80000860`, mode 2 at `0x80000750`-`0x80000758`, mode 3-6 at `0x80000978`-`0x80000984` for a failed marker scan and `0x80000a58`-`0x80000a60` for a failed page load); the dispatch then halts at `0x80000020`. No handler calls another mode and none re-runs the detect.

The application-side gates behave the same way. The staged boot record's trailer gate (`0x1cc0`, the `0xaaaa` halfword behind the `0x24a0000` read) and its storage, segment and decompressor failures call the teardown `0x1de8` and then self-loop (`0x1f18`, `0x1f58`, `0x1f90`, `0x1fd8`, `0x226c`, `0x3d28` in `boot-40048.dis`), with no branch to the SD handlers, to the ROM or to a reset. Record 2 shares the record's images and, on its companion-record check, continues rather than selecting another application (recovery-hardware-routes section 5).

Consequence: a body whose application or first boot record is damaged halts dark. It does not select SD, and no decoded condition makes it do so. The claim's "boot working firmware from the SD card instead of the broken firmware" has no fallback mechanism on this body; it would need the strap pair to present an SD mode, which is the same entry the project has not been able to actuate. **Reported:** the X70 project's path has no fallback either: its case table shows the normal strap booting internal media with the card never read, and pins-low with a missing `ffsys.bin` or no card halting in the ROM's own loop; its card README states that a normal power-on boots the stock camera and that nothing on the path writes internal flash. The reported practice's second half, updating through the normal process, runs under the application.

## 5. What the recorded press sweep actually bounds (hardware-observed, with the bound stated)

E-SD-BOOT-ENTRY-HOLD-150 had the owner power on while pressing Function together with each body button and with the sub-command dial press, with no card and no USB. Every combination booted the application. Under section 3 the pads the ROM samples are Fn's and the sub-command push's, so the sweep's Function-plus-sub-command-push run presented the two mapped controls at power-on. The negative is about the sampled value: a strap move to mode 1 or mode 2 with no card reaches the handler, fails its reads and halts at `0x80000020`, so a normal boot means the reset sample did not present bits 11:10 as 0 and selected no SD mode. The result is not an artifact of pressing controls that never reach those bits.

Why the sample held its value while both mapped controls were held is an electrical and reset-time question, and the bytes bound only its edges:

- The register is live after boot: its bits track the two buttons while the application runs (section 3), and the reset-stage mirror word and the jig-time live read, taken in two different jig boots, differ in other bits (`0x00000d62` against `0x00000d4e`, E-STRAP-READ-150), so it is not a value frozen for all time.
- **Byte-read:** the ROM writes `0xfff89008 = 0x0c000c00` immediately before the two reads (`0x80000270`); that offset's electrical meaning on this SoC is not established, and it is the only firmware-controlled input to the sample besides the pads.
- **Unproved:** whether the switches ground these pads at power-on, whether another agent (a key-matrix scan line, a companion device, a test fixture) holds or drives them until later, and whether a reset-time strap latch is taken before the pads are valid.

What the sweep still does not cover:

- **The card-present hold.** ZJ02217 is unobtained and no run carried a card. If the strap were driven by hardware that arms only when the service card is present, or when some jig condition holds, a cardless sweep could not see it: the main CPU's selection is blind to the card, and such arming would live outside the main firmware.

**Explicitly reopened:** SD-BOOT-CARD-ENTRY-01 (E-SDBOOT-CARD-PRESENT-REOPEN-150) prepares the card-present Fn plus sub-command-dial push as a separate condition from the completed cardless sweep. The owner relayed the X70 author's FN3/record-button plus rear-dial-push advice and `/ffsys.bin`/`/ffboot.bin` filenames; the author says he plans to test firmware this way, so physical execution is not established by that quote. File-presence-dependent entry is a hypothesis, not a decoded main-CPU behavior. Preparation must bind reviewed X-M1 files and an observable result; live execution still requires independent byte review and the owner's go. R2–R4 remain unclaimed.

**Host resolution of the central question (2026-10-10):** [the card-entry review](sd-boot-card-entry.md) carries the pad-driver and selector findings to their byte evidence. The sweep's normal boots fix only that the high pair never read `0b00`; one control low still selects mode 4, so a single failed pad path stays open. The selector is read once before any card access and card detect is a different signal in both the ROM and this body's input table; the missing facts are the board net between each switch and its pad plus the GPIO0 `+0x08` store's update semantics and bit function. The same report reviews the built card's exact bytes and specifies the observable-outcome design required before any owner-run attempt.

- **Non-panel driving of the pads, and the selector's own writability.** Forcing the pads from a fixture or a test point, and the `SELECTOR-WRITE-01` and `RESET-RETENTION-01` questions, are outside anything a button sweep can reach.
- **Any reading of a dark body**, which would show only that some input moved the mode, not which mode was selected.

Two host-prepared, owner-decision operations would test the residue; neither is authorized by this analysis. A read-only observation of both registers with a candidate control held, in an existing maintenance session and through the reviewed read path, would bind each control to its bit at run time, without new write-capable bytes. A power-on with the mapped pair held and the built card inserted would test the reset sample directly: a normal boot leaves the position as it stands, and a dark body means some ROM mode was entered and did not hand off, with the mode-1 path writing nothing persistent and a failure writing only `0xfff88084`; recovery is the power switch or the supply, and that dark halt has been observed on neither body, the X70 halt being marked untested on the camera.

## 6. What a card for this route would have to carry (static-inference over byte-read)

If a mode-1 entry existed, the ROM stages one file from the card and jumps to RAM 0; it supplies no media writer. The vendor package's unbrick role (install firmware on a board shipped bare, reset the flash and adjustment data, E-SD-BOOT-LEAD) therefore has to be carried by `ffboot.bin` itself.

- `ffsys.bin` stays the 1024-byte two-half stock config, the bytes the built card already carries.
- `ffboot.bin` must be a complete first-stage recovery chain, not a witness: A32 code entered at RAM 0 that reads the rest from the same selected card (the ROM leaves channel 0 selected with its FAT context at `0xfff00404` and card state at `0xfff00434`, per the card report section 6.1) and carries the writer half for internal media, or an equivalent complete application route. The ROM contains no erase, program or write command to any medium.
- A mode-2 card has the same shape with the config in blocks 0 and 1 and the chain from block 2.

The X70 project's card is the working shape of that chain (reported, `research/sd-boot-card/README.md`). One variant puts the stock first-stage loader in `ffboot.bin`, so the card supplies what the internal-media staging would; the other carries a complete 31.25 MiB RAM image whose section table sets the preloaded flag, so the application runs from DRAM and patches are file edits. Both ride the ROM's unvalidated chunked read of one file to `0x40000000`, which this body's mode 1 also performs. Neither variant repairs a damaged internal medium: the loader variant reads the same flash, and the full image still reads configuration, resources 2 and 3 and section 5's compressed bytes from flash. A repair on this body therefore needs the payload to carry a writer for the `0xfff52000`/`0xfff52800` medium, which is project work (RECOVERY-WRITE-ROUTE-01) rather than a ROM capability. For the entry test the built card is the instrument already: with the mapped pair held, an entry turns the boot dark and the card's contents stay unchanged.

The built diagnostic payload (512 bytes, one 16-byte RAM store and the ROM's own halt) would run if entry were presented and would restore nothing: it can only show that a mode was entered, and its signature cannot be read back (E-SDBOOT-RAM-SIGNATURE-150).

## 7. Verdict

- **SD boot selection:** strap-only, byte-read, with the halt test corrected in section 1. Mode 1 needs `0xfff89014` bits 11:10 = 0 with the low selector not 7; mode 2 needs `0xfff98000` bits 2:0 = 4 with a nonzero high pair; any low selector 7 halts whatever the high pair reads. Both registers are sampled once per reset before any media or application access; one handler runs per boot and a failure halts.
- **Panel press:** the two sampled pads carry the Fn button and the sub-command dial push on this body (byte-read), and the cardless sweep held both of them at power-on and still booted mode 4 (hardware-observed), so the documented press route is tested-negative at the reset sample. The X70 project reaches the ROM's SD path from the same two pins held low, which shows the mechanism is available to this ROM; this body does not present it from the panel as held.
- **Reachable on a working body:** no decoded software writes the selector and no decoded key path sets it; a previous boot's register state does not carry into the sample except through the unproved electrical route.
- **What remains open:** why the sample reads 3 while the mapped pads' controls are held, an electrical and reset-time question whose only firmware-side edge is the ROM's own `0xfff89008` write; non-panel driving of the pads, including a service fixture or a companion-driven scan; the card-present hold; and the separate `SELECTOR-WRITE-01` and `RESET-RETENTION-01` route, unchanged.
- **Invalid-application fallback:** none in the decoded bytes, on either the ROM side or the record side, and the X70 path has none either: a wrong or missing card leaves the ROM's own halt, and a normal power-on boots stock.
- **Card requirement:** a card for the mode-1 route must carry the full chain in `ffboot.bin`, for which the X70 card shows the stock-loader and full-RAM-image shapes, and a repair additionally needs the internal-media writer the ROM does not contain. The built diagnostic payload is the entry instrument, and its signature is not recoverable (E-SDBOOT-RAM-SIGNATURE-150).
- **Status of the refutation: it stands**, for the route the claim needs and for the no-fallback reading, and it **narrows** in one place only, the reset-time source of the sampled value, which is why a press the firmware reads from those same bits at run time did not move the sample. The press route is now tested with the controls this body's own firmware reads from the sampled pads rather than assumed out of reach; the fallback reading is supported by the X70 material. It is not a boundary on non-panel driving of the two pads or on the low selector's writeability and warm-reset retention, which no firmware byte settles and an emulator can only model by assumption. Separating the card-gated reading from the never-arms reading would still take a card-present press, an operation this analysis does not propose.
