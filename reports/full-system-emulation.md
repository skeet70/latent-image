# Full-system emulation: distance, the T1 boot-handoff build plan, recommendation

The owner's stated interest in a full-system emulator is iteration speed: patches tested without touching the one body. This assessment starts from the bounded native runner and the boot artifacts the project already holds, maps the distance component by component, gives a verdict on the second CPU, states what the boot-ROM dump buys over a reverse-engineered boot, names the smallest useful target with its cost, writes that target's build plan (components in dependency order, per-component acceptance, the dump-comparison criterion, what the tier excludes, what it replaces) and recommends. Host-only: no camera or USB device was touched, and no simulator result here authorizes a firmware flash ([phase 3](../spec/03-phases-and-gates.md#phase-3--recovery-investigation-and-selected-function-emulation)).

## 1. What the project starts from

- Runner: a bounded Unicorn 2.1.4 Cortex-R5F native-case instrument under the X-M1 R4F-only rule. [The harness README](../emulation/README.md) owns current admission, memory, ISA, capacity and declared-substitution limits; unsupported device/coprocessor/exception behavior fails closed. This closure runner is distinct from the full-system runtime.
- Proven stock closures already executed natively: area-3 and area-2 record validators, the film-simulation offer list on stock and patched arrays, label resolution, five parameter-provenance experiments, and 36 writer block-loop cases with interruption injection against a declared medium; the largest closures run tens of thousands of instructions with no stubs (emulated, E-AREA3-VALIDATOR-NATIVE-150, E-FILMSIM-EMUL-150, E-LABEL-RESOLVE-150, E-FILMSIM-PARAM-PROVENANCE-150, E-RECOVERY-EMUL-150).
- Boot artifacts: the 16 KiB boot-ROM block at `0x80000000` (hardware-observed, SHA-1 `bed698ed1d91b5c29ce7c5d650156e6100c32cce`, `JASM_A_1` footer), the exact 1.50 DAT and its decoded images (byte-equal to the installed bytes over their extents apart from 781 runtime-written bytes, E-DUMP-RAM-150), the container media layout, the segment table and its trailer gate, an implementing decompressor grammar and byte-exact encoder, the internal-media controller register decode, the timer tick measured at 99.88 Hz, and this body's strap values (bootrom-window.md, update-validation-and-boot.md, firmware-extraction.md, E-LZ-GRAMMAR, E-LZ-ENCODER-150, E-STRAP-READ-150).
- Recovery context: the recorder rev-2 failed-boot incident and adjacent checks are complete after exact v5 rollback/readback and reported ordinary operation. R2 and scoped R3 are demonstrated; formal R4 acceptance remains unclaimed. [Recovery status](recovery-status.md) owns coverage. Earlier dark trials did not establish physical entry and their authorizations remain consumed.

## 2. Component-by-component distance

| CPU identity | R4F-class inference; MIDR never read by the firmware, cache-identification registers are (CLIDR/CSSELR/CCSIDR) | cache-ID reads that return values the code can use, and an ID surface that does not change code paths | engine gap is bounded but real (spike below) |

The three verdict classes matter for cost. Components with a model already, or with all information held, are engineering: the boot path, decompression, the media read path, DMA, the interrupt banks, timers, the SD path. Components that lack information are the media physics, the display/GPU block, and everything beyond the menu on the way to record mode. The project's own rule already forbids fixtures from depending on behaviour an R4F lacks, and the runner refuses each such feature it can reach (principles, Scope and evidence), so an expanded profile inherits the same evidence obligation.

Two boundaries deserve naming. First, the runner is not a smaller version of a system emulator: its contract is one function closure over declared memory with containment checks and fail-closed device access, while a boot model inverts the defaults so that everything runs and only devices are modelled. Second, the current harness is not size-limited: the area-2 validator closure runs about 52,000 instructions per case with no stubs, and the film-simulation closure runs a 0x6234-byte function through recursion (emulated, E-AREA3-VALIDATOR-NATIVE-150, E-FILMSIM-EMUL-150). What a full system adds is context (interrupts, other tasks, device timing), not reach.

## 3. The second CPU: verdict

Our images describe a two-processor boot, not a maybe. One 256 KiB load stages both boot records into low RAM: record 1 at 0, record 2 at `0x10000`, and the ROM jumps only to record 1 (byte-read, bootrom-window.md section 9). Both records read the ARM debug register discriminator (`mrc p14`, DBGDSAR against `0x4003`) and select loader id 0 (`0x40000`) or id 1 (`0xd0000`) for the apparent processors; record 1 copies both loader records and decompresses image 4, record 2 initializes companion peripherals, reads a companion record, and hands off to shared segment id 1 (byte-read, firmware-extraction.md, update-validation-and-boot.md).

The synchronization is reciprocal and load-bearing: record 1 initializes the cells `0x40020000`/`0x40020004` to `0x22b`, clears its own cell and waits for the peer's; record 2 writes its cell and waits while `0x40020000 == 0x22b`; both waits can hang indefinitely (byte-read). Both loaders are resident in captured RAM (hardware-observed, E-RAM-PROBE-150), and loader B carries a complete second kernel: its header publishes a kernel interface at `0x400ddaa0` where loader A publishes `0x4004dae0`, its own timer block matches loader A's apart from base immediates, and application wrappers dispatch to the calling core's kernel (byte-read, reports/auto-act-arming.md section 13.2). The reported platform lead names the same arrangement: dual-kernel micro-ITRON and a CPU1-starts-at-`0x10000` reading (reported, E-XM1-PLATFORM-LEAD).

The release side is identified in our own bytes, byte-read from the record-1 and record-2 decompilation: record 1's `FUN_00001e4c` sets both cells, copies `0x3e8` bytes from RAM `0x10000` to `0x7fff0000` (the alias of physical `0x3fff0000`, the second core's vector store), writes `0x01000000` to bank-1 `+0x8c`/`+0xac`/`+0xcc`/`+0xec`, initializes storage, reads the segment table and the trailer, copies both loader records, decompresses image 4 and fills its bss, and only then clears its own cell and waits for the peer's; record 2 writes `0x40020004 = 0`, waits for `0x40020000` to leave `0x22b`, looks up shared segment id 1 and hands off through the words at `0x14c80`/`0x14c84` (byte-read, `decode/ghidra/boot-40048.c` FUN_00001e4c/FUN_00001d08/FUN_00002250 and `boot-50048-10000.c` FUN_00011cc0; E-BOOT-RELEASE-PATH-150). The sibling reading (`../x70view/emulator/board.py`, its CPU1 release watch on bank-1 `+0xcc` bit 24) labels the write the second core's release (reported, E-X70-SOC-LABELS-150); T1 takes it as a declared profile entry whose consequence, CPU1 executing its own staged record, is observable in the run.

Verdict. The second CPU is required at boot only as a rendezvous partner, and its side is small: a single-engine model that runs record 1 must satisfy record 1's peer wait, and record 2's own path is the staged `0x4c80` bytes plus a companion read and a handoff, executable on the same engine layer. T1 therefore plans two contexts of one engine over one backing store, with the release write starting CPU1 at the reset vector its own staged table names (`0x11800`); the fallback if the second context's cost grows is the declared peer script, which must then be a named profile entry and its writes marked as substitutions. Whether a single CPU reaches a useful state is a separate question with no answer in the images yet: the one application task whose kernel state is identified, `mujin`, is under loader A's kernel (the `0x4005476c`/`0x40054770` pair, byte-read, reports/auto-act-arming.md section 13.2), no mapped evidence assigns any task or the menu/develop paths to loader B's kernel, and the per-core interface makes a wrong-core call fail visibly (the wrapper selects the current kernel through the interface pointer), so a single-kernel model can be tested for the gap rather than argued about. What must not happen is silently ignoring either wait, because an emulator that returns whatever the peer would have written becomes an assumption, not a model.

## 4. What the boot-ROM dump buys that a reverse-engineered boot would not

- The emulator executes the vendor's own first stage. The 16 KiB block is this body's ROM content, captured from the body and stable across sessions (hardware-observed, E-BOOTROM-PROBE-150, E-BOOTROM-DISCRIMINATOR-150), so a divergence in boot emulation is a device-model bug, while a reverse-engineered boot would make every divergence ambiguous between a wrong model and a wrong understanding.
- It is the device specification. The configuration apply, the media controller's init, page select, block read and paged loader, the DMA descriptor words, the handoff stub and the strap decode are byte-read from the same bytes the model must satisfy; the fail-closed MMIO discipline can be driven by that access census instead of guesses, including the unbounded waits at `0xfff88080` bit 16, `0xfff88038` bit 24 and `0xfff01090` bit 28 that any model must resolve (static-inference, E-CONFIG-APPLY-150).
- It closes the first stage entirely. The block is the unique content, it repeats at every probed base up to 1 MiB, there is no distinct second-stage loader, and the footer marks its end (hardware-observed, E-BOOTROM-EXTENT-150, E-BOOTROM-DISCRIMINATOR-150); a reverse-engineered boot would leave the search space open.
- It makes the recovery routes executable offline. Modes 1 and 2 are ROM code with a decoded FAT/raw parser and a built card image, so the card can be exercised against the body's real parser on a host; the entry gate itself stays a hardware question and no emulator result changes it (byte-read, bootrom-window.md sections 1 and 3; E-SDBOOT-CARD-IMAGE-150, E-SD-BOOT-ENTRY-HOLD-150).
- Limits: the dump supplies code, not device semantics, media physics, or ROM die size, and it says nothing about the discriminator's actual return values per core, only the constant the code compares with.

## 5. Engine reality check

A bounded host spike against the pinned engine, synthetic instruction words only, no X-M1 code (emulated, one run, 2026-10-09):

- Unicorn 2.1 has no Cortex-R4 or R4F model; R5F is the only R-profile model, as the runner already documents.
- `mrc p14` (the boot records' per-core discriminator) is an invalid instruction in the engine: the read form ends emulation with `UC_ERR_INSN_INVALID` under the R5F model and with no model selected, and the write form does the same under R5F. A boot model on this engine must intercept or patch that instruction, which is a declared substitution on a boot-critical decision.
- CP15 is partial and sometimes silent: `mrc p15 c0,c0,0` returns the R5F MIDR `0x411fc153`, `mrc p15 c1,c0,0` returns 0, `mrc p15 c2,c0,0` is invalid, `mrc p15 c13,c0,0` returns 0, and `mrc p15 c0,c1,0` (CTR) returns without writing the destination register. The firmware's cache-identification walk reads CLIDR/CSSELR/CCSIDR (static-inference, firmware-extraction.md CPU profile), so silent or wrong values there feed real code.
- Exceptions are delivered to the hook, not taken: `svc #0` raises interrupt report 2, the PC advances past the SVC, and no mode switch or vector fetch occurs; `msr cpsr_c` does change mode and `wfi` is a no-op. A full-system model on this engine implements exception entry, banking, return and interrupt injection in the harness.
- MPU and cache maintenance are accepted as no-ops (`mcr p15 c6`, `mcr p15 c7`), which is usable only under an explicit coherence assumption.

None of this is disqualifying, and it is the same engine the project already trusts inside its bounded contract. It does mean that "use Unicorn" is not itself a plan for the system layer: the system layer is project-authored C or Haskell either way, validated against captured state.

## 6. The reported X70 emulator and the collaboration option

The 2026-10-09 reports are recorded as reported leads, not as evidence about this body. One reporter has a full-system emulator that boots unmodified X70 firmware from the DAT into record mode, with the bootrom captured from memory, two CPUs with cache models, a functional NAND model, the interrupt controller and the boot path modelled, and HDMI output captured; the same reporter counts about eight systems with a functional model. The other reports the SD-card boot trick as an unbrick route and says he failed to emulate the VIC and gave up on two VICs and two CPUs. Neither is an X-M1 artifact.

What this body's bytes do with that lead: the two-CPU arrangement, the bootrom-from-memory technique, a NAND-class media model and an interrupt controller match the component list this assessment derives independently (sections 2 and 3), so the report is a plausibility statement for the family and no X-M1 fact. It does not refute anything, and nothing in our firmware contradicts it. The one wording worth correcting for our body is "eeprom": our decoded application medium is page-addressed with per-512-byte spare bytes, 128 KiB blocks and a bad-block remap (static-inference, bootrom-window.md section 8), so the EEPROM vocabulary comes from the sibling documentation and the fffw tooling, not from this medium's decoded behaviour.

The sibling emulator supplies inspectable architecture and device-model references. jitl (justjake) explicitly permitted redistribution with credit (E-X70-REDISTRIBUTION-PERMISSION-150), following the earlier personal grant (E-X70-GRANT-150). [Licensing](../LICENSING.md) and [reference terms](x70-emulator-reference.md#12-the-authors-grant) preserve that scope without silently relicensing the inherited implementation. X70 1.10 firmware and per-unit RAM captures are not inputs. The target-addition experiment uses our X-M1 bytes; its findings do not become X-M1 facts until the stated byte comparisons hold.

Source inspection on 2026-10-09 found a ROM capture hash-identical to ours and device models at the blocks our instructions decode (E-X70-SOC-CROSSCHECK-150, E-FFF02000-CALLSITE-150). The clock/GPIO/system/DRAM/reset, timer, decompressor, media and fill/copy models are research references. The `0xfff01000` PHY-class start/ready reading and `0xfffb3000`/`0xfffb4000` interrupt-controller reading are sibling-derived, not established silicon identities. In that clone the ROM, DAT and mapped-section files were Git LFS pointers; our independently captured ROM and owner-supplied X-M1 DAT supplied the experiment inputs. Model adaptation preserves evidence scope and requires separate redistribution review.

**2026-10-09, target-addition executed:** the isolated upstream runtime accepted our stock 1.50 DAT and manifest and executed the actual captured ROM's mode-4 load to record 1's reset-entry branch target `0x1854`, stopping at 166,046 instructions with the 131,072-byte manifest `boot` span, half of the 256 KiB the ROM loaded, equal to the DAT export (E-X70-TARGET-ADD-150, emulated). [The reference assessment, sections 5.7 and 5.8](x70-emulator-reference.md#57-prepared-x-m1-scratch-run) records preparation, commands, the initial environment/input-path stops and the positive terminal. No device-offset or Rust-engine change was needed before that boundary. It is not T1 acceptance: CPU 1, CP14 discrimination, later loaders, kernel handoff and the dump comparison below were not exercised. The author's Rust engine and Python models remain an external scratch tool; only the Haskell manifest exporter is added to this project's tracked code.


## 7. T1 build plan: the boot handoff

T1 makes the mode-4 boot of this body's ROM and container executable on a host and accepts its state against the captured dump. It is the tier the reference re-prices to days of work because the ROM is our own bytes and every wait has a named counterpart; its product is one documented run plus its comparison and a small regression suite, not a general emulator. The plan is ordered; each component's acceptance is a host check that fails rather than a demonstration that passes by construction.

### 7.1 Inputs and declared profile

The run takes only pinned inputs: the 16 KiB ROM block (the checkout's ROM capture is a Git LFS pointer in this clone; our block is hash-identical to the pinned one and substitutes for it); the media store the mode-4 path reads, which is the DAT-derived media bytes (config block at media 0, records at `0x40000`/`0x50000`, segment table at `0x140000`, trailer at `0x24a0000`); the two loader records; images 4, 5 and the plain image as decodes; this body's mode-4 strap values (`0xfff89014` bits 11:10 = 3, `0xfff98000` bits 2:0 = 1, hardware-observed, E-STRAP-READ-150); the retained companion bytes the peer reads (register `0x6000` holding the boot-reason sample, and the sixteen bytes behind the `0x5000`..`0x5f00` reads), pinned from the same boot's high-known capture; and the dump segments themselves (E-DUMP-RAM-150).

Everything that is not a pinned input is a named profile entry printed with every result: the discriminator return per core, the CPU identity and cache-ID values the firmware reads, the media read model's declared semantics (the `+0x404` accept condition, no bad unit inside the read path), the timer base and counter behaviour, the release rule, the interleaving slice, the initial RAM state, the one-backing cache assumption, and the exclusions of 7.4. A profile entry that is a sibling-derived reading keeps its label and its evidence status: adapting the reading from the working sibling is allowed, promoting it to our fact is not (E-X70-GRANT-150), and no result is valid without its profile digest.

Under [phase 3's expansion rule](../spec/03-phases-and-gates.md#3b-native-function-harness) T1 names its experiment (the accepted boot-handoff run and comparison below), its validating traces (E-DUMP-RAM-150, E-STRAP-READ-150, E-BOOTROM-PROBE-150/E-BOOTROM-EXTENT-150, E-RAM-PROBE-150) and its finite completion criterion (section 7.5). The existing bounded runner and its cases are untouched: the system layer is a new binary, not a widening of native-case admission.

### 7.2 Components in dependency order

Each component states what it must do and the observable that accepts it. Names are the intended new targets in the existing `emulation` package; the C/Haskell split follows the current rule, with C as the Unicorn interface and execution authority and Haskell for the models, the driver and the comparator. Device transactions cross the C/Haskell wire as bounded messages; bulk transfers (decompression output, fills, block copies) stay inside the engine or cross as bounded blobs; ordinary instructions and RAM stores make no callouts.

**S1, engine layer, two contexts (`//emulation:system-runner`, C).**
Must do: run two Unicorn contexts over one backing store, with the map of the touched span (RAM through the loaders and images, the `0x40000000` alias of low RAM, the second core's vector store at `0x3fff0000` reached through `0x7fff0000`, the SRAM window at `0xfff00000`, and the MMIO windows of the boot's census); privileged modes and CPSR/SPSR banking; exception entry and return with the vector fetch; IRQ injection; the `mrc/mcr p14` discriminator intercept; the CP15 accesses the boot makes (the CLIDR/CSSELR/CCSIDR walk, `c1`, the MPU `c6` writes, `c9,c1,1`, `c15,c5,0`), each answered from a declared identity table, with the R5F MIDR and CTR values unreachable because the firmware reads neither; MPU and cache maintenance as declared no-ops under the one-backing assumption; `wfi`; an ordered store journal with instruction addresses; instruction and wall budgets; checkpoint and restore; and an MMIO hook that dispatches declared model registers and fails closed, naming the address, on anything outside the census.
Acceptance: an independently derived fixture set passes exactly for mode switches, exception entry and return, IRQ injection at a configured line, the intercept's two return values, and a write-through-the-alias readback; the R4F-only list stays refused or declared (A32 divide, MPIDR and the multiprocessing extensions, R5F ID values, a 16-region MPU, R5 TCM/cache register semantics), with all declared identity values printed in every result; a checkpoint at the record-1 entry with suffix replay to the stop reproduces the identical stop state and journal over the compared extents; from reset the pinned ROM runs to its mode dispatch with no fail-closed access and dispatches mode 4 for the pinned straps; the existing `native-runner-tests` suite is untouched and stays green.

**S2, system, strap, clock, reset and PHY models (`//emulation:system-models`, Haskell).**
Must do: resolve the ROM's three unbounded waits by declared transitions (clock `0xfff88038` bit 28 request then bit 24 ready; clock `0xfff88080` bit 16 ready; PHY `0xfff01000` start bit 0 then `+0x90` bit 28 ready), and carry the rest of the ROM's block traffic: `0xfff89000` port 0 bits 11:10 for the mode detect and the pin-mux writes, `0xfff98000` strap/mode word and the handoff write, `0xfff99000` DRAM writes with the `+0x04`/`+0x08` polls and the `+0x1c` read-modify-write, the `0xfffb2000` five reset offsets, `0xfff98208`, and the 146-word PHY window. The register set is the ROM's access census, which is a pinned artifact from the decode.
Acceptance: the mode detect resolves to 4 for the pinned straps; the config apply completes with the seven stock pair writes at their pinned values, each of the three waits released by a model transition and none pending at the stop; a negative fixture with a flipped strap resolves to a different mode and the run reports it; and the trace shows no model register read before it was written in the run or declared as an input.

**S3, internal-media read model (`0xfff52000`/`0xfff52800`).**
Must do: a page store built from the pinned media bytes in mode-4 geometry (2 KiB units, 64 units per page index, the 512-byte window at `+0x400`); init and device select 1; the page-select loop's six-unit `+0x404` accept (bits 8-15 all `0xff`); the block read's `+0xc8` bits 29:28 test; the done/ack pair at `+0x54` (bit 0, then write `0x000e0001`); `+0x58`, the parameter and command words; and the companion `+0x84`/`+0xa0`/`+0xa4`/`+0xa8` DMA front end with the `0x401000` tag.
Acceptance: the marker scan reads both stock config halves into `0xfff00004`/`0xfff00204`; the 256 KiB load stages media `[0x40000,0x80000)` to `0x40000000` byte-equal; the loader reads equal the pinned records; the trailer read yields `0xaaaa` and a flipped trailer takes the record's halt branch; a unit whose `+0x404` bits are not all ones takes the ROM's failure path with `+0xe8 = 0x00030003`; no access outside the census occurs.

**S4, decompressor engine (`0xfff43000`).**
Must do: the register-level engine (`+0x04` start, `+0x40` source, `+0x44` length with bit 24 mode, `+0x48` destination, `+0x4c` output count, `+0x88` the status and ack word, `+0x8c` cleared at session start) consuming the stream in `0x4000`-byte feeds after the `0x14`-byte header, writing the pinned images with our grammar.
Acceptance: the image-4 output over its destination equals the pinned decode byte for byte and the ack and count reads match the record's polling order; the same model fed the image-5 and plain-image records reproduces their decodes exactly (engine regressions, outside the T1 run).

**S5, fill/copy engine (`0xfff02000`).**
Must do: the record's bss fill through the register-level model decoded from the call site (byte-read, E-FFF02000-CALLSITE-150): `+0x00` a descriptor pointer to the eight value words at `0x400042c0` (through the alias), `+0x04` destination, `+0x08` word count, `+0x0c`/`+0x10`/`+0x14` and `+0x30`/`+0x34`, `+0x28 = 5`, `+0x2c` the mode word, with completion polled at `+0x24` bit 6.
Acceptance: the fill writes zero over `0x0089ec00 + 0x352e00` and changes nothing outside it; the completion bit rises exactly once per transfer; a destination outside the declared map fails closed. The sibling fill/copy model's register set at the same offsets corroborates the reading as a reported lead, not as our fact ([the reference assessment](x70-emulator-reference.md) section 3.2, E-X70-SOC-CROSSCHECK-150).

**S6, interrupt banks, the release and the timer.**
Must do: the two banks at `0xfffb3000`/`0xfffb4000` accepting the config apply's conditional writes, both records' `+0xc00` resets, and record 1's four `0x01000000` writes at bank-1 `+0x8c`/`+0xac`/`+0xcc`/`+0xec`; the release rule, declared: the bank-1 `+0xcc` write starts the second context at the reset vector its own staged table names (`0x11800`), after record 1 has copied `0x3e8` bytes from RAM `0x10000` to `0x7fff0000`; the timer block `0xfff91000` with counter/reload/control, accepting the records' program writes and taking the measured base (`[0xfff91000]/1875`, 99.88 Hz, E-LOG-TICK-SOURCE-150) as a declared input.
Acceptance: the release fires exactly once, at the byte-read site, and the second context's first fetched word is the staged vector's target; the vector-store copy equals the staged record's first `0x3e8` bytes; the rendezvous cells leave `0x22b` in the order the two records define and the stop is reached; a run with the second context held fails the peer wait and reports the cell address; no interrupt is delivered before the stop unless the journal shows the path unmasked it.

**S7, companion bank and the peer path.**
Must do: the command/response engine the second record drives (`+0x1c` command, `+0x18` response) for its register-`0x6000` read into `0x400a00c0` and its sixteen one-byte reads at `0x5000`..`0x5f00` into `0x400a00d0`..`0x400a00df`, with the retained values pinned from the same boot's high-known capture as declared inputs; record 2's own reset path (state and MPU init, the peripheral predicates, the `0x400a0140` flag, the `0x13b80` RAM structure) executed as its real bytes; its shared-id-1 lookup and handoff as the record's own code.
Acceptance: the peer's reads land the pinned values in the pinned cells and its own validity test (byte 14 = `0xaa`, byte 15 = minus the first-15-byte sum) passes on them; a corrupted retained byte is refused by that test; the peer reaches its own handoff, or the run reports its PC at the stop; both contexts' stop tuples appear in the result.

**S8, boot driver and stop rule (`//emulation:system-boot`, Haskell).**
Must do: fix the strap inputs and the media store; start the first context at the ROM vector base with the pinned reset state and the second at the release; interleave the contexts under a declared slice rule; stop each context at its own handoff transfer, and for the first context that is the final transfer of record 1's reset path through the word at RAM `0x4300` with `r0 = *(0x61c40c)` (byte-read: `0x4300` receives the loader record's header word at `+0xc` and `0x4304` receives `*(0x61c40c)` in `FUN_00001d08`, and the reset path's last instructions are the supervisor switch at `0x183c` and the indirect transfer after it); and emit the profile digest, both stop tuples, the write journal, the final image over the compared extents and every pending model wait.
Acceptance: the stop is reached within budget from reset; a second run with a different interleaving slice produces the same stop state and the same compared bytes; disabling or holding the peer fails the wait rather than producing a value; the result prints each context's instruction count and stop site.

**S9, dump comparator (`//emulation:dump-compare`, Haskell).**
Must do: verify the dump segments against their journal hashes and segment-complete records, apply the pinned extent and attribution tables, and produce the per-byte three-way report of section 7.3 (incoming byte A, captured byte D, model byte M, model write journal W, class, verdict); refuse to report when a compared extent holds a difference the attribution set does not cover.
Acceptance: run on the dump alone it reproduces E-DUMP-RAM-150's recorded correspondence exactly (the 781-byte difference set over the five artifacts, the segment table's five runtime bytes, and the bit-30 alias result at `0x409c2800`); a negative fixture that perturbs one model byte fails with that byte, its class and its triple named; a negative fixture that removes one attribution entry fails as underdetermined rather than passing.

### 7.3 The dump-comparison criterion

The acceptance is not a byte diff. The capture is the later state of the same boot: the 21 dump-ram sessions read their segments at different times in one maintenance boot (per-request median 1.00 ms, sessions spanning from seconds to minutes), and the application ran between the boot handoff and those reads, so the dump holds the post-application state over every extent the application touches, while the model stops at the handoff. Equality is therefore defined per byte, at one declared stop, by the capture's own write-time attribution relative to that stop.

The compared extents are the transport's fixed segment table ([DumpRam.hs](../transport/FujiAF/DumpRam.hs)), the same table the capture was planned from, and inside them:

| Class | Range | What equality means at the stop |
| --- | --- | --- |
| 1, strict | loaders `0x00040000`-`0x0004db00` and `0x000d0000`-`0x000ddb00`; image 4 with the segment-table copy `0x0061c000`-`0x0089ec00` | model byte equals dump byte for every byte outside the pinned post-stop set; inside it, model equals the incoming record or decode byte, and the byte is listed with its attributed writer (loader A's four bytes at `0x0004dad4`; image 4's 542 runtime bytes in six blocks; the segment table's three done flags at `0x0061c1c0`/`0x61c1d8`/`0x61c1f0`). `0x0061c188` is record 1's own publication and must hold the dump value `0x00004310`, which the record's handoff code writes before the stop |
| 2, derived | image-4 bss `0x0089ec00`-`0x00bf1a00` | model equals the fill's value, zero over the declared `0x352e00` span, written by the record before the decompression; the dump's bytes there are all post-stop writes and are listed, not compared |
| 3, transported input | the retained cells `0x400a00c0`, `0x400a00c4`, `0x400a00cc` and `0x400a00d0`-`0x400a00df` inside high-known `0x400a0000`-`0x400c0800` | model equals the pinned retained input (cells `0x400a00c0` and `0x400a00d0`-`df`) or the record's own value (`0x400a00c4` = 0, `0x400a00cc` = the peer's validity byte); the first group is marked self-consistent transport, not prediction, because the input's provenance is the dump itself |
| 4, excluded | the rest of high-known (`0x400a0800`-`0x400c07f4`, `0x409c2800`-`0x409c3000`, `0x41acd800`-`0x41acdc00`); the id5 image and bss and the plain image extents (`0xbf1a00`-`0x10e3900`, `0x1100000`-`0x1460000`, `0x1460000`-`0x171bf00`); the filler inside the loader ranges past the records; everything outside the table (low RAM `0`-`0x3ffff`, the sync cells, the loader entry words, the vector store) | listed as post-stop or not yet produced; the low-RAM products (staged records, sync protocol, skip list, loader entry words) are checked instead against the media bytes and the records' own code |

Equality, byte by byte, over classes 1 to 3, with A the incoming byte (the pinned record, decode or segment-table payload byte, or the declared fill value), D the captured byte, M the model byte at the stop, and W the model's last write at or before the stop:

1. Every byte with M ≠ A must have W defined and equal to M: the model changed nothing it did not write.
2. Where D = A, M must equal A. Where D ≠ A, the byte must be in the pinned dump-difference set for that extent; the comparator refuses the run otherwise, because an unattributed difference would make the comparison underdetermined.
3. A difference byte whose attributed writer ran at or before the stop must have M = D and W = M: the model must have executed that writer. One whose writer ran later must have M equal to the stop-time value (A, or the class-2 value) and appears in the result as post-stop.
4. Every model write into a compared extent must be either confirmed by the capture or attributed to a later writer; a model write the capture contradicts fails the run.
5. Zero unexplained differences is the pass condition. The result lists every difference with its class, A, D, M and attribution, so a shrinking allowance cannot hide an error: the attribution set is pinned and closed, and the comparator fails if the dump's differences exceed it.

The dump's own limits carry over: the capture is one boot (the runtime values in the 781 bytes are single-boot snapshots except the 66 bytes in the `0x00828500` window that three boots share), so class-1 equality is claimed only over bytes whose value the artifacts and the model determine, and every byte whose value is boot-local appears in the attribution set with that label.

### 7.4 What T1 excludes, and why

- Media physics: spare-versus-window semantics, bad-mark persistence, erase and program behaviour, the `+0x404` field's identity and owner, and the media technology name. T1's media model is a declared functional read model over the pinned bytes, the run writes nothing media-side, and these are the questions the project's bytes do not answer (unproved, UPDATE-01 work 2).
- Any write to media, and the updater, S-record and writer paths: not on the mode-4 path; the tier's container is read-only.
- The SD controller and ROM modes 1 and 2: mode 4 needs neither; the SD routes stay as decoded under R1, and no emulator result touches the entry gate or the recovery ladder.
- Display and GPU, sensor, lens, audio, USB and the service session, and the remaining per-body peripherals: T1 executes none of their code, its stop precedes the kernel, and the display/GPU block lacks the information a model would need.
- The kernel, RTOS, scheduler, kernel-side interrupt delivery, image 5 and plain-image loading, image 4's own init and flashloader, the jig/service path and the settings and ending machinery: T2 and T3.
- The second core's kernel: CPU1 executes its record to its handoff and stops; loader B's entry is a stop, not a start.
- Cache and timing fidelity: one backing store, declared no-ops for cache maintenance, instruction-count time. The boot path is poll-driven, so the stop is timing-independent; no duration of the model is claimed to match silicon.
- The port decision itself: T1's plan builds our own engine, models and comparator, adapted from the sibling's working semantics where that is the better engineering; whether X70-TARGET-ADD-01 instead ports this body's DAT into their framework is that experiment's question, and its result would replace S1 to S8 rather than extend them ([the reference assessment](x70-emulator-reference.md) section 5.6, E-X70-TARGET-ADD-PLAN-150). Fujifilm's X70 firmware and another body's captures stay non-inputs under the grant (E-X70-GRANT-150).

## 8. What T1 replaces and what it settles

Once the tier exists, the project stops spending camera sessions on boot-stage state: the probe-ram class (E-RAM-PROBE-150's sessions and any future session whose question is what the boot or its loaders left in RAM), the RAM-window re-reads used as boot-state cross-checks, and any future jig dump round whose purpose is the boot's product rather than an ending experiment. The boot-path share of the writer-attribution work also moves to the host: the model's journal attributes every pre-stop writer over the compared extents, and a byte absent from the journal is proven written later, which settles which of the 781 runtime-written bytes are not boot-record writes (loader A's four, the segment table's flags, image 4's 542, image 5's 233 and the plain image's two). The kernel's share stays for T2.

Against hardware-observed inputs, the run would settle as emulated findings: the record-1 path order and the handoff state; the second core's release, discriminator branch, vector-store copy and rendezvous; the `0xfff02000` call-site register set and the fill's bss product; the media read path, trailer gate, segment-table lookup and decompressor engine executed over the pinned bytes; the ROM-side use of the `+0x404` accept field; and the PHY block's start/ready use. It does not settle the `+0x404` field's identity, the media's physical behaviour, the `0xfff01000` block's class, or the interrupt banks' semantics as hardware fact: those stay declared profile readings of which the run tests only their consequences.

What it does not replace, in any tier: the captured correspondence itself; image-pipeline questions (rendering, JPEG output, film-recipe acceptance); lens and sensor behaviour; USB and service-session behaviour; media physics; the persistent-install acceptance on the body; the settings-preservation question, whose path is image 4's, not the boot's; and boot-to-USB timing, which needs the kernel and the service stack. T1 is a boot-state instrument, not a camera.

## 11. Recommendation

**Recovery-bootstrap boundary:** section 11.4 defines the primary native load-to-rollback slice, with the recorder DAT as declared logical media and the saved recovery-card bytes as SD input. Section 11.5 records execution. Its endpoint is an exact native stop and firmware-produced bytes, not an emulator remaining dark. T1's full two-core captured-dump acceptance is separate. New project tooling/models use Haskell/Rust under [current principles](../docs/principles.md#implementation-and-build); the existing C engine is an implementation fact, not the default language for new model work.

**Answer:** the exact proposed post-install logical firmware contents can be installed into a functional read model, including the recorder's changed image-4 call and plain-image payload. The actual failed body's complete post-flash state cannot be recreated from the material held. The completion screen and verified card-side DAT identify the intended install, not a post-install raw-media readback. An emulator can trivially remain dark because it has no display model, because it hits an unsupported register, or because a fixture forces an infinite wait. None reproduces the incident causally. A recovery-useful model reports the selected ROM route, transfer origins and lengths, native stop PC/ABI, loaded tap word, changed bytes, and the exact unsatisfied device wait or unsupported access. At each accepted boundary the observed bytes must come from firmware transfers, not manifest preloads or injected “successful init” returns.

The model cannot establish which physical button press selects a ROM route, pin electrical timing or card-controller compatibility, even when it executes a mode selected by explicit fixture straps. The native trial's darkness does not select among those causes. No emulated result advances R2-R4 or authorizes a repeat, button sweep or persistent write.

### 11.4 Smallest executable target and finite stop

`//emulation:recovery-bootstrap` is a separate bounded instrument, not a widening of `native-case` or a full camera emulator. Haskell selects inputs, logical media/card images, profiles and comparisons; the existing C engine calls Unicorn and executes the primary bootstrap. Its stop is before peer rendezvous/kernel startup. The decoded native dependency chain is `0x1e4c` storage/table/marker initialization → `0x1d08` loader copies and `0x2250` BSS fill/id4 decompression → original close at `0x1fdc` → primary rendezvous clear at `0x1ff8` and peer wait. This is earlier than T1's kernel-handoff stop; section 11.5 records the exercised contract.

Only these missing implementation pieces are required for that target:

1. **Input/profile closure:** accept explicit stock, RC0 and recorder inputs with their corresponding table/decodes; install the complemented DAT tail into a read-only logical medium; serve the exact existing recovery-card sector image. Keep per-unit historical inputs, clean-media assumptions, initial RAM and reset/MPU identity explicit. Fail on attempted persistent-media writes.
2. **Privileged primary engine and ROM reset context:** system/SVC state, CP14 discriminator-zero binding, the actual ROM MPU/cache setup, low/high ROM mapping and low/bit-30 RAM aliases. Execute the reset path rather than skipping to its dispatch without the context it establishes. Unknown CPU features fail closed; the R5F ISA proxy remains labelled.
3. **Boot polls and native transactions:** only the clock/GPIO/system/DRAM/reset accesses, media init/select/read/ack and DMA, fill engine and decompressor that the ROM plus `0x1e4c -> 0x1d08 -> 0x2250` path actually issues. Bind offsets/commands to X-M1 instructions; adapt the sibling laws rather than derive an entire SoC. Preserve native marker/table/error branches. The first unsupported offset/command ends the run, with source/caller PC, rather than acquiring unrelated application peripherals.
4. **Mode-1 SD0 read model:** the captured ROM's initialization, FAT sector PIO and DRAM SDMA transfers over our saved sectors. Declared card-ready/latency and strap inputs drive the model; no physical reader or card is involved. No SD application/filesystem or mode-2 model is required at this stop.
5. **Execution origin, tap and stop accounting:** record full staging bytes and native-loaded outputs, execute the linked rollback bytes, and stop before the store at `0x1ff8` after the original close returns. Record CPU1's release request/vector copy but hold its execution as an explicit primary-only substitution for this minimum. Do not synthesize peer acknowledgment or continue past its wait. Removing that substitution requires the actual record-2/companion input path and two-context comparison, which belongs to T1 rather than this acceptance.

Acceptance is one paired stock/recorder mode-4 load control and one recorder-media mode-1 SD rollback run reaching the declared stop, with the full 256 KiB staging span matching its selected source, both native loader copies matching their source spans, id4 matching its own emitted decode before rollback, BSS zero over its declared extent, and only the expected tap restoration after load. The continuation must preserve its stock ABI and no persistent-media program/erase may occur.
