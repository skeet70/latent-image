# What is publicly known about Fujifilm maintenance and service modes

Scope: a documentary survey, run 2026-10-08, of public material about Fujifilm service/jig/maintenance modes and their USB interfaces, to derive a search list for the X-M1 1.50 firmware. Every claim here is **reported** about another body or an unversioned public text, attributed to its source, unless a line names a project evidence id or a private-analysis pointer. No durable claim about this body is made; nothing was sent to a camera and no USB device was touched.

Sources were read at the addresses in [S20-S31](../spec/09-sources.md#s20). Where a source is a public repository, the commit read is named; where it is a wiki or a vendor PDF mirror, the read date is named and the text is unversioned, so a later revision may differ. The owner's X-M1 manual procedure chapters are surveyed in [reports/service-manual-procedures.md](service-manual-procedures.md) ([S31](../spec/09-sources.md#s31)); the X-M1-specific confirmation and extension it supplies is folded into the sections below and marked as reported from that document.

## Baseline the X-M1 side already binds

The claims below are checked against work already bound in this project, listed here as the yardstick and not restated as findings.

- Transport: control opcodes C0 (open), D0 (command), D1 (result), C4 (close); fixed 12-byte control data with opcode, big-endian length and big-endian session; a 32-byte request; a 128-byte or 292-byte reply (`transport/README.md`, E-SERVICE-QUERY-MAP).
- Request classes: `0x00150000` tag 4 identity read; `0x1a0002` function 2 config read and function 3 config write; `0x200001` function 1 debug log, function 2 RAM read, function 3 RAM write, function 5 text dispatch (E-SERVICE-READ-MAP, E-DEBUG-ERROR-MAP).
- Limits: `0x200001` accepts functions 1 to 5 only and lengths 1 to 256, and every `0x200001` routine returns 2 while adjustment-cache byte `0xf7` is zero (E-DEBUG-ERROR-MAP).
- Config write: function 3 stores into the adjustment cache first, and only a request whose start index is `0x80` then scans the 144-record whitelist at `0x00dc7a84` and posts the matched value to queue 7 (E-ENABLE-COMMIT-150, E-RAW-MEDIA-READ-150).
- Eleven reviewed operations exist as closed commands (`transport/README.md`), and the whitelist table with each record's row, actions and effect class is parsed in `private-data/analysis/x-m1-1.50/end-setting/followup/raw-media-read.md` section 9.1.
- Maintenance mode `0xb` dispatches no menu or shutter action and draws nothing (E-SERVICE-SHOOT-150, E-JIG-OBSERVED).

## What maintenance mode is for, in the factory documents

The W3 manual [S24] documents the purpose and the full workflow, and the X-Pro1 manual [S25] shows the same workflow on an X-series body.

- Jig mode is entered with the camera powered on from a PC connection while the shutter button and the up key are pressed, and the check for readiness is a lit green LED; the W3 manual shows this in both the BOOT-mode path (shutter button, LED red blinking then green) and the normal jig path (shutter and up, LED green) [S24]. X-Pro1 shows "power ON while pressing the shutter button and up key" with the LED lit green [S25]. This is the same entry the X-M1 manual documents (E-SERVICE-MANUAL, reported) and the project observed on 1.00 (E-JIG-OBSERVED, hardware-observed).
- The adjustment software is a Windows program the manuals name HyperFFW, launched from a START menu group, and its menu bar carries Script (Open/Load/Execute/Pause), Mode, Watch variables and Tool commands, all marked "Do not use" for the operator [S24, S25]. The presence of script and watch commands implies a per-model or per-firmware script drives the camera over the connection.
- MAIN PWB Initialize is the first step after replacing the main board: it downloads firmware, resets the flash ROM, formats the internal memory and resets all adjustment data to defaults, and the W3 manual warns that running it on an unreplaced board destroys the adjusted data [S24]. It needs a BOOT SD card [S24].
- The per-part adjustment sequences are closed lists, for example on the W3 `[I] -> [D] -> [F2] -> [F6] -> [F4] -> [F5] -> [F1] -> [F7] -> [F11] -> [F12]` after a main-board replacement and `[F7] -> [F12]` after a flash-unit replacement [S24]. The X-Pro1 list is `[I] -> [F9] -> [L] -> [F4] -> [F5] -> [H] -> [E] -> [F1] -> [F12]` [S25].
- Adjustment items named across the documents: AF adjustment, lens data write, optic axis and magnification, CCD/CMOS defect correction, camera (colour) adjustment against a pattern box, battery voltage, flash, video, level (normal and high temperature), EVF, FPGA download, mount data write, firmware download and End Setting [S24, S25]. The X-M1 manual's own item names are the same family ([I], [F9], [F4], [F5], [F7], [F1], [F8], [F12], E-SERVICE-MANUAL, reported).
- End Setting is the finalizer. The W3 manual states it writes the destination, the USB_ID, the repair site ID, the repair date, an administrator ID and a repair serial number, and switches the camera from repair mode to product mode so that a PC recognises it as a PTP or mass-storage device; omitting it leaves the camera in JIG mode and unrecognised [S24]. It is the one step that releases the body from the service state.
- Firmware download over the jig connection is followed by an "Adjustment Value Protection Reset", described as an EEPROM reset that protects the adjustment values [S24]. The X-M1 manual names the equivalent [F8] step and an adjustment-value-protection reset (E-SERVICE-MANUAL, reported).
- Sibling service manuals name the same parts: the DSC jig driver `ZJ00684-100` in both the W3 manual [S24] and the owner's X-M1 manual (E-SERVICE-MANUAL, reported), and the X-Pro1 software package `ZJ01971-***` for the "X-Pro1_W" tool [S25].
- The identity readback the tool prints is the same shape as the X-M1 tag-4 reply: vendor name, manufacturer, product name, device type, serial number and a "Frame Work" version [S24, S25]. The 2006 F30 manual index shows the same `[F8] Firmware Download` item and an `[F3] LCD Adjustment` [S26].
- The same three-way split holds on the X-M1 primary document, which names three Windows programs for the one mode: the PC adjustment software ZJ02216 ("X-M1 W PC Soft", app HyperFFW), the SD-BOOT package ZJ02217 used by MAIN PWB Initialize, and a dust inspection program ZJ02218 ("X-M1 W Dust Inspection Soft") that enters by the same shutter plus up press and then captures an image over the connection, reporting OK or the dust locations and saving the captured image on the PC (S31 section 4-3-4, reported). Its HyperFFW menu section confirms the same Script and Watch-variables menu marked "Do not use", and its identity screen shows the same six fields [S31, S24, S25]. All of this is manual text about the repair workflow, not firmware evidence.

## The service USB protocol as publicly described

- `ff80` reports the transport as a 12-byte control request plus bulk bodies, with opcodes 0xc0 open, 0xc2 ping, 0xc4 close, 0xd0 command, 0xd1 result, 0xe0/0xe1 bulk write/read, 0xe8 nop and 0x1d reset, and with the vendor/product ID 04cb:ff80 [S21].
- The command classes the tool uses, per its source [S21]: `0x1a0002` with function 1 to size the config area, function 2 to read it and function 3 to write it; `0x200001` with function 1 for the debug log, function 2 for RAM reads, function 3 for RAM writes and function 5 for key or text input; `0x150000` for device-info tags; plus data-test opcodes `0x550001` and `0x760001`, a diagnostic opcode `0x450006`, a firmware-upload opcode `0x660002` with status tags `0xf0001`/`0xf0002`, a timeout query `0x580000` and an unidentified `0x1a0001`. Four of these classes match what the project has mapped on 1.50: `0x150000` tag 4, `0x1a0002` functions 2 and 3, and `0x200001` functions 1, 2, 3 and 5.
- The config interface has a RAM page and a slower direct path: the tool's config read takes a mailbox flag and its own help text calls the non-RAM variant "ROM", and the wiki states reads can come from RAM or directly from EEPROM while writes go only to RAM until a save is issued [S20, S21]. The X-M1 handler's mailbox field is documented only for the RAM value so far.
- The app80 layer is a function table behind the config area: writing a function code to config offset `0x80` starts the corresponding function, and the reply is read back from the same offset, with parameters in the following bytes [S20, S21]. The tool's known codes are 0x01 for a GPIO port read, 0x02 for an analog sensor read, 0x06 for an RTC read and 0x22 for a save of the whole config area from RAM to EEPROM [S20, S21].
- The wiki describes what app80 is for in the author's words: internal API functions "likely used by Fujifilm's service software at repair centers", performing operations such as testing buttons and dials, accessing embedded flash, calibrating phase-detect autofocus, adjusting power regulators and compensating dead pixels and sensor scratches, and notes that the API is highly camera-specific, with different tools or scripts per model and possibly per firmware version [S20].
- Config offset `0xf7` is described as enabling a high-level debug mode in which the camera logs internal operations readable in real time over the interface, and the same page states it is possible to configure the camera to boot straight into `ff80` mode, bypassing the normal USB PTP stack [S20]. The X-M1 side has `0xf7` bound as the gate for every `0x200001` routine and as the connect-edge registration condition, which is a direct agreement in mechanism between the sibling report and the bound work.
- The interface is also described as a code-injection surface on EXR-generation bodies, where executable memory is writable, and as a source of RAM and boot-ROM dumps that need no firmware modification [S20, S28]; the tool's own bootrom command allowlists X-M1, X-A2, X-E2, X-T1 and X-T10, checks for a `JASM` footer at `0x80003ff0` and digests `0x4000` bytes at `0x80000000` [S21]. The X-M1 side captured that block and matched the lead digest (E-BOOTROM-PROBE-150).
- The author claims pre-EXR-II bodies implement software access restrictions that can be bypassed by patching checks in RAM, while X-Processor Pro and later bodies protect executable memory with an MMU [S20]. The sibling platform table places this body in the EXR II generation (E-XM1-PLATFORM-LEAD, reported), and the project's own decode of the installed images found a PMSAv7 MPU rather than an MMU (E-CPU-PROFILE).
- Fujihack's own debug channel is a separate, patched-firmware mechanism: a PTP operation `0x9805` handler planted by a firmware patch, with actions for writing bytes, executing uploaded code and reading a word [fujihack reuse survey](fujihack-reuse-survey.md). The maintainer's blog records that he knows of a buffer overflow in PTP/USB as another code-execution route [S27]. Neither is a service-mode capability and neither is bound on this body.

## Script and file-borne channels

- AUTO_ACT.SCR: the fujihack wiki documents a script at `A:\DCAA\auto_act.scr` executed by the `mujin` task just before the menus initialise, activated only when EEPROM byte `0xa2` holds 2, with CRLF line endings, `//` comments, 20-character tokens, 10 tokens per line and keywords `if`, `func`, `key`, `calc`, `set`, `jump`, `random`, `tp`, `LABEL`, `END`, `WAITSET` and `WT_LOG` [S22]. The `key` keyword can press named keys and can switch a `MODE` on or off, and `WT_LOG` writes a `DSCFXXXX.MSG` log file [S22]. The EEPROM page lists offset `0xa2` as the AUTO_ACT.SCR boot flag and `0x1e8`/`0x1e9` as the two software-version bytes [S22].
- The same wiki and the maintainer's blog state the script is delivered on the SD card, that the update utility ships it next to the firmware file, and that creating the file alone changed nothing on the author's camera [S22, fujihack reuse survey]. One issue comment records a checklist in which the PTP/USB route was marked "NOT" a trigger [S23].
- S3 files: a Motorola S-record file in the `IMFIDX10` directory, a JEIDA "self-recorded Exif directory"; the wiki says the reader appears to apply EEPROM patches and possibly RAM or flash writes, is reached from a function-table handler traced to the `usbcont` task and could possibly be triggered over USB, and the maintainer's blog states it is executed by `usbcont` [S22, S27]. The fujihack tree names the per-model paths, for example `C:\IMFIDX10\XF10RS.S3` for the XF-1 and `C:\IMFIDX10\LX30B.S3` for the X-A2 [S22, fujihack reuse survey].
- Hidden developer surface: an issue reports the firmware string `OSD DEBUG MODE SCREEN SELECT` with key-prompt text for an on-screen hidden menu, and the project's own notes record that calling the referencing function did nothing on the author's camera [S23, fujihack reuse survey].
- Key names: the wiki's key map lists `JIG` as key 825 and the key-code table in the `ff80` source lists `JIG` as 0x33f (831), so the two public tables disagree with each other [S22, S21]. The X-M1 firmware's own key table binds key state `0x339` (825) as the JIG entry condition (E-JIG-ENTRY-KEY-BIND-150).
- Boot-ROM USB: the maintainer's blog claims almost all Fujifilm cameras have a button shortcut that puts the camera into a low-power state and exposes a USB interface from the boot ROM, and that dumping the ROM needs silicon or debug-pin access [S27]. The same author's earlier issue comment records finding a button combination in a service manual that "seemed to open the bootloader" with a green LED and no screen output, and states he had not worked out how to send code through it [S23].

## Claims already contradicted by bound work

| Claim | Source | Bound work that contradicts it |
| --- | --- | --- |
| The `0x200001` command class carries a command-line channel (functions 6 and 7, request and response) | [S21] `ff80` source | E-DEBUG-ERROR-MAP: the 1.50 handler accepts functions 1 to 5 only and stores `(9,3)` for any function above 5, so a function 6 or 7 request cannot be a working channel on this body |
| A key or text command sent over the service channel can drive the camera's menus or shutter | [S20, S21] key and mode claims | E-SERVICE-SHOOT-150: maintenance mode `0xb` dispatches no menu, shutter or draw action, and the modal `0x38` dispatcher's reachable actions contain none; the synthesized key channel exists but lands in an ignore path in state 10 |
| Closing the session (C4) ends service mode or performs End Setting | implicit in the close command of [S21] | E-SERVICE-QUERY-MAP and E-SERVICE-D1-LENGTH: C4 clears the session-active byte only and selects no settings-reset or End Setting path |
| The camera becomes unrecognised as PTP or mass storage after any jig session that skips End Setting | [S24] W3 manual, restated in the X-M1 manual (E-SERVICE-MANUAL) | E-JIG-OBSERVED: after a no-command jig entry and a plain power-off the body enumerated normally over USB for file browsing; the manual's condition applies after the adjustment software has exchanged data, which no project session did |
| AUTO_ACT.SCR cannot be triggered over USB | [S23] issue checklist | A private-analysis pointer in this project's own 1.50 work shows an image-5 handler at `0x00d91988` testing object format `0x3002` and comparing the object name with the `AUTO_ACT.SCR` string at `0x00d92020`; the trace is unproved and this line is a search anchor, not a claim |

Two further claims are neither confirmed nor refuted and stay open: a user-visible hidden menu (the sibling string exists, calling its referencing function did nothing on the author's camera, and no X-M1 binding is claimed) [S23, fujihack reuse survey](fujihack-reuse-survey.md), and the boot-ROM USB interface, whose ROM block is captured on this body while no USB path inside it is bound [S23, S27]. The X-M1 manual's own procedures named the strongest open lead of this survey: the dust inspection program is said to capture an image over the jig connection and report dust locations, and [F4] and [F5] likewise require the camera to produce image data. The firmware search has since found the carrier (E-SERVICE-CAPTURE-PATH-150, [reports/service-manual-procedures.md](service-manual-procedures.md)): the queue-7 imaging-job family drives the recorder from a config write and returns frame data over the service connection, so the capability is a command family and not an operator step, and the OK/NG and dust-location verdict stays PC-side on that reading.

## What this survey does not establish
