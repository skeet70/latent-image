# End Setting candidate live protocol

Status: attempted once on BODY VERSION 1.50 on 2026-10-07 and rejected with error pair `(1,3)`; the cause is the closed adjustment gate `0xf7`, read as `0x00` on 1.50 in the follow-up session ([the result](#result), E-END-SETTING-150-REJECTED, E-ADJ-GATE-BYTE-150). The request bytes passed independent review against the 1.50 images and went out as rehearsed. No further attempt is authorized. Two enable routes are designed in [the next stage](#designed-next-stage-enable-re-edge-end-setting-restore-not-authorized) and neither is authorized: a mid-session write, blocked at its re-edge step, and a persistent commit of the gate, an H3 calibration-storage change for the owner to decide.

## Purpose

Jig-mode exit by power cycle resets date, time, language and the C slot on this body. The experiment asks whether D0 opcode `0x200001`, function 5, text `POWER OFF\n` is accepted, powers the camera off and keeps those settings across the next normal boot. A success would remove the settings-restore chore from every later jig session.

The service manual places HyperFFW `[F12] End Setting` after adjustment work, says it writes destination, USB ID, repair-site ID and WLAN MAC, and switches the camera from repair mode to product mode. The mapped function-5 route has a compatible finalizer shape: a computer-issued service command transitions mode `0xb -> 0xd`, attempts settings persistence, waits on a completion barrier and terminates. No HyperFFW capture or binary binds function 5 to `[F12]`, and the manual does not say that `[F12]` preserves the area-2 user-settings log.

## Static basis

The exact 1.50 images support this conditional route: function 5 parses `POWER OFF`, posts application event `(6,0x80)`, requests application mode `0xd` from service mode `0xb`, runs an `0xa04 -> 0x500e -> 0xa2f` phase, invokes queue-2 opcode 2, attempts ordinary-settings and dirty extra-configuration persistence, waits for a nine-bit completion mask, sends matching `0x816`, emits queue-2 opcode 3 with first payload word `0x81`, enters `0xec5804` and loops after clearing low-level channel/controller state. Because the path calls persistent settings writers, the operation is H3.

Independent review corrected two details without changing that destination. The first outer dispatch leaves state 10 unchanged, so generated `0xa05` selects `0xce02ac -> 0xc25274`, not `0xce0288 -> 0xc24780`. A completion arriving after the full barrier mask uses the reset group-4 state and requests `0x91b`; it does not emit a second `0x816`.

The debug callback is registered on the USB connect edge only when adjustment-cache byte `0xf7` is nonzero and application mode is neither 5 nor 7. That edge is the 0-to-1 transition of bit 0 of the USB status word `0x0146a090`, compared against the latch byte `0x015c229c` inside `0x00ecf8b8`; the registration call `0x00647398(0x00ed19e4)` sits only in that arm, together with a queue-7 `0x1705` post. Mode `0xb` passes the mode test. A null callback is rejected before the indirect call. The live value of `0xf7` is `0x00` on this body under both 1.00 and 1.50 (E-ADJ-GATE-BYTE-150), so the gate is closed and the callback is unregistered.

D1 reply words `(0,0)` mean the parser callback accepted the text; `(1,3)` covers the cache gate, a null callback and parser rejection; `(9,3)`, `(9,1)` and `(0xffff,0)` indicate malformed or unsupported requests. Acceptance does not report persistence success.

## Request

After a C0 session open: control setup `43 00 00 00 00 00 0c 00`; D0 control data `d0 00 00 00 00 00 00 00 00 2e SID_hi SID_lo`; a 46-byte bulk OUT `01 00 20 00`, twelve zero bytes, `05 00 00 00`, twelve zero bytes except bytes 32..35 are `0a 00 00 00`, then ASCII `POWER OFF\n`; D1 control data `d1 00 00 00 00 00 00 00 00 80 SID_hi SID_lo`; one 128-byte bulk IN. No C4 follows. `devenv shell -- bazel run //transport:camera -- rehearse end-setting` prints the exact sequence.

`HVS_0`, `RING_OFF` and other debug keys are excluded: `HVS_0 ON` reaches outer generic event 48 with an unproved mode-`0xb` effect, and `RING_OFF` converges on the same outer event as `POWER OFF`. C4 only closes the protocol session, and a disconnect while powered can enter the mapped reset path.

## Run

1. Note date/time, language and one value in the C slot. Fully charged battery; no firmware file on the card.
2. Power off, then enter jig mode as usual with USB connected.
3. Run `devenv shell -- bazel run //transport:camera -- end-setting`. Touch nothing until it prints its result and exits; its timeouts end it within about a minute.
4. Act on the result:

| Result | What to do |
| --- | --- |
| Accepted and the camera powers off within about 15 s | Wait 10 s, unplug USB, power on normally and check the noted settings. |
| Accepted but the camera stays on | Wait until 60 s after the command, then switch off. If the switch does nothing within 15 s, remove the battery. Either can interrupt persistence and reset settings. |
| Rejected `(1,3)` | Exit jig mode the usual way; settings may reset as usual. |
| Any error, mismatch or odd camera behavior | Exit jig mode the usual way and paste the command output in chat. |

Do not retry, send any other command, or unplug USB while the camera is powered.

## Outcome

Success is an accepted reply, power-off within about 15 s, a normal next boot without the date/language prompt, the noted settings intact and an ordinary shot with playback. A rejection says the live registration gate is closed on this body; it does not show the official request is absent. A reset, hang or unparseable reply is a failed candidate; fix or explain it before another attempt.

One success is enough for product-level acceptance on 1.50. Correspondence to the mapped internal route remains `static-inference`, and equivalence to HyperFFW remains `reported/unproved`.

## Result

The attempt ran at 2026-10-07T05:32:59Z and printed `end-setting: rejected`. Four transfers went out, matching the rehearsal byte for byte with live session id `0x08e5`, and no C4 followed. The C0 reply was `e508000000000100`. The 128-byte D1 reply echoed opcode `0x00200001`, function 5 and text length 10, with error words `1` and `3`:

```
01002000 01000000 03000000 00000000 05000000 ... 0a000000 ... (zeros)
```

The camera stayed powered, which is what `(1,3)` predicts: the rejection returns before the mode change. Host release, close and exit completed without a cleanup error. Six transfers spanned 168.9 ms of journal time.

`(1,3)` is the shared function-5 rejection, so the reply alone does not name the cause. The adjustment-area capture settles it: index `0xf7` is `0x00` on this body, on 1.00 in the S03 windows (E-ADJ-GATE-BYTE-ZERO) and again on 1.50 in the `gate-byte` session (E-ADJ-GATE-BYTE-150), with `X-M1` at `+0x15c` and `55 aa` at `+0x202` binding both captures to adjustment offsets. A zero gate means the debug callback is never registered on the connect edge, so function 5 rejects before parsing `POWER OFF`.

What this does not establish: that the request bytes are wrong, that the mapped orderly-exit route is absent, or that HyperFFW uses a different request. The experiment never reached the parser.

Opening the gate is a write to adjustment index `0xf7` through config opcode `0x1a0002` function 3, which is [set B of the H2 read proposal](h2-read-scope-proposal.md#23-the-gate-byte-is-calibration-data), dropped by decision 4 on 2026-10-05. It lands in the body's own calibration cache, is temporary only while the session never posts config index `0x80`, and changes the service lifecycle on the connect edge. Reinstating it is an owner decision about calibration risk, not a protocol detail.

That check is answered, and it does not separate the three causes. The two error words are the reply fields at `0x014698a0` and `0x014698a4`, and in `0x00d803cc` exactly four sites write them: `0x00d805b8` stores `(9,3)` for a function above 5 from the test at `0x00d80450`, for a length outside 1 to 256 from the test at `0x00d8045c`, and for callback status 3; `0x00d805d4` stores `(1,0xffff)` for status 2; `0x00d8059c` stores `(1,3)` for status 4 and for nothing else; `0x00d805f0` sets the transfer flag `0x01469cc0` for status 1. The arms are selected by the table at `0x00d8058c`–`0x00d80598` indexed by status minus 1 from the `ldrls pc` at `0x00d80584`, so `(1,3)` on this opcode means the function routine returned 4, and every other status leaves the error words at the zeros the dispatcher's clearing loop at `0x00d80ac4` wrote.

Function 5's routine `0x00647bd4` returns 4 or 0 and nothing else, and all six of its 4 returns are the recorded causes: the gate test `0x0069f8fc(0xf7) == 0` at `0x00647c18`, the text-splitter rejections at `0x00647c30` (no space in the text), `0x00647c44` (space first) and `0x00647c54` (nothing after the space), the null test on callback slot `0x0089edd8` at `0x00647c94`, and the callback returning 0 at `0x00647cb0`. The success return 0 at `0x00647cb4` leaves the cleared error words, which is the `(0,0)` acceptance. The three splitter sites cannot fire for the request as sent: `POWER OFF\n` has its space at index 5, which is neither 0 nor the text length minus 2, so the key is `POWER` and the argument is `OFF`. The live `(1,3)` therefore names the three recorded causes and reaches them through the same two stores at `0x00d805a8` and `0x00d805b0`.

The echoes do not discriminate either. The opcode is copied into the reply at `0x00d80ab4` before the handler runs, the function echo at `0x014698ac` is written at `0x00d8042c` ahead of the length test, and the text-length echo at `0x014698bc` is written at `0x00d80578` after `0x00647bd4` returns and for every value it returns. The observed `10` at reply offset 32 proves the request reached the routine and excludes the two `(9,3)` request rejections, which `(1,3)` already excludes; it distinguishes none of the six internal returns.

The debug handler does not copy the configuration handler. `0x00d801cc` translates status with the compare chain at `0x00d802c8`–`0x00d802dc`, which has arms for 2, 3 and 1 only, so a status 4 there falls to the common tail and reports `(0,0)`. `0x00d803cc` adds the status-4 arm, and that arm is the only `(1,3)` producer in the two handlers. Neither handler tests the gate; the five function routines do, and function 5 is the one that reports it as 4. Functions 1 to 4 return 2 for the same closed gate at `0x00647938` and `0x00647b1c`, which would produce `(1,0xffff)`, so the single return value given for all five routines in [the H2 proposal](h2-read-scope-proposal.md#22-debug-ram-read-opcode-0x200001) does not hold for function 5.

Which of the three fired is settled. The `gate-byte` read on 1.50 at 2026-10-07T06:08:12Z returned adjustment index `0xf7` as `0x00` (E-ADJ-GATE-BYTE-150), with `X-M1` at `+0x15c` and `55 aa` at `+0x202` in the same session, so the body is on its own calibration and the gate is closed. The gate test precedes the other returns in `0x00647bd4`, so the rejection is the gate and the null callback and the callback's own verdict on `POWER` were never reached. The same four windows compared against the 1.00 capture differ in six bytes, `+0x80`, `+0x81`, `+0x205`, `+0x275`, `+0x276` and `+0x2ec`; the oracle and flag windows are byte-identical, and `0xf7` did not move. This is one reader on the 1.50 images for the handler's status table; no second reader has re-derived it (E-DEBUG-ERROR-MAP).

End Setting stays out of reach while `0xf7` is zero, and the gate is what a host request opens. The public fffw tool does this as routine preamble: `ffjlib.py:171-179` reads config byte `0xf7`, writes it to 1 when it differs, and restores the old value afterwards (E-FFFW-NO-END-SETTING, [the transport audit](source-and-transport-audit.md)). Its config write is the same opcode `0x1a0002` function 3 that section 2.3 of the H2 proposal describes, and its separate `cfgdata save`, `app80_request(0x22,[0xff])`, is what commits the cache to storage. So a session that writes the gate and never sends that save is the documented shape of every debug command in the public tool, and the owner reports HyperFFW exposes End Setting over this same jig connection across Fujifilm bodies. The design question that followed was where the connect edge is evaluated: registration happens on the USB connect edge, so a write inside an established session arrives after the test it needs to pass; the next section settles it.

## Designed next stage: enable, re-edge, End Setting, restore (not authorized)

No run is proposed or authorized by this section. It records the sequence the mapped firmware forces and the exact bytes it would use, so that the missing piece and the decision in front of the owner are concrete. Nothing here weakens the standing rules: no retry, no C4 before the request, no config index `0x80`, no commit, no powered cable pull while a request is outstanding.

The edge is now identified. Counter `0x00ecf8b8` compares bit 0 of the USB status word `0x0146a090` - a cached copy of bit 31 of the controller register `0xFFF55104` - against the latch byte `0x015c229c`, and only a change of that bit, with cache byte `0xf7` nonzero and application mode not 5 or 7, runs the registration arm. Status reports reach it as queue-7 message `0x1714`, posted only by the observer `0x00ecfe64`, which the driver invokes with the current status. A write into an established session therefore changes nothing until the bit changes again or a second handler clears the latch.

**Re-edge step, the blocker.** The only established producer of a fresh 0-to-1 edge is a physical replug: the controller's raw bit drops, the poll at `0xd81d10` calls `0xd814f4(0)`, the replug calls `0xd814f4(1)`, the driver re-invokes the observer, and `0x1714` reaches the registration arm with the gate open. But the drop half first runs the gate-open disconnect arm of `0x00ecf8b8`, and in an active session that arm emits application event `0x90`, because `0x9134f8` is 1 from transport activation (`0x00ec2900`) to transport stop (`0x00dc754c`). Application event `0x90` is the head of the mapped settings-reset route (`0x504 -> 0x00ec290c -> 0x006a6fd8(1)`), so a powered replug is not settings-preserving and must not be used. The settings-preserving candidate is the second status handler `0x00ecf9c8`, which stores 0 to the latch when the gate is open and mode is not 5 or 7; any later `0x1714` with bit 0 set then registers. That handler runs only on queue-7 message `0xB400` in USB-manager state 1, through the chain queue-7 opcode `0x1700` -> transport `0x3400` (`0x00d822a8` posts it and registers `0x00ecfdd8` at `0x0146a0dc`) -> `0xB400`. The chain's first link is not producer-free: the `0x1700` builder `0x00ed112c` has two callers in image 5, `bl` at `0x00ec2c58` in `0x00ec2c30` (queue-2 group-3 action 2, selected only by group-3 event 0 at state 0 of matrix `0x00ec4abc`) and `bl` at `0x00ec81fc` in the task init `0x00ec8014` (reached from `0x00ec8214` when the nine completion callbacks bring mask `0x015c1e5c` to `0x1ff`). Both are internal queue-2 or task paths, and no C0/D0/D1/C4 handler posts `0x1700`, `0xB400` or `0x1714` or writes the latch, so a host-only re-edge is out of reach on the mapped command surface rather than missing from the images (corrected 2026-10-07 from an earlier no-producer reading). What settles the residue: a trace of the state halfword `0x015c20ae` and latch `0x015c229c` across one host-only session, a reachability check of queue-2 group-3 event 0 and the `0x015c1e5c` mask from the host command surface, or a live probe that can confirm registration (never refute it) - after the enable write, send function 5 with `HVS_0 ON`; `(0,0)` proves the callback was registered after the write, `(1,3)` distinguishes nothing.

**Persistent variant, a second route and still not authorized.** Noted for completeness only: this route requires a config write at index `0x80`, which this project's standing rules forbid sending in any value, since the cache store runs before the whitelist check and value `0x22` commits the whole adjustment area to storage. It is not a proposed path and is not reachable under those rules. The other route reaches registration without an in-session edge: commit the gate to storage so the next boot's connect edge sees `f7 != 0`. The commit is config opcode `0x1a0002` function 3 at index `0x80` with value `0x22`: the callback `0x00dc7564` writes the cache byte, matches record 26 of the 144-record whitelist at `0x00dc7a84`, and posts queue-7 `0x1707` with payload `0x22`; group-2 row 26 action `0x00ecc66c` runs `0x0069fea8`, which writes the whole `0x420000` area through `0x006a9fdc` (33 units of 128 KiB from block `0x3a9`, the storage-ready gate `0x00828574 == 1`, and the write stops with earlier units written if a unit fails). The config write's own reply is `(0,0)` in every non-request outcome and reports nothing about the commit; the only host-visible completion is cache byte `0x81` (`0x00` success, `0x01` failure), written after the storage call and readable at index `0x80`, so the host polls it with a timeout and never treats a power cycle as the acknowledgement. Because the trigger requires `cache[0x80] == 0x22` and the commit writes the whole area, every commit leaves index `0x80 = 0x22`. The live 1.50 page-zero window reads `00 00 00 00` at `+0x80..+0x83` and `0x00` at `+0xf7` (the pre-update 1.00 capture held `+0x80 = 0x22` and `+0x81 = 0xff`; E-ADJ-GATE-BYTE-150 records the update moving both), so the enable commit changes index 0x80 from 0x00 to 0x22 and the restore commit leaves it at 0x22: the restore cannot return index 0x80 to 0x00, and the committed 0x80 = 0x22 has no proved behavioural meaning.

The variant would run three jig entries: entry 1 reads `0x80..0xf7`, writes `0x81 = 0xff`, writes `f7 = 0x01`, writes `0x80 = 0x22` and polls byte `0x81` to `0x00`; entry 2 is an ordinary jig entry whose connect edge now registers, followed by the End Setting request above; entry 3 reads, writes `f7 = 0x00`, writes `0x80 = 0x22`, polls to `0x00`, verifies `f7 = 0x00` and `0x80 = 0x22`, and exits jig the usual way. Costs and open points: three jig entries, two full-area storage writes, the ordinary-mode consequences of a committed gate (the f7-gated app-level USB `0x10`/`0x90` notification at `0x00ec8118` is suppressed, the `0x73ae10` notifier takes its record-walking arm, and the debug log writers become eligible once the callback registers), and the same unproved handshake-state link as the mid-session design; a torn commit has no mapped recovery. The arming write of `0x81 = 0xff` is also persisted by the whole-area write, so it is a design choice rather than a requirement: skipping it keeps index 0x81 at its live `0x00` and reduces the forced storage change to index 0x80 alone, with the next entry's read of `f7` (0x01 after the enable commit, 0x00 after the restore commit, both reloaded from storage) as the commit's real verification. It is an H3 persistent change to calibration storage and it needs the owner's decision and a review of new bytes before any run. Until that decision the standing rules stand: no commit, no C4 before the request, no retry, no powered cable pull while a request is outstanding.

**Sequence, one C0 session, no C4 until the end.** Session id `SS SS` is the big-endian 16-bit session from the C0 reply; every control setup is `43 00 00 00 00 00 0c 00`.

1. C0 open: data `c0 00 00 00 00 00 00 00 00 08 00 00`, 8-byte bulk IN. Accept only bytes 2..7 `00 00 00 00 01 00`.
2. Enable read, config opcode `0x1a0002` function 2 at `mb=1, page=0, offset=0xf7, length=1`: D0 data `d0 00 00 00 00 00 00 00 00 24 SS SS`; 36-byte bulk OUT `02 00 1a 00`, twelve zero bytes, `02 00 00 00`, `01 00 00 00`, `00 00 00 00`, `f7 00 00 00`, `01 00 00 00`; D1 data `d1 00 00 00 00 00 00 00 00 80 SS SS`; 128-byte bulk IN. Accept only error words `(0,0)` at bytes 4..11, function echo 2 at 16..19, the parameter echoes `mb=1`, `page=0`, `offset=0xf7`, `length=1` at 20..35; the gate byte is at offset 36 (observed `0x00` on this body). Skip step 3 if it is already nonzero.
3. Enable write, function 3 with one data byte `01`: D0 data `d0 ... 00 25 SS SS`; 37-byte bulk OUT as step 2 with function `03 00 00 00` and a trailing `01`; D1 as step 2. The callback `0x00dc7564` writes the cache byte through `0x0069fc94` before any other test and, for a start index other than `0x80`, returns without posting anything. Accept only `(0,0)` and the echoes.
4. Verify read: repeat step 2; accept only `0x01` at offset 36.
5. Re-edge: required, not implementable on current evidence. Do not replug.
6. End Setting request, unchanged from the reviewed bytes above: D0 data `d0 ... 00 2e SS SS`; 46-byte bulk OUT as recorded; D1 data `d1 ... 00 80 SS SS`, 128-byte bulk IN. `(0,0)` with function echo 5 and text length 10 means the callback accepted; `(1,3)` covers the six shared rejections; `(9,3)`, `(9,1)` and `(0xffff,0)` are request faults.
7. Outcome: on `(0,0)` send nothing further; the body either powers down within about 15 s or stays powered, and either way the RAM write dies with the power-off. On any rejection or abort the body stays powered and step 8 is required.
8. Restore write: function 3 with the original byte from step 2; verify by repeating step 2. Only after that verify, and only with the body known powered, may one C4 (`c4 00 00 00 00 00 00 00 00 02 SS SS`, 2-byte bulk IN) close the session; C4 clears the session-active byte only and restores nothing.

Budget: 5000 ms per transfer, per-stage aggregate deadlines, 60 s for the post-accept power-off and 15 s for the switch before the battery. Transfers: 2 + 12 + 4 (+ 4 restore, + 2 C4); the measured channel runs sub-second, so the cost is the jig entry, the power-off and the settings check.

**Commit-free.** The only write is the config callback's cache byte. The three storage paths are the whole-area writer `0x0069fea8` (callers `0x00db932c` update completion, `0x00dbc8e4` = service command `0x22`, `0x00d5cf0c` = on-camera editor), the bounded writer `0x006a0028` (init task `0x0073d3ec`, never index `0xf7`) and the reload `0x0069fe20` (`0x00db9228`, `0x00dbc8c4` = service command `0x21`). The sequence posts neither service command - the queue-7 `0x1707` post exists only in the `index == 0x80` whitelist arm - runs no update and opens no editor, so the cache byte stays in RAM: the write is temporary under a session that never posts index `0x80`, and a power cycle reloads the area from storage. No connect or disconnect handler writes the cache and no connection event triggers a reload; the edge-path functions contain no cache-write or storage call.

| Symptom | Action |
| --- | --- |

**Owner decision.** Set B's calibration-risk analysis applies to the enable write: in the mid-session sequence it lands in the body's own calibration cache and is temporary while no index-`0x80` commit is posted, and that sequence is blocked at its re-edge step. The persistent variant reaches registration but performs the two whole-area commits it describes, one before and one after the run, and the trigger forces committed index `0x80 = 0x22`, which no mapped route can undo; its boot-time registration also rides the unproved handshake-state link. Neither route is authorized. The owner decides whether to pursue one, and the persistent route additionally needs a review of its new bytes before any run.

## Registration path, re-edge decision and step justification

This section is the byte basis for the sequence above: where the callback slot is written, which event installs it and in which application mode, which re-edges exist, what each step rests on, and why the write stays out of storage. The full listings and scan outputs are in `private-data/analysis/x-m1-1.50/safe-jig-exit/gate-enable-sequence.md` (E-GATE-ENABLE-SEQUENCE).

### The slot, the event and the mode

Across both images `0x0089edd8` has one writer and one reader: the `movw`/`movt`/`str` sequence at `0x0064743c`-`0x00647444` inside `0x00647398`, which stores its argument, and the load at `0x00647c84` inside `0x00647bd4`. No clear site exists in either image, and image 5 never references the slot (whole-image `movw`/`movt` and literal scan). The only caller of `0x00647398` is `bl` at `0x00ecf95c`, passing the constant `0x00ed19e4` formed at `0x00ecf954`/`0x00ecf958`, so registration installs the debug key parser and nothing else.

The event is queue-7 message `0x1714`, built only by the connection observer `0x00ecfe64` at `0x00ecfe78` with payload `{driver status word, argument}`. The second handler `0x00ecf9c8`, called from `0x00ecc23c` inside `0x00ecc228`, installs nothing. ### The verdict and what the alternatives cost

A single jig session cannot do this. The connect edge that decides registration runs before the host can send anything, and no host command re-runs the test inside the connection. A powered replug keeps the RAM write and the reconnect edge registers, but its detach half runs the gate-open detach arm of `0x00ecf8b8`, which during an active session posts application event `0x90` because `0x009134f8` is 1 from entry completion (`0x00ec2900`) to transport stop (`0x00dc754c`); `0x90` is the head of the mapped conditional reset chain that reaches `0x006a6fd8(1)`, the ordinary and custom default constructor with guarded persistence ([the reset map](service-query-and-jig-reset.md)), so the replug costs the settings reset End Setting exists to avoid. A power-cycled re-entry costs the write instead: boot reloads the adjustment cache from the class-2 flash blocks, the stored `0x00` returns, and the new connect edge does not register. The persistent variant above is the only mapped route to registration from a stock body, and its price is two whole-area storage commits and a committed index `0x80 = 0x22`; it is an owner decision and is not part of this sequence.

Reply contract for opcode `0x1a0002`, the complete set: error words `(0,0)` on the success paths; `(9,3)` for function outside 1 to 3, `mb` above 1, or callback status 3; `(1,0xffff)` for callback status 2; `(1,3)` is unreachable in this handler (`error-mapping.md`). A reply with zero error words is not proof of a write, so every write in this sequence is followed by its read.

If the camera stops responding mid-sequence: do not retry and do not re-send; power the body off with the switch, and remove the battery if the switch does nothing within the timeout. A power cycle alone restores `0xf7` to `0x00`, because storage is untouched and initialization reloads the cache from the class-2 flash blocks (H2 section 2.3); this holds unless an index-`0x80` commit ever ran, which this sequence never sends. While the body is left powered the residual `0x01` is closed by the step-8 restore when the session answers, and by the power cycle when it does not.

## Physical and mixed-input exits

The owner allows physical steps in an exit sequence, so the question is not only what a host request can reach. Three physical routes were traced and none reaches the orderly exit, but the trace changes where the settings reset comes from.

No physical control constructs the orderly exit's entry event. Application id `0x0086` has one constructor in the loader, images 4, 5 and 6: the function-5 debug callback `0x00ed19e4` (E-EXIT-ENTRY-PRODUCERS-150). The same encoded word exists in a second domain as a physical key record, and that record's mapped consumer is a different machine: `0x00634b40` strips qualifier `0x80`, clears POWER bit 6 in the key-state bitmap, and only base code `0x11` is forwarded to the application sender. Reading the debug table's `POWER` and `OFF` spellings as a physical binding to the application event is the error; the two paths share an encoding, not a destination (E-POWER-KEY-DIRECT-COMMIT-150).

The power switch reaches neither chain. Its key record runs `0x00639b1c` -> `0x00634b40` -> poller `0x00635280` -> direct commit `0x0063975c`, which copies pending mode into current mode without emitting `0x0a05`. That skips the modal-`0x62` lifecycle, so it skips the ordinary and extra-configuration persistence, the nine-bit barrier, `0x0816` and the terminal; it equally skips `0x90`, `0x504`, `0x00ec290c` and the default constructor `0x006a6fd8(1)`. Whether an electrical shutdown after that commit retains settings not already written is unproved.

The Playback route is dead code. Application event `0x0a4d` selects modal-`0x38` action 5 `0x00c37008`, which joins the same `0x00d350c4(0x0e)` request function 5 uses and depends on no cache byte, but its only constructor `0x00d34ccc` runs only as the timer callback registered by `0x00d3d390`, and all 26 callers of that wrapper sit behind a test of `0x006394e8`, which returns literal zero. In maintenance modal `0x38`, K_PLAY ON selects the disabled arming action directly (E-PLAYBACK-A4D-DEAD-150).

What this leaves is a map that does not explain the symptom. The owner reports that every jig cycle on this body has ended with the power switch first and the cable pulled only after full power-down (E-JIG-EXIT-ORDER-OWNER), so the detach arm never ran while the firmware was live, and `E-JIG-OBSERVED` records the same reset after an entry that sent no commands at all. The `0x90` route is therefore not what costs this body its settings. The direct-commit path the switch does run constructs no defaults either, so the surviving candidates are on the entry side or the boot side: something about maintenance entry or the maintenance power-off leaves the settings records in a state the next ordinary boot replaces with defaults. The barrier model already names two origins of that shape, `StartupFallback` and `CustomReadFallback`, and neither has been traced to live code. Closing that is the open work; the orderly exit remains worth reaching only if it is what writes the records back.
