# X-M1 1.50 service query and settings reset

## Conclusion and scope

The exact C0/open, D0/product-tag-4, D1/reply and C4/close command branches change session, request, reply and status RAM. The product branch copies an existing cached identity field. No settings-reset or persistent-storage writer is selected by those command bytes in the mapped branch. **The surrounding service lifecycle is not read-only:** a conditional vendor-service disconnect/exit path invokes full settings reset, including changed-header writes and a compare-before-commit custom-record path. A separate initialization-validity fallback can also default settings. Physical entry and exit are bound too: the boot key states select application mode `0xb` through the polled mode commit, and the power switch reaches that same direct commit, not either mapped lifecycle exit. C4 closes a protocol session, not jig mode.

Host-only static inference on the public X-M1 1.50 DAT, SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490`. Inputs, inferred decoding and load addresses are bound in [firmware extraction](firmware-extraction.md). Addresses below use decoded image 4 at `0x0061c400`, image 5 at `0x00bf1a00`, plain code at `0x01100000` and the supplied loader/boot records. `FUN_` names are analysis labels. No camera enumeration, opening, command, reset or firmware write occurred.

The owner's reset observation was on installed **1.00**: jig entry, no adjustment software, ordinary power-off/on, then date/language prompts and custom defaults; the SD photo survived and ordinary USB mode returned. That observation does not bind a 1.50 reset branch or identify the storage technology. The analysed update is not the installed code or a body-specific backup.

## Exact query dispatch

[The source audit](source-and-transport-audit.md#exact-first-identity-wire-flow) owns the eight transfers and exact packet bytes. Setup is `43 00 00 00 00 00 0c 00`. Control data is 12 bytes: opcode at 0, big-endian length at 6–9, big-endian session ID at 10–11. D0's 32-byte bulk payload has little-endian opcode `0x00150000` at 0 and tag `4` at 16; all other bytes are zero.

In USB transport mode 3, table `0x00d7f314` binds vendor setup `0x00d7ef20`, completed control data `0x00d7f234`, bulk OUT source/completion `0x00d7ef78`/`0x00d7f104` and bulk IN source/completion `0x00d7efd4`/`0x00d7f0c0`. Control completion checks frame byte 1's upper three bits, then dispatches opcode through `0x00d7fae8`.

| Command | Handler | Accepted conditions and effects |
| --- | --- | --- |
| C0 open, length 8, SID 0 | `0x00d7f56c` | Requires inactive byte `0x01469898`, zero input SID and length 8. Sets active, seeds/increments SID halfword `0x0146989a`, masks it to 13 bits and replaces zero with 1. Prepares fixed 8-byte reply and success status. |
| D0 command, length 32, returned SID | `0x00d7f80c` | Requires active session, matching SID and length ≤512. Selects fixed request buffer `0x01469a9c`. Successful bulk completion invokes `0x00d80a80`; opcode `0x00150000` selects `0x00d7fdec`, whose tag-4 branch calls `0x0069f388`. |
| D1 result, length 128, returned SID | `0x00d7f8a4` | Requires active session, matching SID and nonzero length. Requests 128 bytes of the prepared result. Bulk source returns the lesser of requested and available length; tag 4 prepares 512 available bytes. |
| C4 close, length 2, returned SID | `0x00d7f760` | Requires matching SID and length 2, but does not require active=1. Clears only the session-active byte and prepares a 2-byte SID reply plus status. It does not invoke the mapped settings reset; no End Setting semantics are established. |

Common fixed RAM fields are requested length `0x01469868`, available length `0x0146986c`, reply pointer `0x01469870`, transfer flags `0x01469874`/`75`, status-pending byte `0x01469894`, status halfword `0x01469896` and reply buffer `0x0146989c`. Command failure branches prepare transport error/stall state; they do not select a replacement application command. There is no per-session heap allocation/free in the inspected C0/C4 handlers. USB transfer DMA reservation, release and controller programming are separate effects.

### Product data and replies

`0x00d80a80` clears the reply body/status words and unused request tail before dispatch. `0x0069f388` copies at most 19 bytes from `*(0x0096ca50)+0x15c` into stack scratch and appends a NUL. The tag-4 branch expands 20 bytes into the low bytes of UTF-16LE reply code units starting at reply+16; the high bytes remain zero. D1 supplies the first 128 bytes, including opcode, zero status words, product text and padding.

Initialization `0x0069f204` sets the cache pointer to `0x41acd800`, giving product source `0x41acd95c`. This is a runtime identity/calibration cache, not a literal in the tag-4 handler. The supplied fallback offset/value table at `0x007c8ad4` encodes `X-M1` at offsets `0x15c`–`0x15f`; the update's fallback adjustment template agrees. Neither source proves what an installed body's cache contains. The query does not trigger those initialization reads.

C0 writes reply bytes `SID_lo SID_hi 00 00 00 00 01 00`. The handler at `0x00d7f56c` stores the SID through the little-endian 16-bit helper `0xd7f364` and the four bytes at 4 to 7 through the little-endian 32-bit helper `0xd7f384` holding the constant 65536, so the tail is `00 00 01 00` in every captured open reply on both 1.00 and 1.50 (E-DBG-C0-FIELD-150). No mapped artifact reads that field back and the D0 handler's own length cap is 512, a different field, so its units stay unnamed; the sibling host names it a maximum size, a lead only. The transport's `identify` and `end-setting` now require the exact little-endian tail rather than the big-endian range they used before. C4's successful reply is the stored SID in little-endian order.

If C0 needs a SID seed, `0x00d7be08` → `0x007257a8` selects a supplied loader interface and reads shared tick cell `0x400c0800`. Loader initializers `0x00040430`/`0x000d0430` bind interface slot `+0x174` to that cell and slot `+0x1618` to selector wrappers `0x000412bc`/`0x000d12bc`. The selector reads a coprocessor register; this bound seed path is a counter read, not a storage writer.

## Settings defaults, validity and writes

### Initialization fallback

Task constructor `0x0073c0d4`, called through `0x0073afe0`, registers queue/task `0x3b`, name `initcont`, and entry `0x0073e048`. The entry clears its state cells, sets phase `0x0095709c=0`, and dispatches through `0x0073db90` → `0x0073dab4`. Group 0's initial matrix cell at `0x00817724` selects action 2, callback `0x0073e0b0`, which calls `0x0073cbfc`. This binds settings validation to the task's initial phase, before its queue-receive loop. It does not establish which physical jig-entry/exit event starts the task.

`0x0073cbfc` calls settings initialization `0x006a75a4` after its preceding initialization check succeeds. That routine reads general-settings log area 2, record size `0x200`, and accepts saved ordinary settings only when all three conditions hold:

- The log read succeeds.
- Header marker byte `0x409c29c6` is `0xaa`.
- The sum of the 16 header bytes `0x409c29b8`–`0x409c29c7`, modulo 256, is zero.

Failure calls `0x006a6fd8(0)` and sets flag `0x0089f834=1`. Subsequent custom initialization `0x006a8abc` consumes that flag, constructs custom defaults through `0x006a877c`, and invokes compare-before-commit routine `0x006a86c4`. A failed custom-record read also takes this default/commit-attempt path. These are initialization-validity branches, not a code-bound jig-exit trigger.

The first supplied header source is the companion boot snapshot `0x400a00d0`: supplied flag `0x0082856c=1` makes initialization copy it once. Later reads use the encoded retained-byte interface. Companion routine `0x00013244` reads 16 encoded bytes into the snapshot and independently checks marker/checksum. The application revalidates it. Invalidating this snapshot or failing the log read can therefore produce defaults at initialization; no mapped edge yet attributes either condition to the owner's jig exit.

### The date and language setup dialog

The dialog's boot predicate is `0x0073cb24`, consumed only by init-task phase actions `0x0073e680` (action-table slot `0x00817764`) and `0x0073e75c` (slot `0x0081776c`). `0x0073e680` consults the predicate only when the boot cell `0x009570dc` is neither 0, 6 nor 7; `0x0073ccb8` fills that cell through `0x00639b1c`'s switch, which maps committed application mode `0xb` to 7 and mode 3 to 1, so the decision is an ordinary-boot decision and a maintenance boot never reaches the predicate. `0x0073cb24` returns 1 when `0x006a83b4()` (bit 7 of logical offset `+0x64`) is 0, condition row id `0x0f` holds byte `+0x15 == 1`, `0x006a8358()` (language, logical offset `+0x21` bits 0..5) is 0, and `0x009570dc == 1`. **byte-read**.

Condition row id `0x0f` is the ADAPTER condition of the 36-row table at `0x00828120` (28-byte stride, lookup `0x006a0b4c`, reader `0x006a0bb0`); row ids are the debug-key and application-event ids of table `0x00ed2df8`, and `0x006a1c50` treats `0x0f`/`0x8f` as the ADAPTER ON/OFF pair before dispatching through `0x006a1b40` to the handler registered at `0x0095b074` by `0x006a1e5c`. The condition-15 input is therefore the ADAPTER-ON event. **byte-read** for the id binding, **static-inference** for the event identity; the loader-side producer of that event and the registered handler body remain **unproved**.

The fields are closed. Date and time take `0x006b2138` → `0x006a5ed0`, which checks the six date fields against the 1461-entry table `0x007c9c28`, converts them to a 32-bit day/second counter and writes retained registers `0x41..0x44` (descriptor indices 9..12) with index `0xd` toggled 0→1 around the write and index `0xe` cleared; the clock is not in the settings record, so a settings reset does not clear it. Language takes the logical write-through `0x006a6f3c`, which copies into `0x409c281c` and calls `0x006a6ddc`; the default path sets `+0x21` from `0x0069f8fc(0x20b)` clamped to 1 above 34 and sets bit 7 of `+0x64` to `(language field == 0)`. **byte-read**.

Which arm of `0x0073e680` displays the dialog is **unproved**: the predicate-0 arm sets `0x00972e8e = 3`, `0x009570d8 = 1`, raises `0x0072872c` flags `0x11040000`/`0x1040000` and runs `0x0073d7d8`, while the predicate-1 arm runs `0x0073d828`, which registers FUJIDEMO.MOV playback. **static-inference** narrows it: after any default construction the predicate is 0 whatever configuration index `0x20b` holds, so the owner's post-reset boots take the predicate-0 arm. The binding fact is the consumer of `0x009570d8`/`0x00972e8e` in the UI images or a live first-boot observation.

### Which origin this body actually takes

The disconnect reset below is not what costs this body its settings. The owner ends every jig cycle with the power switch first and the cable only after full power-down (E-JIG-EXIT-ORDER-OWNER), so the detach arm never runs while the firmware is live, and E-JIG-OBSERVED records the same loss after an entry that sent no commands. The reset is therefore on the boot that follows the maintenance session, and the initialization fallback above is where it happens (E-RESET-ORIGIN-BOOT-150).

Three further results narrow it. The two halves of the settings live in different stores: header bytes 0 to 15 in the retained device, written through on every logical write by `0x006a6f3c` -> `0x006a6ddc`, and the `0x118` ordinary bytes in the area-2 flash log, written only by `0x006a8074`. Both `0x006a8074` and `0x00647f40` have exactly two callers in the whole firmware, `0x00ec2cb8` and `0x00ec4154`, both queue-2 lifecycle callbacks, so the maintenance power-off skips the save by routing rather than by suppression. Skipping it is not sufficient to explain the symptom: `0x0063975c` contains no settings, log, retained-register or configuration write, a reachability walk from the key path visits none, and nothing on the skipped path erases or unmarks either store, so a boot after a maintenance power-off would read a valid header and a valid newest record.

The timing follows from which symptoms appear together. A fallback on the jig boot itself would cost the custom slot while date, time and language returned, because area 2 is untouched and no commit runs in maintenance. All three are lost, so the fallback runs on the next ordinary boot.

`0x006a6ddc` writes the 16 header bytes as 16 independent single-byte device transactions with the checksum byte last, so the header is not atomic across a power loss, and the constructor always repairs it. That is why a header-caused reset would be one-shot.

The ending route decides what the next ordinary boot finds. On 2026-10-08 the owner twice ended a no-command jig session by cutting power at the dummy-battery supply instead of the POWER switch, then unplugged USB, reconnected the supply and booted normally; neither boot showed the setup menu and, in the second trial with specific shooting settings and SET-UP menu values selected for watching, none had been reset (E-JIG-POWERCUT-PRESERVES-150). Every same-day jig cycle that ended with POWER/OFF still produced the setup menu on its next ordinary boot. Area 2 also stays marked across such an ending: the jig boot that directly followed a jig POWER/OFF read snapshot sequence `0x23bb` at `0x409c2d54..55` instead of the `ff ff` failure image (session `20261008T045812Z-probe-area2`), and the ordinary boot after that cycle still showed the setup menu. The trigger the ordinary boot acts on is therefore persisted by the physical POWER/OFF path, not by the maintenance session or the power-down itself; tracing it to its consume point is the open step.

### The experiment result

The discriminating cycle ran on 2026-10-07 and returned the flash-side branch (E-RESET-ORIGIN-AREA2-150). The owner entered jig with the cable connected, sent nothing, switched off, unplugged and booted; the settings reset as always. A battery pull in place of the second orderly power-off, then a boot, returned the body to the setup menu a second time. Only the area-2 origin predicts that: a custom-record or retained-header failure is repaired during the resetting boot itself, so either would have left the pre-jig ordinary settings readable. Area 2 is written only by `0x006a8074`, whose two callers are the queue-2 lifecycle callbacks, so it is repaired only by an orderly power-off.

The cable-free variant of the same cycle is impossible on this body: shutter, up and power on boots normally with no cable (E-JIG-ENTRY-REQUIRES-USB), so no cycle can exclude the USB surface.

That result contradicts the direct reachability finding: nothing mapped in the no-command maintenance-entry or physical POWER/OFF paths erases or writes area 2. The twenty-window probe then found the retained header valid and identical to its snapshot, the area-3 mirrors coherent, the log handles active and the discriminator on its continuing-startup output. The exact invalidator remains below the closed direct settings graph. Ranked possibilities are area 2 already rejected during the maintenance boot, a hidden out-of-artifact erase or append, raw service/update-family access, the journal pair path with a firmware-unwritten `0x2b` link byte, a persistent controller read fault, parity/ECC rejection of every marked record and, demoted, autonomous controller or rail-loss behavior. Area 2 is logical blocks `0x3d6`/`0x3d7`; a decisive result needs their record sequence and parity/ECC state before an orderly repair, or the RAM snapshot, lower object and fixed record buffer listed in the private trace.

The second `probe-ram` session read adjustment-cache indices `0x3b9` and `0x3ba` as zero (E-RESET-PROBE-150). `0x006a5c08` is a retained-register writer: `0x006a59b8` transforms descriptor `0x5800` into command `0xd800 | value`, whose bit 15 selects the write branch. Its header-byte-8 write is gated on `0x3ba`, so it was disabled at probe time; the mapped physical POWER/OFF path does not call it, and the battery-pull result independently excludes a retained-header-only origin. A later gate change or indirect call is unproved.

### Conditional vendor-service disconnect reset

Application mode `0x009500ec=0xb` enters a frontend path through `0x00c2453c`, selects outer UI state `0x0a`, and posts internal request `0x503` with payload `0x81` through `0x00c32708` → `0x00db5b94` to queue 2. The backend routes it through `0x00ec284c`, then completion `0xac00` selects `0x00ec28a8` → `0x00ed117c(2,0x00ec9834)`. Queue-7 request `0x1705` can select `0x00ecc104`, which activates USB transport mode 3 through `0x00d82478` and invokes the saved callback that posts `0x9705`. Mode 3 selects the four-command vendor table mapped above.

After the internal `0x503` entry response, queue-2 backend root state is 3, group 7 state is 1 and group 1 state is 0. The internal requests/events below are camera queues, not additional host USB commands.

```text
USB disconnect notification -> queue-1 event 0x90
  -> application-mode-0xb disconnect action 0x00c36fa0
  -> 0x00d350c4(0xe), pending application mode 0xd, event 0xa05
  -> 0x00c32690 -> internal queue-2 request 0x504
  -> 0x00ec2870
       -> USB-stop request 0x1706, callback posts 0x9706
       -> queue-0x22 request 0x3200, callback posts 0x1200
  -> both completions -> 0x00ec290c -> 0x006a6fd8(1)
```

This path requires the disconnect to pass frontend filters, a pending candidate other than `0xc`/`0xd`/`0xe`, the selected modal states, completed service entry, and delivery of both stop completions. Important frontend guards are `0x00950110!=1`, `0x0095039c!=3`, `0x00954d60!=2`, and not both `0x00d36090()` and `0x00d173d8()` returning 1; the error filter must also accept the event. The modal `0x4f` and `0x2f` request-producing paths use state 0. These are runtime predicates, not observed camera states.

USB-manager group 0 has a separate four-state matrix at `0x00ecf6f8`. Start moves state 0 to 1; completion `0xb403` moves state 1 to 3. Stop in state 3 selects the two-byte cell `0x00ecf706={04,fe}`, calls `0x00ecc178` → `0x00d824d4`, and moves to state 2. Stop is also accepted in state 1, but not states 0/2. Completion `0xb404` in state 2 selects `0x00ecf714={06,00}` → `0x00ecc1ac`, invokes saved callback `0x00ec9878`, and returns state to 0. The consumer dispatches that completion even for nonzero driver status; the already-disconnected status `-13` is not by itself a callback barrier.

The other registered callback is consumed by queue-`0x22` request `0x3200`: `0x006d35e0` → `0x006d33c8` can invoke saved `0x00ec554c` immediately when no transition steps are required, including current/target mode 1. A nonempty transition plan instead waits for its completion event before consuming the saved callback. This binds both callback consumers, not an unconditional hardware-completion guarantee.

`0x00ec2870` sets backend group 1 to state 4 and registers callbacks `0x00ec9878`/`0x00ec554c`, which post `0x9706`/`0x1200`. Matrix `0x00ec47fc`, stride 7, accepts either completion order:

| First completion in state 4 | Intermediate state | Second completion and reset action |
| --- | ---: | --- |
| `0x1200`, cell `0x00ec483c` | 5 | `0x9706`, cell `0x00ec485a`, action 8 → `0x00ec290c` |
| `0x9706`, cell `0x00ec4858` | 6 | `0x1200`, cell `0x00ec4840`, action 8 → `0x00ec290c` |

`0x00ec290c` calls `0x006a6fd8(1)` before sending the `0x816` response or evaluating its returned status. No identity query is required by this reset branch. A `0x504` with backend group 7 in state 0 instead reports `0x91b` without selecting this reset. Callback delivery, queue failures, concurrent transitions and installed 1.00 correspondence are not established by these static cells.

Action 8 is a data word, not a branch. Dispatcher `0x00ec090c` loads the machine-1 action table from `0x00ec52c4` (`0x00ec52c0 + 4*1`), which holds `0x00ec47b0`; it indexes that table at `0x00ec0980` and calls through `blx` at `0x00ec0990`. The table's slot 8 is `0x00ec47d0` = `0x00ec290c` and slot 7 is `0x00ec47cc` = `0x00ec28d4`. Matrix cells `0x00ec4840` and `0x00ec485a` are the only cells naming action 8, and `0x00ec47d0` is the only aligned word in image 5 holding `0x00ec290c`; no `bl` targets it. The callback's 52 bytes `0x00ec290c`-`0x00ec293f` are `push`, `mov r0,#1`, `bl 0x006a6fd8` at `0x00ec2918`, then `movw r0,#0x816` and `bl 0x00ec631c` with `[0x015c1e84+0x1bc]` and the 3/`0xff` status, so the reset call is one instruction separable from the `0x816` notification. Reset dispatch `0x006a7010` (`cmp r7,#2`) sends every value but 2 to the factory copy, and `0x006a7554`-`0x006a7560` add the custom defaults and compare-before-commit for value 1 (E-JIG-EXIT-ACTION8-150).

**Lead, static only:** x70view proposes a RAM guard that rewrites `0x00ec47d0` to a copy of this callback with the `bl 0x006a6fd8` replaced by a NOP and the `bl 0x00ec631c` relocated, keeping the `0x816` notification, and states that X-M1 has no established bypass ([`service-exit/xm1-150.md`](https://github.com/justjake/x70view/blob/6287653605/research/service-exit/xm1-150.md), unreviewed). The relocation word for a stub at `0x010f8000` checks as `0xebf738bd`. Its region ownership, cache publication, writer path and physical exit ordering are open there, and no patch is built here. The mapped End Setting route (function 5) sends its `0x816` from the modal-`0x62` lifecycle cleanup, not from action 8 ([lifecycle limits](#lifecycle-limits-and-session-implication)), so the guard bears only on the disconnect route above.

### Reset routine and persistence

`0x006a6fd8(0 or 1)` copies a default 16-byte header and `0x118` ordinary-setting bytes, overlays cached model/configuration values, clears selected fields and restores counter fields from the saved mirror. It is not a calibration-area erase. Language state is among the ordinary fields. `0x006a6ddc` recomputes the header checksum and issues changed-byte writes through the encoded retained-byte interface.

Argument 1 additionally invokes custom constructor `0x006a877c` and compare-before-commit routine `0x006a86c4`; argument 0 can reach the same routine through the startup flag. Argument 2 follows a narrower counter/header reset path. Full ordinary reset also calls `0x00648368`, which clears configuration RAM structures and marks dirty flag `0x0089f66c`. Consumer `0x00647f40` can attempt to commit the resulting `0x800`-byte configuration record through `0x006abddc` and the native writer, using logical blocks `0x3ea`/`0x3eb`.

`0x006a86c4` compares bytes `0x0089f83a`–`0x0089f863` against `0x0089f876`–`0x0089f89f`. Equal bytes skip the native commit. A difference can reach this route, subject to the backend guards:

```text
0x006a86c4 -> 0x006ac7d4 -> 0x006ad3f4 -> 0x006addf0
             -> 0x006ab2f4 -> 0x006a8c94 -> 0x006fb7c8 -> 0x006fdb60
```

This is the native flash-log write route. Custom area descriptors at `0x007c8d38`/`44` select logical blocks `0x3d8`/`0x3d9`. General-settings logical area 2 selects `0x3d6`/`0x3d7` through `0x006adbe4` case 2 and `0x006aafdc`; the previously inherited `0x3d2`/`0x3d3` pair belongs to backend case 1. These logical block identities do not establish installed physical placement or write success. The retained-byte interface behind those writes is now identified. The header writes take `0x006a6ddc` → `0x006a59b8(index, byte, 0)` → `0x006a57e4` → `0x006a5750`, one command/response byte transaction on device interface `(9,2)` opened by `0x0064a65c` (select `0x64bf40`, command word `0x64c4e0`, status poll `0x64d29c`, byte read `0x64d1f0`, end `0x64c1cc`, release `0x64bd1c`); the command word is `(address & 0x7f00) | 0x8000 | value` for a write and `address & 0x7f00` for a read. The companion side uses the same encoding (`0x5000 + (i << 8)` reads, `0xd000 + (i << 8) | byte` writes in `FUN_00012ad0`) over the channel engine at `0xfff84040`, so both sides address one serially attached retained register bank: header bytes `0x50..0x5f`, boot-mode register `0x6000`, clock counter `0x41..0x44` and the flag registers, retained across power-off. **byte-read**, and the live probe read identical header bytes through both sides. The physical device technology (serial EEPROM, RTC or PMIC register file, or another battery-backed bank) is not named by any artifact and remains **unproved**; the binding fact is the identity of the interface-`(9,2)` driver family, a component marking or a schematic.

Ordinary reset does not directly commit the general-settings log. Commit routine `0x006a8074` builds and compares the live record against its saved snapshot, then calls `0x006ac7d4` for area 2 when changed. Callbacks `0x00ec2cb8` and `0x00ec4154` invoke both this routine and `0x00647f40` under their own state-dependent selectors. Post-exit commit ordering is closed at the byte level. On the orderly route the queue-2 code-2 handler `0x00ec2cb8` runs `0x006a8074(1)` and `0x00647f40` and only then enqueues the `0x93e7` step, and the group-4 base cell `0x015b8080` reaches 1 only through the code-2 cell `0xec4778`, so `0x00ec2d18` and its `0x7401` journal trigger cannot run in any cycle where the save did not run first (**byte-read**, `event-route.md` sections 4.1 and 7). On the reset route `0x00ec290c` calls `0x006a6fd8(1)` before sending the `0x816` response or evaluating its status. The queue-2 receive loop `0x00ec2668` is single-threaded with infinite timeout, so codes are processed in arrival order, and matrix `0x00ec47fc` accepts either stop-completion order (states 4→5→8 or 4→6→8). Error behavior: the four query handlers' failure branches prepare transport error/stall state and no replacement application command; the driver event-9 stop rows post `0xb404` with their status from all twelve states and `0x00eca214` dispatches nonzero status as well, so error completions can still reach the clear; completion events 2 and 3 set barrier bits `0x002`/`0x001`, the full mask resets group-4 state before cleanup and a later completion requests `0x91b` through `0x00ec2d04` rather than a second `0x816`; the replay covers missing, duplicate, reordered and late completions and reports `normal_boot_exit_proved=false` in every scenario (**byte-read**, **inherited** from `event-route.md`, `physical-exit.md` and the offline replay). Physical exit ownership, runtime delivery and timing of the asynchronous completions, the concrete channel-state precondition (group-0 base 3, group-2 base 2) for the save dispatch, the consumer of the `0xa04 → 0x500e → 0xa2f` request table at `0x14e32b0`, which of `0x00ec2cb8`/`0x00ec4154` an ordinary power-off selects, and native write success under power loss whose return values the callers discard all remain **unproved**.

### Explicit reset callers and early boot state

Service-side dispatcher `0x00dbaa50` separately invokes `0x006a6fd8(1)` when its selector, read from configuration index `0x81`, equals 5. The disconnect callback `0x00ec290c` reaches the same constructor through the state graph above. Neither route is identified as HyperFFW End Setting. ## Settings-preserving exit research
