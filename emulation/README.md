# Emulator development runtime

New full-system emulator development uses jitl (justjake)'s FujiMod Rust runtime, with Haskell host orchestration. The retained Python engine is frozen legacy for surfaces not yet ported and remains the gating reference until one reviewed cutover qualifies the FujiMod counterparts with the complete `verify-candidate` and zero non-timing differences. The bounded native tools below remain independent gates.

The checked-in Nix build fetches the exact FujiMod commit and submodules in `build-support/fujimod.nix`; `build-support/fujimod-xm1.nix` builds our adapter against that source. No sibling checkout is needed. To upgrade, bump `rev`, the recursive source `hash` and `cargoHash`, review upstream changes and `fujimod-unicorn-context-align.patch`, and refresh `emulation/fujimod-xm1/Cargo.lock` if dependencies change. Requalify the resulting engine before changing acceptance gates. Use the existing `--fujimod` counterparts where available.

The retained engine still owns acceptance gates and unqualified browser, flash-candidate, fixed-scene, strict-conversion, diagnostic and fixture workflows. Bulk-read and AF-ring have FujiMod counterparts pending qualification; updater verifier/NAND coverage remains separate. The [decision report](../reports/emulator-runtime-decision.md#retained-capabilities-still-missing-from-the-supported-fujimod-path) records the boundaries and the weaker mutable-code CPU-admission guard.

The owner accepted USB-toggle comparison exclusions for `sid` and `cells_after_start`. They are engine bookkeeping, not camera behaviour. Other retained comparison assertions remain unchanged.

Local FujiMod development does not authorize binary distribution. Our software remains AGPL-3.0-only; [LICENSING item 7](../LICENSING.md#release-decisions) retains the no-conveyed-FujiMod-binaries restriction until an upstream licence file lands and is reviewed, alongside the separate Unicorn obligations.

## Secondary-core peer witness: pre-execution plan

[#134](https://github.com/skeet70/latent-image/issues/134) adds a distinct observation of retained record-2 startup. It does not replace the existing core-0 first-stage witness or retire record 2. The frozen observer SDK passes its 70 package harness tests (`E-PEER-OBSERVER-SDK-HARNESS-150`). One separately reviewed natural-reset baseline reaches all four core-1 stops and passes the production receipt consumer (`E-PEER-NATURAL-RESET-BASELINE-150`); held-sentinel and delayed-release guest controls remain unrun. Source findings are `E-PEER-ENTRY-FRAME-HANDOFF-SOURCE-150` and `E-PEER-MODEL-OBSERVATION-SOURCE-150`; the [startup inventory](../reports/replacement-inventory-baseline.md#86-retained-secondary-core-startup-boundary) owns the exact frame, banking, publication and unresolved-vector facts.

### Frozen baseline

The baseline is one natural reset, no checkpoint or owned candidate, using the original X-M1 1.50 DAT SHA-256 `43d67afa1a2bc9ae8481bc0acf02cb085ed0f515122dcbd26addcae102cd1490` and captured 16 KiB ROM SHA-256 `4ecedfbfc1910bde488d36abe4380621f8845e6afcfc6cf54a49a33ec0abf9be`. It uses FujiMod pin `3d90035d7d8d651e126f89f94f30765506e6f53f` plus the checked-in context-alignment patch and the X-M1 run document. Freeze the adapter/consumer revision, run-document bytes, contract and expected-input identities before the future run. Keep failed receipts and diagnostics. Do not repeat an unchanged failure.

Preparation validates the DAT and record-2 hash `2f1bf3f0e483b892d2890599679c1b515cfc1be8b8c27cbb06d4d913e428abb4`, extracts/decodes original image 4 with the existing `fflzd` convention and derives its word `+0xc` (`0x0069cdf8` for these bytes). It also checks segment id 1's load `0xd0000` and header entry `0xd0020`. The target and argument are independent fields. No SDK execution is necessary to prepare this contract or to consume a saved receipt.

Before the first guest instruction, validate the configured processor identities, held/released core states and static/decoder memory-map assumptions; arm instruction points on **both** cores and the alias-aware memory watch. Configured CP14 identities `0x4003`/`0x5003`, Cortex-R5F proxies with the R4F guard, initial held PC `0x3fff0000`, vector SRAM aliases and software-interrupt-driven release are model laws, not measured physical facts. Do not set either core's PC, seed a rendezvous cell or force release from the host.

The SDK interface is `--peer-witness CONTRACT.json`, mutually exclusive with `--witness`; its closed schema-1 contract is `{"schema":1,"budget":20000000}`. The baseline aggregate entered-instruction cap is 20,000,000, within a hard maximum of 50,000,000. It ends at the pre-instruction loader-B entry, not a later application or menu milestone.

| Ordered stop, always core 1 | Required observation |
| --- | --- |
| `record-2-entry`, `0x11800` | r0–r12, SP, LR, CPSR and shared state before initialization; no fixed entry-register or frame assumption |
| `record-2-rendezvous-tail`, `0x11f40` | Current r6 = 1, `r11=sp+60`; 24 saved bytes at `r11-20`, saved LR `0x1183c` |
| `record-2-handoff`, `0x11850` | Masked A32 little-endian SVC; r3/target = `0xd0020`, r0/argument = original image-4 `+0xc`; restored SP = tail SP + 64 |
| `loader-b-entry`, `0xd0020` | Same handoff argument and restored SP; independent shared-state readback |

Each stop retains aggregate entered-instruction counts and must be strictly later than the preceding stop. Matching an address on core 0 is a refusal, not a peer observation. Stop snapshots expose only the active register bank. Neither incoming banked state nor all SPSRs become known by sampling current SP/LR/CPSR.

The watch covers physical rendezvous `[0x20000,0x20008)`, completion `[0xa00c4,0xa00c8)` and publications `[0x14c80,0x14c88)`, including guest `0x40000000` aliases and decoder views. Require core-0 `0x22b` write attempts at PC `0x1e64`/`0x1e68`, core-0 clear at `0x1ff8`, core-1 clear of guest `0x40020004` at `0x11f4c` and core-1 target/argument stores at `0x11f98`/`0x11fb0`. Retain guest/physical address, width, value, before bytes, byte order, core, PC, aggregate instructions and tick for CPU attempts. A pre-store callback is not a committed-store receipt: require both cells zero and the expected target/argument in the later handoff and loader-entry snapshots. Record completion without requiring it to remain zero while core 0 executes concurrently.

Model-bus transfers and host reads/writes retain distinct sources and null CPU identity/counters; they cannot satisfy a CPU-writer requirement. Snapshot readback itself produces `host-read` rows. CPU reads and fetches remain typed separately from writes. The watch includes polling reads and has a 16,384-row cap; overflow or any watch violation fails with retained evidence. The complete `peer-witness.json`, including failure output, is bounded to 16 MiB.

Future execution uses one emulator slot (`XM1_EMULATOR_SLOTS=1`), the normal Nix daemon without sudo or a containment workaround, and a separate Bazel output base with `--batch --jobs=2`. Preparation, host verification and guest execution remain separate steps. Source inspection and receipt-consumer controls do not establish guest runtime acceptance.

### Host preparation and explicit launch interface

`//emulation:peer-stage-witness` is the SDK-independent host target. It has receipt-only and preparation modes; neither starts a guest. Set `PEER_STAGE_WITNESS` to its reviewed built launcher, `FFLZD` to the existing decoder, and `DAT` to the original validated input. ```

The expected-input file records the firmware path/hash, record-2/loader-B/image-4 hashes, decoded argument/source address, loader load/entry, CP14 identities, stop labels and row limit. Receipt-only validation needs no firmware or SDK dependency:

Instruction/watch/receipt caps do not replace these host bounds. The single baseline exited successfully after 5,845,535 aggregate instructions with 5,063 watch rows and no watch violation; it stopped before executing loader-B entry. Its resource-only launcher verified 4 GiB memory, zero swap, 25% CPU quota and CPUs 4,5 inside the existing guard service, then admitted its sole start sample at 55.125°C.

### Source-bound guest-side wait controls

`//host:peer-wait-control` prepares two fixed guest-side controls from the original validated DAT. `//replacement/peer_wait_control:peer-wait-control-image` supplies the exact linked delayed-release veneer; the builder checks its bytes, symbols and branch destinations before either control can be accepted. `ControlManifest` binds the original and candidate DAT/record-1 identities, unchanged record-2 and loader-B identities, expected/replacement words, file/slot/guest coordinates, checksum change and all other DAT bytes remaining equal. Control DATs and manifests belong only under ignored `private-data/`. These source interfaces do not qualify an executed guest control.

- Held sentinel: let the guest establish the original `0x22b` value, hold the guest writer before its clear, and observe core 1 repeatedly taking the original equality wait. Bound the wait, require unchanged sentinel readback and no handoff, and stop before later startup.
- Delayed release: after observing that hold, let the guest control permit the original core-0 clear. Require its core/PC-qualified attempt and committed readback before core 1 exits the wait and reaches the original handoff with the original target/argument.
- Wrong-core and wrong-handoff receipt mutations exercise host-consumer rejection only. They are not executed guest controls and supply no evidence of natural release, wait duration, loader-B completion or application entry.

Both controls change only the original core-0 gate at `0x1ff4`; delayed release additionally uses the 104-byte padding interval `[0x100,0x168)`. The original STR at `0x1ff8`, DSB at `0x1ffc`, record 2 and loader B remain unchanged. The delayed veneer saves r0-r3/r12/LR and NZCVQ, polls the peer cell with a bounded backoff, waits after acknowledgment, restores the gate context and branches to the original clear. Its stack requirement is a checked runtime precondition, not a previously observed fact.

The existing SDK option accepts the closed control contract `{"schema":2,"control":"held-sentinel","budget":10000000}`, or `delayed-release`. Schema 1 remains the natural baseline. Schema 2 adds core-1 `peer-wait-loaded` at `0x11f78` and core-0 gate/acknowledgment/clear/failure stops at `0x1ff4/0x14c/0x1ff8/0x148`. All applicable sites are prearmed on both cores; matching the wrong core fails. Gate/peer/acknowledgment ordering is partial. The fourth held-load observation ends held sentinel; delayed release keeps handoff/loader guards active after removing only completed control sites.

Gate acceptance requires core-0 SP `0x700007f0`, masked A32 little-endian SVC, the source register context, committed low-RAM decoder choice 1 with mapping `0 -> physical 0`, size `0x4000`, permissions 7, actual ATCM/BTCM registers `0x70000011/0`, and exact virtual/physical code bytes at `[0x100,0x168)` and `[0x1fe0,0x2000)`. Forty stack bytes at `[0x700007d8,0x70000800)` are read through core 0. This TCM has private CPU backing; it is not claimed equal to Board physical RAM. Failed receipts may retain a gate stop with null bindings when binding observation fails; passing receipts require complete bindings.

All schema-2 instruction counts are aggregate **entered** counts, including attempted-access counters. Each clear microstep records both per-core counters and requires aggregate delta exactly one; any other delta fails closed. Delta alone is not instruction-execution or retirement evidence. Original-clear completion additionally requires core 0 before PC `0x1ff8`, original STR bytes `00 20 83 e5`, after PC `0x1ffc`, unchanged CPSR, no machine failure, matching core-0/PC attempted metadata and immediate physical zero readback before another CPU entry. The final attempt and readback entered counts are equal. The SDK scheduler retains `next_core` and remaining quantum across pauses (`board/mod.rs:779-795,894-904`, `board/schedule.rs:9-29`); the observer neither selects a core nor resets its quantum.

An instruction-point stop excludes its unconsumed next entry. A completed original LDR's attempted-read count may equal the following `0x11f78` stop count. Acceptance permits that equality only with the exact core/PC/alias/value/preimage, loaded registers, independent state and watch-cursor interval. All four held-load stops must still precede the original clear. New public-SDK fixtures cover load/stop equality and rejected site removal during active capture observation; they remain unrun.

The original record-2 word `0x0afffff8` at `0x11f7c` branches to `0x11f64`. The first equality load bypasses the delay; subsequent loads are 304 core-1 entries apart: MOV, 100 NOP/SUBS/BNE iterations, LDR/CMP/BEQ. The veneer release loop uses 8,192 core-0 entries, plus its setup and restoration. The scheduler preserves partial 1,000-entry slices across observation stops. TCM selectors are BTCM 0 and ATCM 1 in the pinned model.

The fixed control limits are 10,000,000 aggregate entered instructions; 4,000,000 through the primary gate; gate-to-four-loads 4,000,000 for held sentinel; gate-to-clear 5,100,000 for delayed release; 2,048 one-entry clear windows; committed-clear-to-loader 20,000; exactly four recorded held loads, at most 128 actual peer equality reads and 8,192 veneer polls. Successful receipts permit at most 12,288 watch rows under the existing 16,384-row collector and 16 MiB receipt limits. The existing 120-second child and 1 MiB per-stream host bounds remain active.

Host-only control preparation and saved-receipt consumption use:

```sh

"$PEER_STAGE_WITNESS" --control-receipt "$CONTROL_RECEIPT" --control-manifest "$CONTROL_PREPARATION/peer-control-manifest.json"

Explicit control launch passes the candidate DAT through the existing `--update` argument. `//host/firmware:peer-wait-control-tests` and `//emulation:peer-wait-witness-tests` exercise artifact/receipt consumers. Serialized wrong-core, wrong-handoff, wrong-alias and attempted-without-readback cases are consumer controls, not guest fault evidence.

All six host suites pass: first-stage/peer-stage/peer-wait receipt consumers, first-stage/control artifacts and research schemas. ## Case contract and execution authority

[Native-case schema v1](../schemas/native-case.schema.json) precedes the consumer. The Haskell `native-case` adapter uses pinned Aeson, shared strict JSON guards and the trusted host `sha256sum` executable to reject duplicate/unknown fields, unsupported profiles, non-regular files, bad hashes/slices, overflow/overlap, unsupported permissions/state, invalid expectations and zero budgets. Artifact paths stay beneath the physical case directory. It verifies each complete artifact's exact SHA256, then sends the same observed bytes and declared slices in a bounded text wire to the runner, which never reopens artifact paths. This small host adapter avoids adding a target JSON/crypto dependency. The runner is the execution authority and independently checks its closed wire version, all addresses/lengths, permissions, logical containment, stack/state, functions/stubs, and nonzero limits, including malformed direct wire.

All r0–r12, SP, LR and CPSR are supplied. CPSR admits user ARM mode with explicit NZCV flags only; entry and LR/exit are separate explicit addresses. The stack top is eight-byte aligned inside writable memory. Regions carry `r`, `rw` or `rx` permissions; each region's bytes are zero-initialized explicitly or come from an exact artifact slice with explicit zero-filled remainder. An expected memory entry in an `r` region is admitted only when its bytes equal that region's initial slice, so it observes an unchanged value and grants no write permission; a changed expectation there is refused before execution. `rx` regions must end at or below `0x7ffffffc`: the MPU stays disabled, the PMSAv7 default memory map is execute-never from `0x80000000` (on an R4F too), and the four-byte margin makes running off a region's end report `fetch_guard` rather than an abort. Every transitive function starts at an allowlisted address and has a nonoverlapping bounded executable range. ARM BL/BLX-register calls are tracked to declared functions or register-only stubs; B/BX tail transfers to declared functions retain the current call frame. Returns use BX LR or LDM with PC naming the recorded return address or exit sentinel. Thumb and untracked PC-loading returns are excluded. Register-only stubs require exact named input values and explicit r0–r12 outputs, change LR to the return address, and emit exact input/output events; unknown targets and mismatched inputs fail.

Unicorn requires page-aligned backing, but the runner's logical regions can start/end inside pages; each backing page carries the union of the permissions of the regions it touches, and backing pages grant no guest access. The memory hook admits every guest read and write at the engine-reported address against exact logical containment, permission and natural alignment, and refuses any other access through the engine's native access refusal before it happens: the instruction stops at its own PC without that access, and earlier permitted accesses stand. At the first access of an LDM/STM or a pre-indexed immediate or register-offset LDRD/STRD the hook admits the instruction's whole transfer, so a refused transfer leaves memory and destination registers unchanged. Doubleword transfers require word alignment. Unmapped accesses fault and are refused. Addresses wrap modulo 2^32, as the architecture computes them, before containment is checked. Instruction semantics belong to the engine. The profile refuses as `unsupported_instruction`, before execution and regardless of condition, coprocessor, supervisor-call, unconditional-space, status-register write, hint and synchronization-primitive words, A32 divide, any PC destination outside the tracked branch, call, return and dispatch forms, and the ARMv7 UNPREDICTABLE or UNKNOWN forms: writeback with Rn = PC or Rn among the transferred registers, register-offset Rm = PC, byte Rt = PC, doubleword Rt = 14, a load-dual offset register in the pair, multiply PC operands and RdHi = RdLo, empty or Rn = PC LDM/STM lists, LDM writeback with the base listed, and STM writeback with the base listed but not lowest. Words the engine decodes as undefined also stop as `unsupported_instruction`. Shared-page RX/RW and multi-store failure fixtures require unchanged protected bytes.

The runner checks every engine call, stops on any exception the core raises, and imposes the instruction budget, a monotonic wall deadline and the engine watchdog. The adapter adds a process timeout, an 8 MiB cap per stdout/stderr stream, process-group termination and bounded reaping, and preserves partial diagnostics if the engine stalls. ## Outputs and limitations

The report identifies the exact case, verified artifacts, wire and runner by SHA256. It preserves full register/final logical memory state, instruction count, monotonic elapsed nanoseconds, the engine error code, stub events and the last 64 instruction/access records. `trace_total` and `access_total` expose truncation; access values are meaningful for writes, while read hook values are unspecified. The access log holds reads, writes and faults, not fetches, and a refused access is its last entry. Expected memory spans define the entire permitted final change set; every undeclared byte must equal its initial value. A normal return alone cannot satisfy a fixture. Invalid case, runner error, expectation mismatch and external timeout all exit nonzero with diagnostics.

`memory_provenance` retains the first 4096 valid logical read/write events in execution order, with the instruction PC, instruction word, address, width and value. Read values are sampled from emulated memory rather than Unicorn's unspecified read-hook argument. Write values are sampled at the pre-store hook. `memory_provenance_total` exposes truncation; a provenance experiment must reject a truncated log. Guard-rejected accesses remain in `accesses`, not `memory_provenance`. These are emulation events, not silicon bus observations or an automatic taint analysis.

This subset models no X-M1 stock ABI, exceptions, peripherals/MMIO, scheduler, interrupts, DMA, caches, coprocessors or hardware timing. Changing the profile's refusals requires independent fixtures. The scanner copies the preceding raw `+0x16` to `+0x17`, evaluates the new external level, then calls `0x006a2fa8` for rows without flag `0x100` (`0x006a3478..0x006a34a4`). The ADC navigation rows 14..20 and GPIO dial-push row 22 have debounce threshold `+0x14 = 2`. `0x006a2fa8` resets equal-sample count `+0x18` to 1 on a changed raw level, otherwise increments it, and changes debounced `+0x15` only at the threshold (`0x006a2ff0`). Press and release each require two matching scanner observations, one complete 10-tick scan interval apart, plus the phase to the first observation and dispatch latency. There is no phase-independent shortest guest-instruction hold. Host release polls request 250,000 instructions and pause at ordinary scheduler quantum boundaries. The exercised running rows have repeat initial/reload counters 40/10. The sub-command registration at `0x006a406c` uses period argument 2 and callback `0x006a3b4c`. These are firmware/model bindings, not measured physical scan periods.

The [saved input timebase findings](../reports/autofocus-static-map.md#emulator-input-timebase-saved-initial-states) record the instrumented first-OK comparison and actual metadata-only checkpoint decodes (`E-XM1-KEY-PULSE-TIMEBASE-150`). The accepted and newer checkpoints have different saved clock, phase, instruction and scheduler initial states. The newer first OK still fails under the unchanged pulses, and the newer pin remains unqualified.

`devenv.nix` points `X70_UNICORN_LIBRARY` at jitl's public Unicorn fork (`build-support/unicorn-x70.nix`), whose `uc_embedder_*` exports the preserved native engine uses for translation filtering, exact block budgets, budgeted block accounting and page-granular store hooks. The engine falls back to its slower paths when an export is absent, so setting `X70_UNICORN_LIBRARY` to the stock `pkgs.unicorn` library still runs. The engine never enables the fork's parallel TCG or asynchronous pause, and its only unmapped-access callback never reports an access handled, so the unmapped-hook TLB refill of `586dd3b2` does not apply to it. The library's SHA-256 is part of a portable checkpoint's native identity, so checkpoints saved under one library do not load under the other.

Rust also owns X-M1 phase-clock deadline advancement, pending-route delivery, source-edge lookup and linear-gradient pixel sampling. Device register dictionaries, checkpoint fields, IRQ order and quantum boundaries are retained. Scene pixels are generated at image DMA delivery after destination/route validation, without suppressing frames or altering the animated source.

Rust (`xm1-upstream/native/src/irq_mask.rs`) also owns interrupt-source ownership across the kernel's group-mask window. X-M1 1.50 `0x42b00`/`0x42eb0` clear a source's whole 32-source enable group and restore it on the calling core's bank (E-XM1-IRQ-GROUP-MASK-WINDOW-150). A line that a clear-enable write disables stays owned by that bank until the next set-enable write to its group there. A source raised at an owned, masked line latches pending; that write delivers it if it re-enables the line and discards it otherwise. Image data (`image_stream` and the image-work data profile), `producer_stream`, `display_timing`, the application timer and both control-bus profiles route through these owners instead of live enable bits; a source with no owner, or with two where it needs one, still refuses. **The latching law is declared and unmeasured:** whether physical sources latch while masked is not hardware-observed. Python keeps the bank words and register dispatch in `xm1-upstream/emulator/interrupts.py` (E-XM1-IRQ-MASK-LATCH-150).

Haskell owns the supported launcher and candidate validation; Rust owns native execution/raster/statistics paths. Substantial retained Python device/scheduler/viewer code remains migration debt. Unicorn bindings are available to Haskell and Rust; C ABI dependencies do not require C callers. [Current Haskell/Rust ownership](../docs/principles.md) applies to new work.

This is a usable stock-firmware UI testbed, not a complete silicon-faithful hardware emulator. It does not accept the original T1 captured-dump gate, autofocus/exposure accuracy, physical recovery or every menu/mode. [Current evidence and ABI boundary](../reports/full-system-emulation.md#119-interactive-x-m1-application-emulation); capture upgrades are tracked in [GitHub Issues](https://github.com/skeet70/latent-image/issues).

## Portable checkpoint keys

The Haskell launchers compute every portable-checkpoint key (`emulation/Emulation/CheckpointKey.hs`) and pass it to the bridge, which saves and restores under that name and records the key document beside the checkpoint. A key is the SHA-256 of a schema-2 document naming the checkpoint route, the guest-state digest and the route's own inputs.

The guest-state digest covers each file of the staged `emulator`, `firmware`, `inputs`, `native` and `tools` trees by runtime-relative path and SHA-256, the Unicorn library's SHA-256 and the Python interpreter: the canonical store path of `XM1_VIEWER_PYTHON`, or for the cardless bridge the embedded runtime's environment, base interpreter, ABI and version. It leaves out the viewer's HTTP server, page and launcher (`emulator/server.py`, `emulator/web/`, `tools/start_setup_viewer.py`), the scanout launcher and its bridge commands (`tools/continue_rec_scanout.py`, `tools/scanout_commands.py`), the Rust sources and tests beside the staged `_native.abi3.so`, every other entry of the runtime directory (the launcher copy, `.tools/`, run outputs), the Haskell launchers and the runtime root. The rest of `tools/` stays in: `scanout_attach.py` assembles the cold board and drives the first-start keys and ff80 attach, `probe_setup_menus.py` and `menu_render_settle.py` drive the guest to the saved boundary, `firmware_registry.py` resolves the profile, and the testbed modules the device models import reach `x70_buttons.py`, `decode_af_sweep.py` and `afs_load.py`. An edit to any of them, such as d6c552d's first-start pulse change, cold-boots the next run. A command-handling edit changes no attach key: the launcher only parses options and serves the protocols, and `scanout_commands.py` executes the transfers, keys, captures and checkpoint saves the e2e asks for after the attach boundary.

| Checkpoint | Directory beneath `private-data/emulator-checkpoints/` | Route inputs in the key |
| --- | --- | --- |
| Card attach (`xm1-viewer --ram-push-e2e`, flash candidates included) | `xm1-ram-push/KEY` | profile path, installed DAT, adjustment NAND and card image SHA-256, attach-hold key, UI conversion profile and fixed scene frame when set |
| Cardless attach (`cardless-ram-push-bridge`) | `xm1-ram-push-cardless/KEY` | profile path, installed DAT and adjustment NAND SHA-256, UI conversion profile, fixed scene frame when set, the board options the bridge sets before boot (`entry`, `sd_card_present`, `sd_card_profile`) |
| USB-toggle route boot (`usb-toggle-emu`) | `xm1-usb-toggle/KEY` | profile path, installed DAT and adjustment NAND SHA-256, reset inputs, the first-start route steps, the fixed scene frame when set |

Install checkpoints `KEY-installed-H` extend an attach key with the pushed manifest and runtime hashes and the host RAM-push procedure: the `RamPushProcedure` digest of the compiled procedure sources (`EmulatorUsb.hs`, `Xm1RamPushE2E.hs`, `CardlessRamPush.hs`, `FujiAF/RamPush.hs`, `FujiAF/Transport.hs`) and the staged `tools/scanout_commands.py`, combined by `Emulation.CheckpointKey.hostProcedure`. The bridge records `procedure_sha256` in the install record and names the directory with it, and the launcher restores an install checkpoint only when it matches. A command-handling or compiled-driver change therefore restores the attach checkpoint and pushes again, saving a new install checkpoint instead of loading the old one. FujiMod install checkpoints keep their own bridge identity. Other inputs from 256 MiB, such as the 4 GiB card image, are hashed with the devenv OpenSSL (`XM1_OPENSSL`). `//emulation:checkpoint-key-tests` checks which staged edits keep an attach key or an install identity and which change it.

A checkpoint restores under any runtime root. The portable checkpoint's own load check compares loaded-module digests; `emulator/provenance.py` encodes code filenames and `Path` constants beneath the runtime root as `<runtime>/RELATIVE`, and `emulator.boot` imports the viewer server only in its command-line entry, so the factory module's identity does not include server code. Model state holds absolute paths only in provenance records (the installed DAT's NAND-overlay provenance, the recorded NAND and card paths), which nothing reads back into the guest.

`bazel run //emulation:checkpoint-warmup` saves the shared checkpoints of the current tree: the card attach checkpoint of the recipe-bank and Classic Chrome e2e inputs (prefix RC0 DAT, `f7-1.nand`, the Classic Chrome `card.img`), the E8 hold-Q attach checkpoint (`rc0-pinned-dat`, `f7-0.nand`, the same card), the cardless attach checkpoint (prefix RC0 DAT, `f7-1.nand`) and the five USB-toggle route boots. It starts `xm1-viewer --ram-push-e2e --warm-checkpoint` three times and `usb-toggle-emu --warm-checkpoints` together, each in its own emulator slot, and writes their logs and runtimes to `private-data/checkpoint-warmup/MICROS/`. Each launcher restores a checkpoint whose key exists and cold-boots and saves the others; `--warm-checkpoint` takes the e2e's input options for other inputs.

## USB toggle attach scenarios

`//emulation:usb-toggle-emu` runs the full-system runs E2-E7 of [the USB toggle verification plan](../reports/usb-personality-toggle.md#82-full-system-emulator) in one emulator slot and writes one `receipt.json` per scenario plus `summary.json` into a fresh directory beneath `private-data/`. Scenarios, the expected behaviour (the table of report section 3.2) and the checks are in `emulation/UsbToggleEmu.hs`; the retained Python bridge only serves primitive commands (`continue_rec_scanout.py --toggle-server`).

```sh
devenv shell -- bazel run //emulation:usb-toggle-emu -- --receipt-output private-data/analysis/usb-toggle/emu/RUN [--runs e2,e3,e4e5,e5u,e6,e7,control] [--dats stock,cc-base,cc-toggle,rc0-toggle,cc-icon-base,cc-icon-toggle] [--fresh-boot]
```

Inputs are pinned by SHA-256: the stock, Classic Chrome base, CC+toggle, RC0+toggle, design-B Classic Chrome (`cc-icon-base`, `98a66780…1606`) and CC-icon+toggle (`c1bfc9aa…ad8f`) DATs, and three adjustment NANDs layered with `--adjustment-nand` over the installed DAT: stored `0xf7 = 1` (`stored-f7/emulation/inputs/f7-1.nand`), stored 0 (`usb-toggle/emu/inputs/f7-0.nand`, f7-1 with byte `0xf7` of page `0x381*64` restored to `00`) and stored 0 with cache bytes `0x102..0x103 = b6 02` (`f7-0-pid02b6.nand`). `--dats` keeps only the scenarios on the named DATs. The template NANDs carry `0x102..0x103 = 80 ff`, which makes the boot poller choose maintenance (system mode 7) when the cable is present at reset; the body reads `b6 02` there, so E6 runs on both. Route boots restore a checkpoint saved at the shooting screen after the first-start route (100,000,000 instructions, Up twelve times, OK, OK, 40,000,000 instructions) under `private-data/emulator-checkpoints/xm1-usb-toggle/KEY`, keyed by the USB-toggle route-boot key of [portable checkpoint keys](#portable-checkpoint-keys); each run stages a fresh `private-data/xm1-usb-toggle-PID-MICROS` runtime. `--warm-checkpoints` saves or restores the route checkpoint of each DAT and NAND the chosen families boot, then stops. E2 cold-boots with the native access probe on `[0x00bf4454, 0x00bf44e4)` from the first instruction; E6 cold-boots with the cable level, and for the Q variant ADC channel 9 at Q's calibration midpoint, set before the first instruction.

Each receipt names the DAT, NAND, checkpoint key and key document (which carries the guest-state digest), lists every check with expected and observed values, and records per step the cells (`cache[0xf7]`, system mode `0x009570dc`, `0x0146a0c0`, `0x01469810`, `0x0146a0cc`, latch `0x015c229c`, Q row 19 `+0x14..+0x16`, UI bitmap bit, driver state and status, fill witnesses), the trace hits at handler A, its three arms, `0x00ed117c`, `0x00ed11a4`, `0x00ecf894`, the service start, transport start, fill, stub entry and Q key-state read with r0, r1, SP and LR, the device descriptor, the ff80 service session (C0, identity, config window 0, one function-2 read) and the usbcont stack: SP at `0x00ecf900` and the high-water mark of the `0x07` fill.

Bridge primitives added for this driver: `--toggle-server` with `run` (bounded, optionally stopping at a trace label), `key`, `press`, `release`, `adc`, `cable`, `read-memory`, `trace-sites` (optional r0 filter), `trace-hits`, `enumerate` (standard enumeration without a descriptor expectation), `transfer`, `capture`, `access-probe` and `save-checkpoint`; `--cable-at-reset`, `--adc-at-reset CHANNEL=SAMPLE` and `--access-probe-range LOW:HIGH` set inputs before the first instruction. `--ram-push-server --attach-hold-key KEY` holds a key from one default pulse before the attach edge until enumeration ends; `//emulation:xm1-viewer -- --ram-push-e2e --attach-hold-q` uses it for every boot of the e2e, including the Classic Chrome cold restart, and keys the attach checkpoint by it.

Model boundary: the endpoint model raises no controller event when the cable level drops. The transport driver samples the presence bit `0xfff55104[31]` (`0x00d7b98c`) only while its state word `0x0146a180` is 0..4 (`0x00d81d04`), so a detach after a PTP start (state 8) or after enumeration (state `0xa`) never reaches connect handler A. Detach edges are observable only after an unenumerated `ff80` start; the `e5u` scenarios exercise the E5 edge sequence that way and the `e4e5` scenarios record the boundary.

### USB toggle on FujiMod

`//emulation:usb-toggle-emu -- --fujimod ...` serves the same primitives from `fujimod-xm1-toggle` (crate `emulation/fujimod-xm1`, built by `@lab_fujimod_xm1`) on jitl (justjake)'s FujiMod runtime, with the R4F guard armed. Each receipt and `summary.json` name the `engine`.

`--fujimod --ram-push` selects the [RAM-toggle session](../reports/usb-personality-toggle.md#14-ram-push-variant): boot unpatched RC0 (`rc0`, `acb0fbbb…ca8`) with stored 1, enumerate `ff80`, allocate `0xd20`, authenticate the relink at the returned base, upload/publish the exact 23-word payload, then attempt detach and both Q attaches. ```sh

```

The FujiMod mapping:
- the cable level is the run document's `usb_cable` logic input, and `--adc-at-reset` sets a raw sample before the first instruction;
- `state` reports `asserted_keys` as the ADC keys whose calibrated interval holds their channel's sample, and `inputs_ready` as the scanner-registered word;
- `enumerate` waits for controller activation within the budget, then enumerates with no descriptor expectation; the host waits 1,000,000 instructions after SetAddress's status stage, standing for USB 2.0's 2 ms recovery interval (without it, the CC+toggle configuration-descriptor request after a Q-held attach went unanswered). ## Flash-image boot check

`//emulation:flash-boot-check` checks that an exact flash image boots to the stock menus in the full-system emulator. A flash image, such as a `//extensions:build-extension` output, must pass it before a flash go ([camera-run procedure](../spec/07-governance-and-handoff.md#3-camera-runs)).

```sh
devenv shell -- bazel run //emulation:flash-boot-check -- --firmware CANDIDATE.DAT [--output private-data/flash-boot-checks/NAME]
devenv shell -- bazel test //emulation:flash-boot-route-tests
```

The launcher applies the viewer's container validation, takes an emulator slot and stages a runtime with the viewer's inputs (`emulation/Emulation/ViewerRuntime.hs`). `--output` names a fresh directory beneath `private-data/` whose parent exists; the default is `private-data/flash-boot-check-PID-MICROS`. The upstream `start_setup_viewer.py` cold-boots the staged DAT bytes with the captured ROM, from erased settings with no card, to 80,000,280 instructions and saves a portable snapshot. The upstream `probe_setup_menus.py --interactive` then drives the route from that snapshot: Up twelve times and OK (English), OK (date), 40,000,000 instructions to live view, MENU, and 90,000,000 instructions for the menu to render. Every press is `key NAME 8000000 8000000`; with the probe's per-class default presses the route does not reach SHOOTING MENU: the language screen does not advance under the animated source, and under a fixed scene frame the MENU press leaves the retained menu node at 67/56. The command exits 0 only when every step completes without a model stop and the retained menu node ends at SHOOTING MENU, menu id 1, setting id 5, cursor 2. Any other outcome exits 1 and names the phase.

The receipt is `OUTPUT/flash-boot-receipt.json`. It records the result; the failure kind (`boot-stopped`, `model-stopped`, `input-refused`, `drive-ended` or `menu-missed`), phase, message and the viewer's `boot-failure.json`; the DAT path, size and SHA-256; the emulator source identity (one SHA-256 over the staged `emulator`, `firmware`, `native`, `tools` and `inputs/x-m1-1.50` trees, plus the ROM, native engine and Unicorn library digests and the Python path); the boot instruction and tick counts and boot frame hash; the route; one milestone per phase with instruction count, menu node and frame hash; the final instruction count and frame hash; and the final frame PNG for the owner's visual check. `boot.stderr`, `drive.stdout` and `drive.stderr` sit beside it.

Observed 2026-10-18 (emulated): stock 1.50 boots to 80,000,280 instructions, reaches menu node (1, 5, 2) at 360,016,051 and passes at 450,019,207 with the rendered SHOOTING MENU page 1. The negative control replaces the image-4 entry word at `0x0069cdf8` with `UDF` in the decoded image, re-encodes it with `//lz:lz-encode` and rebuilds the container with `//host/firmware:rebuild-update replace-record4`; `rebuild-update verify` and the launcher's container validation pass. That DAT stops at 7,867,227 instructions with an invalid instruction at CPU0 PC `0x0069cdf8` and fails as `boot-stopped`.

Boot to the stock menus is necessary, not sufficient. The check covers the first-start route from erased settings storage with no card; it does not exercise retained settings or body calibration, the updater install, card or USB paths, extension behaviour, menus past SHOOTING MENU page 1, or peripherals the model refuses. The menu node is retained firmware state, and the rendered frame is not compared automatically; the owner's visual check covers it. A model stop can be an emulator gap rather than a firmware defect, such as an unsupported peripheral transport; either way the check fails and the stop needs an explanation before a go.

### On FujiMod's runtime

`//emulation:fujimod-flash-boot-check -- --firmware DAT [--output DIR]` runs the same route on jitl (justjake)'s FujiMod EXR II runtime ([issue 97](https://github.com/skeet70/latent-image/issues/97)). `validateFirmware` admits the DAT, then the launcher holds an emulator slot and runs the driver `@lab_fujimod_xm1//:bin/fujimod-xm1` (`build-support/fujimod-xm1.nix`, crate `emulation/fujimod-xm1`) on its run document. Bazel builds the driver through Nix the first time a target needs it, capped at two jobs and four cores; `devenv shell` does not build FujiMod. The driver builds a strict FujiMod session from the X-M1 run document: the catalog's `xm1-150` processor and memory graph, the document's EXR II device plan and scene, and the DAT complemented from offset 604 into the NAND image without a catalog identity check. It answers the probe's `key`/`run`/`quit` protocol, so `judgeProbeOutput` judges its transcript. The receipt is `OUTPUT/fujimod-flash-boot-receipt.json`, with every state's frame in `OUTPUT/frames/` and the driver's wall time in `drive_wall_seconds`.

FujiMod opens Unicorn as a Cortex-R5F. Both FujiMod drivers arm an R4F guard (`emulation/fujimod-xm1/src/r4f.rs`, [principles](../docs/principles.md#scope-and-evidence)), built only on FujiMod's exported CPU hooks: a block hook on every core records each newly entered block, and after each run window of at most 1,000,000 instructions the guard decodes those blocks. It refuses:
- A32 SDIV/UDIV;
- PLDW;
- CP15 c0 ID register reads with opc1 0, which includes MIDR, MPIDR, MPUIR and TCMTR; the cache identification registers stay admitted;
- CP15 c15 accesses other than the stock data-cache invalidate `c15,c5,0`;
- CP15 c9 TCM registers other than the `c9,c1,{0,1}` region registers;
- after any block that writes CP15 c6, an enabled MPU region 12-15 on either core.

A refused block stops the run with an `R4F guard:` failure naming the instruction, its address and core, even when Unicorn itself would stop on the same instruction. T32 SDIV/UDIV are admitted, as Cortex-R4 has them. A block rewritten in place with the same address and length is decoded once. The synthetic boot-ROM fixtures in `emulation/fujimod-xm1/tests/r4f_guard.rs` run in the Nix build's check phase, so a guard regression fails `@lab_fujimod_xm1`: ordinary A32 code and a CLIDR read run, each refused encoding stops, region 12 stops and region 11 runs. **Opt-in bounded capture continuation observations**

The JSON-lines RAM-push server accepts these read-only observation requests. They add no guest execution; `shutter-sequence` still advances exactly 8M/8M/4M/4M instructions, and `capture-observation-window` remains one 40M-instruction advance. Without opt-in, legacy trace responses and shutter phase replies remain unchanged.

| Request | Response fields, in addition to `ok` |
| --- | --- |
| `{"command":"capture-observation-begin"}` | `active: true` and `bounds` |
| `{"command":"capture-observation-hits","from":0}` | A serialized page with `bounds`, `from`, `next`, `retained`, `total`, `dropped`, `incomplete`, `first_instructions`, `last_instructions`, `sites` and `hits` |
| `{"command":"capture-observation-state"}` | `snapshot` and typed `timing` inspection of the `image_input` node |

Begin rejects an active rendezvous or unconsumed legacy hits. It discards legacy trace storage and freezes the armed site set for the remaining session. A rendezvous stop during bounded observation is an error. The declared `bounds` are `sites: 256`, `label_bytes: 64`, `details_per_site: 64`, `details_total: 2048`, `ram_bytes_per_event: 512`, `page_details: 64` and `retained_memory_bytes: 2097152`. `charged_storage_bytes` reports the fixed record arena, 256 per-site statistics, collector header and 128 KiB reserved overhead; a compile-time assertion keeps their sum within 2 MiB. Allocation occurs only after validating the site and label bounds. Events with no remaining detail capacity are counted without copying registers or RAM.

Before activation, each retained site label must have both length and capacity at most 64 bytes. Labels already within that capacity are untouched. Excess capacity is shrunk conditionally; activation fails if the allocator leaves it above the bound.

`total` counts every observed hit since begin, including hits without retained detail. `retained` counts stored details; `dropped` counts hits missing detail. Each `sites` entry reports `address`, `site`, `total`, `dropped`, `retained`, `first_instructions`, `last_instructions`, `first_dropped_instructions` and `last_dropped_instructions`. Top-level and per-site first/last instruction counts cover all observed hits, not just retained details. `incomplete` is cumulative since begin and stays true after any dropped detail or incomplete RAM capture. It is not a property of only the returned page.

`from` and `next` index retained details, not total hits. Each page contains at most 64 `hits`; request `next` for the following page. A hit has `site`, `address`, `core`, `instructions`, `registers` (four numeric r0-r3 values), `sp`, `lr`, `cpsr`, `ram` and `ram_incomplete`. Each RAM entry contains `address`, `requested`, `status` and hexadecimal `bytes`. Status is `complete`, `outside-ram`, `read-failed` or `byte-limit`; failed spans retain no bytes. At most 24 span descriptors and 512 copied bytes are stored per event. Only physical RAM below `0x20000000` and its `0x40000000` alias are admitted; aliases are reported as physical addresses. The queue descriptor and its declared payload size are retained at source-bound send/receive points, subject to that byte limit. Pagination does not consume or reset cumulative counters. A page is bounded by 64 fixed-size detail views and 256 counter views, with less than 1 MiB of JSON output; it is not retained by the collector.

Detailed events prioritize the event's message descriptor/payload, callback storage and queue-specific state before the common controller/frontend/subscriber windows. Common spans that no longer fit remain present with `status: "byte-limit"` and empty `bytes`, and set `ram_incomplete`; they are not silently omitted. Phase-boundary snapshots instead collect the complete common windows and recorder bitsets, requiring 362 RAM bytes for a valid selected context.

The source-level queue-`0x30` admission calculation for `0x4007` is `12 + 12 + 12 + 4 + 4 + 4 + 4 = 52` priority bytes: descriptor, declared payload, copied arguments, callback slot, queue state and two predicate words. The common request is 246 bytes, giving 298 retained bytes across 21 descriptors. Every span is `complete`, and the event's `ram_incomplete` is false, if all direct RAM reads succeed. This is a deterministic byte-admission calculation, not a guest observation. The separate `0x104`-byte receiver copy is not a payload length; the observer retains the consumed arguments and callback words, not that copy's unused tail.

New observer instruction positions use a transparent instruction-count unit constructed from the board's per-core counts with checked aggregation. Their JSON representation remains an unsigned integer; legacy `Hit` responses are unchanged.

State can be requested at the pre-sequence and post-window stops without another guest advance. `snapshot` is the direct `CaptureSnapshot` (`instructions`, `ram`, `ram_incomplete`), or `null` while bounded observation is inactive. Controller, frontend, subscriber and recorder RAM comes from direct physical RAM reads. The request performs no acknowledgement-capable MMIO reads.

`timing` is `{"status":"available","state":{...}}`, `{"status":"absent"}` or `{"status":"unsupported","reason":"..."}`. It uses `board.inspect_device::<ImageInput, _>` and the existing fingerprint from pinned FujiMod `3d90035d7d8d651e126f89f94f30765506e6f53f`, without a model change. The named state fields are `phase_due` (two nullable device-tick deadlines), `phase_pending` (two flag words), `phase_period` (device ticks), `sensor_due` (nullable device-tick deadline), `r` (the 256-word register bank), `capture_ack` and `capture_irq_sent` (booleans). Each field is wrapped as `{"status":"present","value":...}`, `{"status":"absent"}` or `{"status":"unsupported"}`. A present nullable deadline may be `null`; a missing or unsupported field is never replaced with a guessed deadline, zero register or acknowledgement state.

While bounded observation is active, each `shutter-sequence` phase additionally returns `before` and `after` objects with the same `snapshot` and `timing` fields. `before` is captured before changing the physical shutter position; `after` is captured after that phase's existing advance. These expanded phase observations are returned only in the immediate reply and are not appended to `key_log` or retained in SDK logs.

##### Open joins and bounded read-only observation design

Physical-1's sequence record, complete for `0x00fe9580`, shows twelve `0x3f00` posts after `0x3f49` and before the stream start (above); the controller states that consumed them are not retained. ### Trajectory variants on FujiMod

Render and key timing differ between the engines, so a recorded trajectory can need different press timing on FujiMod. A FujiMod variant of `NAME.json` is a separate file, `NAME.fujimod.json`, next to it. It may differ from the retained file only in press timing:
- a segment's `key_pulse`;
- a step's optional fifth element `{"hold_instructions": H, "release_instructions": R, "settle_instructions": S}`. H and R, both or neither, replace the segment's pulse for that key. S caps the instructions the bridge runs for the render drain before the key plus the settle after it (default 90,000,000), and a key whose drain does not finish within S is not pressed (`prior-render-pending`). Only the FujiMod bridge takes S, and the e2e refuses a trajectory carrying S on the retained engine.

Every other field is an assertion and must equal the retained file's: phases, mode dials, captures, keys and expected menu states, messages, observe flags, reads, requirements, film rows and trace sites. `bazel run //emulation:trajectory-variant-check -- RETAINED.json VARIANT.json` checks this, and `//emulation:ui-trajectory-tests` checks every checked-in `*-trajectories.fujimod.json` against its retained file.

A FujiMod route counts as acceptance for a payload only when all three hold:
1. Its variant passes `trajectory-variant-check` against the retained file. A route without a variant runs the retained file itself.
2. The FujiMod e2e passes with the variant, so every required menu state, message id and film row holds.
3. `bazel run //emulation:e2e-observation-compare -- RETAINED_RECEIPTS FUJIMOD_RECEIPTS` reports no difference from a retained-engine run of the retained file with the same payload, DAT, NAND and card mode. It compares every `e2e-observation-N.json` (steps, reads, menu message ids, D3 hook entries, Classic Chrome site entries and trace hits) and every capture's menu state.

The comparison leaves out wall seconds, guest instruction counts, stack pointers, file paths, frame numbers and capture PNG digests. It compares a segment's Classic Chrome site entries as live-view develop passes, each starting at `cc-entry-marker`: consecutive identical passes count once, and the passes before the first and after the last pass that enters a converter (`cc-entry-settings-converter` or `cc-entry-capture-converter`) are dropped. One converter pass split by idle passes counts as one pass when every pass between its parts is idle and the continuation's entries before its first converter equal the first part's; the merge drops that duplicated frame prefix and keeps every remaining continuation entry in order, so a split compares equal to the unsplit pass. How many frames a segment window spans and which frame a converter call lands in are timing. Any other difference fails the rule.

### Synthetic sensor source on FujiMod

`//emulation:fujimod-xm1-sensor-fixture` derives a separate run document whose `image_input` node has a declared synthetic frame source ([#131](https://github.com/skeet70/latent-image/issues/131)). ```sh

```

Both print the identity record: fixture id and SHA-256, base and derived run-document SHA-256, and the sensor's frames name, raster, scene, asset and period. `verify` fails unless the document is byte-identical to the derivation. A run uses the derived document as the bridge's `--run`.

Attachment contract (source-inspected, FujiMod `9bb8bd90`): the image-input model takes an optional `sensor` of `frames`, `options` and `controls` (`crates/emulator-exr2-isp-input/src/construct.rs`), whose frames come from a scene `sensors` entry of width, height, `raw16` or `rgb24` pixels and a generated asset (`crates/emulator/src/session/preparation.rs`). `options.sensor_period_ticks` runs a sensor clock beside the periodic phase clock. At each sensor period `frame()` (`input.rs`) latches the frame and arms RAW channel 2 when bit 0 of `0x004` and bit 0 of `0x35c` are set, no channel-2 completion is pending and no transfer is active; channel 3 arms the same way on `0x378`. Channel 2 needs format `0x354` bits 20-22 of 3 or 4 and bit 1 of `0x004` clear; bit 16 of `0x004` selects Packed12, otherwise U16. The window is left `0x014` bits 16-29, top `0x018` bits 16-29, height `0x018` bits 0-13 plus 1 and width `0x024` bits 0-13, even and at most `0x014` bits 0-12 plus 1, and must lie inside the sensor raster. The transfer writes the window's rows to `0x358` over `raw_dma_ticks` (153,600) with pitch `row_bytes(width rounded up to (4 if Packed12 else 1) << (format + 3) samples) + 0x360`. Completion raises core 0 line 36 when `0x354` bit 28 is set, and line 37 for channel 3 with `0x370` bit 28; bit 0 of the guest's `0x350`/`0x36c` ACK rearms the channel. The fixture attaches no sensor controls, so every readout is valid, sensor commands and timing are ignored and no exposure, aperture or projection applies.

X-M1 window programming (static inference over the decompiled 1.50 images; values unobserved): `0x0065f51c` writes `0xfff10014` and `0xfff10018` from a `{x, w, y, h}` rectangle with `w` at most `0x2000` and `h` at most `0x4000`. Its only caller `0x00d9fd54` passes the rectangle at `0x016996b8` when bit 0 of `u32[0x01699698]` is set. `0x0065f8bc` writes `0xfff10024`, at most `0x3000`.

Fixture choices in `fixtures/fujimod-sensor/xm1-150-raw16-ramp12.json` are declared emulator inputs, not sensor measurements:
- Raster 5120 × 3348, the smallest raster containing the channel-2 window traced on the S2 route of a 5120 × 3300 run, which stopped at the bounded-window check: the operands of the last stores were `0x014` = `0x13ff`, `0x018` = `0x003c0cd7` and `0x024` = `0x1368`, giving left 0, top 60, height 3288 and width 4968 (emulated, 2026-10-29; operands of guest stores, not device-register reads). - CFA: the base `image_input` 6×6 layout. RAW16 readout ignores it; FujiMod's RAW readback uses it.

### updater-f7 on FujiMod

`bazel run //emulation:fujimod-updater-f7 -- --recovery-ram RAM --sd-image CARD --installed-nand NAND --output DIR` runs the same route on FujiMod (`fujimod-xm1-updater`, crate `emulation/fujimod-xm1`) in one emulator slot, with the run document, the captured boot ROM and the stock 1.50 DAT (the committed image's flash base). Sites, schedule, presses and receipt fields follow `UpdaterF7.hs`. Phase B is a second session in the same process, built from the exported file alone.
- The session starts from the raw handoff as `load_recovery_cpu0` does (`src/handoff.rs`): the companion's CRC, native-entry frame, SRAM return witness and cache-off MPU/CP15 state are checked; selection word 1 is written to `0xfff98008` so address 0 decodes DRAM, and the 32 MiB RAM image and 4 KiB SRAM are written; CPU0's banked, general, MPU, CP15 and VFP registers are set; and the three bootstrap device writes go to the clock and GPIO devices. CPU1 stays held at reset.
- The restore card loads whole (`Backing::Complete`): an image of at most 128 MiB, like the retained `immutable_backing=True`, with the 65,536-sector dirty bound left for guest writes.
- The committed NAND image (`src/nand_image.rs`) is applied by erasing every committed block and programming its pages over the base and the recorded data overlay. Export writes the retained `export_image` bytes: sorted keys, no spaces, ASCII escapes, Python's gzip header with mtime 0, and the deflate stream of zlib's `compress2` at level 9 (linked from nixpkgs). zlib-ng and zlib-rs streams differ from it.
- The run counts as idle when the whole-area commit has run, the NAND controller is not busy and the medium's fingerprint is unchanged over one 15 M-instruction chunk.

## Live-RAM calibration

`//emulation:ram-calibration` captures paused low RAM from either existing cardless ff80 bridge and compares it with the owner's Run-3 capture. `capture retained|fujimod DAT NAND PRIVATE_OUTPUT` cold-boots clean firmware with no card, enumerates ff80 and saves `[0,0x05aa0000)` before any RAM allocation or payload. It holds an emulator slot and performs no physical camera or USB I/O.

`compare BODY RETAINED_RAM FUJIMOD_RAM OUTPUT_JSON` reports disjoint region counts, zero/`0xff` populations, differing words, decoded task-stack extents and the narrow Run-3 classification rules. Input dumps must be exactly `0x05aa0000` bytes. `words BODY MODEL BEGIN_HEX END_HEX` emits the differing aligned words in a physical window. `references RAM OUTPUT_JSON` scans the recorder rev-2 span's incoming numerical pointer, A32 B/BL and bounded MOVW/MOVT candidates and records the old hook words; it does not prove arbitrary computed reachability.

The [calibration report](../reports/ram-calibration.md) owns reproduction, per-engine headline numbers, unresolved device-model families and the hardware-observed recorder remainder after rollback. All dumps and detailed receipts stay under ignored `private-data/`. A raw difference, stack permutation or synthetic-scene pixel is not automatically a model defect.
