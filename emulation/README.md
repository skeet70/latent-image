# Bounded C native-function harness

The runner uses Unicorn's C API and a closed Cortex-R5F ARM/little-endian profile for synthetic and admitted stock cases. Unicorn has no Cortex-R4; R5F is its closest model to the ARMv7-R, PMSAv7, VFPv3-D16 core inferred for the X-M1 in [E-CPU-PROFILE](../reports/firmware-extraction.md#cpu-profile). Nothing may depend on R5F-only behavior ([rule](../docs/principles.md#scope-and-evidence)); the runner rejects A32 SDIV/UDIV, and coprocessor exclusion keeps R5F ID, MPU and TCM/cache registers out of reach. Synthetic fixtures supply no X-M1 behavior or ABI evidence. No camera is enumerated or opened. `unicorn-info.c` remains the smaller engine-initialization check. Follow [phase 3](../spec/03-phases-and-gates.md#3b-native-function-harness) and the [runtime contract](../spec/08-artifact-and-runtime-contracts.md). The implemented C engine boundary and retained host C models do not establish a general C policy; [current principles](../docs/principles.md#implementation-and-build) govern new implementation and migration.

```sh
devenv shell -- bazel test //emulation:native-runner-tests
devenv shell -- bazel build //emulation:native-runner
devenv shell -- bazel run //emulation:native-case -- --runner bazel-bin/emulation/native-runner emulation/fixtures/arithmetic.json
```

The last command prints a JSON report and returns zero only when the exact expected registers, complete final memory and stub events match the expected exit. A negative fixture can pass by reproducing its independently expected guard failure; inspect `runner.status` alongside the outer validation status. Redirect reports into an explicitly chosen local artifact directory when retaining a run. [Fixture provenance](fixtures/PROVENANCE.md) derives the expected results independently of execution; `devenv shell -- bazel run //emulation:generate-fixtures -- --output /tmp/fuji-native-fixtures` writes a new directory with exact binary bytes and structurally identical JSON manifests. Canonical Haskell serialization changes JSON whitespace/key ordering; the original checked-in manifests keep their historical formatting.

## Case contract and execution authority

[Native-case schema v1](../schemas/native-case.schema.json) precedes the consumer. The Haskell `native-case` adapter uses pinned Aeson, shared strict JSON guards and the trusted host `sha256sum` executable to reject duplicate/unknown fields, unsupported profiles, non-regular files, bad hashes/slices, overflow/overlap, unsupported permissions/state, invalid expectations and zero budgets. Artifact paths stay beneath the physical case directory. It verifies each complete artifact's exact SHA256, then sends the same observed bytes and declared slices in a bounded text wire to C; C never reopens artifact paths. This small host adapter avoids adding a target JSON/crypto dependency. The C engine is the execution authority and independently checks its closed wire version, all addresses/lengths, permissions, logical containment, stack/state, functions/stubs, and nonzero limits, including malformed direct wire.

All r0–r12, SP, LR and CPSR are supplied. CPSR admits user ARM mode with explicit NZCV flags only; entry and LR/exit are separate explicit addresses. The stack top is eight-byte aligned inside writable memory. Regions carry `r`, `rw` or `rx` permissions; each region's bytes are zero-initialized explicitly or come from an exact artifact slice with explicit zero-filled remainder. `rx` regions must end at or below `0x7ffffffc`: the MPU stays disabled, the PMSAv7 default memory map is execute-never from `0x80000000` (on an R4F too), and the four-byte margin makes running off a region's end report `fetch_guard` rather than an abort. Every transitive function starts at an allowlisted address and has a nonoverlapping bounded executable range. ARM BL/BLX-register calls are tracked to declared functions or register-only stubs; B/BX tail transfers to declared functions retain the current call frame. Returns use BX LR or LDM with PC naming the recorded return address or exit sentinel. Thumb and untracked PC-loading returns are excluded. Register-only stubs require exact named input values and explicit r0–r12 outputs, change LR to the return address, and emit exact input/output events; unknown targets and mismatched inputs fail.

Unicorn requires page-aligned backing, but the runner's logical regions can start/end inside pages. Hooks reject every executed fetch or access that lacks logical containment/permission. Stopping inside a valid Unicorn write hook can still commit the current store. The runner therefore preflights **every admitted memory instruction before execution**: immediate-offset ARM LDR/STR byte or word; immediate-offset LDRH/STRH, including supported pre/post-indexed writeback; pre-indexed register-offset byte/word/halfword transfers with optional writeback and immediate LSL/LSR/ASR shifts for byte/word forms; pre-indexed immediate or register-offset LDRSB/LDRSH without writeback; immediate pre-indexed LDRD/STRD with optional writeback; ordinary LDM/STM; PC-relative and register-base load-to-PC dispatch; and tracked LDM returns. It rejects misalignment, positive address carry, cross-boundary access, unsupported PC operands and writeback-base aliasing before any transfer. U=0 subtraction wraps modulo 2^32 before containment checking. Dispatch entries must be four-byte-aligned ARM targets contained in the current function; returns must name the recorded return or exit sentinel. Register-specified-shift and ROR/RRX offsets, post-indexed register-offset forms, unprivileged transfers, atomic/banked transfers, system/PSR writes, coprocessors and other memory forms remain excluded. Register-only MOVW/MOVT, UXTB/UXTH/SXTB/SXTH with ROR #0/8/16/24, UBFX/SBFX/BFI/BFC, MUL/MLA/MLS and UMULL/SMULL without S, and tracked BLX calls are admitted subject to their operand/field restrictions; immediate and register tail transfers preserve the tracked call frame. Shared-page RX/RW and multi-store failure fixtures require unchanged protected bytes. Memory hooks remain a second guard and access log; backing pages do not grant guest access.

The C runner checks every Unicorn error-returning call and exact header/runtime version, traps interrupts, and imposes instruction and monotonic wall deadlines plus Unicorn's wall timeout. The adapter adds a process timeout, an 8 MiB cap per stdout/stderr stream, process-group termination and bounded reaping, and preserves partial diagnostics if the engine stalls. Compiled adapter limits are 16 logical regions, 4 MiB total logical bytes, 256 functions, 32 stubs, 512 expected events, 4,000,000 instructions and 10,000 ms. `//emulation:native-runner-tests` runs a case with exactly 256 functions and refuses one with 257; it admits an instruction budget of 4,000,000 and refuses 4,000,001. Artifacts are each at most 4 MiB (20 maximum); JSON input is at most 16 MiB. The engine-private wire accepts up to 512 stub definitions, but the public adapter does not expose that capacity. The checked-in v1 schema matches the 256-function and 4,000,000-instruction bounds but keeps narrower 1 MiB/32-event/16-artifact bounds; a case accepted by the compiled adapter can therefore fail schema validation. This contract gap is not permission to widen safety limits. The C wire is private v1: profile/header and limits, 16 initial register values, bounded region/function/stub counts, exact region hex bytes, function ranges and indexed register stub bindings, with no trailing tokens. All numbers are bounded before conversion/allocation.

Load-to-PC table entries are validated before execution: both register-base and PC-relative dispatch refuse targets with either low bit set. Every code hook also refuses CPSR.T. This prevents a 32-bit Thumb instruction from being interpreted as an A32 conditional instruction and executing outside the profile's preflight.

Admitted PC-relative and register-base LDR-to-PC dispatches share the B/BX tail-transfer containment after their table word is readable and their loaded target is ARM-aligned. A target inside the current function keeps that function; a target inside another declared function changes the current function without changing the caller's frame. Exact function spans and executable fetch permissions remain enforced. Condition-false dispatches do not read the table or update tracking.

`//emulation:native-runner-tests` includes 20 public dispatch controls across both addressing forms: declared, interior and in-function targets return to the original caller; condition-false skips an overflowing or unreadable table; Thumb, unaligned, undeclared, outside-span, unreadable-table and overflowing-table cases retain their refusal outcomes. The declared-target PC-relative control was observed failing with `unknown_call` before target tracking was corrected; the complete suite passed with the correction. The recipe UI's stock `LDRLS PC,[PC,R0,LSL#2]` getter path remains a separate exact-candidate behavioral gate.

## Outputs and limitations

The report identifies the exact case, verified artifacts, wire and runner by SHA256. It preserves full register/final logical memory state, instruction count, monotonic elapsed nanoseconds, Unicorn version/error, stub events and the last 64 instruction/access records. `trace_total` and `access_total` expose truncation; access values are meaningful for writes, while read/fetch hook values are unspecified. Expected memory spans define the entire permitted final change set; every undeclared byte must equal its initial value. A normal return alone cannot satisfy a fixture. Invalid case, runner error, expectation mismatch and external timeout all exit nonzero with diagnostics.

`memory_provenance` retains the first 4096 valid logical read/write events in execution order, with the instruction PC, instruction word, address, width and value. Read values are sampled from emulated memory rather than Unicorn's unspecified read-hook argument. Write values are sampled at the pre-store hook. `memory_provenance_total` exposes truncation; a provenance experiment must reject a truncated log. Guard-rejected accesses remain in `accesses`, not `memory_provenance`. These are emulation events, not silicon bus observations or an automatic taint analysis.

This subset models no X-M1 stock ABI, exceptions, peripherals/MMIO, scheduler, interrupts, DMA, caches, coprocessors or hardware timing. Extending an ISA/profile requires preflight for every newly admitted memory/state operation and independent fixtures. A stock case (`origin: "stock"`) is admitted only with an independently known result and exact input provenance; the CPU family remains static inference only. D-01's host preparation is tested and one stock path is reproduced in the next section, accepted for G3 on 2026-10-08. See the [validation scope](../reports/validation.md) and [evidence ledger](../docs/evidence.jsonl).

Stock cases below require owner-supplied proprietary decodes or body captures; they are not bundled redistributable fixtures. Public [record-acceptance and custom-continuation findings](../reports/adjustment-and-service-interfaces.md#record-acceptance-and-custom-continuation) retain the area-2/area-3 interface analysis behind the private provenance notes.

The declared profile uses a low reset ROM alias, shared DRAM aliases, source-bound primary identity, virtual PMU cycles, read-only logical media with clean-read assumptions, and coherent cache substitutions. CPU1 release requests are observed but CPU1 execution is held. No application, display, physical card entry, flash programming, bad-block/OOB physics, hardware cache visibility or failed-body state reconstruction is proved. Input preparation, builds and execution perform no camera or card-reader I/O. See [the recovery assessment](../reports/full-system-emulation.md#11-recommendation) for acceptance results and limits.

## Physical block-14 recovery startup lifetime

The physical-recovery smoke also accepts a linked stage, exact `ffrecov.bin`, captured primary kernel and independently carried recorder block. It checks stage/body identity, loads the real kernel over RAM `0x40000`, executes all three known startup zero calls, the complete zero-arm log initializer and initial idle IRQ frame, then runs the delayed recovery stage with a mutable modeled physical block. Success requires every RC0 reference fragment to survive, status 20 and complete media equality with the carried RC0 block.

Canonical and uncached RAM aliases share host backing. The replay substitutes the storage locks, cache operations, lower device and primary identity return; it executes the real initialization instructions rather than the whole scheduler. The regular synthetic blocks use a deterministic index-dependent pattern, four declared rollback words and a final four-byte CRC correction. Refusal cases cover changed bytes inside and outside rollback words, changed final locked reads, final read failure, non-14 mappings, writer failures and post-write readback outcomes. Turning to `P`, `AUTO`, `Sports`, `Landscape`, `Portrait`, `C` or `M` runs one develop-task job 4 on the `0xfff63000` engine. The X-M1 profile selects `fff63_profile` `xm1-150-declared-fff63-job4-completion-unmeasured` (the Rust device `FFF63Engine` in `xm1-upstream/native/src/fff63.rs`), which models the stock driver sequence byte-read from `0x0065a478`, `0x0065a58c`, `0x0065a548` and handler `0x00d99570`: COMMAND `0x118` = 1 latches STATUS `0x004` bit 16, which `0x0065a4b8` polls; writing the read STATUS back clears it; CONTROL `0x000` = `0x100` resets and reads back with bit 8 clear; ten programming words follow; CONTROL bit 0 starts the job. After a declared two-tick delay the model sets STATUS bit 4 (success) and raises IRQ `0x4c` (descriptor `0x48` at `0x007c9484`) on the core that enabled it. `0x014` reads 0 and `0x108` reads back the word written to `0x100`; the handler stores `0x014` and the difference in its job record and nothing reads them. The engine's function is unbound and the model writes no memory. The COMMAND 4 continuation, STATUS bits 17 and 24, other registers and other orders refuse. The Rust tests in `fff63.rs` cover the sequence and its refusals.

The same device decides STOP admission and status. X-M1 cleanup at `0x00d99a2c` resets the engine without programming another job, and the next job calls stop/reset again at `0x00d99728`. STOP is therefore also admitted after a reset with zero status, no programmed fields and no IRQ76 pending, active, injected or present in either controller's ancestor stack. It performs the ordinary stop acknowledgment, not a no-op. Active jobs, partial programming, other commands and the existing start/IRQ-owner checks retain their refusals. E-XM1-FFF63-CLEANUP-RESET-150 binds the repeated handshake and completion trace. A RAM installation in C followed by M and the first SELECT opens NONE on empty-bank media; this does not explain the physical SELECT failure.
