# `//transport:camera`

The closed X-M1 service operations and the narrow native USB provider behind them. Building, `--help` and `rehearse` never load libusb, and of the tests only `//transport:native-usb-tests` does: it enumerates the host bus to exercise the lister, with no camera attached and no device opened, claimed or transferred. The live `identify`, `read-config`, `end-setting`, `probe-ram`, `read-log`, `probe-bootrom`, `probe-area2`, `probe-straps`, `probe-code`, `probe-ownership`, `probe-routes`, `dump-ram`, `read-media`, `arm-auto-act`, `commit-f7-enable`, `commit-f7-restore`, `read-ram`, `ram-push` and `ram-unload` commands are the only paths that open a device or transfer. Running one is a camera run and follows [the camera-run procedure](../spec/07-governance-and-handoff.md#3-camera-runs).

`OUTDIR` must be absolute and must not exist; the command creates it with mode 0700. Without it, `bazel run` supplies `BUILD_WORKSPACE_DIRECTORY` and the output goes to `private-data/sessions/<UTC yyyymmddTHHMMSSZ>-<operation>/`; with neither, the operation refuses. Each command prints the output directory and one result line, and exits nonzero on any stop.

## Device selection

A run refuses unless exactly one connected device is `04cb:ff80` and carries the supported profile: one configuration, interface 0, alternate setting 0, exactly one bulk IN and one bulk OUT, and at most six non-bulk extra endpoints. Endpoint numbers, packet sizes and intervals are read from the live descriptors; no value is expected or pre-recorded, and no physical path selects the device. Inventory is capped at 64. Zero devices, two eligible devices and an unsupported profile each stop before a handle is opened.

`arm-auto-act --wait-for-device` is the exception to the zero-device refusal: it can start before camera power-on, prints a waiting message, lists at 50 ms spacing for at most 120 s and proceeds without a prompt when one supported device appears. Only no eligible device continues the wait. Multiple eligible devices, unsupported profiles, inventory overflow and initialization/list/open/claim failures stop without retry. No service transfer is sent during the empty-device wait. Without the flag the original immediate selection applies.

## Operations and their bytes

Every control write is `bmRequestType=0x43`, `bRequest=0`, `wValue=0`, `wIndex=0` with twelve data bytes: opcode, seven zero bytes, big-endian length at bytes 8–9, big-endian session at bytes 10–11. `S_hi S_lo` below is that session, zero for C0.

| Stage | Control data | Following transfer |
| --- | --- | --- |
| Open C0 | `c0 00 00 00 00 00 00 00 00 08 00 00` | bulk IN, exactly 8 bytes |
| Close C4 | `c4 00 00 00 00 00 00 00 00 02 S_hi S_lo` | bulk IN, exactly 2 bytes |

The C0 reply's bytes 0–1 are the little-endian session; bytes 2–3 are a zero halfword and bytes 4–7 the little-endian constant 65536, which the C0 handler at `0x00d7f56c` writes unconditionally (E-DBG-C0-FIELD-150). `identify`, `end-setting`, `commit-f7-enable`, `commit-f7-restore` and `read-ram` require that exact tail; the other operations carry it without interpretation.

**`identify`** sends C0, then `d0 ... 00 20 S_hi S_lo` with the 32-byte tag-4 request

```text
00 00 15 00 00 00 00 00 00 00 00 00 00 00 00 00
04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

then `d1 ... 00 80 S_hi S_lo` with a 128-byte bulk IN, then C4: eight service transfers. The reply must be exactly 128 bytes with opcode `00 00 15 00`, zero status words, zero unknown header fields and UTF-16LE `X-M1`. It prints that model string.

**`read-config`** sends C0, then four transfers per planned window, then C4: `d0 ... 00 24 S_hi S_lo`, the 36-byte request frame, `d1 ... 01 24 S_hi S_lo` and a 292-byte bulk IN. The request frame is little-endian opcode `0x1a0002`, twelve zero bytes, function 2, mb 1, page `offset / 256`, in-page offset 0 and length 256, with no appended data. Function 3 of the same opcode writes the adjustment cache and opcode `0x200001` reads arbitrary RAM; neither value occurs here, and the tests assert that over the emitted bytes.

A reply must be exactly 292 bytes, echo the opcode, function 2 and mailbox 1, keep the reserved word at `0x0c` zero, and echo page, in-page offset and length at `0x18`, `0x1c` and `0x20`. Error words `(0,0)` yield the 256 data bytes at `0x24`, `(9,3)` are rejected arguments and `(1,0xffff)` is callback status 2; any other pair is a status the handler cannot produce. The window named by the plan's oracle must carry the product string at the plan's byte offset. Each accepted window is written to `windows/OFFSET.bin` with mode 0600 and its SHA-256 journaled. It prints the completed window count.

The plan is the `read-plan.schema.json` document `//readplan:read-plan` generates. It is read and validated in full before the provider exists: version, closed keys, the fixed channel, 256-aligned strictly increasing offsets below `0x420000`, indexes equal to their position, a contained product oracle and a bounded generator binding. The journal allowance is `65536 + 4096 * windows`, refused above 8 MiB, which caps a plan at 2032 windows.

**`end-setting`** sends C0, then `d0 ... 00 2e S_hi S_lo`, the 46-byte request, `d1 ... 00 80 S_hi S_lo` and a 128-byte bulk IN: six transfers and no C4. The request is little-endian opcode `0x00200001`, twelve zero bytes, function 5, twelve zero bytes, parameter word 10, then the ten ASCII bytes `POWER OFF\n`. The reply must be exactly 128 bytes echoing that opcode, a zero reserved word at offset 12 and function 5 at offset 16; `(0,0)` is accepted and `(1,3)` is rejected. It prints `accepted` or `rejected`. Acceptance describes parser callback acceptance, not physical shutdown, persistence success or settings preservation.

**`probe-ram`** opens C0, writes adjustment index `0xf7` to 1 through `0x1a0002` function 3 (`d0 ... 00 25 S_hi S_lo`, a 37-byte frame: opcode, twelve zero bytes, function 3, mb 1, page 0, in-page offset `0xf7`, length 1, appended byte `01`), then reads the config window at index 0 and requires byte `0xf7` to be 1. It then reads the 20 fixed probe windows, two 128-byte `0x200001` function 2 requests each (`d0 ... 00 24 S_hi S_lo`, a 36-byte frame with the address at `+0x1c` and length at `+0x20`; `d1 ... 00 a4 S_hi S_lo` and a 164-byte bulk IN), checks the three cache-window oracles, writes index `0xf7` back to 0, reads the config window again and requires byte `0xf7` to be 0 before C4. Every routine of opcode `0x200001` acts only while `0xf7` is nonzero, and function 3 posts no service command for an index other than `0x80`, which no frame here carries. The gate is therefore open only in RAM for the session, and the operation restores it explicitly.

The probe list is fixed in `FujiAF.Probe`: the adjustment cache at `0x41acd800` (`+0x100` product string at `+0x15c`, `+0x000` readback comparison, `+0x200` signature at `+0x202`, `+0x300` for indices `0x3b9` and `0x3ba`), the loader bases `0x00040000` and `0x000d0000`, the 1 KiB segment table at `0x0061c000`–`0x0061c3ff`, the decoded image loads `0x0061c400` and `0x00bf1a00` with one window at `+0x10000` each and one at `0x0061c400+0x200000`, the plain image's linked base `0x01100000` and second extent base `0x011c0000`, the settings fallback flags at `0x0089f800`, and the retained settings header at `0x409c2800` and its snapshot at `0x409c2900`. The three oracle cache windows run first. Each accepted window is written to `probes/ADDRESS.bin`, eight lowercase hex digits, with mode 0600 and its SHA-256 journaled; the two config readbacks are written as `probes/gate-readback-enabled.bin` and `probes/gate-readback-restored.bin`. The reply contract the operation enforces is opcode, function and address/length echoes, zero reserved word and the error pairs `(0,0)`, `(9,3)` and `(1,0xffff)`; anything else stops the session with the raw reply journaled.

**`read-log`** runs the same gate enable, readback and restore sequence as `probe-ram` over a fixed list of the 1.50 log store: 512 256-byte windows from `0x400a0800`, each two 128-byte `0x200001` function 2 requests, covering the whole `0x1fff4`-byte store and its 8188 entry slots, with the last window reaching twelve bytes past the store's end, plus the tick cell `0x400c0800` read twice in a row before the store and once after it, which measures that cell's rate against the host clock over a short baseline and checks it across the session. Loader A's writer `0x42188` appends 0x10-byte entries there from `+0x34`, under a header holding the capacity halfword `0x1ffc` at `+0x1c` and the next index at `+0x1e`; each entry holds a type byte, a thread byte, a 16-bit delta, the tick word from `0x400c0800` and one eight-character string prefix at `+0x3c`, so the window bytes are judged host-side and no window is an oracle. Both header halfwords land in the first window, so a run also shows how much of the ring was occupied at read time. Whether that store is the console ring opcode `0x200001` functions 1 and 4 drain is unestablished. Each store window is written to `windows/ADDRESS.bin`, the three tick samples to `windows/tick-a.bin`, `windows/tick-b.bin` and `windows/tick-end.bin`, and the two gate readbacks to `windows/gate-readback-enabled.bin` and `windows/gate-readback-restored.bin`.

**`probe-bootrom`** runs the same gate enable, readback and restore sequence as `probe-ram` over a fixed window list: 64 256-byte windows tiling `0x80000000`–`0x80003fff`, the pinned fffw bootrom lead range of 0x4000 bytes with a signature at `+0x3ff0` and a digest over the whole range; 64 windows tiling `0x80004000`–`0x80007fff`, the suspected repeat of that block; one window at `0x80008000`, the period probe; and one window at `0x00000000`, the boot handoff target. Each window is two 128-byte `0x200001` function 2 requests. The window bytes are judged host-side after the run (the lead digest and marker matched this body on 2026-10-08, E-BOOTROM-PROBE-150), so no window is an oracle. Each window is written to `windows/ADDRESS.bin` and the two gate readbacks to `windows/gate-readback-enabled.bin` and `windows/gate-readback-restored.bin`.

**`probe-area2`** runs the same gate enable, readback and restore sequence as `probe-ram` over the fixed area-2 evidence list of the area-2 invalidation analysis `private-data/analysis/x-m1-1.50/end-setting/followup/area2-invalidation.md` section 9: 27 256-byte windows in strictly increasing address order, each two 128-byte `0x200001` function 2 requests at `+0x00` and `+0x80`, so 54 read requests of four transfers each and 236 transfers in total. The windows are the storage-readiness words at `0x00828500`, the lower-object pool with the area-2 object at `0x0089f900` and its tail and the area-3 object at `0x0089fa00`, cache slot 0 at `0x008a0000`–`0x008a0100` and cache slot 1 at `0x008c0000`–`0x008c0100`, the read-cache tags and ages at `0x008e0000`, the fixed area-2 record buffer at `0x008e1700`–`0x008e1800`, the backend bank and offset words at `0x00917f00`, the eleven block-`0x28` directory journal windows `0x00919b00`–`0x0091a500` and the pending and snapshot settings records `0x409c2b00`–`0x409c2f00`. Those pages hold RAM copies and working state whose expected values are unproved, so the window bytes are judged host-side after the run and no window is an oracle. Each window is written to `probes/ADDRESS.bin` and the two gate readbacks to `probes/gate-readback-enabled.bin` and `probes/gate-readback-restored.bin`, matching `probe-ram`. The aggregate deadline is 5000 ms times `8 + 16 + 8 * 27`, and each journal file is bounded at `8192 * windows` bytes, 221184 for these 27 windows.

**`probe-straps`** runs the same gate enable, readback and restore sequence as `probe-ram` over the fixed ROM-MAP-01 capture list of `private-data/analysis/x-m1-1.50/bootrom/strap-read-safety.md` section 8, in that order: one 64-byte read at `0x400a0000`, the boot-time mirror of the 16 port registers whose word 0 is `0xfff89014`; the two 256-byte ROM alias windows `0x80010000` and `0x80100000` as two 128-byte requests each, which separate address-bit aliasing from a bounded repeated image; and last, 4 bytes each at `0xfff89014` and `0xfff98000`, the registers the boot ROM's mode detect reads bits 11:10 and 2:0 of at `0x80000274`/`0x80000278` and whose combined 5-bit value selects the mode. The two strap reads are last and single because a byte access to a 32-bit MMIO register is unobserved on this body: every firmware access to those two blocks in the boot ROM, both boot records, both loaders and images 4, 5 and the plain image is 32-bit, while the service channel can only issue one byte load per byte through image 4 `0x647b1c` (`ldrb r2,[r6,r3]`), so each register is read once at 4 bytes and no request covers a 256-byte MMIO window. No target has a known content, so no read is an oracle: the in-session checks are the reply contracts, the two gate readbacks and the journaled hashes. Each target is written to `windows/ADDRESS.bin`, the two gate readbacks to `windows/gate-readback-enabled.bin` and `windows/gate-readback-restored.bin`, and the run prints the captured byte count. A strap read is `d0 ... 00 24 S_hi S_lo` with a 36-byte `0x200001` function 2 frame carrying the address at `+0x1c` and length 4 at `+0x20`, then `d1 ... 00 28 S_hi S_lo` and a 40-byte bulk IN. The capture records the strap state of the jig-entry power-up and the ROM's recorded mode word; it does not observe the documented Function-button and command-dial SD-BOOT hold, which is a different power-on state.

**`probe-code`** runs the same gate enable, readback and restore sequence as `probe-ram` over the seven 256-byte windows covering the executed closure of the stock native case (E-AREA3-VALIDATOR-NATIVE-150, [the case section](../emulation/README.md#stock-native-case-150-area-3-record-validation)): `0x006a8300`, `0x006a8400`, `0x006a8500` and `0x006a8600` cover the parity builder `0x006a83f4` size `0x90` (window `0x006a8300` covers `0x006a83f4`–`0x006a83ff`, window `0x006a8400` covers `0x006a8400`–`0x006a8483`) and the validator `0x006a84d4` size `0x188` (window `0x006a8400` covers `0x006a84d4`–`0x006a84ff`, window `0x006a8500` covers `0x006a8500`–`0x006a85ff`, window `0x006a8600` covers `0x006a8600`–`0x006a865b`); `0x00722100`, `0x00722200` and `0x00722300` cover the word-fill `0x007221a0` size `0x28` (window `0x00722100` covers `0x007221a0`–`0x007221c7`), memset `0x007221c8` size `0x50` (window `0x00722100` covers `0x007221c8`–`0x007221ff`, window `0x00722200` covers `0x00722200`–`0x00722217`) and memcmp `0x0072232c` size `0xb8` (window `0x00722300` covers `0x0072232c`–`0x007223e3`), so no byte of any of the five function spans is left unread. The four windows first named as the closure path (`0x006a8400`, `0x006a8500`, `0x00722100`, `0x00722300`) leave three tails unread: the parity builder's first 12 bytes `0x006a83f4`–`0x006a83ff`, the validator's last 92 bytes `0x006a8600`–`0x006a865b` and memset's last 24 bytes `0x00722200`–`0x00722217`, so the probe adds `0x006a8300`, `0x006a8600` and `0x00722200`. Each window is two 128-byte `0x200001` function 2 requests at `+0x00` and `+0x80`, so 14 read requests of four transfers each, 76 transfers in total and 80 units for the aggregate deadline. The correspondence of these bytes to the image-4 decode is already established by E-DUMP-RAM-150: the reviewed 2026-10-08 id4-image dumps match the decode with zero differences over exactly these seven windows (dump offset `0x8c300` against decode `0x8bf00` for 1024 bytes, and dump offset `0x6100` against decode `0x105d00` for 768 bytes), and the stock case's own `code-validator.bin` and `code-runtime.bin` are identical to the decode at `+0x8bff0` and `+0x105da0` of `lz/id4-0061c400.bin`, so `probe-code` re-confirms the installed bytes on a fresh boot in one bounded session rather than establishing them; the window bytes are judged host-side against the decode and no window is an oracle: the in-session checks are the reply contracts, the two gate readbacks and the journaled hashes. A stop before the restore leaves adjustment index `0xf7` at 1 until the next power cycle, the stop-time residual every gate-using operation here carries. Each window is written to `windows/ADDRESS.bin` and the two gate readbacks to `windows/gate-readback-enabled.bin` and `windows/gate-readback-restored.bin`. The aggregate deadline is 5000 ms times `8 + 16 + 8 * 7`, and each journal file is bounded at `8192 * windows` bytes, 57344 for these 7 windows.

**`probe-ownership`** runs the same gate enable, readback and restore sequence as `probe-ram` over six fixed 256-byte windows in increasing address order. Each window takes two 128-byte `0x200001` function 2 requests, so the twelve RAM requests plus gate/session operations total **68 service transfers**. The windows `0x0093e600`, `0x0093e700`, `0x0093e800` and `0x0093e900` cover the namespace owner-word table at `0x0093e6f4`, with one word per id 1..169. The windows `0x00829900` and `0x00829a00` cover the allocation-break cell `0x00829a08` and adjacent loaded data.

The namespace words are routing markers, not a live-object bitmap: destruction clears entries, and some fixed-id creation paths do not update them. A zero at capture time does not prove an id free at boot-hook time. The allocation break is not a proven high-water mark. Neither snapshot accepts placement or the 64 KiB carve. A shooting boot followed by a maintenance reboot does not preserve the shooting boot's cursor.

Each window is written to `windows/ADDRESS.bin`; the enabled/restored gate readbacks are written to `windows/gate-readback-enabled.bin` and `windows/gate-readback-restored.bin`. There is no RAM-content oracle. Success prints `probe-ownership: 6 windows`. The aggregate deadline is 360 seconds, including native setup, and each journal file is bounded at 49,152 bytes. Gate restoration runs on the normal path only; an early stop may leave `0xf7` enabled until the next power cycle. Start with a fresh maintenance boot and use the established supply-cut exit on success or failure.

**`probe-routes`** runs the same gate enable, readback and restore sequence as `probe-ram` over the marker-0 route capture of [the marker-0 read plan](../reports/marker0-read-plan.md), in the operation's two CLI forms. `probe-routes fixed` is phase 1: the class descriptor table and its adjacent objects at `0x0096bd20`, 256 bytes as two 128-byte requests, then the allocation-search cursor cell `0x00a0f86c`, 4 bytes as one request. `probe-routes derived PLAN_JSON` is phase 2: the RAM window list the plan file names, its cursor window first and then one 32-byte `p+0x60` plus one 40-byte `p+0x140` window per distinct class descriptor word `p` of the plan's binding, one request per short window. Phase 1 is 3 read requests and 32 transfers; phase 2 is `1 + 2k` read requests and `24 + 8k` transfers for `k` distinct descriptor words, which is `192 + 8k` over the plan's four runs, 208 at the captured pair.

`transport/marker0-read-session.sh` is the plan's schedule as executable steps, in its order: `probe-ownership`, `probe-routes fixed`, the derivation of the phase-2 window list from the first two words of phase 1's `windows/0096bd20.bin` with the plan's own `od`/`awk` command, `probe-routes derived`, `probe-ownership`. The derivation takes one window pair per distinct descriptor word and skips words whose `+0x60` or `+0x140` window would collide with the cursor cell. It writes the derived list to `private-data/read-plans/marker0-routes-phase2.json` under `umask 077`, prints the distinct descriptor word count with the phase-2 request and transfer counts, and takes `CAMERA` in place of the devenv camera command.

Each window is written to `windows/ADDRESS.bin`, the enabled/restored gate readbacks to `windows/gate-readback-enabled.bin` and `windows/gate-readback-restored.bin`, and one `window-complete` journal record carries the window's plan index, address, length, purpose and SHA256, so the records map onto the plan's window list. There is no RAM-content oracle: window 0's words are bound by category host-side and only the descriptor pair is dereferenced as struct pointers, and the cursor cell's value is classified by the two search families' domains afterwards. Success prints the read-request count, 3 for phase 1 and `1 + 2k` for phase 2. A plan file that repeats an address, names an address outside the 32-bit space, an index other than its position or a length outside 1..256 bytes is refused before the session. Gate restoration runs on the normal path only; an early stop may leave `0xf7` enabled until the next power cycle.

Every bound is 256-aligned. `id4-image`, `id4-bss`, `id5-image`, `plain` and `id5-bss` split their listed range into contiguous parts of at most 1 MiB with the remainder last: `id4-image` and `id4-bss` are image 4's load area and bss (live segment table entry `{4, 0x0061c400, 0x282828, 0x0089ec00, 0x352e00}`), `id5-image` and `id5-bss` are image 5's load area and bss (`{0x01460000, 0x2bbe40}`, end rounded up to 256), `plain` is the plain image's linked base and second extent, `high-known` is the boot snapshots and syslog store, the retained settings header and its snapshot, and the adjustment cache, and `loaders` is the two loader images at their load bases. A segment's request count is the sum of `ceil(range bytes / 248)` over its ranges. The range ends are the raw extents rounded up to 256; the tails that rounding adds are +0x20 and +0x60 for the two loader ranges, +0xa0 for the `id5-image` range and +0xc0 for the `id5-bss` range. The area-2 structures inside `id4-bss` are listed in the area-2 invalidation analysis `private-data/analysis/x-m1-1.50/end-setting/followup/area2-invalidation.md` section 9.

The requests journal no per-frame lines: before the first request the segment's complete outgoing frame sequence is written to `outgoing.v1` in send order and fsynced once, so every outgoing byte is durable before any of it is sent, and each request appends its data bytes to `OUTDIR/<segment>.bin` and one `request-complete` line with its index, address, length, status pair, SHA-256 of the data bytes and monotonic time, made durable every 256 requests and at segment end. An unexpected reply, short transfer or expired deadline journals the full raw reply hex and the failing context before the stop. The aggregate deadline is 5000 ms times `8 + 16 + 4 * requests`, each journal file is bounded by `65536 + 1024 * requests` bytes (4396032 for a 1 MiB segment of 4229 requests), and the segment file holds exactly the segment's bytes, at most 1 MiB.

**`read-media`** performs one bounded raw storage read of the two area-2 banks over the queue-7 action 37 path and nothing else, one request per bank. It sends C0, reads the 256-byte adjustment window at index 0 as the session-start snapshot, writes index `0xf7` to 1 and reads the window back as `probe-ram` does, reads the group-2 state halfword at `0x015c20b0`, the map object read through `0x00919a20`, the map header as u32s at `map + 0` (the start word) and `map + 8` (the entry count) in one request and the two area-2 map entries as u16s at `map + 0x10 + 2 * 0x56` and `map + 0x10 + 2 * 0x57`, then per bank writes the staging fields, triggers the read, polls the result byte and captures the bank's block; every exit path ends with the disarm, the restores and C4. A bank's block is the map-resolved raw block `entry + start`, `start` the map object's own start word and not a constant, which is the numbering the firmware's own area-2 read resolves through the same map, so the start word, the entry count and the entries are read per run and the encoded bases `0x3d6`/`0x3d7` hold only under the identity map. The staging reads are `0x200001` function 2 requests at 248-byte stride inside the bank's own window offset, 529 requests whose last carries 128 bytes, each hashed with SHA-256 and appended to `OUTDIR/bank-0.bin` and `OUTDIR/bank-1.bin`, and the session-start window and the two gate readbacks go to `OUTDIR/cache-snapshot.bin`, `OUTDIR/gate-readback-enabled.bin` and `OUTDIR/gate-readback-restored.bin`.

The safety limits live in the types rather than in checks. The only values index `0x80` can carry are the trigger `0x35` and the disarm `0x33`; every config function 3 request is the 37-byte length-1 form with one appended data byte at one of the indices `0x80`..`0x8a` or `0xf7`, so no request is zero-length or starts below `0x80` and spans it, and `0x84`..`0x8a` are restore-only; the run's own write to index `0x81` passes zero, and a restore write there cannot scan the whitelist because only a write starting at `0x80` is scanned; index `0x82` is derived per bank from its map entry as `(entry + start) >> 3` with the bank at `((entry + start) & 7) * 0x20000`, and a map start that is not a raw block of the `0x400`-block device, an entry index at or above the map's entry count, a `0xffff` entry naming no physical block, a selector above `0x7f` and two entries naming the same raw block are each refused when the map is parsed; the staging requests are generated from the fixed per-bank walks, so no staging address leaves its bank's block inside `[0x4b2ece00, 0x4b2ece00 + 0x100000)`.

The `0xff` sentinel is written to `0x83` before each trigger and the poll accepts only its transition to 0, 1 or 2 before that bank's first staging byte is read, because the firmware fills the window page by page and nothing orders these reads against it; result 1 or 2 stops the run without capturing that bank. The state halfword at `0x015c20b0` is a precondition and reported as one: state 4 sends action 37 to action 3, so the read cannot run there. The disarm `0x80 = 0x33` precedes each bank's staging field writes and repeats at the end, and `0x81`..`0x8a` and the `0xf7` gate are written back to their session-start values on every exit path, including a stop and a transfer timeout. The aggregate deadline is 5000 ms times `8 + 4 * 31 + 4 * 1058 + 4 * 2 * 1024`, where 1024 is the poll bound per bank, and each journal file is bounded by `65536 + 4096 * (1058 + 2 * 1024)` bytes, 12787712.

The run leaves the storage driver shut down: action 37 opens it at `0xdbcfe0` and closes it at `0xdbd030` with no refcount and no already-open guard, so the owner power-cycles the body before using it normally, including after a failed or stopped run. The staging window is the head of the frame-buffer pool rather than private scratch, so the session must have no capture, live view or playback in flight: a frame written during the window corrupts the capture and the read corrupts a frame in progress.

**`arm-auto-act`** performs [the owner session](../reports/auto-act-session-script.md). **`commit-f7-enable REFERENCE_BIN`** and **`commit-f7-restore REFERENCE_BIN`** store adjustment index `0xf7` through the only host-reachable storage route, the whole-area commit ([the stored-f7 report](../reports/stored-f7-ordinary-usb-read.md) sections 4 and 5, E-ENABLE-COMMIT-150). Enable stores `0xf7 = 0x01` on a body whose `0xf7` reads `0x00`; restore stores `0x00` on a body whose `0xf7` reads `0x01`. The trigger's D1 is therefore held for the whole commit (the `0x35` trigger of `read-media` held it 127 ms and 137 ms on this body), and its status reports the post, not the commit; byte `0x81` is the completion signal.

`REFERENCE_BIN` is the owner's at-rest capture of config window `0x000000`, for this body `private-data/sessions/20261016T044012Z-read-config/windows/000000.bin` (SHA-256 `409d56adca05fb4f8d2353f152a60c53b2904bb806ab18076ede6f62f6af98a3`). It is read before the output directory exists under the plan-file rules (absolute path, owned regular non-symlink file, no group or other permission bits) and must be exactly 256 bytes; its hash is printed and journaled. No body bytes are compiled into the tool.

Each sends C0 and requires the constant reply tail, sends the `identify` tag-4 request and requires `X-M1`, and reads the config windows `0x000000`, `0x000100` and `0x000200` with function 2, written to `config-OFFSET.bin`. Before any write it refuses unless `+0x15c` holds the product string, `+0x202` holds `55 aa`, `0xa2` is `0x00`, window 0 equals `REFERENCE_BIN` outside `0x80`, `0x81` and `0xf7`, `0xf7` holds the start value, `0x80` is `0x00` or `0x22` and `0x81` is `0x00` or `0xff`. The commit stores every cache byte, so RAM residue of an earlier command in the same boot would become permanent: `0xa2 = 0x02` is the arm `arm-auto-act` leaves until the power cycle and is refused by name whatever the reference holds, and any other window-0 difference from the reference is refused with its offsets. A fresh boot loads `0x80` from storage: `0x00` in every 1.50 capture (E-ADJ-GATE-BYTE-150, E-ADJ-BACKUP-GAP-READ-150) or `0x22`, which every commit stores and the 1.00 body held at rest. `0x33` or `0x35` there is RAM from an earlier `0x80` write in the same boot, and `read-media` leaves the storage driver closed until a power cycle, so `0x33` is refused with a power-cycle instruction. `0x81` reads `0x00` on 1.50 and `0xff` where an armed commit stored it. State 4 refuses; enable first writes `0xf7 = 0x00`, requires that readback and then closes, so a refusal leaves the cache as the session found it.

The sequence after the preconditions: `0xf7` to the target, then window 0 read back, requiring the target at `0xf7` and every other byte unchanged (`gate-readback.bin`); `0x81 = 0xff` with the same readback (`arm-readback.bin`); `0x80 = 0x22`, whose D1 is given the commit allowance of 33000 ms (33 units at 1000 ms each) instead of 5000 ms; window 0 polled until `0x81` leaves `0xff`, the first poll immediate and expected terminal after a held reply, the rest 100 ms apart, at most 330 polls; `0x80 = 0x33`, the flag-0 record `read-media` uses, which posts nothing and makes a later zero-length or repeated-`0x33` request at `0x80` in this boot inert (a later `0x22` there would still start another commit), then window 0 read back requiring `0x80 = 0x33`, the target `0xf7` and the polled result at `0x81` (`disarm-readback.bin`); C4. `0x81 = 0x00` is success and `0x01` the commit's failure, still followed by the disarm; any other value stops. If the trigger frame went out and its reply did not come back (the D1 or its bulk IN failed or timed out), the commit may still be programming units. The run then sends nothing until 33000 ms after the trigger frame, reads window 0 once (`held-reply-readback.bin`), and only then sends the disarm, its readback and C4. A trigger answered with a status other than `(0,0)` posted no commit and is disarmed at once.

The result line names one outcome: `committed` (result `0x00`, disarm confirmed, session closed), `commit-failed` (result `0x01`, disarm confirmed, session closed; units already rewritten stay new), `refused` (no cache byte differs from session start) or `uncertain` (every other end). The command exits nonzero for every outcome but `committed`. A stop after the first write is `uncertain`; the only write sent after a stop is the `0x80 = 0x33` disarm, when the trigger frame went out and no disarm had been attempted. Nothing is retried, the commit included. Every line ends with the supply-cut instruction except an `uncertain` one where the trigger frame went out and no window-0 read after it showed `0x81` at `0x00` or `0x01`: that line says the commit may still be running, not to cut power, to leave the camera untouched for at least one minute, then cut the supply and report the output. **`ram-relink ALLOC_STATE OUTDIR`** opens no device. **`ram-push ALLOC_STATE MANIFEST`** reads both private files and sibling `runtime.bin` before opening a device. It requires the compiled reviewed source-identity map, 250-word transaction contract and base-derived entry addresses. It then runs the pinned relinker at the retained base and requires byte-for-byte equality of both supplied files with that build. The pinned relinker is `host/firmware/build-recipe-bank-ram.sh` and `//host/firmware:build-recipe-bank` from the running binary's runfiles (every binary linking `//transport:camera-core` carries them), executed by a Nix-store bash with an environment holding only the tool paths, the pinned private inputs and `PATH` set to the Nix-store coreutils directory. Clang, ld.lld, llvm-objcopy, llvm-nm, llvm-objdump, bash and coreutils are Nix store paths resolved at build time by `//host/firmware:ram-push-toolchain-module` from the locked nixpkgs. The builder refuses unless the script passed exactly those paths, and its manifest carries two compiled identities in `source_identity`: `build-recipe-bank`, the SHA-256 over its workspace Haskell sources, and `ram-push-toolchain`, the SHA-256 over the tool store paths. A stale or substituted builder or toolchain therefore fails the compiled source-identity map. The build runs from the workspace (`BUILD_WORKSPACE_DIRECTORY`, else the current directory) in a fresh mode-0700 directory under `private-data/analysis/x-m1-1.50/ram-push`. It requires both allocation and manifest size to equal `0x1b6d8`, then re-pins product, config gate, table, slot, the full allocation SHA-256 and every old publication word before its first camera write. It uploads the padded runtime in at most 248-byte function-3 chunks with full readback, performs CPU0 cache maintenance, invokes INSTALL, restores the slot, verifies all 250 new words and writes `ram-push-state.json`. The stock `0x450006` reply to INSTALL and ROLLBACK is a 32-byte header whose word at +20 is the output length; the host requires opcode `0x00450006` and length 104, reads the output pointer and length from `0x01469878`, requires that mailbox wholly inside the allocation and reads it with function 2. X-M1 function 2 reads are capped at 248 bytes because its 284-byte DMA reply contains 36 metadata bytes.

**`ram-free ALLOC_STATE`** re-pins the allocation session facts and unchanged full allocation SHA-256, then writes and reads back the tag `RPFREED\0` at the allocation base before calling stock free. Stock free can coalesce the block into the top chunk without touching its payload, so the tag is what makes the same state's SHA-256 check refuse a second `ram-free` or a later `ram-push` while the payload survives; a failure after the tag write is uncertain. When `ram-free` ends freed or uncertain it creates `ALLOC_STATE.consumed` beside the state, exclusively and with mode 0600, recording the base, the allocation SHA-256 and the outcome; if that file cannot be written the outcome is uncertain. `ram-free` and `ram-push` refuse a state whose `.consumed` file exists before any USB call, so a reused or overwritten block whose tag is gone cannot pass the hash check. **`ram-unload PUSH_STATE`** rebuilds the reviewed runtime at the state's base before USB and requires the stored hashes, entries and all 250 publications to equal that build and the compiled contract. It then requires the exact active new words, callback slot and table pointer, invokes ROLLBACK, verifies all 250 old words and writes `ram-unload-state.json`. The block remains allocated until power-off. ROLLBACK uses the same two-core rendezvous, restores all 250 old words in reverse order and performs both-core D/I maintenance before releasing CPU1.

The camera binary offers no way past these pins. The emulator e2e's `--unreviewed-relink` mode (`emulation/Xm1UnreviewedRelink.hs`, library `//emulation:ram-push-unreviewed`) runs the same runfiles relinker and toolchain through `FujiAF.RamPush.withRelinkedBuildUsing`, which returns the build without the compiled source-identity and publication-contract checks but after the [bank ELF allowlist](#bank-elf-allowlist) check, and pushes and unloads it with `runRamPushWith` and `runRamUnloadWith`; its receipt records `"relink": {"mode": "unreviewed"}`, the build's source identity and the allowlist outcome. `//transport:ram-push-camera-pins` runs the camera's `ram-push` and `ram-unload` on inputs that differ from the compiled source identity or publication contract and requires each refusal, and `//transport:camera-unreviewed-relink-exclusion` requires that `//transport:camera` depends on `//transport:ram-push-pins` and not on `//emulation:ram-push-unreviewed`. The pins come from [the RAM-push review record](#ram-push-review-record).

Operate `ram-push` and `ram-unload` only with the camera idle at the shooting screen, with no menu open and no SD-card activity. This reduces unrelated work but is not the publication safety boundary. The installer posts a command `0x6800` job directly to CPU1 channel `0x58`; the job masks CPU1 IRQs, cleans and invalidates its copies of the publication lines, publishes PARKED and waits for COMMIT. CPU0 masks IRQs, validates all 250 words, publishes COMMIT and waits for CPU1 acknowledgement, then performs all 250 aligned stores and CPU0 D/I maintenance before GO. Each rendezvous cache line has one writing core: CPU0 writes the command line (IDLE, COMMIT, GO, CANCEL) and CPU1 writes the response (PARKED, ACKNOWLEDGED, LEFT), completion and peer-report lines, so neither core's write-back can replace the other's state. CPU1 leaves without parking if it first reads anything but IDLE, and leaves on CANCEL in every wait. CPU1 cannot self-release after COMMIT; after GO it performs D/I maintenance over the publication lines, unmasks and reports completion. A timeout before COMMIT cancels with no publication store. A timeout after COMMIT leaves publication state uncertain and requires power-off.
Every bounded wait stops after `0x80000` iterations. One iteration is a line clean+invalidate, a DSB and a reload of that line; at 2 µs per iteration a bound is 1.05 s, so CPU0's two IRQ-masked waits end within 2.1 s and inside the 5000 ms transfer timeout. The per-iteration time on the body is not measured. The mailbox reports the rendezvous nonces, the spin bound, CPU0's PARKED-wait and ACK-wait iteration counts, CPU1's iteration count and per-core PMCCNTR deltas; the host requires the bound to equal `0x80000` and both CPU0 counts to be below it. Ordinary boot leaves PMU counting disabled, so zero cycle and instruction fields mean unavailable; the offline emulator receipt records exact per-core retired-instruction deltas and virtual ticks at `ram_push_rendezvous_locked`, `ram_push_cpu0_window_exit` and `ram_push_cpu1_window_exit`.


The relinker guarantees every accepted 8-byte-aligned base fits in `0x1b6d8` bytes. The worst low half is `0x1f88`, where the bank ends at offset `0x19b98`; adding the `0x1b40` installer extent gives `0x1b6d8`. Run the split flow without powering off between commands:

```sh
ALLOC_OUT="$PWD/private-data/sessions/xm1-ram-alloc"
LINK_OUT="$PWD/private-data/analysis/x-m1-1.50/ram-push/operator-linked"
PUSH_OUT="$PWD/private-data/sessions/xm1-ram-push"
SIZE=0x1b6d8
devenv shell -- bazel run //transport:camera -- ram-alloc "$SIZE" "$ALLOC_OUT"
devenv shell -- bazel run //transport:camera -- ram-relink "$ALLOC_OUT/ram-alloc-state.json" "$LINK_OUT"
devenv shell -- bazel run //transport:camera -- ram-push "$ALLOC_OUT/ram-alloc-state.json" "$LINK_OUT/ram-push-manifest.json" "$PUSH_OUT"
```

If installation was not attempted, free the unchanged retained block with `devenv shell -- bazel run //transport:camera -- ram-free "$ALLOC_OUT/ram-alloc-state.json"`. After successful installation, unload with `devenv shell -- bazel run //transport:camera -- ram-unload "$PUSH_OUT/ram-push-state.json"` and then power off before further camera use; unload never frees the installed block. A timeout after any target write is uncertain and is never retried or blindly freed.

The manifest carries 250 publications, 167 setup then 83 activation: the bank's 94 (logical 0-93) and the D3 film-simulation delta over RC0 (logical 94-249, [the D3 design](../reports/ram-push-d3-design.md)). The order is bank setup `0-35,55-68,85,36-53`, D3 setup `94-191` (the prefix band `[0x0061c1fc,0x0061c340)`, the image-2 `0x83d` record, the film rows), D3 activation `192-249` (list pointers, the prefix overlap `[0x0061c340,0x0061c400)` with the hook, the Q pointers, the image-5 site `0x00d50a48`, the current-row getter `0x00d5a088`), then bank activation `75,76,72,73,74,69,70,71,77,78,79,80,86,87,88,89,90,91,92,93,81,82,83,84,54`. Parent labels 55 remain inert while the old values list terminates earlier; parent values 54 is the final discoverability root. Rollback reverses this exact sequence.

The 32-byte bootstraps execute from request-owned `[0x01469b20,0x01469b40)`, D0 request buffer `0x01469a9c + 0x84`. Every helper query, slot update and executing query in a bootstrap sequence is exactly 164 bytes and carries identical bootstrap bytes at `+0x84`; no short or intervening D0 request is permitted. The first helper query cleans the received bytes, the second performs DSB/I invalidation/ISB, and the final query runs the bootstrap. Every retarget path attempts a verified stock-slot restore under masked cleanup. A successful cleanup reports that the stock slot was restored; an uncertain restore reports that the slot may still point at request or runtime bytes and requires immediate power-off without further camera use.

The old static-inference bootstrap tail `[0x015c22b4,0x015c22d4)` is not used. Byte inspection found that mode-3 action `0x00ecc104` can asynchronously recopy all 68 callback-table bytes through `0x00ecfa60 -> 0x00dc74b4`, including that tail. The request-owned window is serialized by USB task `0x24`; any short/intervening D0 request or link reset destroys it and is an uncertain stop.

The request-owned peer-prepare bootstrap invokes stock synchronous core-1 range wrapper `0x006b0c3c` over the allocated block before upload, evicting stale peer lines before CPU0 stores runtime bytes. CPU0 then performs whole D clean-and-invalidate and instruction-cache maintenance. Before the peer fetches uploaded adapter code, the installer repeats `0x006b0c3c` over the runtime and every distinct publication line, then submits stock action `0x0061c490` through `0x006b0aa8` for DSB/ICIALLU/ISB. The uploaded worker action repeats range maintenance through loader helper `0x00042634`, invalidates I-cache, records raw CP14 identity and returns through synchronous row completion. The callback must report CPU0 `0x4003`; the peer raw value is accepted only when it differs from the same session's CPU0 value. No X70 or emulator CPU1 identity is used. The stock synchronous waits can hard-loop on internal failure, so a host timeout is uncertain and never retried.

No argument of any command can set an opcode, function, mailbox, parameter, text, endpoint or transfer order. Plan files set config window offsets (`read-config`) and RAM window addresses and lengths (`probe-routes derived`, `read-ram`), and `read-ram` and `probe-sd-host` take a bounded pass count and interval; no other argument sets a length or address, and `probe-sd-host`'s peripheral windows are compiled in. There is no raw, debug, firmware, detach, reset or retry command.

## RAM-push review record

`transport/ram-push-review.json` is the only source of the RAM-push pins. At build time `//transport:ram-push-pins-module` runs `//transport:ram-push-pins-generator` over it and writes the module `RamPushReviewedPins`, whose `reviewedContract` holds the source-identity map and publication contract digest that `ram-relink`, `ram-push` and `ram-unload` require. That module is the library `//transport:ram-push-pins`; `//transport:camera`, `//transport:ram-push-camera-pins`, `//transport:ram-push-reviewed-build-check` and the emulator e2e's reviewed relink link it, and `//transport:camera-core` does not, so a re-pin recompiles one module. A record that does not parse fails the build. The generator compiles every entry whatever its status: the camera binary does not read verdicts, so a pin recorded `unreviewed` is accepted like an approved one, and the pre-go gate below is the check that the pinned bytes were reviewed.

`FujiAF.RamPushReview` parses the record with the strict JSON parser and closed keys:

- `reviews`: one entry per independent review: `id`, `reviewer` (agent and model), `session` (transcript path), `verdict` (`approve` or `changes-required`), `scope`, `date` (`YYYY-MM-DD`) and `commit` (full hash of the reviewed tree).
- `content_checks`: the bank-content tier, one entry per checked candidate: `id`, `commit`, `date`, `elf_allowlist_receipt` and `emulator_run` (each `path` and `sha256`) and `owner_visual_check` (where the owner's check is recorded). `elf_allowlist_receipt` is the `relinked/bank-allowlist.json` the candidate's relink writes, with `"result": "pass"`; an overridden result does not content-check a candidate.
- `pins`: one entry per key of the manifest's `source_identity`, at most 32: `identity`, `source`, `component`, `sha256` and `status`. `source` is `workspace` for a checked-in file whose identity is its path, `private` with a `path` under `private-data/`, `builder` for `build-recipe-bank` or `toolchain` for `ram-push-toolchain`. `component` is `mechanism` or `bank-content`.
- `publication_contract`: `sha256` and `status`.
- `status` is `{"verdict":"approved","review":ID,"commit":HASH}`, naming a `reviews` entry; `{"verdict":"content-checked","check":ID}`, naming a `content_checks` entry and allowed on bank-content pins only; or `{"verdict":"unreviewed","commit":HASH}`, the commit that pinned the bytes.

Mechanism pins are `menu/ram_push_*`, `menu/recipe_bank_ram.ld`, `menu/recipe_bank_boot.S` and `.ld`, `menu/recipe_bank_allowlist.json` (its `stock_calls`, `stock_stores` and 40 `unproven` declarations included), the relinker and builder sources, the builder and toolchain identities, the RC0 images and the publication contract. Bank-content pins are `menu/recipe_bank_{actions,arm,edit,fields,hook,probe,storage,ui}.*`, `recipe_bank_spec` and the D3 images: the sources the [bank ELF allowlist](#bank-elf-allowlist) confines.

### Pre-go gate

Before asking the owner for a `ram-push` go, the model runs

```sh
devenv shell -- bazel test --lockfile_mode=error --repository_disable_download //transport:ram-push-review-verdicts //transport:ram-push-review-bytes
```

Both are tagged `manual`. `ram-push-review-verdicts` reports every pin and the contract whose status is `unreviewed` or approved by a `changes-required` review. `ram-push-review-bytes` reports every workspace pin whose file differs from its `sha256` and a builder or toolchain identity that differs from the digests `//host/firmware:ram-push-toolchain-module` compiles; a workspace pin must be listed in `//transport:ram-push-pinned-workspace-files`, else it is reported unreadable. Private pins and the contract are compared by the camera's relink; `devenv shell -- bazel run //transport:ram-push-reviewed-build-check` runs that relink at both reference bases. A go is asked for only when all three pass.

### Re-pin

1. Add the approving review to `reviews`, or the passed candidate to `content_checks`. A new manifest identity also needs its `pins` entry (`identity`, `source`, `component`) and, for a workspace file, a place in `//transport:ram-push-pinned-workspace-files`.
2. Run `devenv shell -- bazel run //transport:ram-push-repin -- approved REVIEW_ID COMMIT SUBJECT...`, `content-checked CHECK_ID SUBJECT...` or `unreviewed COMMIT SUBJECT...`, where `SUBJECT` is a pin identity or `publication-contract`. It relinks the current tree at `0x00c20000` from private-data, takes each subject's digest from that build's manifest, sets the status, rewrites the record and prints the remaining verdict findings and any identity on which the manifest and the record disagree.
3. Commit the record with the change it pins.

## Bank ELF allowlist

`//host/firmware:check-bank-allowlist` (library `//host/firmware:bank-allowlist`) checks the bank part of a relinked RAM-push ELF, the code and data `menu/recipe_bank_ram.ld` places in `[RAM_PUSH_BASE+0x500, __rb_image_end)`, against `menu/recipe_bank_allowlist.json`. The installer (`.ram_push.*` from `menu/ram_push_installer.c`), the bootstraps and the host operations are outside it and keep independent review. The allowlist file is mechanism: changing it needs the same review as the installer.

`FujiAF.RamPush.withRelinkedBuildUsing` runs the check on every relinked build before returning it. It reads the allowlist from the workspace and refuses unless the file's SHA-256 equals the `menu/recipe_bank_allowlist.json` entry of the build manifest's source identity, which `build-recipe-bank` hashes. The camera binary (`ram-relink`, `ram-push`, `ram-unload`) and the reviewed emulator e2e always enforce it: a violation refuses the build before USB and names the first violations. Only the emulator e2e's `--unreviewed-relink` accepts `--allowlist-override REASON`, which returns a failing build; the e2e then records `"relink": {"allowlist": {"result": "overridden", "override_reason": REASON, "violations": [...]}}` in `e2e-result.json` and writes the same object to `relinked/bank-allowlist.json`. A passing build records `"result": "pass"` there with every declared site it matched.

A pass establishes the following for the bank's ELF. The analysis runs per function symbol in bank `.text`, and per run of ARM code no symbol covers, over every path from the function's entry; registers carry constants, small sets, unsigned intervals, stack offsets and pointer provenance, narrowed by compares on each branch.

- Layout: the allocated sections are exactly bank `.text` and `.data` and the four `.ram_push.*` installer sections. Bank `.text` starts at `RAM_PUSH_BASE+0x500` and is executable and not writable; `.data` is writable and not executable and ends at `__rb_image_end`, below the generated data at `RAM_PUSH_BASE+0x8000`. The installer starts at the 32-byte boundary after `RAM_PUSH_BANK_END` and ends inside the `0x1b6d8`-byte allocation. No loadable segment is both writable and executable, the bank holds no Thumb code, and every instruction is reached from its function's entry.
- Instructions: every reached word decodes in the admitted A32 set. Refused: coprocessor transfers (CP15 cache, MPU and system control; CP14 debug; VFP and Advanced SIMD), SVC, BKPT, SMC, MRS and MSR, CPS, DMB, DSB and ISB, LDREX, STREX, SWP and CLREX, WFI, WFE and SEV, exception returns and banked LDM/STM, unprivileged loads and stores, SDIV and UDIV, BLX immediate and undefined encodings.
- Branches and calls: a transfer out of its function goes to a bank function entry or to an address in `stock_calls`. A target elsewhere in the allocation, a misaligned target or an undeclared stock address fails. A transfer through a register or a loaded PC must resolve to a set of such targets (constants, literal pools, jump tables with a compare-bounded index), return through the entry `lr`, or match a declaration.
- Stores: a store is proven when every address it can reach lies in bank `.data` and `.bss`, in the generated data `[RAM_PUSH_BASE+0x8000, RAM_PUSH_BANK_END)`, at a constant offset below the entry stack pointer, or inside a `stock_stores` extent. A store that can reach bank code, the allocation header, the installer, the allocation past the runtime, stock image code, boot ROM or device registers (`0x80000000` and up) or undeclared stock RAM fails. A variable-offset stack store fails when it can reach the registers saved on entry, the return address or the caller's frame. A load from `0x80000000` and up fails.
- Unproven pointers: a store or indirect transfer whose address the analysis cannot bound passes only when an `unproven` declaration names its function, its access (`store` or `branch`) and its provenance: an entry argument register, a word of the caller's frame, a word loaded from a bank object, the generated data or a stock address, a call result, an unbounded index into one of those, or a word loaded through any of them (`deref`). A direct bank call to a function declared on an argument puts the same requirement on the caller's value of that argument.

A pass does not establish:

- Where a declared site writes or branches. Its declared reason bounds it, not the check, and a content change inside a declared function that keeps the same provenance passes.
- Anything about callers the analysis does not see: argument requirements follow direct bank calls only, so calls through function pointers and calls from stock into hook entries are trusted as declared.
- Stack depth: a deep or recursive call chain can overflow the stock task's stack.
- What a stock callee does with the arguments the bank passes, including whether it writes persistent state. `stock_calls` is the reviewed list of callees.
- Values, timing, concurrency, cache coherence and cross-core effects; the publications, the installer and the generated data contents; loads through unbounded pointers. Calls are assumed to follow the AAPCS: r4 to r11 and sp survive them, r0 to r3, r12 and lr do not.

A declaration no site matches still passes; the checker lists it as unused.

```sh
devenv shell -- bazel test //host/firmware:bank-allowlist-tests
devenv shell -- bazel run //host/firmware:check-bank-allowlist -- "$PWD/menu/recipe_bank_allowlist.json" "$PWD/private-data/analysis/x-m1-1.50/ram-push/DIR/kernel.elf" --report "$PWD/private-data/analysis/x-m1-1.50/ram-push/DIR/bank-allowlist.json"
```

The checker prints each declared site, unused declaration and violation with its address, and exits 0 on a pass, 1 on a violation and 2 on unreadable input. `bank-allowlist-tests` relinks the current bank sources with the real `build-recipe-bank-ram.sh` at the reference bases `0x00c20000` and `0x00c21f88`, with its RC0 packaging step replaced by a no-op, and requires both to pass. Its fixtures are the `0x00c20000` build with one word replaced: an undeclared stock call, an undeclared indirect call, stores to undeclared stock RAM, device registers, bank code and the installer mailbox, a CP15 cache maintenance instruction, an SVC and a CPS. Each must fail with exactly that violation.

`stock_calls` and `stock_stores` cite the source of each address: the `rb_stock_*` symbols of `menu/recipe_bank_ram.ld`, the `recipe_bank_arm.S` trampolines and the `#define`s of the bank sources. Each `unproven` declaration carries its reason.

## Journal

`OUTDIR/outgoing.v1` carries every outgoing frame; `OUTDIR/journal.v1` carries everything else. Each line is one `Read`/`Show` tuple of schema version, origin `camera`, a decimal monotonic nanosecond clock, an event kind and its body. Outgoing bytes are written and fsynced before dispatch, and raw replies are journaled before parsing, including native status with a partial count, except for the `dump-ram` requests described above. The session writes one `native-outcome` line per transfer, with the provider's status, count and reply hex, whichever provider carried it; `dump-ram` writes it only for a failing or short transfer. Both files are mode 0600 and bounded: 1 MiB for `identify`, 4 MiB for `read-log`, 65536 bytes for `end-setting`, the plan-derived allowance for `read-config` and `probe-routes`, 256 KiB for `probe-ram`, 1 MiB for `probe-bootrom` and `probe-straps`, `8192 * windows` for `probe-area2`, `probe-code` and `probe-ownership`, `65536 + 1024 * requests` for `dump-ram`, `65536 + 4096 * (1058 + 2 * 1024)` for `read-media`, `1048576 + 4096 * 197` for `arm-auto-act` (1855488 bytes, including the bounded device wait), `65536 + 4096 * 342` for `commit-f7-enable` and `commit-f7-restore`, and `65536 + 4096 * requests` for `read-ram`. A cap overflow, symlink or non-regular journal stops before the next dispatch.

RAM-alloc, RAM-push, RAM-free and RAM-unload derive each journal cap from the operation's completed transfer path at the reviewed 0x1b6d8 size: every transfer counts its stage-intent, native-outcome, reply-before-deadline-check and stage-complete lines with packet bytes at 0xff, replies at full length and a 20-digit clock, plus the four acquisition stages and a 65536-byte margin for note lines, the stop record and one failing outcome. Their aggregate deadlines include four transfers for every allocation-hash read, eight for every verified runtime chunk and 200 fixed-transfer slots.

## What stops a run

Any unexpected reply layout, status, echo, length or product bytes; a short, partial or oversized transfer; a write returning bytes; a fixed 5000 ms per-transfer timeout, 33000 ms for the `commit-f7` trigger's D1 only; an expired aggregate deadline; a device-selection refusal; a journal durability failure; an existing or relative output directory stops the run. The aggregate budgets are 5000 ms times 15 for `identify`, 13 for `end-setting`, `8 + 4 * windows` for `read-config`, `8 + 16 + 8 * 515` for `read-log`, `8 + 16 + 8 * 130` for `probe-bootrom`, `8 + 16 + 8 * 27` for `probe-area2`, `8 + 16 + 8 * 7` for `probe-code`, `8 + 16 + 8 * 6` for `probe-ownership`, `8 + 16 + 4 * requests` for `probe-routes` (3 in phase 1, `1 + 2k` in phase 2), `8 + 16 + 4 * 7` for `probe-straps`, `8 + 16 + 4 * requests` for `dump-ram`, `8 + 4 * 31 + 4 * 1058 + 4 * 2 * 1024` for `read-media`, `8 + 4 * 197` for `arm-auto-act` after acquisition, with a separate 120 s acquisition bound in wait mode, `8 + 4 * 342` plus 33 s for the held trigger reply and 33 s of poll spacing for `commit-f7-enable` and `commit-f7-restore`, and `8 + 4 * (2 + requests)` plus the pass pauses for `read-ram`. These are provider/session budgets, not a process watchdog. Nothing is retried and no substitute command is sent. Completed captures stay on disk; a stopped `arm-auto-act` may have raw pre-arm replies only in the journal if it stopped before deferred file writes. Gate restore is attempted only after its write was attempted; protocol close uses only a known SID.

Interface release, handle close and context exit are attempted once each, independently, after a protocol failure, and after an expired deadline only while whole milliseconds remain; a known session identifier permits one C4 attempt, and an unknown one permits none. A cleanup failure makes the outcome uncertain. Host cleanup is not stock restoration, and a successful reply is not a statement about camera state. Native initialization, libusb cancellation loops and filesystem stalls can exceed these budgets; they are not a hard process watchdog. See [the native effect audit](../reports/source-and-transport-audit.md#native-runtime-and-kernel-effects) for effect scope.

## Native provider

`native_usb.c` is compiled against the locked Nix libusb headers and links nothing from it. `FUJI_LIBUSB_PATH`, generated at build time from the same locked dependency, is opened with `dlopen` inside `usbInit` and nowhere else; `//transport:cli-rejections` asserts the binary declares no libusb or libudev dependency. The shim refuses a non-sysfs `/sys/bus/usb/devices`, so the USBFS discovery fallback, which can open unselected nodes and issue GET_CONFIGURATION, is never used. It refuses a transfer timeout above 33000 ms, the `commit-f7` held-reply budget; the Haskell side gives every other transfer 5000 ms. Haskell code reaches USB only through the injected `UsbApi` record; `rehearse` and every test but the one below construct their own. `nativeApi` is `nativeApiWith` over the shim's entry points; `//transport:provider-parity` passes its own `NativeCalls` and never calls the shim.

`rehearse` runs without the native provider. Existing scripted operations print and consume their exact transfer plans. RAM-alloc, RAM-push, RAM-free and RAM-unload rehearsals parse their private inputs and exercise the pre-provider refusal; `//transport:ram-push-tests` runs their complete protocols against the in-process camera model.

`//transport:native-usb-tests` builds the native provider and calls its lister three times, requiring a readable inventory each time and the same inventory each time. `fuji_usb_list` keeps the device list in static state, so one listing per process was an assumption only the C held: the synthetic tests inject the `UsbApi` record and never run it. The test needs no camera and enumerates the host bus through the sysfs path only; it opens, claims and transfers nothing, so an attached camera changes only the inventory it reads.

`//transport:audit-inventory` writes the static public source and ELF byte inventory to its `OUTPUT_JSON` argument without loading any of it.

## Provider parity

The live provider (`FujiAF.Native` over `native_usb.c`) and the emulator provider (`emulation/EmulatorUsb.hs` over the RAM-push bridge's JSON lines) only carry a transfer and return its count and bytes. Everything a transfer journals or refuses is computed once, in `dispatchTransfer` and `txWithin` of `FujiAF.Transport`: the outgoing frame line, the stage lines, the shape refusal (a twelve-byte `0x43` control write or a bulk transfer of 1 to 292 bytes, the shapes `native_usb.c` accepts), the `native-outcome` line and the `reply-before-deadline-check` line. Journal caps exist only in the operations' sessions, so the emulator e2e meets the same caps the body does. The first live `ram-alloc` stopped on a journal cap when the native provider wrote `native-outcome` lines the emulator provider did not (E-RAM-ALLOC-JOURNAL-STOP-150).

What still differs between the two providers, none of it reaching an outgoing byte or a journal line of a completed transfer:

- Listing: the native provider reads the body's descriptors; the emulator provider presents a constant profile (bulk `0x81` and `0x02` at 64 bytes, interrupt `0x83`) and ignores the bridge's listed candidate. Only the endpoint numbers enter packets, and they agree.
- Per-transfer timeout: libusb receives it; the bridge answers synchronously and ignores it. The session's budget and deadline checks wrap both.
- Failures: a nonzero libusb status or an out-of-range count reaches the session as `ProviderFailure` and is journaled as a `native-outcome` line before the stop; a bridge error (`"ok": false`) stops the run with no `native-outcome` line.
- Init, open, claim, release, close and exit: libusb calls against no-ops, under the same stage lines.

`//transport:provider-parity` runs every USB operation of `//transport:camera` twice against one scripted device: the rehearsal scripts for `identify`, `read-config`, `end-setting`, `probe-ram`, `read-log`, `probe-bootrom`, `probe-area2`, `probe-straps`, `probe-code`, `probe-ownership`, `probe-routes fixed`, `dump-ram loaders`, `read-media`, `arm-auto-act`, `commit-f7-enable`, `commit-f7-restore` and a two-pass `read-ram`, and the `RamPushModel` camera of `//transport:ram-push-tests` for `ram-alloc`, `ram-push`, `ram-unload` and `ram-free`. One run goes through `nativeApiWith` with the shim's entry points answered by the device, the other through `bridgeUsbApi` with each bridge request line answered by the device, both under a clock that steps per reading. The test requires the two output directories to hold the same files with the same bytes, apart from the journal clock column, and the same result, and names the first differing line otherwise. It lists, opens and transfers on no USB device.
